## 하네스 엔지니어링 예시란 ?
- [하네스 엔지니어링](../README.md) 문서에서 본 장치(지시 파일, 스킬, 훅, 검증 장치, 권한)를 실제로 어떻게 만드는지 보여 주는 예시 모음
- 장치마다 개념이나 원문에 나온 예를 먼저 요약하고, 이 노트 레포에 실제로 만들어 둔 하네스를 이어 붙였다
- 원문은 미첼 하시모토의 [My AI Adoption Journey](https://mitchellh.com/writing/my-ai-adoption-journey)(참고 자료 1)와 Claude Code 공식 문서 [Automate actions with hooks](https://code.claude.com/docs/en/hooks-guide)(참고 자료 2)에서 가져왔다. 2026-10-21에 확인한 내용이다

### 좋은 하네스의 기준
하시모토는 에이전트가 실수할 때마다 시간을 들여, 그 에이전트가 다시는 그 실수를 하지 않도록 해결책을 만들어 두는 것을 하네스 엔지니어링이라 한다(참고 자료 1). 그래서 좋은 하네스는 한 번에 설계해 완성하는 것이 아니라, 실제로 나온 실수 하나하나에 대응하며 자란다. 아래 예시도 대부분 실제 실수에서 나왔다.

<br/>

## 1. 지시 파일: 실수 하나에 한 줄
### 원문 예
하시모토는 하네스를 두 가지로 나눈다(참고 자료 1).

- 더 나은 암묵적 지시(implicit prompting): 에이전트가 틀린 명령을 반복해서 돌리거나 엉뚱한 API를 찾는 것 같은 단순한 문제는 `AGENTS.md` 같은 지시 파일을 고쳐 해결한다
- 실제로 만든 도구: 에이전트를 위한 도구를 만들고, 보통 지시 파일에도 그 도구가 있다고 적어 둔다

그는 자기 터미널 프로젝트 Ghostty의 `AGENTS.md` 를 예로 들며, 그 파일의 줄 하나하나가 에이전트의 나쁜 행동 하나에서 나왔고 이렇게 해서 그 문제들이 거의 다 해결됐다고 쓴다.

### 이 레포의 예
이 레포의 지시 파일은 `.claude/CLAUDE.md` 다. 그중 두 규칙을 옮긴다.

```markdown
## 파일 구조
- 여러 장으로 이어지는 주제는 책처럼 나눈다. 상위 폴더 README.md를 목차로 두고,
  장마다 `NN_한글명(English Name)` 폴더를 만든다. ...

## 내용 기준
- 출력이나 결과를 적은 코드 예시는 실행해 본 값을 쓴다. 실행하지 못한 예시는 보고에 적는다.
```

첫 규칙은 파이썬 노트를 한 문서에 몰아 썼다가 장별로 나누라는 요청을 받은 뒤 생겼다. 둘째 규칙이 있어서 노트를 쓸 때마다 예시 코드를 실행하고, 결과가 주석과 다르면 문서를 고친다.
규칙만으로 문장이 어떻게 달라지는지 알기 어려운 것은 `.claude/docs/writing-guide.md` 에 피할 예와 고친 예로 따로 적고, `CLAUDE.md` 안의 `@docs/writing-guide.md` 한 줄로 함께 불러오게 했다.

<br/>

## 2. 스킬: 절차를 폴더 하나로
### 개념
스킬은 특정 작업의 절차와 참고 자료를 묶어 두고 필요할 때만 불러오는 장치다([하네스 엔지니어링](../README.md) 참고). 절차가 길고 매번 같을 때 지시 파일에 다 적는 대신 스킬로 뺀다.

### 이 레포의 예
노트를 쓰는 절차는 `.claude/skills/note/SKILL.md` 에 묶었다. 맨 위에 언제 쓰는 스킬인지 적고, 본문에 단계를 소제목으로 적는다. 아래는 단계 제목만 추린 것이다.

```markdown
---
name: note
description: Note 레포에 학습 노트를 새로 쓰거나, 책처럼 이어지는 노트의 다음 장을 쓰거나,
  기존 노트를 개정할 때 쓴다. ...
---

## 1. 요청 종류 판단
## 2. 위치 결정
## 3. 작성
## 4. 검증
## 5. 리뷰
## 6. 연결 갱신
## 7. 보고
```

7단계 보고에는 커밋과 push를 단계마다 나눠 실행하고, 원격으로 나갈 커밋에 Claude가 만들지 않은 커밋이 섞여 있으면 push하지 말고 물으라는 절차가 들어 있다. 내가 작업 도중에 직접 만든 커밋과 미리 스테이징해 둔 파일이 Claude의 push에 함께 올라간 일이 있은 뒤에 넣은 단계다.

## 3. 훅: 부탁을 장치로
### 원문 예
Claude Code 문서는 훅을 생명 주기의 특정 시점에 자동으로 도는 셸 명령이라고 설명한다. 생명 주기(lifecycle)의 정해진 시점마다 돌기 때문에, 모델이 실행하기로 고르기를 바라는 대신 특정 동작이 항상 일어나게 하는 결정적인(deterministic) 통제라는 것이다(참고 자료 2). 문서에 나온 예는 아래와 같다.

파일을 고칠 때마다 Prettier로 정리하는 훅이다. `PostToolUse` 사건(event)의 `matcher` 에 `Edit|Write` 를 적어, 파일을 고치는 도구가 끝난 뒤에만 돈다.

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write"
          }
        ]
      }
    ]
  }
}
```

막는 훅도 있다. `.env`, `package-lock.json`, `.git/` 같은 파일을 고치려 하면 `PreToolUse` 훅의 스크립트가 종료 코드 2로 끝나며 수정을 막는다. 이때 오류 출력(stderr)에 쓴 이유가 Claude에게 전달되어, Claude가 그 이유를 보고 방법을 바꿀 수 있다(참고 자료 2).

```bash
if [[ "$FILE_PATH" == *"$pattern"* ]]; then
  echo "Blocked: $FILE_PATH matches protected pattern '$pattern'" >&2
  exit 2
fi
```

### 이 레포의 예
이 레포는 파일을 고칠 때마다 도는 훅을 `.claude/settings.json` 에 걸어 두고, 스크립트 안에서 `.md` 파일만 골라 문체 규칙을 검사한다. 이 훅은 `PostToolUse` 라서 파일은 이미 써진 뒤에 돈다. 쓰기를 막지는 못하고, 고칠 것을 Claude에게 되돌려준다.

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "node",
            "args": ["<레포 경로>/.claude/hooks/check-note-style.js"],
            "timeout": 10
          }
        ]
      }
    ]
  }
}
```

`check-note-style.js` 는 이번에 쓴 내용에서 이모지, 쓰지 않기로 한 단어, 콜론으로 끝나고 줄을 바꾸는 문장, 코드 스팬 뒤 대시를 찾는다. 찾으면 `{"decision": "block", "reason": ...}` 을 출력해 무엇을 어떻게 고칠지 Claude에게 되돌려준다. 글쓰기 가이드에 "쓰지 않는다"고 부탁만 해 두었을 때는 가끔 빠뜨렸던 규칙이다.

훅도 실수를 겪으며 고쳤다.

- 처음에는 규칙을 설명하는 `.claude` 아래 문서까지 검사해서, 쓰지 않을 단어를 예로 든 글쓰기 가이드를 쓸 때마다 고치라는 지적이 돌아왔다. 그래서 `.claude/` 경로는 검사에서 뺐다
- `↔` 같은 화살표 기호를 이모지로 잘못 잡았다. 그래서 그림 문자로 보이는 것만 잡도록 판정을 좁혔다

## 4. 검증 장치: 스스로 확인하게
### 원문 예
하시모토가 말한 두 번째 하네스, 실제로 만든 도구의 예는 스크린샷을 찍는 스크립트와 일부 테스트만 골라 돌리는 스크립트다(참고 자료 1). 에이전트가 자기 결과를 사람 없이 확인할 수 있게 하는 도구다.

### 이 레포의 예
노트는 링크가 자주 깨진다. 폴더 이름에 공백과 괄호가 많기 때문이다. 그래서 링크를 점검하는 스크립트를 만들었다.

```bash
node .claude/scripts/check-links.js "Python"
# 상대 링크 76개 중 깨진 링크 0개
```

처음 만든 스크립트는 정규식으로 링크를 찾다가 폴더 이름 안의 괄호에서 링크가 끝난 것으로 잘못 읽었다. 그래서 괄호 짝을 맞춰 읽도록 고쳤다.
코드 예시를 실행해 결과를 확인하는 일도 같은 역할을 한다. 파이썬 노트를 쓸 때 트레이스백 예시를 실행해 보고 나서야, Python 3.11부터 오류 위치에 `~^` 표시가 붙는다는 것을 반영할 수 있었다.

<br/>

## 5. 리뷰 전용 에이전트와 권한
### 개념
권한과 격리는 에이전트가 할 수 있는 일을 제한하는 장치다([하네스 엔지니어링](../README.md) 참고). 검토만 할 에이전트에게 고치는 도구까지 주면, 검토하다 말고 파일을 고쳐 버릴 수 있다.

### 이 레포의 예
노트 검토는 `.claude/agents/note-reviewer.md` 에이전트가 맡는다. 맨 위에 쓸 수 있는 도구를 읽기 전용 세 개로 묶어 두었다.

```markdown
---
name: note-reviewer
description: ... 파일은 고치지 않고 지적 목록만 돌려준다.
tools: Read, Grep, Glob
---
```

리뷰 에이전트는 실제로 사실 오류를 여러 번 찾았다. 파이썬 17장에서 12장에 나온 적 없는 `StopIteration` 을 12장에서 봤다고 쓴 것, 19장에서 `int`, `str` 이 클래스라는 설명이 있는 장을 3장으로 잘못 짚은 것이 그 예다.
리뷰 에이전트도 틀린다. 토큰 노트를 검토할 때는 문서에 적힌 수치를 기억에 기대어 다른 값으로 고치라고 했다. 그래서 지적을 그대로 반영하지 않고, 사실에 관한 지적은 원문을 다시 열어 확인한 뒤에만 반영한다.

<br/>

## 6. 하네스가 막지 못한 것
하네스는 걸어 둔 길로 일할 때만 동작한다. 이 레포에서 실제로 겪은 빈틈은 아래와 같다.

- 훅은 `Edit|Write` 도구에만 걸려 있다. 리뷰 지적을 스크립트로 한꺼번에 반영하면 훅이 돌지 않는다. 그래서 그럴 때는 훅을 직접 돌려 확인한다
- 하네스 파일 자체가 사라지면 하네스도 사라진다. 작업 중 다른 브랜치로 바뀌어 `.claude` 파일이 작업 폴더에서 잠시 빠진 일이 있었고, 그 세션에서는 스킬을 불러오지 못했다. 두 일이 이어진 것으로 추정하지만 원인을 확인하지는 못했다

이 두 빈틈은 아직 절차에 넣지 않았다. 다시 겪으면 스킬의 검증 단계에 한 줄씩 더할 생각이다. 실수가 나올 때마다 장치를 고친다는 하시모토의 방식을 따르면 그렇게 된다.
