## 스펙 주도 개발과 바이브 코딩 예시란 ?
- [스펙 주도 개발과 바이브 코딩](../README.md) 문서에서 본 두 태도가 실제로 어떤 모습인지, 스펙 주도 개발의 단계(명세, 계획, 작업, 구현)를 어떻게 밟는지 보여 주는 예시 모음
- 원문에 나온 예를 먼저 옮기고 적용 예를 이어 붙였다. 이 노트 레포에서 실제로 쓰는 것은 그렇다고 밝혔고, 나머지는 설명을 위해 만든 예다
- 원문은 마틴 파울러의 [Vibe Coding](https://martinfowler.com/bliki/VibeCoding.html)(참고 자료 1)과 GitHub 블로그의 [Spec-driven development with AI](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/)(참고 자료 2)에서 가져왔다. 2026-10-21에 확인한 내용이다

### 고르는 기준
파울러는 바이브 코딩이 만든 사람이나 위험을 알고 받아들이는 적은 사람만 쓰는, 쓰고 버릴 소프트웨어에 가장 잘 맞는다고 한다(참고 자료 1). 반대로 더 복잡하고, 더 많이 쓰이고, 위험의 결과가 큰 코드일수록 잊어서는 안 된다고 한다. 얼마나 오래, 얼마나 많은 사람이 쓸지가 고르는 기준이다.

<br/>

## 1. 바이브 코딩의 실제 모습
### 원문 예
파울러의 글에 인용된 카파시의 2025년 2월 게시물은 바이브 코딩을 이렇게 설명한다(참고 자료 1, 번역).

```text
"바이브 코딩"이라고 부르는 새로운 코딩이 있다. 느낌에 완전히 몸을 맡기고, 코드가 있다는 것조차 잊는다.
나는 늘 "모두 수락(Accept All)"을 누르고, 더는 변경 내용(diff)을 읽지 않는다.
오류 메시지가 나오면 아무 말 없이 그대로 복사해 붙여 넣는다. 보통은 그걸로 고쳐진다.
보고, 말하고, 돌리고, 복사해 붙여 넣으면 대체로 돌아간다.
```

파울러가 꼽는 위험 가운데 가장 큰 것은 보안이다. 바이브 코딩으로 만든 소프트웨어가 민감한 데이터나 비밀 키를 드러낼 수 있다고 한다. 코드 품질이 빠르게 나빠지고, LLM이 지어낸 내용으로 오류가 들어가며, 나중에 고치기 어려워진다는 점도 든다.

### 적용 예
```text
바이브 코딩이 괜찮은 예
내 컴퓨터의 다운로드 폴더에서 한 달 넘은 파일 목록만 뽑아 주는 일회용 스크립트

바이브 코딩을 피할 예
회원 비밀번호를 다루는 로그인 API, 팀이 함께 고쳐 나갈 결제 화면
```

<br/>

## 2. AI에게 맡겨도 코드를 잊지 않기
### 원문 내용
파울러는 바이브 코딩과 에이전틱 엔지니어링(Agentic Engineering)을 나눈다(참고 자료 1). 에이전틱 엔지니어링에서도 코드 대부분은 LLM이 쓰지만, 개발자는 그 코드를 검토하고 내부 구조에 신경을 쓴다. 코드가 있다는 것을 잊지 않는다는 점이 바이브 코딩과의 차이다. 그는 바이브 코딩이라는 말이 에이전틱 엔지니어링까지 가리키는 말로 퍼지면서 뜻을 잃었다고 보고, 두 개념을 나눠 써야 한다고 한다.

### 이 레포의 예
이 레포의 노트는 대부분 AI가 쓰지만 바이브 코딩이 아니다. 노트마다 리뷰 에이전트가 검토하고, 사실에 관한 지적은 원문을 다시 열어 확인하고, 커밋 전에 사용자가 결과 보고를 읽는다. 파울러의 구분으로는 에이전틱 엔지니어링 쪽이다.

<br/>

## 3. 명세 쓰기 (Specify)
### 원문 예
GitHub 블로그는 스펙 주도 개발을 명세(Specify), 계획(Plan), 작업(Tasks), 구현(Implement) 네 단계로 나누고, Spec Kit에서 앞의 세 단계를 `/specify`, `/plan`, `/tasks` 명령으로 연다(참고 자료 2).
명세 단계에서는 무엇을 왜 만드는지를 설명하면, 에이전트가 사용자, 경험, 성공 기준을 담은 자세한 명세를 만든다. 글은 막연한 요청의 예로 "내 앱에 사진 공유를 추가해 줘"를 든다. 이렇게만 말하면 모델이 말하지 않은 수많은 요구 사항을 짐작해야 한다는 것이다.

### 적용 예
```text
막연한 요청
파이썬 노트에 데코레이터 장 추가해 줘.

명세
- 누가 읽나: 11장(함수)까지 읽은 입문자
- 무엇을: 함수를 값으로 다루기, 클로저, @ 문법, functools.wraps, 인자를 받는 데코레이터
- 왜: 15장에서 @property를 데코레이터를 배운 뒤로 미뤘다
- 완료 조건: 모든 예시 코드를 실행해 주석과 결과가 같고, 깨진 링크가 0개이며,
  목차와 17장의 다음 링크, TODO가 함께 갱신되어 있다
```

이 레포에서 실제로 받은 요청은 위의 막연한 요청에 가까운 "데코레이터 장 이어서 작성해"였다. 그래도 엉뚱한 결과가 나오지 않은 것은, 명세에 들어갈 내용 대부분이 이미 지시 파일과 목차에 적혀 있었기 때문이다. 다음 절의 계획이 그 역할을 했다.

<br/>

## 4. 계획 쓰기 (Plan)
### 원문 내용
계획 단계에서는 기술 방향(스택, 구조, 제약)을 주면 에이전트가 기술 계획을 만든다(참고 자료 2). 글은 계획에 들어갈 수 있는 것으로 써야 할 기술, 기존 시스템과의 연결, 지켜야 할 규정, 성능 목표를 든다. 견본 계획은 싣지 않았다.

### 이 레포의 예
이 레포에서 계획 역할을 하는 것은 장마다 새로 쓰지 않고 늘 그대로 두는 문서들이다.

- `.claude/CLAUDE.md`: 폴더 이름 형식, 장 끝 링크, 첫 섹션은 "OO이란 ?", 예시 코드는 실행해 본 값을 쓴다는 규칙
- `.claude/docs/writing-guide.md`: 문장을 어떻게 쓸지 피할 예와 고친 예
- 목차 README: 어떤 장이 이미 있고 무엇이 다음인지

계획을 한 번 써 두면, 장마다 요청이 짧아도 모든 장이 같은 구조로 나온다.

<br/>

## 5. 작업 나누기 (Tasks)
### 원문 예
작업 단계에서는 에이전트가 명세와 계획을 작고 검토할 수 있는 단위로 나눈다. 각 작업은 따로 시험할 수 있어야 한다(참고 자료 2). 글의 예는 아래와 같다.

```text
너무 큰 작업
build authentication (인증 만들기)

알맞은 작업
create a user registration endpoint that validates email format
(이메일 형식을 검사하는 회원 가입 엔드포인트 만들기)
```

### 이 레포의 예
목차 README의 TODO 목록이 작업 목록 역할을 한다. "데코레이터", "타입 힌트"처럼 한 항목이 한 장이 되고, 장 하나는 따로 쓰고 따로 검증하고 따로 커밋한다. 장을 쓰다 다루지 못한 주제는 "functools 모듈 (cache, partial 등)"처럼 새 항목으로 TODO에 더한다.

<br/>

## 6. 구현하고 사람이 확인하기 (Implement)
### 원문 내용
구현 단계에서는 에이전트가 작업을 하나씩, 되는 곳은 나란히 처리한다(참고 자료 2). 글은 사람의 주된 역할이 방향을 잡는 것이고, 대부분의 글쓰기는 코딩 에이전트가 한다고 한다. 단계마다 사람이 검토하고 다듬는다. 명세가 의도를 담았는지, 계획이 실제 제약을 반영했는지, AI가 경계 상황을 놓치지 않았는지를 본다. 글은 이를 AI가 산출물을 만들고 사람이 그것이 맞는지 확인한다고 요약한다.

### 이 레포의 예
이 레포에서 사람이 확인하는 지점은 장마다의 보고와 커밋이다. 에이전트는 무엇을 썼는지, 무엇을 확인했는지, 무엇을 확인하지 못했는지를 보고하고, 사용자가 읽은 뒤 "커밋하고 푸시해"라고 맡겨야 원격에 올라간다. 사람이 중간에 범위를 바꾼 일도 있다. React 소개 보강과 Archive README의 소개 섹션 삭제를 함께 요청했다가, 작업 도중 React 소개만 진행하라고 범위를 좁혔다.

<br/>

## 7. 완료 조건을 평가로 바꾸기
명세의 완료 조건은 그대로 평가 문제가 된다. 3절의 완료 조건을 평가로 옮기면 아래처럼 된다.

| 완료 조건 | 평가 방법 | 채점 |
| --- | --- | --- |
| 예시 코드 결과가 주석과 같다 | 예시를 실행해 출력과 주석을 비교 | 코드 |
| 깨진 링크가 0개다 | `check-links.js` 실행 | 코드 |
| 목차, 앞 장 링크, TODO가 갱신됐다 | 목차에 새 장 항목이 있는지, 앞 장 끝에 다음 링크가 있는지 검색 | 코드 |
| 입문자가 읽을 수 있다 | 글쓰기 가이드를 기준표로 리뷰 에이전트가 검토 | LLM |

평가 문제를 만들고 돌리는 방법은 [평가 주도 개발 예시](../../%5BAI%20활용%5D%20평가%20주도%20개발(Eval-driven%20Development)/예시(Examples)/README.md)에 있다. 완료 조건을 `/goal` 의 멈출 조건으로 쓰는 예는 [루프 엔지니어링 예시](../../%5BAI%20활용%5D%20루프%20엔지니어링(Loop%20Engineering)/예시(Examples)/README.md) 1절에 있다.

<br/>

## 8. 언제 스펙 주도 개발이 가장 쓸모 있나
GitHub 블로그는 세 가지 경우를 든다(참고 자료 2).

- 처음부터 새로 만들 때(0에서 1): 명세와 계획이 AI가 흔한 평균값 같은 결과를 내지 않게 막는다
- 이미 있는 시스템에 기능을 더할 때(N에서 N+1): 계획에 구조의 제약을 담아 새 코드가 기존 프로젝트에 맞게 한다
- 오래된 시스템을 새로 만들 때: 업무 규칙을 새 명세에 담고 구조를 새로 설계해, 기술 부채를 옮겨 오지 않는다

이 레포의 파이썬 노트는 둘째 경우다. 이미 있는 장들의 구조를 계획(지시 파일과 목차)에 담아 두고, 새 장을 그 구조에 맞춰 더해 왔다.

<br/>

## 단계 요약
| 단계 | 한 줄 요약 | 적용 예 |
| --- | --- | --- |
| 명세 (Specify) | 무엇을 왜 만드는지, 언제 다 된 것인지 | 데코레이터 장 명세 (만든 예) |
| 계획 (Plan) | 기술 방향과 지킬 제약 | 이 레포의 CLAUDE.md, 글쓰기 가이드, 목차 |
| 작업 (Tasks) | 따로 시험할 수 있는 작은 단위 | 이 레포의 목차 TODO, 장 하나씩 |
| 구현 (Implement) | 에이전트가 만들고 사람이 단계마다 확인 | 이 레포의 장별 보고와 커밋 위임 |
| 완료 조건을 평가로 | 완료 조건을 코드나 LLM 채점으로 | 장 완료 조건 평가표 (만든 예) |
