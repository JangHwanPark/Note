## AI 활용 방법이란 ?
- 거대 언어 모델(LLM)에게 일을 맡겨 원하는 결과를 안정적으로 얻기 위한 방법들
- 처음에는 질문 문장을 잘 쓰는 프롬프트 엔지니어링에서 시작했고, 모델에게 줄 정보를 고르는 컨텍스트 엔지니어링, 모델을 둘러싼 도구와 검증 장치를 만드는 하네스 엔지니어링, 사람 대신 시스템이 AI를 계속 돌리게 하는 루프 엔지니어링으로 범위가 넓어졌다
- LLM, 토큰, 프롬프트, 추론, 환각 같은 기본 용어는 [인공지능](../README.md) 노트에 정리했다

### 활용 (Utilization)
사전적 의미는 충분히 잘 이용함이다. 가진 것을 그냥 쓰는 데 그치지 않고 쓸모를 최대한 끌어낸다는 뜻이다.
AI에서 활용이라고 하면 모델 자체를 새로 만들거나 고치는 일이 아니라, 이미 만들어진 모델에게 무엇을 어떻게 맡길지 설계하는 일을 말한다. 같은 모델을 써도 맡기는 방식에 따라 결과가 크게 달라지기 때문에 맡기는 방법 자체를 따로 연구한다.

### 엔지니어링 (Engineering)
사전적 의미는 공학, 즉 과학 지식을 써서 쓸모 있는 것을 설계하고 만드는 일이다.
아래 기법 이름 끝에 엔지니어링이 붙는 것은 감에 기대지 않고 원인을 찾고, 고치고, 다시 재 보는 공학적 방식으로 AI를 다루자는 뜻으로 읽을 수 있다.

### 에이전트 (Agent)
사전적 의미는 대리인이다. 남을 대신해 일을 처리하는 사람을 말한다.
여기서는 사람이 한 번 질문하고 답을 받는 데서 끝나지 않고, 도구를 쓰며 여러 단계를 스스로 진행하는 AI를 말한다. 아래 기법 대부분이 에이전트를 전제로 하므로 먼저 짚어 둔다. 미리 정한 순서를 따르는 워크플로와의 차이는 뒤의 워크플로와 에이전트에서 다룬다.

## 신입 사원에게 일 맡기기로 이해하기
네 가지 기법은 새로 온 신입 사원에게 일을 맡기는 과정으로 비유하면 차이가 잘 보인다. 이 사원은 아주 똑똑하지만 회사 사정은 하나도 모르고, 하루가 지나면 어제 일을 잊는다.

| 기법 | 신입 사원에게 하는 일 | AI에게 하는 일 |
| --- | --- | --- |
| 프롬프트 엔지니어링 | 지시를 분명하게 말한다 | 질문과 지시문을 잘 쓴다 |
| 컨텍스트 엔지니어링 | 일에 필요한 자료만 골라 책상에 올려 준다 | 모델이 볼 정보를 고르고 정리한다 |
| 하네스 엔지니어링 | 업무 매뉴얼, 도구, 검수 체크리스트를 갖춰 준다 | 지시 파일, 도구, 테스트, 자동 검사를 만든다 |
| 루프 엔지니어링 | 매일 아침 할 일을 받아 처리하고 검수받는 업무 절차를 만든다 | 사람이 말하지 않아도 AI가 일하고 검증받는 반복 구조를 만든다 |

뒤로 갈수록 한 번의 대화가 아니라 일하는 환경 전체를 설계하는 쪽으로 넓어진다. 2026년 8월 arXiv에 올라온 루프 엔지니어링 연구도 이 흐름을 프롬프트 문장 다듬기에서 컨텍스트 설계로, 다시 모델을 둘러싼 하네스 설정으로, 그리고 사람 대신 시스템이 프롬프트를 보내는 루프로 이어지는 단계로 설명한다(참고 자료 13).

뒤의 기법이 앞의 기법을 대신하는 것은 아니다. 하네스 안에도 프롬프트가 있고, 루프도 결국 컨텍스트를 관리해야 한다. 앞 단계를 잘해야 뒤 단계가 의미가 있다.

## 프롬프트 엔지니어링 (Prompt Engineering)
### 정의
프롬프트의 사전적 의미(재촉하다, 대사를 일러 주다)는 인공지능 노트에서 보았다.
프롬프트 엔지니어링은 모델에게 주는 질문과 지시문을 설계해 원하는 답을 얻는 기법이다. Anthropic은 이를 좋은 결과를 얻도록 LLM에게 줄 지시를 쓰고 구성하는 방법이라고 설명한다(참고 자료 3).

### 왜 필요할까
모델은 사람처럼 눈치를 보고 빈칸을 채워 주지 않는다. "보고서 써 줘"라고만 하면 누구를 위한 보고서인지, 길이는 어느 정도인지, 어떤 형식인지 모른 채 그럴듯한 평균값을 낸다. 같은 모델이라도 지시가 구체적일수록 결과가 원하는 쪽에 가까워진다.

### 대표 기법
Anthropic 문서는 분명하게 쓰기, 예시 주기, 태그로 구조 나누기, 역할 주기, 생각하게 하기, 프롬프트 체이닝을 기본 기법으로 든다(참고 자료 2). 하나씩 보면 아래와 같다.

- 분명하고 구체적으로 쓴다. 목적, 읽을 사람, 형식, 길이를 적는다
- 예시를 준다. Shot의 사전적 의미는 한 번 쏘기, 한 번의 시도다. 모델에게 보여 주는 예시 하나를 한 번의 시도로 세어, 예시 몇 개를 주는 방식을 퓨샷(Few-shot) 프롬프팅이라고 한다. 2020년 GPT-3 논문이 예시 몇 개만으로 모델이 새 일을 해내는 것을 보이며 널리 알려졌다(참고 자료 4)
- 단계적으로 생각하게 한다. 답만 묻지 않고 풀이 과정을 거치게 하는 방식을 생각의 사슬(Chain-of-Thought, CoT) 프롬프팅이라고 한다. 생각 하나하나를 사슬의 고리처럼 이어 답까지 간다는 뜻이다. 2022년 Google 연구진은 풀이 과정이 담긴 예시를 주면 큰 모델에서 수학 문제 정답률이 크게 오르고, 작은 모델에서는 효과가 없다고 보고했다(참고 자료 5)
- 역할을 정해 준다. "너는 10년 차 QA 엔지니어다"처럼 관점을 주면 말투와 다루는 관점이 그 역할에 맞춰진다(참고 자료 2)
- 구조를 나눈다. 지시, 자료, 예시를 태그나 제목으로 구분해 섞이지 않게 한다(참고 자료 2)
- 일을 쪼갠다. Chain의 사전적 의미는 사슬이다. 큰 일을 여러 프롬프트로 나눠 앞 결과를 다음 입력으로 사슬처럼 넘기는 방식을 프롬프트 체이닝(Prompt Chaining)이라고 한다(참고 자료 1)

```text
피할 예
코드 리뷰해 줘.

고친 예
아래 React 컴포넌트를 리뷰해 줘.
- 목적: 머지 전에 버그 가능성을 찾는 것. 스타일 지적은 빼 줘
- 기준: 상태 업데이트 누락, 의존성 배열 오류, 접근성 문제
- 형식: 문제마다 위치, 이유, 고친 코드 한 줄
<code>
...
</code>
```

### 시작 전에 할 일
Anthropic 문서는 프롬프트를 고치기 전에 세 가지를 먼저 갖추라고 한다. 무엇이 성공인지에 대한 기준, 그 기준으로 결과를 실제로 재 볼 방법, 고쳐 나갈 첫 프롬프트다(참고 자료 2). 기준 없이 프롬프트를 고치면 나아졌는지 나빠졌는지 알 수 없다. 이 생각은 아래 평가 주도 개발로 이어진다.

## 컨텍스트 엔지니어링 (Context Engineering)
### 정의
Context의 사전적 의미는 맥락, 문맥이다. 어떤 말이나 일이 놓인 앞뒤 사정을 말한다. 같은 "괜찮아"도 앞뒤 사정에 따라 뜻이 달라진다.
컨텍스트 엔지니어링은 모델이 답을 만들 때 보는 정보 전체를 고르고 관리하는 기법이다. 여기서 컨텍스트는 프롬프트뿐 아니라 시스템 지시, 대화 기록, 붙여 넣은 문서, 도구 실행 결과까지 모델에게 들어가는 모든 것을 말한다.

이 말은 2025년 6월 무렵 널리 쓰이기 시작했다. Shopify CEO 토비 뤼트케(Tobi Lutke)는 이를 LLM이 그럴듯하게 풀 수 있도록 일에 필요한 맥락을 모두 주는 기술이라고 했고, 안드레이 카파시(Andrej Karpathy)는 프롬프트 엔지니어링보다 이 말이 낫다며 다음 단계에 꼭 맞는 정보로 컨텍스트 창을 채우는 섬세한 기술이라고 했다(참고 자료 6). Anthropic은 2025년 9월 29일 글에서 컨텍스트 엔지니어링을 프롬프트 엔지니어링이 자연스럽게 발전한 형태로 보고, 추론(학습이 끝난 모델이 답을 내는 단계, 인공지능 노트 참고) 동안 가장 알맞은 토큰(정보) 묶음을 고르고 유지하는 전략이라고 정의했다(참고 자료 3).

### 왜 필요할까
Window의 사전적 의미는 창문이다. 창문으로는 바깥 풍경의 일부만 보인다. 모델이 한 번에 볼 수 있는 양을 컨텍스트 창(Context Window)이라고 부르는 것도 이 때문이고, 이 창의 크기에는 한계가 있다.
게다가 많이 넣는다고 좋아지지도 않는다. Rot의 사전적 의미는 썩음이다. Anthropic은 컨텍스트가 길어질수록 그 안의 정보를 정확히 떠올리는 능력이 떨어진다고 설명하고, 이를 컨텍스트 부패(Context Rot)라고 부른다(참고 자료 3). 책상에 서류를 산더미처럼 쌓아 주면 신입 사원이 정작 중요한 한 장을 놓치는 것과 같다.

### 대표 기법
- 필요할 때 불러오기(Just-in-time Retrieval). 자료를 처음부터 다 넣지 않고 파일 경로나 링크만 들고 있다가 필요할 때 도구로 읽는다
- 압축(Compaction). Compact의 사전적 의미는 빽빽하게 다진, 작게 줄인이다. 대화가 길어지면 지금까지의 내용을 요약하고 그 요약으로 새로 시작한다
- 메모 남기기(Structured Note-taking). 진행 상황을 컨텍스트 밖 파일에 적어 두고 나중에 다시 읽는다
- 하위 에이전트(Sub-agent) 나누기. 조사 같은 일을 깨끗한 컨텍스트를 가진 다른 에이전트에게 맡기고 요약만 돌려받는다

필요할 때 불러오기는 Anthropic 글이 컨텍스트를 고르는 방법으로, 나머지 세 가지는 오래 걸리는 작업을 위한 방법으로 소개한 것이다(참고 자료 3).

### 검색 증강 생성 (Retrieval-Augmented Generation, RAG)
Retrieve는 되찾아 오다, Augment는 늘리다, 보강하다, Generation은 생성이다. 찾아온 자료로 보강해서 만든다는 뜻이다.
공학적으로는 질문과 관련된 문서를 먼저 검색해 컨텍스트에 넣고, 모델이 그 문서를 근거로 답하게 하는 방식이다. 모델이 학습하지 않은 회사 문서나 최신 정보를 다룰 때 쓴다. 모델이 기억에만 기대지 않고 찾아온 문서를 근거로 삼게 되므로 환각을 줄이는 데도 쓴다. 2020년 Facebook AI 연구진(현재 Meta) 등이 쓴 논문에서 이름이 붙었다(참고 자료 7). 오픈북 시험처럼 외운 것만으로 답하지 않고 책을 펴 보고 답하게 하는 셈이다.

## 하네스 엔지니어링 (Harness Engineering)
### 정의
Harness의 사전적 의미는 말에 채우는 마구, 또는 몸에 매는 안전띠다. 말의 힘이 아무리 세도 마구가 없으면 수레를 원하는 방향으로 끌게 할 수 없다. 마구는 힘을 쓸모 있는 방향으로 묶어 주는 장비다.
소프트웨어에서는 원래 시험할 코드를 감싸 실행하고 결과를 확인하는 틀을 테스트 하네스(Test Harness)라고 불렀다. AI에서 하네스는 이 뜻이 넓어져 모델을 둘러싼 실행 환경 전체를 말한다. 지시 파일, 쓸 수 있는 도구, 권한, 테스트와 자동 검사 같은 장치가 여기에 들어간다. 모델이 말이라면 하네스는 마구다. 하네스 엔지니어링은 이 환경을 고쳐서 AI가 안정적으로 일하게 만드는 기법이다.

하네스 엔지니어링이라는 이름은 HashiCorp 공동 창업자 미첼 하시모토(Mitchell Hashimoto)가 2026년 2월 5일 글 "My AI Adoption Journey"에서 자기는 이렇게 부르게 되었다고 쓰면서 알려졌다. 그는 에이전트가 실수할 때마다 다시는 같은 실수를 하지 않도록 해결책을 만들어 두는 것을 하네스 엔지니어링이라고 설명했다(참고 자료 8). 엿새 뒤인 2월 11일 OpenAI도 사람이 직접 쓴 코드 없이 Codex로 제품을 만든 경험을 같은 이름의 글로 공개했다(참고 자료 9).

### 왜 필요할까
프롬프트로 "테스트를 꼭 돌려"라고 매번 말해도 AI는 가끔 빠뜨린다. 말로 하는 부탁은 지켜질 수도 있고 아닐 수도 있다. 하네스는 부탁을 장치로 바꾼다. 테스트가 실패하면 다음 단계로 못 넘어가게 막는 식이다. 신입 사원에게 "꼼꼼히 해"라고 말하는 대신 검수 체크리스트와 자동 검사기를 주는 것과 같다.

### 무엇으로 이루어질까
하시모토는 하네스를 두 가지로 나눴다. 하나는 AGENTS.md 같은 지시 파일을 고쳐 나쁜 행동을 반복하지 않게 하는 것이고, 다른 하나는 스크린샷 스크립트나 일부만 돌리는 테스트처럼 에이전트가 스스로 결과를 확인할 수 있는 도구를 만들어 주는 것이다(참고 자료 8). 실제 도구에서 쓰이는 장치는 아래와 같다.

- 지시 파일. 프로젝트 규칙과 금지 사항을 적어 두면 에이전트가 작업할 때마다 읽는다. Codex는 AGENTS.md, Claude Code는 CLAUDE.md를 쓴다
- 도구 연결. 에이전트가 DB, 이슈 트래커, 브라우저 같은 바깥 시스템을 쓰게 한다. Protocol의 사전적 의미는 외교 의례, 지켜야 할 절차이고, 통신에서는 주고받는 방식의 약속을 말한다. Anthropic이 2024년 11월 25일 공개한 모델 컨텍스트 프로토콜(Model Context Protocol, MCP)은 AI와 바깥 도구가 주고받는 방식을 표준으로 정한 약속이다(참고 자료 10)
- 스킬(Skill). 사전적 의미는 솜씨, 숙련된 기술이다. 특정 작업의 절차와 참고 자료를 폴더 하나에 묶어 두고 필요할 때만 불러오게 한다. Anthropic은 2025년 10월 SKILL.md 파일을 중심으로 한 Agent Skills를 발표했다(참고 자료 11)
- 훅(Hook). 사전적 의미는 갈고리다. 파일 수정, 명령 실행 같은 사건에 갈고리를 걸어 두고 그때마다 검사 스크립트를 자동으로 돌린다
- 검증 장치. 테스트, 린터(코드 규칙 위반을 자동으로 찾는 도구), 타입 검사, 리뷰 전용 에이전트처럼 결과가 맞는지 확인하는 장치다
- 권한과 격리. 에이전트가 할 수 있는 일을 제한하고, 위험한 작업은 사람 승인을 받게 한다

### 이 레포의 예
이 노트 레포에도 하네스가 있다. 노트 형식은 지시 파일과 글쓰기 가이드에 적어 두었고, 노트 작성 절차는 스킬로 묶었다. 금지 문자는 파일을 쓸 때마다 훅이 검사하고, 깨진 링크는 점검 스크립트가, 내용은 리뷰 전용 에이전트가 확인한다. 이 폴더의 인공지능 노트를 처음 쓸 때도 리뷰 에이전트가 커밋 전에 약한 AI를 Narrow AI의 번역으로 소개한 오류를 찾아냈다. 실수가 나올 때마다 이 장치를 고쳐 나가는 것이 하시모토가 말한 하네스 엔지니어링이다.

## 루프 엔지니어링 (Loop Engineering)
### 정의
Loop의 사전적 의미는 고리, 둥글게 이어진 줄이다. 끝이 처음으로 돌아와 다시 이어지는 모양이다.
공학적으로 루프 엔지니어링은 사람이 매번 AI에게 지시하는 대신, AI를 일하게 하고 결과를 확인하고 다시 일하게 하는 반복 구조를 설계하는 기법이다. IBM은 이를 에이전트가 사람의 단계별 지시 없이 행동하고, 결과를 확인하고, 조정하는 작업 흐름을 설계하는 일이라고 설명한다(참고 자료 12).

Google의 애디 오스마니(Addy Osmani)는 2026년 6월 7일 글 "Loop Engineering"에서 루프를 목적을 정해 두면 AI가 그 목적을 다 이룰 때까지 스스로 다시 도는 목표라고 설명하고, 루프 엔지니어링을 에이전트에게 프롬프트를 보내는 사람의 자리를 시스템으로 바꾸는 일이라고 했다. 또 루프 엔지니어링이 하네스보다 한 층 위에 있다고 했다(참고 자료 14). 하네스가 AI가 일하는 작업장이라면, 루프는 그 작업장을 언제 어떻게 돌릴지 정하는 업무 절차다.

### 왜 필요할까
하네스를 잘 만들어도 사람이 매번 "이거 해 줘", "테스트 실패했으니 고쳐 줘"라고 말해야 한다면 사람이 병목이 된다. 루프는 이 왕복을 시스템에 넘긴다. 신입 사원이 매일 아침 업무 목록을 확인하고, 처리하고, 검수를 받고, 결과를 일지에 적는 절차가 정해져 있으면 팀장이 일일이 말하지 않아도 일이 굴러가는 것과 같다.

### 어떻게 동작할까
IBM은 루프를 네 단계로 설명한다(참고 자료 12).

1. 목표. 멈출 조건이 분명한 목표를 정한다. 예를 들면 모든 단위 테스트가 통과하고 요구 사항을 만족하면 멈춘다
2. 행동. 에이전트가 코드를 쓰거나 버그를 고친다
3. 관찰. CI(코드를 올릴 때마다 자동으로 테스트를 돌리는 장치) 같은 장치로 결과를 확인한다
4. 조정. 결과를 보고 접근 방식을 바꿔 다음 바퀴를 돈다

오스마니는 루프에 필요한 부품을 아래처럼 꼽았다(참고 자료 14).

- 자동화. 정해진 시각에 일을 시작시킨다
- 워크트리(Worktree). Git에서 한 저장소를 여러 작업 폴더로 동시에 꺼내 쓰는 기능이다. tree는 폴더가 가지처럼 뻗은 구조를 말한다. 여러 에이전트가 서로의 작업을 덮어쓰지 않게 나눈다
- 스킬. 프로젝트 지식을 담는다
- 플러그인과 커넥터. 바깥 도구와 잇는다
- 하위 에이전트. 일을 제안하는 쪽과 검사하는 쪽을 나눈다
- 상태(State). 사전적 의미는 놓여 있는 모양이나 형편이다. 여기서는 대화 밖에 적어 두는 진행 기록을 말한다. 마크다운 파일이나 이슈 보드가 쓰인다

모델은 실행이 끝나면 모든 것을 잊기 때문에 기억은 컨텍스트가 아니라 디스크에 있어야 한다는 것이 오스마니의 설명이다(참고 자료 14).

### 조심할 점
- 비용. 오스마니도 토큰 비용을 반드시 조심하라고 했다. 하위 에이전트는 각자 모델과 도구를 쓰므로 토큰을 더 쓴다(참고 자료 14)
- 완료는 증명이 아니다. 오스마니는 완료가 주장일 뿐 증명이 아니라고 했다(참고 자료 14). 그래서 루프가 끝났다고 해도 결과는 사람이 다시 확인해야 한다
- 이해의 빚(Comprehension Debt). 사람이 보지 않는 사이 코드가 쌓이면 나중에 아무도 그 코드를 이해하지 못하는 상태가 될 수 있다. 오스마니는 지켜보지 않는 루프가 이 빚을 키운다고 경고했다(참고 자료 14)
- 기록 없는 루프. 2026년 8월 연구는 루프를 쓰는 저장소 대부분이 루프 설정은 커밋하지만, 권장되는 상태 파일은 거의 커밋하지 않는다고 보고했다(참고 자료 13)

## 그 밖에 알아 둘 활용법
### 워크플로와 에이전트 (Workflow, Agent)
Workflow는 일(work)의 흐름(flow)이다. 에이전트의 사전적 의미(대리인)는 첫 섹션에서 보았다.
Anthropic은 2024년 12월 글에서 둘을 이렇게 나눴다. 워크플로는 LLM과 도구가 미리 정해 둔 코드 경로를 따라 움직이는 시스템이고, 에이전트는 LLM이 스스로 진행 순서와 도구 사용을 정하는 시스템이다(참고 자료 1). 정해진 노선을 달리는 버스와 목적지만 듣고 길을 고르는 택시의 차이다.

같은 글은 워크플로 패턴 다섯 가지를 소개한다. 일을 단계로 나눠 잇는 프롬프트 체이닝(Prompt Chaining), 입력 종류에 따라 다른 처리로 보내는 라우팅(Routing), 여러 일을 동시에 돌리는 병렬화(Parallelization), 지휘하는 호출이 일을 나눠 주는 오케스트레이터-워커(Orchestrator-workers), 한 번의 호출이 답을 만들고 다른 호출이 평가해 고치게 하는 평가자-최적화(Evaluator-optimizer)다. 그리고 가장 단순한 방법부터 찾고, 필요할 때만 복잡도를 올리라고 권한다(참고 자료 1). 에이전트나 루프가 늘 정답은 아니라는 뜻이다.

### 평가 주도 개발 (Eval-driven Development)
Evaluation의 사전적 의미는 평가, 값어치를 따져 매기는 일이다.
LLM은 같은 입력에도 답이 조금씩 달라서, 한두 번 써 보고 괜찮다고 판단하기 어렵다. 평가 주도 개발은 테스트 주도 개발(Test-Driven Development, TDD), 즉 코드보다 테스트를 먼저 쓰는 방식처럼 먼저 평가 문제 묶음과 채점 기준을 만들고, 프롬프트나 모델을 바꿀 때마다 같은 평가를 돌려 점수로 판단하는 방식이다(참고 자료 15). 앞에서 본 Anthropic 문서의 성공 기준과 측정 방법을 먼저 갖추라는 조언과 같은 생각이다. 채점을 다른 LLM에게 맡기는 방식을 LLM 평가자(LLM-as-a-Judge)라고 부르며, 2023년 논문에서 사람의 판단과 상당히 일치한다고 보고했다(참고 자료 16).

### 스펙 주도 개발 (Spec-driven Development)
Spec은 Specification의 줄임말로 사전적 의미는 명세, 자세히 적은 설명서다.
코드를 바로 시키지 않고 요구 사항, 완료 조건, 설계, 작업 목록을 문서로 먼저 쓰고 에이전트가 그 문서를 기준으로 구현하고 검증하게 하는 방식이다. GitHub은 2025년 9월 이 방식을 돕는 오픈소스 도구 Spec Kit을 공개하며, 에이전트를 검색 엔진처럼 대하지 말고 말을 글자 그대로 받아들이는 페어 프로그래머처럼 대하라고 했다(참고 자료 17). 집을 지을 때 설계도부터 그리는 것과 같다.

### 바이브 코딩 (Vibe Coding)
Vibe의 사전적 의미는 분위기, 느낌이다.
카파시가 2025년 2월에 쓴 말로, 코드를 자세히 읽지 않고 AI가 내놓은 변경을 그대로 받아들이며 느낌대로 만들어 가는 방식을 말한다. 마틴 파울러(Martin Fowler)는 이렇게 만든 소프트웨어가 유지보수성, 정확성, 보안에서 문제를 보이기 쉬워 적은 사람이 쓰고 버릴 소프트웨어에 알맞다고 했다(참고 자료 18). 스펙 주도 개발과 하네스, 루프는 모두 이 방식의 불안정함을 줄이려는 시도로 볼 수 있다.

### 파인튜닝 (Fine-tuning)
Fine은 섬세한, Tune은 조율하다이다. 악기 줄을 미세하게 맞추는 일을 떠올리면 된다.
이미 학습된 모델을 특정 데이터로 조금 더 학습시켜 모델 자체를 바꾸는 방법이다. 위의 기법들이 모델 바깥을 설계하는 일이라면 파인튜닝은 모델 안쪽(인공지능 노트에서 본 파라미터)을 고친다. 비용과 준비가 많이 들어서 흔히 권하는 순서는 프롬프트, 컨텍스트, RAG로 먼저 해결해 보고 부족할 때 고려하는 것이다. 엄밀히는 이 노트에서 말한 활용의 범위 밖이지만, 언제 활용만으로 부족한지 가늠하려고 함께 적었다.

## 어디서부터 시작할까
1. 한 번 쓰고 끝나는 질문이라면 프롬프트를 구체적으로 쓰는 것으로 충분하다
2. 답이 엉뚱하다면 모델이 필요한 정보를 받았는지부터 본다(컨텍스트)
3. 같은 실수가 반복된다면 말로 부탁하지 말고 지시 파일, 훅, 테스트 같은 장치로 막는다(하네스)
4. 매번 같은 지시를 사람이 반복하고 있다면 그 반복을 시스템에 넘긴다(루프)
5. 어느 단계든 나아졌는지 판단할 기준과 평가가 먼저다

Anthropic이 권한 것처럼 가장 단순한 방법부터 쓰고, 그것으로 부족할 때만 다음 단계로 넘어간다(참고 자료 1).

## 한눈에 보는 용어
| 용어 | 사전적 의미 | 쉽게 말하면 |
| --- | --- | --- |
| 활용 (Utilization) | 충분히 잘 이용함 | 만들어진 모델에게 일을 잘 맡기는 법 |
| 에이전트 (Agent) | 대리인 | 도구를 쓰며 여러 단계를 스스로 진행하는 AI |
| 프롬프트 엔지니어링 (Prompt Engineering) | 프롬프트: 재촉함, 대사를 일러 줌 | 지시문을 잘 쓰는 기술 |
| 퓨샷 (Few-shot) | 몇 번의 시도 | 예시 몇 개를 보여 주고 따라 하게 하기 |
| 생각의 사슬 (Chain-of-Thought) | 생각을 고리처럼 이음 | 답 전에 풀이 과정을 거치게 하기 |
| 프롬프트 체이닝 (Prompt Chaining) | 체인: 사슬 | 큰 일을 나눠 앞 결과를 다음 지시에 넘기기 |
| 컨텍스트 엔지니어링 (Context Engineering) | 컨텍스트: 맥락, 문맥 | 모델이 볼 정보를 고르고 관리하는 기술 |
| 컨텍스트 창 (Context Window) | 맥락을 보는 창문 | 모델이 한 번에 볼 수 있는 양 |
| 컨텍스트 부패 (Context Rot) | 맥락이 썩음 | 너무 많이 넣으면 정보를 잘 못 떠올리는 현상 |
| 압축 (Compaction) | 빽빽하게 다짐, 작게 줄임 | 긴 대화를 요약하고 새로 시작하기 |
| 검색 증강 생성 (RAG) | 찾아온 것으로 보강해 만듦 | 관련 문서를 찾아 넣고 그걸 근거로 답하게 하기 |
| 하네스 (Harness) | 마구, 안전띠 | 모델을 둘러싼 지시 파일, 도구, 검사 장치 전체 |
| 모델 컨텍스트 프로토콜 (MCP) | 프로토콜: 의례, 지켜야 할 절차 | AI와 바깥 도구를 잇는 표준 약속 |
| 스킬 (Skill) | 솜씨, 숙련된 기술 | 특정 작업 절차를 묶어 필요할 때 불러오는 폴더 |
| 훅 (Hook) | 갈고리 | 특정 사건마다 자동으로 도는 검사 |
| 루프 엔지니어링 (Loop Engineering) | 루프: 고리, 둥글게 이어진 줄 | 사람 대신 시스템이 AI를 일하게 하고 확인하는 반복 구조 설계 |
| 워크트리 (Worktree) | 작업 폴더 구조 | 한 저장소를 여러 작업 폴더로 나눠 쓰는 Git 기능 |
| 상태 (State) | 놓여 있는 모양이나 형편 | 대화 밖에 적어 두는 진행 기록 |
| 이해의 빚 (Comprehension Debt) | 이해하지 못한 채 쌓인 빚 | 아무도 읽지 않은 코드가 쌓인 상태 |
| 워크플로 (Workflow) | 일의 흐름 | 정해진 순서대로 AI와 도구가 움직이는 구조 |
| 평가 주도 개발 (Eval-driven Development) | 평가: 값어치를 따져 매김 | 채점 기준을 먼저 만들고 바꿀 때마다 점수로 판단하기 |
| 스펙 (Spec) | 명세, 설명서 | 구현 전에 먼저 쓰는 요구 사항 문서 |
| 바이브 코딩 (Vibe Coding) | 바이브: 분위기, 느낌 | 코드를 안 읽고 AI 결과를 그대로 받아들이는 방식 |
| 파인튜닝 (Fine-tuning) | 미세 조율 | 모델을 추가로 학습시켜 안쪽을 고치기 |
