## 컨텍스트 엔지니어링 예시란 ?
- [컨텍스트 엔지니어링](../README.md) 문서에서 본 기법과, 같은 Anthropic 글이 다룬 시스템 프롬프트, 도구, 예시 고르기를 실제로 어떻게 쓰는지 보여 주는 예시 모음
- 기법마다 공식 글의 내용을 먼저 요약하고 적용 예를 이어 붙였다. 이 노트 레포에서 실제로 쓰고 있는 것은 그렇다고 밝혔고, 나머지는 설명을 위해 만든 예다
- 원문은 Anthropic의 [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)(참고 자료 1)와 [Contextual Retrieval](https://www.anthropic.com/news/contextual-retrieval)(참고 자료 2)에서 가져왔다. 2026-10-21에 확인한 내용이다

### 좋은 컨텍스트의 기준
Anthropic 글은 컨텍스트를 한정된 자원으로 보고, 원하는 결과가 나올 가능성을 가장 높이는 가장 작은 정보 묶음을 찾으라고 한다(참고 자료 1). 많이 넣을수록 좋은 것이 아니라, 꼭 필요한 것만 넣는 것이 기준이다. 많이 넣으면 생기는 문제는 [토큰](../../%5BAI%20활용%5D%20토큰(Token)/README.md) 문서의 컨텍스트 부패에서 보았다.

<br/>

## 1. 시스템 프롬프트의 높이 맞추기
### 원문 조언
글은 시스템 프롬프트가 흔히 빠지는 두 가지 실패를 든다(참고 자료 1).

- 너무 구체적인 경우: 원하는 동작을 정확히 끌어내려고 복잡하고 깨지기 쉬운 if-else 규칙을 프롬프트에 박아 넣는다
- 너무 막연한 경우: 원하는 결과에 대한 구체적인 신호 없이 높은 수준의 방향만 준다

둘 사이의 알맞은 높이(right altitude)를 찾으라고 한다. altitude의 사전적 의미는 고도, 비행 높이다. 너무 낮게 날면 땅의 세부만 보이고 너무 높이 날면 방향만 보이듯, 프롬프트도 세부 규칙과 막연한 방향 사이의 알맞은 높이에서 써야 한다는 뜻이다. 글은 프롬프트를 `<background_information>`, `<instructions>`, `## Tool guidance`, `## Output description` 같은 구역으로 나누는 방법을 예로 든다. 처음에는 가장 좋은 모델로 최소한의 프롬프트부터 시험해 보라고 한다.

### 적용 예
```text
너무 구체적인 예
사용자가 "환불"이라고 하면 1번 답변을, "반품"이라고 하면 2번 답변을, 둘 다 말하면 1번 다음 2번을 말하고,
주문 번호가 없으면 3번을 말한다. ...(규칙 50줄)

너무 막연한 예
친절하게 고객을 도와줘.

알맞은 높이의 예
<background_information>
온라인 의류 쇼핑몰의 고객 문의 상담이다. 환불은 받은 날부터 7일 안에만 된다.
</background_information>
<instructions>
고객이 무엇을 원하는지 먼저 확인하고, 주문 번호가 없으면 요청한다.
정책으로 해결할 수 없는 요청은 상담원 연결을 안내한다.
</instructions>
```

알맞은 높이의 예는 모든 경우를 규칙으로 적지 않는다. 판단에 필요한 배경과 원칙만 주고, 구체적인 대응은 모델에게 맡긴다.

## 2. 도구는 적게, 겹치지 않게
### 원문 조언
도구 정의도 컨텍스트에 들어간다. 글은 도구가 스스로 완결되고, 오류에 강하고, 쓰임이 아주 분명해야 한다고 한다(참고 자료 1). 흔한 실패로는 기능을 너무 많이 담거나 어떤 도구를 써야 할지 애매한 지점을 만들어, 비대해진 도구 모음을 든다.
판단 기준도 준다. 사람 엔지니어도 이 상황에 어느 도구를 써야 하는지 분명히 말할 수 없다면, 에이전트도 더 잘하리라 기대할 수 없다는 것이다. 그래서 꼭 필요한 최소한의 도구만 골라 두라고 권한다.

### 적용 예
```text
겹치는 예
search_files, find_files, grep_files, look_up_file
(이름만 다르고 하는 일이 비슷해 무엇을 쓸지 헷갈린다)

나눈 예
find_files: 파일 이름 패턴으로 파일 목록을 찾는다
search_content: 파일 내용에서 문자열을 찾는다
```

## 3. 예시는 대표적인 것 몇 개만
### 원문 조언
글은 퓨샷(Few-shot, 뜻은 [프롬프트 엔지니어링](../../%5BAI%20활용%5D%20프롬프트%20엔지니어링(Prompt%20Engineering)/README.md) 참고) 예시를 넣는 것을 강하게 권하면서도, 경계 상황을 길게 늘어놓은 목록(laundry list)으로 프롬프트를 채우는 것은 권하지 않는다고 한다(참고 자료 1). 대신 기대하는 동작을 잘 보여 주는, 서로 다르면서도 대표적인(canonical) 예시를 골라 두라고 한다. 예시는 천 마디 말만큼의 값을 하는 그림이라고 표현한다.

### 적용 예
이 레포의 [글쓰기 가이드](../../../.claude/docs/writing-guide.md)가 이 방식이다. 경우를 모두 늘어놓지 않고, 대부분의 규칙에 피할 예와 고친 예를 한 쌍만 둔다.

## 4. 필요할 때 불러오기와 미리 넣어 두기
### 원문 조언
에이전트는 데이터를 미리 다 넣지 않고, 파일 경로, 저장된 쿼리, 웹 링크 같은 가벼운 식별자만 들고 있다가 실행 중에 필요한 것을 불러온다(참고 자료 1). 글은 Claude Code를 예로 든다.

- 큰 데이터를 다룰 때 `head`, `tail` 같은 명령으로 필요한 부분만 본다. 전체를 컨텍스트에 올리지 않는다
- 파일 이름과 위치도 정보가 된다. `tests` 폴더 안의 `test_utils.py` 는 다른 폴더의 같은 이름 파일과 쓰임이 다르다고 짐작할 수 있다
- 섞어 쓰는 방식(hybrid): `CLAUDE.md` 파일은 처음부터 컨텍스트에 그대로 넣고, 나머지 파일은 `glob`, `grep` 으로 찾아 필요할 때 읽는다

다만 실행 중에 찾는 방식은 느리고, 안내가 없으면 도구를 잘못 써서 막다른 길을 쫓느라 컨텍스트를 낭비할 수 있다고 덧붙인다.

### 적용 예
이 레포도 섞어 쓰는 방식이다.

- 늘 필요한 규칙은 미리 넣는다. `.claude/CLAUDE.md` 가 세션 시작 때 들어가고, 그 안의 `@docs/writing-guide.md` 줄이 글쓰기 가이드까지 함께 불러온다
- 나머지는 필요할 때 찾는다. 노트를 이어 쓸 때는 목차 README와 앞 장만 열어 보고, 다른 노트는 검색으로 찾는다

<br/>

## 5. 압축
### 원문 조언
글은 Claude Code의 압축을 예로 든다(참고 자료 1). 지금까지의 대화 기록을 모델에게 넘겨 가장 중요한 내용만 요약하게 하고, 그 요약에 최근에 연 파일 다섯 개를 더해 이어서 일한다.

- 남기는 것: 설계 결정, 아직 풀리지 않은 버그, 구현 세부 사항
- 버리는 것: 중복된 도구 출력이나 메시지

가장 가볍고 안전한 압축으로는 도구 결과 지우기(tool result clearing)를 든다. 대화 기록 깊숙이 있는 도구 결과를 에이전트가 원본 그대로 다시 볼 일은 드물기 때문이다.

### 적용 예
긴 작업을 하다 대화를 새로 시작할 때 남길 요약은, 예를 들면 아래처럼 쓸 수 있다.

```text
지금까지 한 일: 파이썬 노트 19장까지 작성, main에 push 완료
정한 것: 장 폴더 이름은 NN_한글명(English Name), TODO는 목차에만 둔다
남은 일: 20장 주제 정하기 (목차 TODO 참고)
버린 것: 각 장의 예시 코드 실행 로그 (결과는 문서에 이미 반영함)
```

<br/>

## 6. 메모 남기기
### 원문 조언
에이전트가 진행 상황을 컨텍스트 밖에 적어 두고 나중에 다시 읽는 방식이다. 글은 Claude Code가 할 일 목록을 만드는 것, 직접 만든 에이전트가 `NOTES.md` 파일을 관리하는 것을 예로 든다(참고 자료 1).
Claude가 포켓몬 게임을 하는 실험도 소개한다. 에이전트는 "피카츄가 목표인 10레벨 가운데 8레벨을 올렸다" 같은 진행 상황, 탐험한 지역의 지도, 전투 전략 메모를 스스로 적어 둔다. 컨텍스트가 초기화된 뒤에도 자기 메모를 읽고 몇 시간짜리 훈련이나 던전 탐험을 이어 간다.

### 적용 예
예를 들면 아래처럼 쓸 수 있다.

```markdown
# NOTES.md
## 진행 상황
- [x] 1~10장 링크 점검
- [ ] 11~19장 링크 점검

## 알게 된 것
- 링크 점검은 node .claude/scripts/check-links.js <폴더> 로 한다
- 폴더 이름의 공백은 %20으로 쓴다
```

## 7. 하위 에이전트에게 맡기기
### 원문 조언
조사 같은 일을 깨끗한 컨텍스트를 가진 하위 에이전트에게 맡기는 방식이다(참고 자료 1). 하위 에이전트는 수만 토큰 넘게 쓰며 넓게 탐색할 수 있지만, 돌려주는 것은 작업을 압축한 요약(흔히 1,000~2,000토큰)뿐이다. 자세한 탐색 내용은 하위 에이전트 안에 남고, 주 에이전트는 결과를 종합하고 분석하는 데 집중한다.

### 적용 예
이 레포의 `note-reviewer` 에이전트가 이 방식이다. 노트를 다 쓰면 주 세션이 파일 경로와 볼 관점을 넘기고, 리뷰 에이전트가 앞 장과 관련 노트를 따로 읽어 대조한다. 주 세션은 그 파일들을 직접 읽지 않고 위치, 문제, 제안으로 정리된 지적 목록만 받는다. 리뷰 에이전트가 파일을 고치지 못하게 도구를 읽기 전용(Read, Grep, Glob)으로 묶어 둔 것은 [하네스 엔지니어링](../../%5BAI%20활용%5D%20하네스%20엔지니어링(Harness%20Engineering)/README.md)에 해당한다.

## 8. 검색 증강 생성(RAG)에서 잃어버린 맥락 되살리기
### 원문 예시
RAG는 긴 문서를 작은 조각으로 나눠 저장해 두고, 질문과 관련된 조각을 찾아 컨텍스트에 넣는다. 그런데 Anthropic의 2024-09-19 글은 문서를 조각으로 나누면 맥락이 사라지는 문제를 든다(참고 자료 2). 회사 공시 문서의 한 조각이 아래와 같다면, 어느 회사의 어느 분기 이야기인지 알 수 없어서 검색에 잘 걸리지 않는다.

```text
원래 조각 (번역)
회사의 매출은 직전 분기보다 3% 늘었다.

맥락을 붙인 조각 (번역)
이 조각은 ACME사의 2023년 2분기 실적에 관한 SEC 공시에서 나왔다. 직전 분기 매출은 3억 1400만 달러였다.
회사의 매출은 직전 분기보다 3% 늘었다.
```

조각마다 이런 짧은 설명을 앞에 붙여 저장하는 방식을 맥락 검색(Contextual Retrieval)이라 부른다. 글에 따르면 관련 조각을 상위 20개 안에 찾지 못하는 비율이 5.7%에서 아래처럼 줄었다. 임베딩(Embedding)은 글을 뜻이 비슷하면 가까운 숫자 묶음으로 바꾼 것이고, BM25는 질문의 낱말이 얼마나 겹치는지로 점수를 매기는 키워드 검색 방식이다. 재순위화(Reranking)는 찾은 후보를 다른 모델로 한 번 더 줄 세우는 단계다. 임베딩은 상위 문서의 TODO에서 이어 다룬다.

| 방식 | 검색 실패율 | 줄어든 비율 |
| --- | --- | --- |
| 맥락 임베딩 (Contextual Embeddings) | 3.7% | 35% |
| 맥락 임베딩 + 맥락 BM25 | 2.9% | 49% |
| 위에 재순위화(Reranking) 추가 | 1.9% | 67% |

### RAG가 필요 없는 경우
같은 글은 자료 전체가 20만 토큰(약 500쪽)보다 작으면 RAG 없이 자료를 프롬프트에 통째로 넣어도 된다고 한다(참고 자료 2). 검색 단계가 없으니 만들기도 쉽다. 다만 이 기준은 2024년 글에 나온 것이다. 지금은 컨텍스트 창이 100만 토큰인 모델도 있지만([토큰](../../%5BAI%20활용%5D%20토큰(Token)/README.md) 문서), 많이 넣을수록 컨텍스트 부패와 요금이 늘어나므로 창 크기만 보고 통째로 넣을지 정하지는 않는다.

## 기법 요약
| 기법 | 한 줄 요약 | 적용 예 |
| --- | --- | --- |
| 시스템 프롬프트 높이 맞추기 | 규칙을 박아 넣지도, 막연하지도 않게 | 쇼핑몰 상담 프롬프트 (만든 예) |
| 도구는 적게 | 쓰임이 겹치지 않는 최소한의 도구 | 파일 찾기 도구 이름 (만든 예) |
| 대표적인 예시 | 경계 상황 나열 대신 대표 예시 몇 개 | 이 레포의 글쓰기 가이드 |
| 필요할 때 불러오기 | 늘 쓰는 것만 미리, 나머지는 찾아서 | 이 레포의 CLAUDE.md와 가이드 import |
| 압축 | 결정과 남은 일만 남기고 요약 | 새 세션으로 넘길 요약 (만든 예) |
| 메모 남기기 | 진행 상황을 파일에 적어 두고 다시 읽기 | NOTES.md (만든 예) |
| 하위 에이전트 | 탐색은 맡기고 요약만 받기 | 이 레포의 note-reviewer 에이전트 |
| 맥락 검색 | 조각마다 맥락 설명을 붙여 저장 | 없음 |
