## 워크플로와 에이전트 예시란 ?
- [워크플로와 에이전트](../README.md) 문서에서 본 다섯 가지 워크플로 패턴과 에이전트, 원문 부록의 도구 설계 조언이 실제로 어디에 쓰이는지 보여 주는 예시 모음
- 패턴마다 원문이 든 쓰임새와 예를 먼저 옮기고 적용 예를 이어 붙였다. 이 노트 레포에서 실제로 쓰는 것은 그렇다고 밝혔고, 나머지는 설명을 위해 만든 예다
- 원문은 Anthropic의 [Building effective agents](https://www.anthropic.com/research/building-effective-agents)(참고 자료 1)에서 가져왔다. 2026-10-21에 확인한 내용이다

### 고르는 기준
원문은 패턴마다 언제 쓰는지(When to use)를 짧게 정리한다. 아래 절은 그 내용을 먼저 옮긴다. 공통된 기준은 상위 문서에서 본 것처럼 가장 단순한 방법부터 쓰고, 필요할 때만 복잡도를 올리는 것이다(참고 자료 1).

<br/>

## 1. 프롬프트 체이닝 (Prompt Chaining)
### 원문 예
일을 고정된 하위 작업으로 쉽고 깔끔하게 나눌 수 있을 때 알맞다고 한다(참고 자료 1). 원문의 예는 두 가지다.

- 마케팅 문구를 쓰고, 그다음 다른 언어로 옮기기
- 문서 개요를 쓰고, 개요가 기준을 만족하는지 확인하고, 그 개요로 문서를 쓰기

### 이 레포의 예
이 레포의 노트 작성 절차(`.claude/skills/note/SKILL.md`)가 이 패턴과 같은 생각이다. 요청 종류를 가른 뒤(2절), 위치 결정, 작성, 검증, 리뷰, 연결 갱신, 보고를 정해진 순서로 한다. 작성한 파일이 검증 단계에서 코드 실행과 링크 점검의 대상이 되고, 검증에서 고친 파일이 리뷰 에이전트에게 넘어가는 식이다.
다만 원문의 체이닝은 코드가 호출과 호출을 이어 주는 구조이고, 이 레포는 한 세션이 절차 문서를 읽고 순서를 따른다. 단계를 나누고 앞 결과를 넘긴다는 생각은 같지만 코드로 고정된 경로는 아니다(6절 참고).

<br/>

## 2. 라우팅 (Routing)
### 원문 예
따로 다루는 편이 나은 뚜렷한 종류가 있고, 그 분류를 LLM이나 전통적인 분류 모델로 정확하게 할 수 있을 때 잘 맞는다고 한다(참고 자료 1). 원문의 예는 두 가지다.

- 고객 문의를 일반 질문, 환불 요청, 기술 지원으로 나눠 서로 다른 처리, 프롬프트, 도구로 보내기
- 쉽고 흔한 질문은 Claude Haiku 4.5 같은 작고 값싼 모델로, 어렵거나 드문 질문은 Claude Sonnet 4.5 같은 더 강한 모델로 보내기

### 이 레포의 예
노트 작성 절차의 첫 단계가 라우팅과 같은 생각이다. 요청을 새 노트, 이어 쓰기, 개정 중 하나로 먼저 가르고, 종류마다 다음에 할 일이 달라진다. 새 노트면 주제 폴더를 새로 만들고, 이어 쓰기면 쓸 주제가 목차 TODO에 있는지 확인하고, 개정이면 원문을 먼저 읽고 바꾸는 범위를 요청 범위로 좁힌다. 어느 쪽인지 애매하면 한 번 묻는다.

<br/>

## 3. 병렬화 (Parallelization)
### 원문 예
나눈 하위 작업을 동시에 돌려 속도를 낼 수 있을 때, 또는 더 믿을 만한 결과를 위해 여러 관점이나 여러 번의 시도가 필요할 때 효과적이라고 한다(참고 자료 1). 원문은 두 가지 방식으로 나눈다.

- 나누기(Sectioning): 한 모델이 사용자 질문을 처리하는 동안 다른 모델이 부적절한 내용인지 걸러 내는 안전장치. 평가를 자동화할 때 호출마다 다른 측면을 평가하게 하기
- 투표(Voting): 여러 프롬프트가 같은 코드를 따로 검토해 취약점을 표시하기. 내용이 부적절한지 여러 프롬프트로 판단하고, 거짓 양성과 거짓 음성의 균형을 맞추도록 투표 기준을 다르게 두기

### 적용 예
노트 작성 절차는 리뷰(5단계)를 마친 뒤 연결 갱신(6단계)을 하도록 순서를 정해 두어서, 절차에는 병렬화가 없다. 쓴다면 리뷰 에이전트가 검토하는 동안 주 세션이 리뷰 대상이 아닌 목차 README와 앞 장의 다음 링크를 고치는 식으로 나눌 수 있다. 리뷰 대상 파일은 건드리지 않으니 두 일이 서로 부딪히지 않는다.
투표 방식도 쓰지 않는다. 리뷰는 한 에이전트가 한 번 한다.

<br/>

## 4. 오케스트레이터-워커 (Orchestrator-workers)
### 원문 예
필요한 하위 작업을 미리 알 수 없는 복잡한 일에 잘 맞는다고 한다(참고 자료 1). 병렬화와 비슷해 보이지만, 하위 작업이 미리 정해져 있지 않고 지휘하는 쪽이 입력을 보고 정한다는 점이 다르다. 원문의 예는 두 가지다.

- 매번 여러 파일을 복잡하게 바꾸는 코딩 제품
- 여러 출처에서 관련 정보를 모으고 분석하는 검색 작업

### 적용 예
레포 전체의 폴더를 정리하는 일이라면 이렇게 나눌 수 있다. 지휘하는 쪽이 먼저 폴더를 훑고 폴더마다 필요한 일을 정한다. README가 없는 폴더에는 목차 초안 쓰기를, 링크가 깨진 폴더에는 링크 고치기를 맡기는 식이다. 일꾼들이 돌려준 결과는 지휘하는 쪽이 모아 형식을 맞춘다. 어떤 하위 작업이 몇 개 생길지는 폴더를 본 뒤에야 정해진다.
이 레포에서 최상위 폴더 14곳의 README를 만들 때는 이렇게 나누지 않고, 한 세션이 폴더 목록과 노트 첫 부분을 읽고 한 번에 썼다.

<br/>

## 5. 평가자-최적화 (Evaluator-optimizer)
### 원문 예
평가 기준이 분명하고, 고쳐 나갈수록 측정할 수 있는 만큼 나아질 때 특히 효과적이라고 한다(참고 자료 1). 원문의 예는 두 가지다.

- 문학 번역: 번역하는 LLM이 처음에는 놓치는 뉘앙스를, 평가하는 LLM이 쓸모 있는 비평으로 짚어 줄 수 있을 때
- 복잡한 검색: 여러 번 검색하고 분석해야 할 때, 더 찾아볼지를 평가하는 쪽이 정하게 하기

### 이 레포의 예
노트 작성과 리뷰는 이 패턴의 한 바퀴에 해당한다. 주 세션이 노트를 쓰고(최적화하는 쪽), `note-reviewer` 에이전트가 CLAUDE.md와 글쓰기 가이드를 기준으로 평가해 지적을 돌려주면, 주 세션이 고친다. 리뷰 에이전트의 구성은 [하네스 엔지니어링 예시](../../%5BAI%20활용%5D%20하네스%20엔지니어링(Harness%20Engineering)/예시(Examples)/README.md) 5절에 있다.
평가 기준이 정해져 있어 원문의 첫째 조건은 맞는다. 하지만 고친 뒤 다시 평가받지 않아서, 반복할수록 나아지는지는 재지 않는다([루프 엔지니어링 예시](../../%5BAI%20활용%5D%20루프%20엔지니어링(Loop%20Engineering)/예시(Examples)/README.md) 참고).

## 6. 에이전트 (Agent)
### 원문 예
에이전트는 필요한 단계 수를 미리 알기 어렵거나 불가능하고, 정해진 경로를 코드로 박아 둘 수 없는 열린 문제에 쓴다고 한다(참고 자료 1). 원문의 예는 두 가지다.

- 과제 설명을 보고 여러 파일을 고쳐야 하는 SWE-bench 과제를 푸는 코딩 에이전트. SWE-bench는 실제 GitHub 이슈를 고치게 해 코딩 능력을 재는 벤치마크다
- Claude가 컴퓨터를 직접 써서 일을 해내는 컴퓨터 사용(computer use) 참고 구현

원문은 에이전트를 만들 때 지킬 세 가지 원칙도 든다.

1. 설계를 단순하게 유지한다
2. 에이전트의 계획 단계를 드러내 보여 투명하게 한다
3. 도구 문서를 꼼꼼히 쓰고 시험해 에이전트-컴퓨터 인터페이스(Agent-Computer Interface, ACI)를 공들여 만든다

### 이 레포의 예
노트 레포에서 Claude Code가 하는 일은 에이전트에 가깝다. "데코레이터 장 이어서 작성해" 같은 요청을 받으면, 어느 장을 읽을지, 어떤 예시를 실행해 볼지, 어느 링크를 고칠지를 그때그때 정한다. 다만 절차의 뼈대는 스킬이 정해 둔 워크플로라서, 정해진 길 위에서 판단하는 섞인 구조다.

<br/>

## 7. 도구를 실수하기 어렵게
### 원문 예
원문 부록은 사람-컴퓨터 인터페이스(Human-Computer Interface, HCI)에 들이는 만큼 에이전트-컴퓨터 인터페이스(ACI)에도 공을 들이라고 한다(참고 자료 1). 그리고 도구를 포카요케(poka-yoke)하라고, 즉 실수하기 어렵게 인자를 바꾸라고 한다. 포카요케는 일본 제조업에서 쓰는 말로, 부품을 잘못 끼울 수 없게 모양을 만드는 식의 실수 방지 장치를 뜻한다(이 뜻풀이는 원문이 아니라 일반적인 뜻이다).
원문의 예는 파일 경로다. 에이전트가 루트 디렉터리(root directory)를 벗어난 뒤 상대 경로로 도구를 쓰다 실수하는 것을 보고, 도구가 늘 절대 경로를 요구하도록 바꿨더니 모델이 이 방식을 문제없이(flawlessly) 썼다고 한다. SWE-bench용 에이전트를 만들 때는 전체 프롬프트보다 도구를 다듬는 데 더 많은 시간을 썼다고도 적었다.

### 적용 예
아래는 설명을 위해 만든 예다. 이 레포의 `check-links.js` 는 지금 상대 경로를 받는다.

```text
실수하기 쉬운 도구
check_links(path)        # 상대 경로면 지금 폴더에 따라 다른 곳을 본다

실수하기 어려운 도구
check_links(abs_path)    # 절대 경로만 받고, 상대 경로가 오면 오류와 함께 이유를 돌려준다
```

도구를 적게, 겹치지 않게 두는 조언은 [컨텍스트 엔지니어링 예시](../../%5BAI%20활용%5D%20컨텍스트%20엔지니어링(Context%20Engineering)/예시(Examples)/README.md) 2절에 있다.
