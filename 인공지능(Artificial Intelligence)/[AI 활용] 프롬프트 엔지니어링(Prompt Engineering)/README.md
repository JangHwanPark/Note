## 프롬프트 엔지니어링이란 ?
- 모델에게 주는 질문과 지시문을 설계해 원하는 답을 얻는 기법
- AI 활용 방법 가운데 가장 먼저 나왔고, 컨텍스트, 하네스, 루프 엔지니어링도 결국 그 안에 프롬프트를 품고 있다
- 전체 흐름은 [AI 활용 방법](../%5BAI%20활용%5D%20AI%20활용%20방법(AI%20Usage%20Methods)/README.md) 문서에 있다

### 프롬프트 엔지니어링 (Prompt Engineering)
프롬프트의 사전적 의미(재촉하다, 대사를 일러 주다)는 [인공지능](../README.md) 노트에서 보았다. 엔지니어링은 공학, 즉 설계하고 만드는 일이다.
합치면 AI에게 일러 줄 말을 설계하는 일이 된다. Anthropic은 이를 좋은 결과를 얻도록 LLM에게 줄 지시를 쓰고 구성하는 방법이라고 설명한다(참고 자료 1).

<br/>

## 왜 필요할까
모델은 사람처럼 눈치를 보고 빈칸을 채워 주지 않는다. "보고서 써 줘"라고만 하면 누구를 위한 보고서인지, 길이는 어느 정도인지, 어떤 형식인지 모른 채 그럴듯한 평균값을 낸다. 같은 모델이라도 지시가 구체적일수록 결과가 원하는 쪽에 가까워진다.

새로 온 신입 사원에게 "이거 정리해 줘"라고만 하면 엉뚱한 결과가 나오는 것과 같다. 누가 볼 자료인지, 언제까지인지, 어떤 양식인지 알려 줘야 한다.

<br/>

## 대표 기법
Anthropic 문서는 분명하게 쓰기, 예시 주기, 태그로 구조 나누기, 역할 주기, 생각하게 하기, 프롬프트 체이닝을 기본 기법으로 든다(참고 자료 2).

### 분명하고 구체적으로 쓰기
목적, 읽을 사람, 형식, 길이를 적는다. 사람에게는 당연한 것도 모델에게는 적어 줘야 한다.

### 예시 주기, 퓨샷 (Few-shot)
Shot의 사전적 의미는 한 번 쏘기, 한 번의 시도다. 모델에게 보여 주는 예시 하나를 한 번의 시도로 세어, 예시 몇 개를 주는 방식을 퓨샷 프롬프팅이라고 한다. 예시 없이 지시만 주면 제로샷(Zero-shot)이라고 부른다.
2020년 GPT-3 논문이 예시 몇 개만으로 모델이 새 일을 해내는 것을 보이며 널리 알려졌다(참고 자료 3).

### 생각하게 하기, 생각의 사슬 (Chain-of-Thought, CoT)
Chain의 사전적 의미는 사슬이다. 생각 하나하나를 사슬의 고리처럼 이어 답까지 간다는 뜻이다.
답만 묻지 않고 풀이 과정을 거치게 하는 방식이다. 2022년 Google 연구진은 풀이 과정이 담긴 예시를 주면 큰 모델에서 수학 문제 정답률이 크게 오르고, 작은 모델에서는 효과가 없다고 보고했다(참고 자료 4). 암산으로 바로 답을 말하게 하는 대신 연습장에 풀이를 쓰게 하는 것과 같다.

### 역할 주기
"너는 10년 차 QA 엔지니어다"처럼 관점을 주면 말투와 다루는 관점이 그 역할에 맞춰진다(참고 자료 2).

### 구조 나누기
지시, 자료, 예시를 태그나 제목으로 구분해 섞이지 않게 한다(참고 자료 2). 긴 자료를 붙여 넣을 때 어디까지가 지시이고 어디부터가 자료인지 모델이 헷갈리지 않게 하려는 것이다.

### 일 쪼개기, 프롬프트 체이닝 (Prompt Chaining)
큰 일을 한 번에 시키지 않고 여러 프롬프트로 나눠 앞 결과를 다음 입력으로 사슬처럼 넘기는 방식이다(참고 자료 5). 요약하기, 요약에서 문제 찾기, 문제마다 고칠 방법 쓰기를 세 번에 나눠 시키는 식이다. 프롬프트 체이닝은 Anthropic이 꼽은 워크플로 패턴 가운데 하나이기도 하다([워크플로와 에이전트](../%5BAI%20활용%5D%20워크플로와%20에이전트(Workflow%20and%20Agent)/README.md) 참고).

<br/>

## 예시
```text
피할 예
코드 리뷰해 줘.

고친 예
아래 React 컴포넌트를 리뷰해 줘.
- 목적: 머지 전에 버그 가능성을 찾는 것. 스타일 지적은 빼 줘
- 기준: 상태 업데이트 누락, 의존성 배열 오류, 접근성 문제
- 형식: 문제마다 위치, 이유, 고친 코드 한 줄
<code>
...
</code>
```

고친 예에는 목적, 기준, 형식이 있고, 코드는 태그로 지시와 구분했다. 위에서 본 분명하게 쓰기와 구조 나누기를 함께 쓴 것이다.

<br/>

## 시작 전에 할 일
Anthropic 문서는 프롬프트를 고치기 전에 세 가지를 먼저 갖추라고 한다. 무엇이 성공인지에 대한 기준, 그 기준으로 결과를 실제로 재 볼 방법, 고쳐 나갈 첫 프롬프트다(참고 자료 2). 기준 없이 프롬프트를 고치면 나아졌는지 나빠졌는지 알 수 없다. 이 생각은 [평가 주도 개발](../%5BAI%20활용%5D%20평가%20주도%20개발(Eval-driven%20Development)/README.md)로 이어진다.

<br/>

## 한계
프롬프트는 부탁이다. 아무리 잘 써도 모델이 가끔 지키지 않는다. 또 대화가 끝나면 사라지기 때문에 매번 다시 써야 한다. 모델이 볼 정보 전체를 다루는 것은 [컨텍스트 엔지니어링](../%5BAI%20활용%5D%20컨텍스트%20엔지니어링(Context%20Engineering)/README.md)이, 부탁을 장치로 바꾸는 것은 [하네스 엔지니어링](../%5BAI%20활용%5D%20하네스%20엔지니어링(Harness%20Engineering)/README.md)이 맡는다.

<br/>

## 한눈에 보는 용어
| 용어 | 사전적 의미 | 쉽게 말하면 |
| --- | --- | --- |
| 프롬프트 엔지니어링 (Prompt Engineering) | 프롬프트: 재촉함, 대사를 일러 줌 | 지시문을 잘 쓰는 기술 |
| 퓨샷 (Few-shot) | 몇 번의 시도 | 예시 몇 개를 보여 주고 따라 하게 하기 |
| 제로샷 (Zero-shot) | 시도 없음 | 예시 없이 지시만 주기 |
| 생각의 사슬 (Chain-of-Thought) | 생각을 고리처럼 이음 | 답 전에 풀이 과정을 거치게 하기 |
| 프롬프트 체이닝 (Prompt Chaining) | 체인: 사슬 | 큰 일을 나눠 앞 결과를 다음 지시에 넘기기 |
