# StudyRoom Invitation Dialog 개발 회고
이번 스터디룸 초대 기능은 단순한 UI 개발이 아니라 `요구사항이 불명확한 환경에서 문제를 정의하고 이를 구조적 설계와 문서화를 통해 해결한 경험`이었다.

이 과정을 통해 나는 개발자의 역할은 코드를 작성하는 것이 아니라 혼란을 구조화하는 일이라는 것을 배웠다.

앞으로의 목표는 이번 경험을 기반으로
팀 전체의 프로세스와 문서화를 하나의 프론트엔드 개발 표준으로 정립하는 것이다.

## 1. 요구사항 및 분석
이번 작업은 스터디룸 초대 다이얼로그(Invitation Dialog) 기능 개발이었다.

표면적으로는 `학생 초대 기능`이라는 피처가 존재했지만`구체적인 스펙`이 정의되어 있지 않았다.

- 누가 누구를 초대하는가? 
- 초대 가능한 대상의 조건은 무엇인가?
- 이미 초대한 사용자는 어떻게 처리할 것인가?
- 초대 요청 후 UI는 어떻게 갱신되어야 하는가? 

이런 핵심 흐름들이 문서화되어 있지 않았다.

그래서 개발 시작 단계부터 요구사항을 스스로 분석하고 재정의하는 과정이 필요했다. 기존 회의록과 API 문서를 검토하며 다음과 같이 기능 범위를 직접 도출했다.

- 교사는 이메일을 통해 학생을 검색하고 초대할 수 있다. 
- 이미 초대된 사용자는 재초대할 수 없다.
- 초대 시 연결된 보호자도 함께 입장된다.
- 초대가 완료되면 새로고침 없이 UI에서 바로 반영되어야 한다.
- 초대 버튼은 검색 결과가 있고 초대 대상이 존재할 때만 활성화된다.

이 과정을 통해 깨달은 건 `요구사항이 불명확한 상황에서는 기능 구현보다 행동 단위를 먼저 정의해야 한다는 것`즉 사용자가 언제 무엇을 기대하는가?를 먼저 설계하지 않으면 기술 스택이 아무리 좋아도 유지보수 가능한 코드가 나오지 않는다.

## 2. 설계 방향과 마주한 문제들
처음엔 단순한 입력 폼으로 시작했지만 검색, 초대, 상태 관리, 캐시 갱신 UI 안에서 얽히면서 문제가 발생했다.

- 렌더링 시 초대 리스트가 초기화되는 문제 
- 검색 결과와 초대 대상이 서로 다른 상태로 분리되어 데이터 일관성 붕괴 
- API 요청이 반복 호출되며 서버 부하 발생

이 문제를 해결하기 위해 가장 먼저 내린 결론은 이건 단순한 폼이 아니라 상태 중심의 프로세스 UI다. 그래서 아래와 같은 방향으로 설계를 재정의했다.

### 2.1. UI와 로직의 분리 (Controller Pattern)
- useInvitationController 훅을 만들어 검색, 초대, 입력 상태를 한 곳에서 관리
- 컴포넌트는 UI만 담당하고 로직은 컨트롤러가 담당하도록 설계

### 2.2. React Query 도입으로 비동기 흐름 제어
- useSearchInvitationQuery(검색)와 useSendInvitationMutation(전송)을 별도 훅으로 분리
- enabled 대신 명시적 트리거(search 함수) 를 사용하여 Enter 키 입력 시에만 요청 수행
- 초대 성공 시 invalidateQueries로 캐시를 무효화하여 자동 UI 갱신

### 2.3. studyRoomId 주입식 설계
- 하드코딩된 ID(테스트용으로 만든 아이디)를 제거하고, 상위 다이얼로그에서 studyRoomId를 props로 주입
- 검색과 초대 로직이 동일한 context를 공유하도록 구조 통합

### 2.4. 요약
| 영역      | 기술                                      | 이유                     |
| ------- | --------------------------------------- | ---------------------- |
| 상태 관리   | Custom Hook (`useInvitationController`) | UI-로직 분리 및 상태 일관성 확보   |
| 비동기 제어  | React Query (`useQuery`, `useMutation`) | 캐시 기반 요청 및 자동 갱신       |
| 검색 UX   | 명시적 트리거 (Enter Key 기반)                  | 불필요한 요청 방지, 사용자 의도 명확화 |
| 데이터 구조  | Map                                     | 중복 초대 방지 및 삭제 성능 최적화   |
| 디자인 시스템 | Radix UI + TailwindCSS                  | 접근성 및 시각적 일관성 확보       |

## 3. 문제 해결 포인트
### 3.1. 명시적 검색(Enter 기반)
현재 검색은 자동이 아닌 사용자가 Enter 키를 입력해야 실행되는 명시적 방식이다. 초기엔 자동 검색도 고려했지만 다음 이유로 명시적 검색을 선택했다.

- 불필요한 API 요청을 최소화하기 위해 
- `의도한 검색`과 `오타 입력`을 명확히 구분하기 위해
- 서버에서 검색 제한 로직이 존재해 즉시 검색이 UX적으로 불안정했기 때문

이 접근은 반응성보다는 안정성을 우선시한 결과였다.

### 3.2. submit을 컨트롤러가 아닌 UI에서 처리
처음에는 컨트롤러(useInvitationController) 내부에 submit()을 두었으나
React Query 훅은 컴포넌트 스코프 내에서만 안전하게 호출된다.
따라서 컨트롤러는 상태만 관리하고,
실제 초대 API 호출(mutate())은 다이얼로그(UI) 컴포넌트에서 실행하도록 변경했다.

이유: 컨트롤러는 행동 정의만 담당하고 서버 호출은 뷰에서 수행해야 테스트성과 재사용성이 보장되기 때문.

## 4. 배운점 및 회고
이번 작업을 통해 단순히 기술적인 개선뿐 아니라 `팀 프로세스와 문서화의 중요성`을 실감하게 되었다. 그동안 나는 팀 프로젝트를 할 때 항상 문서화를 강조하는 편이었지만 이번 스터디룸 초대 기능을 진행하면서 `왜 문서화가 중요한가`를 더 명확히 체감했다.

이번 피처는 기능명세(FEAT)는 존재했지만 스펙(입력 조건, 에러 케이스, 예외 흐름 등)이 명확히 정의되지 않은 상태에서 시작됐다. 그 결과 개발 초기부터 이 API가 언제 호출되어야 하는가? 초대 실패 시 어떤 피드백을 보여줄 것인가? 같은 세부 이슈들이 반복적으로 발생했다.

이때 가장 큰 교훈은 다음이었다.
- 명확한 문서와 프로세스는 코드를 줄이는 것만큼 팀의 리소스를 절약한다.
- 기능 정의서가 없다면 개발자가 직접 요구사항을 재정의하는 사람이 되어야 한다.

결국 나는 Controller → Query → UI 계층을 명확히 분리하고 기능 단위별로 QueryKey와 API 스펙을 문서화하면서 팀 내 기준을 세웠다. 이를 통해 코드 품질뿐 아니라 팀 전체의 커뮤니케이션 효율이 확실히 개선되는 것을 느꼈다.

즉 이번 경험은 나에게 좋은 개발자란 단순히 코드를 잘 짜는 사람이 아니라 팀의 사고방식을 정돈하는 사람이다.라는 확신을 주었다.

- 자동 검색(디바운스 기반) 기능 추가로 UX 개선
- Optimistic UI 업데이트를 도입하여 초대 즉시 반영
- 공통 에러 핸들링 레이어 구축(Toast + ErrorBoundary 통합)

### 5.2. 팀 프로세스 및 문서화 개선
- 다음 회고 주제는 `프로세스 리디자인`이 되어야 한다. 이번 기능을 통해 얻은 교훈을 바탕으로 프로젝트의 요구사항 수집 → 명세 작성 → 구현 → QA 문서화 흐름을 재정의할 계획이다.
- FDD(Feature-Driven Development)기반 문서 포맷을 도입하여 각 기능별 명세서에 기획, 디자인, API, 테스트케이스를 연결하는 구조로 개선한다.
- 단일 문서 레퍼런스 시스템을 구축(예: Notion 또는 GitHub Wiki 기반)하여 모든 기능이 동일한 템플릿으로 관리되도록 표준화할 예정이다.
- 컨트롤러 - 쿼리 - UI구조를 표준화하여 현재 초대 다이얼로그 구조를 팀 전체 공통 패턴으로 정립해 일관된 개발 및 코드 리뷰 기준을 마련할 계획이다.
