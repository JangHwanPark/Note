## 로딩 상태 표시란 ?
- 로딩 상태 표시(Loading Indicator)는 시스템이 사용자의 요청을 받아 처리하고 있다는 것을, 결과가 나오기 전까지 화면에 알려 주는 UI 패턴이다
- 스피너, 진행 표시줄, 스켈레톤 화면, 버튼 안의 로딩 상태처럼 기다리는 동안 무언가를 보여 주는 방법이 있고, 낙관적 업데이트처럼 기다림 자체를 거의 보여 주지 않는 방법, 준비된 부분부터 먼저 보여 주는 방법이 있다
- 이 노트는 각 패턴이 무엇이고 언제 쓰는지, 기다리는 시간에 따라 어떻게 고르는지, 화면을 못 보는 사용자에게 어떻게 전하는지(접근성)를 다룬다. 특정 라이브러리 구현은 다루지 않고, React 문서와 spin-delay는 개념을 보여 주는 예로만 인용한다

loading의 사전적 의미는 짐을 싣는 일, 적재다. 컴퓨팅에서는 프로그램이나 데이터를 저장 장치나 네트워크에서 가져와 쓸 수 있는 자리에 올려놓는 일을 말한다. indicator의 사전적 의미는 무언가를 가리켜 보여 주는 것, 계기나 표시기다. 자동차 계기판의 연료 표시기처럼 눈에 보이지 않는 상태를 바깥으로 드러내는 장치라는 뜻이 화면 용어로 이어진다. 둘을 합치면 화면 뒤에서 일어나는 가져오기와 처리 과정을 사용자 눈에 보이게 하는 표시가 된다.

알림 전반(토스트, 스낵바, 배너, 모달 등)과 라이브 영역, `status` 와 `alert` 의 차이, WCAG 4.1.3의 기본 내용은 [알림과 피드백](../알림과%20피드백(Notifications%20and%20Feedback)/README.md) 노트에 정리했다. 이 노트에서는 그 내용을 로딩 상황에 적용하는 부분만 쓴다. 불러오기가 끝났는데 보여 줄 내용이 없을 때의 화면은 [빈 상태](../빈%20상태(Empty%20State)/README.md) 노트에 있다. 불러오기가 실패했을 때와 시간 초과는 [오류 상태](../오류%20상태(Error%20State)/README.md) 노트에서 다룬다.

<br/>

## 왜 필요할까
### 아무 변화가 없으면 생기는 일
사용자가 버튼을 눌렀는데 화면이 그대로면, 사용자는 시스템이 일하는 중인지 멈췄는지 구분할 수 없다. NN/g(Nielsen Norman Group)의 진행 표시 글은 사용자의 기다림이 화면을 누르거나 키를 누른 순간부터 시작되며, 시스템이 요청을 받았다는 시각적 변화를 곧바로 주지 않으면 대부분의 사용자가 동작이 접수되지 않았다고 여기고 다시 시도한다고 쓴다. 결제나 주문처럼 두 번 실행되면 곤란한 작업에서는 이 재시도가 실제 문제로 이어진다.

### 기다리는 동안의 신뢰
같은 글은 네브래스카 링컨 대학교의 연구를 소개한다. 링크를 누르고 페이지를 기다리는 동안 반복해서 움직이는 진행 표시줄을 본 그룹은 아무 표시도 보지 못한 그룹보다 만족도가 높았고, 평균 세 배 더 오래 기다리려 했다. 진행 표시는 시간을 줄여 주지는 않지만 시스템이 살아 있다는 확신을 주어 기다림을 견딜 만하게 만든다.

### 체감 성능 (Perceived Performance)
perceive의 사전적 의미는 감지하다, 인식하다다. 체감 성능은 실제로 측정한 속도가 아니라 사용자가 느끼는 속도를 말한다. 같은 3초라도 화면에 아무것도 없으면 길게, 내용이 차오르는 것이 보이면 짧게 느낀다.

Luke Wroblewski는 2013년 글 Mobile Design Details: Avoid The Spinner에서 진행 표시가 그 정의상 사람이 기다려야 한다는 사실에 주의를 끈다고 지적했다. 그의 팀이 만들던 Polar 앱에 스피너를 넣자 사용자들이 앱이 느리다고 불평했고, 팀은 스피너 때문에 진행이 아니라 기다림 표시 자체에 초점이 쏠렸다고 돌아본다. 이 글은 스켈레톤 화면이라는 말을 처음 쓴 글로 여러 디자인 블로그에서 소개되지만, 1차 자료로 확인하지는 못했다(확인 필요).

다만 NN/g의 스켈레톤 화면 글은 스켈레톤 화면이 기다림이 짧다는 착각을 줄 수는 있어도 성능 최적화를 대신하지는 못한다고 쓴다. 체감 성능을 다듬는 일은 실제 속도를 줄이는 일과 함께 가야 한다.

식당에서 반찬이 먼저 깔리면 메인 요리를 같은 시간 기다려도 덜 길게 느껴지는 것과 비슷하다.

### 이 노트에서 쓰는 말
진행 표시(Progress Indicator)는 스피너와 진행 표시줄처럼 작업이 진행 중임을 보여 주는 표시를 함께 부르는 말로 쓴다. 진행률 표시는 그 가운데 얼마나 했는지를 길이나 숫자로 보여 주는 확정형을 말한다. 확정형과 비확정형은 진행 표시줄 절에서 자세히 본다. 로딩 상태 표시는 이 둘에 스켈레톤 화면, 버튼의 로딩 상태까지 아우르는 이 노트 전체의 주제다.

## 응답 시간의 세 가지 한계
### 닐슨의 0.1초, 1초, 10초
Jakob Nielsen은 1993년 책 Usability Engineering에서 응답 시간의 세 가지 한계를 정리했고, NN/g 웹 글에 그 내용이 실려 있다. 2014년에 덧붙인 내용에서는 웹 애플리케이션에도 같은 기준이 그대로 적용된다고 쓴다.

0.1초 안에 반응하면 사용자는 시스템이 즉시 반응했다고 느낀다. 이때는 결과를 보여 주는 것 말고 따로 알릴 것이 없다. 목록에서 항목을 고르면 바로 강조되는 것처럼 화면을 직접 조작하는 느낌이 이 시간 안에서 생긴다.

1초 안이면 사용자는 지연을 알아채지만 생각의 흐름은 끊기지 않는다. 특별한 표시는 필요 없다. 다만 덧붙인 내용은 1초가 넘는 지연이면 커서 모양을 바꾸는 식으로 시스템이 일하는 중임을 보여 주라고 쓴다.

10초는 사용자가 작업에 주의를 붙들어 둘 수 있는 한계다. 이보다 길어지면 사용자는 기다리는 동안 다른 일을 하려 하므로, 언제 끝날지 알려 주는 표시가 필요하다. 덧붙인 내용은 이보다 느린 작업에는 진행률(percent-done) 표시와 분명한 중단 방법을 두라고 쓴다.

### 그래서 언제 무엇을 보여 주나
NN/g의 진행 표시 글은 이 한계를 표시 방법으로 옮긴다. 소제목으로는 약 1초보다 오래 걸리는 작업에 진행 표시를 쓰라고 하고, 1초가 안 걸리는 작업에는 진행 표시를 쓰지 않는다. 반복 애니메이션을 띄우면 사용자가 무엇이 지나갔는지 따라가지 못하고, 화면에 번쩍 나타난 것 때문에 불안해할 수 있다고 쓴다. 2~10초 걸리는 작업에는 스피너 같은 반복 애니메이션을 쓰고, 10초 이상 걸리는 작업에는 진행률 표시를 쓴다. 이 글의 결론은 반복 표시를 2~9초, 진행률 표시를 10초 이상으로 정리하면서, 시간을 미리 정확히 알 수 없다면 진행률 표시로 넘어가는 기준을 더 낮추라고 권한다. 예상 시간이 들쭉날쭉할수록 기준을 낮춘다. 1~2초 구간은 글에서 따로 형태를 정하지 않았고, 이 노트의 표는 본문 기준인 2~10초를 따른다.

여기서 1초 미만에 아무것도 보여 주지 말라는 말은 진행 표시를 띄우지 말라는 뜻이다. 버튼이 눌린 모양으로 바뀌는 것 같은 즉각적인 반응은 시간과 상관없이 항상 준다.

Material Design 3(이하 M3)의 진행 표시 지침은 기준 시간을 다르게 잡는다. 200밀리초 미만이면 표시 없이 바로 콘텐츠를 보여 주고, 200밀리초에서 5초까지는 로딩 표시(Loading indicator), 5초를 넘으면 진행 표시(Progress indicator)를 쓰며(M3는 둘을 별개 컴포넌트로 둔다), 아주 긴 작업은 끝나는 동안 사용자가 다른 화면으로 갈 수 있게 하라고 쓴다. 숫자는 출처마다 다르지만, 짧으면 아무것도 띄우지 않고, 중간이면 일하는 중임을, 길면 얼마나 남았는지를 보여 준다는 방향은 같다.

### 너무 짧은 로딩이 깜빡이지 않게
응답 시간은 미리 알 수 없어서, 보통은 빠르지만 가끔 느린 요청이 많다. 요청을 보내자마자 스피너를 띄우면 빠른 요청에서는 스피너가 한 번 번쩍이고 사라진다. 이 깜빡임을 줄이는 흔한 방법은 두 가지 시간을 함께 쓰는 것이다. 요청이 어느 시간 이상 걸릴 때만 표시를 띄우고(지연), 일단 띄웠으면 최소한 얼마 동안은 유지한다(최소 표시 시간).

React용 라이브러리 spin-delay의 README가 이 문제를 그대로 설명한다. 50밀리초 만에 끝나는 요청에 스피너를 그릴 이유가 없으니 지연을 두는데, 지연을 200밀리초로 두면 210밀리초 걸린 요청에서는 스피너가 10밀리초만 보였다 사라져 오히려 거슬린다. 그래서 지연 뒤에 띄우고 최소 시간 동안 남겨 두며, 기본값은 지연 500, 최소 시간 200이다(README의 예시 코드 기준, 단위는 README에 적혀 있지 않지만 앞 설명으로 보아 밀리초다). 정해진 표준값은 없고, 서비스의 평소 응답 속도를 보고 정한다(내 판단).

## 스피너 (Spinner)
### 이름의 뜻
spin의 사전적 의미는 빙빙 돌다, 회전하다이고, spinner는 도는 것, 팽이처럼 회전하는 물건이다. 화면 용어로는 원이나 점들이 제자리에서 계속 도는 애니메이션으로, 작업이 진행 중이지만 얼마나 남았는지는 알 수 없음을 나타내는 표시를 말한다. 언제 끝날지 정해지지 않은 표시라서 비확정형(indeterminate) 표시라고도 한다. Apple Human Interface Guidelines(이하 HIG)는 이 모양을 활동 표시(Activity Indicator)라고 부른다.

### 쓰임과 동작
스피너는 시스템이 멈추지 않고 일하고 있다는 것 하나만 알린다. 끝날 시점을 계산할 필요가 없어서 만들기 쉽다. NN/g는 이 쉬움 때문에 모든 지연에 반복 애니메이션을 쓰고 싶어지지만, 10초가 넘는 작업에는 권하지 않는다고 쓴다. 스피너가 끝없이 돌면 사용자는 시스템이 아직 일하는지 멈췄는지 확신할 수 없어 작업을 포기할 수 있다. 서버에서 데이터를 받는 경우는 연결 상태를 개발자가 통제할 수 없어서, 평소 2초면 될 일이 15초가 걸릴 수도 있다는 점도 함께 경고한다.

Apple HIG는 백그라운드 작업의 상태를 알리거나 공간이 좁을 때 스피너를 쓰라고 하면서도, 가능하면 진행률을 보여 주는 확정형 표시를 먼저 고르라고 쓴다. 확정형 표시가 있어야 사람들이 기다릴지, 나중에 다시 할지, 그만둘지 정할 수 있기 때문이다.

전화를 걸었을 때의 연결음과 같다. 아직 연결 중이라는 것은 알지만 상대가 언제 받을지는 알 수 없다.

### 언제 쓰고 언제 피하나
NN/g 기준으로 2~10초쯤 걸리는 작업, 그리고 화면 전체가 아니라 카드 하나, 동영상 하나처럼 한 영역만 기다릴 때 맞다. 무엇을 기다리는지 글자를 함께 두면 더 낫다. NN/g는 "Loading comments…"(댓글 불러오는 중)처럼 기다리는 이유를 알려 주는 글자를 예로 든다. 1초 미만의 짧은 작업, 10초가 넘는 긴 작업, 파일 업로드처럼 진행률을 알 수 있는 작업에는 쓰지 않는다.

### 접근성
스피너는 대개 그림이나 CSS 애니메이션뿐이라 스크린 리더(Screen Reader)에는 아무 의미도 전달되지 않는다. 방법은 두 가지가 흔하다. 하나는 스피너를 값이 없는 진행 표시로 표현하는 것이다. 아래 진행 표시줄 절에서 보듯 `role="progressbar"` 에 `aria-valuenow` 를 빼면 비확정형 진행 표시가 된다. 다른 하나는 미리 만들어 둔 `role="status"` 영역에 "댓글 불러오는 중" 같은 글자를 넣는 것이다. WCAG 4.1.3 이해 문서는 사용자가 어떤 과정을 시작한 뒤 바쁨을 뜻하는 아이콘이 나타나고 스크린 리더가 "application busy"라고 알려 주는 경우를 상태 메시지의 예로 든다.

같은 이해 문서는 끝났다는 사실도 전하라고 쓴다. 눈으로 보는 사람은 "기다리는 중" 표시가 사라지면 끝났다고 알지만, 화면을 보지 않는 사람은 표시가 사라진 것을 모른다. 그래서 표시를 지울 때 "불러왔습니다" 같은 보이지 않는 상태 메시지를 남기는 방법을 든다.

```html
<!-- 처음부터 비워 두고, 기다리기 시작하면 글자를 넣는다 -->
<div role="status"></div>
```

움직임에 관한 기준은 아래 움직임과 접근성 절에서 함께 본다.

## 진행 표시줄 (Progress Bar)
### 이름의 뜻
progress의 사전적 의미는 앞으로 나아감, 진행이고, bar는 막대다. 화면 용어로는 작업이 나아간 정도를 막대가 채워진 길이로 보여 주는 표시를 말한다. 직접 만드는 방법은 [프로그래스 바](../../React/UI%20컴포넌트%20만들기(Building%20UI%20Components)/프로그래스%20바(Progress%20Bar)/README.md) 노트에 정리했고, 이 노트에서는 언제 어떤 형태를 쓰는지를 본다.

### 확정형과 비확정형
determinate의 사전적 의미는 확정된, 한정된이고, indeterminate는 그 반대인 확정되지 않은이다. 확정형(Determinate) 진행 표시는 전체 양과 진행된 양을 알 때 0%에서 100%까지 채워진다. 비확정형(Indeterminate) 진행 표시는 얼마나 남았는지 모를 때 쓰며, 막대 안에서 일부가 계속 오가거나 늘었다 줄었다 하면서 일하는 중임만 보여 준다. 그래서 비확정형 막대는 모양만 막대일 뿐 하는 일은 스피너와 같다.

M3는 확정형이 실제 진행을 정확히 반영해야 한다고 쓰고, 정보가 생기면 비확정형에서 확정형으로 바꾸라고 한다. Apple HIG도 걸리는 시간을 알게 되면 확정형으로 바꾸라고 하지만, 원형에서 막대로 모양을 바꾸지는 말라고 쓴다. 모양이 갑자기 바뀌면 화면이 흐트러지기 때문이다.

전자레인지의 남은 시간 표시와 같다. 얼마나 남았는지 보이니 앞에서 기다릴지, 다른 일을 하고 올지 정할 수 있다.

### 막대가 움직이는 방식
NN/g는 진행률 표시를 천천히 시작해 끝으로 갈수록 빨라지게 하라고 쓴다. 처음에 빨리 차면 사용자가 그 속도를 기대하게 되는데, 시스템이 그 속도를 지키지 못하면 실망하기 때문이다. 예상 시간은 넉넉하게 잡는다. 일찍 끝나는 것은 즐거운 놀라움이 된다. 문서나 레코드를 여러 개 처리하는 작업이면 10초 미만이라도 "50개 중 3번째 주소 갱신 중"처럼 개수로 보여 줄 수 있다.

Apple HIG는 진행 표시가 멈춰 있으면 사람들이 작업이 멈췄거나 앱이 얼었다고 여긴다고 쓰고, 진행이 멈췄다면 그 이유와 할 수 있는 일을 알려 주라고 한다. 오래 걸리는 작업에는 중단해도 해가 없으면 취소 버튼을 두고, 취소하면 진행한 것을 잃는 경우에는 일시 정지를 두라고 한다. 닐슨이 10초 넘는 작업에 분명한 중단 방법을 두라고 한 것과 같은 방향이다.

### 하나로 모아 보여 주기
M3는 여러 항목을 함께 불러올 때 항목마다 따로 진행을 보여 주지 말고 전체 진행을 표시 하나로 보여 주라고 쓴다. 페이지 전체를 불러올 때는 페이지 위쪽에 하나를 두고, 서로 따로 움직이는 요소가 있을 때만 표시를 따로 둔다. 막대형은 불러오는 영역의 가장자리에, 원형은 영역 가운데에 두는 것을 기본으로 한다.

### 언제 쓰고 언제 피하나
업로드, 다운로드, 파일 변환, 설치처럼 전체 양을 셀 수 있고 10초 이상 걸리는 작업에 확정형을 쓴다. NN/g의 스켈레톤 화면 글도 다운로드, 업로드, 파일 변환에는 스켈레톤이 아니라 진행 표시줄을 쓰라고 한다. 전체 양을 모르는데 확정형처럼 보이도록 막대를 꾸며 채우는 것은 M3의 실제 진행을 반영하라는 지침과 맞지 않는다.

### 접근성
MDN의 progressbar 역할 문서에 따르면 `role="progressbar"` 는 접근 가능한 이름이 반드시 있어야 하고, 보이는 라벨이 있으면 `aria-labelledby`, 없으면 `aria-label` 로 준다. 현재 값은 `aria-valuenow` 로 주며, 최솟값과 최댓값은 `aria-valuemin` 과 `aria-valuemax` 로 주는데 빠지면 0과 100으로 본다. 비확정형이면 `aria-valuenow` 를 아예 넣지 않는다.

보조 기술은 `aria-valuenow` 를 흔히 퍼센트로 읽는다. "100개 중 23개"처럼 퍼센트로 읽으면 맞지 않는 값이라면 `aria-valuetext` 로 읽을 글자를 따로 준다.

MDN은 ARIA를 붙인 `div` 보다 HTML의 `progress` 요소를 먼저 쓰라고 권한다. `progress` 는 `value` 가 있으면 확정형, `value` 를 빼면 비확정형이 된다. 이미 값을 준 막대를 비확정형으로 되돌리려면 `value` 속성을 지워야 한다.

```html
<!-- 확정형 -->
<label for="upload">문서 올리는 중</label>
<progress id="upload" max="100" value="70">70%</progress>

<!-- 비확정형: value가 없다 -->
<progress aria-label="댓글 불러오는 중"></progress>

<!-- ARIA로 만든 비확정형: aria-valuenow가 없다 -->
<div role="progressbar" aria-label="댓글 불러오는 중"></div>
```

`progress` 태그 사이의 글자는 접근 가능한 이름이 아니라 오래된 브라우저를 위한 대체 글자일 뿐이라고 MDN은 쓴다. 또 `progressbar` 역할의 자식 요소는 의미를 잃고 모두 표현용으로 취급되므로, 안에 제목이나 버튼을 넣지 않는다.

값이 바뀌는 것을 스크린 리더가 알아서 계속 읽어 준다고 기대하면 안 된다. WCAG 4.1.3 이해 문서는 업그레이드 진행 표시줄을 두고 스크린 리더가 진행 상황을 이따금 알려 주는 경우를 예로 들고, 진행 과정을 알리는 기법으로 라이브 영역으로 진행 표시줄의 상태를 전하는 방법(ARIA25)과 `ariaNotify` 로 전하는 방법(ARIA27)을 든다. MDN은 `ariaNotify` 를 2026년에 Baseline에 든 새 API로 표시하므로, 오래된 브라우저에서는 쓸 수 없다고 보고 확인한 뒤 쓴다(2026-11 확인). 몇 퍼센트마다 알려 줄지는 이해 문서가 정하지 않는다. 1%마다 읽히면 사용자가 다른 것을 들을 수 없으므로 25%, 50%처럼 간격을 두는 것이 자연스럽다(내 판단).

## 스켈레톤 화면 (Skeleton Screen)
### 이름의 뜻
skeleton의 사전적 의미는 뼈대, 해골이고, 건물이나 계획의 골격을 뜻하기도 한다. 화면 용어로는 콘텐츠가 들어올 자리에 회색 상자와 막대를 먼저 그려, 완성될 화면의 뼈대만 미리 보여 주는 로딩 표시를 말한다. Wroblewski는 2013년 글에서 스켈레톤 화면을 정보가 점점 채워지는 빈 버전의 페이지라고 설명했다.

### 쓰임과 동작
스피너가 일하는 중이라는 사실을 알린다면, 스켈레톤 화면은 무엇이 어디에 나타날지를 알린다. NN/g는 스켈레톤 화면이 페이지 구조를 미리 보여 주어 인지 부담을 줄이고, 사이트가 고장 났다고 오해하지 않게 하며, 기다림이 짧다는 착각을 준다고 쓴다. Wroblewski의 표현을 빌리면 초점이 불러오는 중이라는 사실에서 불러오는 콘텐츠로 옮겨 간다.

NN/g는 세 가지로 나눈다. 정적 스켈레톤은 글과 이미지 자리에 연한 회색 상자를 두는 가장 흔한 형태다. 애니메이션 스켈레톤은 맥박처럼 깜빡이거나(pulse) 빛이 훑고 지나가는(shimmer) 움직임을 더해 시스템이 일하는 중임을 보여 주는데, 산만하거나 접근성 문제를 만들 수 있다고 쓴다. 틀만 보여 주는 형태(Frame-display)는 머리글과 바닥글, 배경만 그리는 것으로, 페이지 구조를 알려 주지 못해 사실상 스피너와 같다며 권하지 않는다.

식당에서 음식이 나오기 전에 접시와 수저가 자리마다 먼저 놓이는 것과 비슷하다. 아직 음식은 없지만 무엇이 몇 개 어디에 올지는 보인다.

### 언제 쓰고 언제 피하나
NN/g 기준으로 10초 미만의 페이지 전체 로딩에 쓴다. 1초 안에 끝나는 페이지에는 스켈레톤도 스피너도 쓰지 않는다. 깜빡임이 오히려 방해가 되기 때문이다. 다운로드, 업로드, 파일 변환처럼 페이지를 불러오는 일이 아닌 과정에는 진행 표시줄을 쓴다.

뼈대가 실제 화면과 다르면 안 된다는 점도 중요하다. 상자 세 개를 그려 놓고 글 열 개가 들어오면 콘텐츠가 들어오는 순간 화면이 크게 밀린다. 실제 레이아웃과 비슷한 크기로 그려야 미리 보여 준 의미가 있다(내 판단).

### 접근성
스켈레톤의 회색 상자는 의미가 없는 장식이다. 스크린 리더가 빈 상자들을 하나씩 만나지 않도록 장식은 보조 기술에서 숨기고, 불러오는 중이라는 사실은 따로 알리는 방식이 자연스럽다(내 판단).

불러오는 영역에는 `aria-busy` 를 쓸 수 있다. busy의 사전적 의미는 바쁜, 일하는 중이다. MDN에 따르면 `aria-busy="true"` 는 요소가 고쳐지는 중이라 보조 기술이 변경이 끝날 때까지 기다렸다가 내용을 알리는 편이 좋다는 신호다. 다 불러오면 `false` 로 돌리거나 속성을 지운다. MDN의 `progress` 문서와 progressbar 역할 문서는 페이지 한 영역의 로딩을 진행 표시로 보여 줄 때 그 영역에 `aria-busy="true"` 를 두고 `aria-describedby` 로 진행 표시를 가리키라고 쓴다.

```html
<section aria-busy="true" aria-describedby="feed-loading">
  <!-- 회색 상자들. 장식이므로 보조 기술에서 숨긴다 -->
  <div class="skeleton" aria-hidden="true"></div>
  <div class="skeleton" aria-hidden="true"></div>
</section>
<progress id="feed-loading" class="visually-hidden" aria-label="글 목록 불러오는 중"></progress>
```

`visually-hidden` 은 화면에서는 감추고 보조 기술에는 남기는 CSS 클래스를 뜻한다. 화면에는 스켈레톤만 보이고, 진행 표시는 보조 기술에 불러오는 중이라는 이름을 전하는 용도로만 둔다(내 판단).

MDN은 `aria-busy` 가 보조 기술에 기다리라고 알리는 신호라고 설명할 뿐, 모든 스크린 리더가 이를 어떻게 처리하는지는 쓰지 않는다. 스크린 리더마다 실제로 어떻게 읽는지는 확인 필요다. 다 불러온 뒤 `aria-busy` 를 그대로 두면 그 영역의 변화가 계속 알려지지 않을 수 있으므로, 실패했을 때도 반드시 되돌린다(내 판단).

## 버튼 안의 로딩 상태 (Loading Button)
### 무엇인가
저장, 결제, 보내기 버튼을 누른 뒤 버튼 안에 작은 스피너를 넣거나 글자를 "저장 중"으로 바꾸고, 그동안 다시 누르지 못하게 하는 방식이다. 페이지 전체가 아니라 사용자가 방금 누른 바로 그 자리에서 결과를 기다린다는 점이 다르다.

disabled의 사전적 의미는 능력을 잃은, 쓸 수 없게 된이다. 화면에서는 보이기는 하지만 누를 수 없는 상태를 말한다. 버튼의 로딩 상태는 바쁜(busy) 상태이면서, 그동안 누를 수 없게 막은 상태를 겸하는 경우가 많다.

### 왜 필요할까
NN/g가 쓰듯 사용자는 반응이 없으면 다시 누른다. 버튼에서 곧바로 "접수했다"는 표시를 보여 주면 두 번 누르는 일이 줄어든다. NN/g는 "다시 누르면 주문이 한 번 더 들어갈 수 있습니다" 같은 경고 문구를 최악의 설계로 꼽는다. 사용자를 위협하지 말아야 하고, 어차피 사용자는 그런 글을 너무 늦게 읽기 때문이다. 경고하지 말고 첫 번째 클릭이 받아들여졌다는 것을 보여 주라는 뜻이다.

엘리베이터 호출 버튼에 불이 들어오는 것과 같다. 불이 켜졌으니 눌렀다는 것이 접수됐고, 여러 번 더 누를 필요가 없다는 것을 안다.

### 동작과 주의할 점
M3는 버튼 안에 원형 표시를 넣어 그 동작이 진행 중임을 보여 줄 수 있다고 쓰고, 5초 미만의 짧은 비확정형 작업에 쓰라고 한다. 목록의 버튼마다 표시를 넣는 것은 피하라고 한다.

GOV.UK 디자인 시스템은 두 번 누르기를 막는 속성을 제공하면서, 사용자가 실제로 정보를 두 번 보내는 일이 잦다는 조사 결과가 있을 때 쓰라고 한다. 이 방법은 자바스크립트가 켜진 사용자에게만 통하므로 서버에서도 중복 요청을 막아야 한다고 쓴다. 화면에서 막는 것은 사용자를 돕는 일이고, 중복 처리 방지는 서버의 몫이다.

같은 문서는 비활성 버튼이 명암 대비가 낮고 일부 사용자를 헷갈리게 하므로 되도록 피하고, 조사로 이해가 쉬워진다는 근거가 있을 때만 쓰라고 한다.

### 접근성
HTML의 `disabled` 속성을 붙이면 버튼이 키보드 탭 순서에서 빠진다. 버튼에 포커스가 있던 키보드 사용자나 스크린 리더 사용자는 그 순간 자기가 있던 자리를 잃는다. GitHub의 Primer 디자인 시스템은 로딩 중인 버튼을 DOM에서 빼거나 `disabled` 를 붙이지 말고, `aria-disabled="true"` 로 로딩 상태를 나타내라고 쓴다. 이렇게 하면 포커스는 그대로 남는다. 다만 MDN에 따르면 `aria-disabled="true"` 는 비활성이라는 의미만 알릴 뿐 동작을 막지 않고 포커스 가능 여부도 바꾸지 않는다. 그래서 로딩 중에 들어온 클릭과 키보드 실행은 스크립트에서 무시해야 하고, 비활성으로 보이게 하는 스타일도 따로 준다.

Primer는 로딩 상태를 알리는 방법으로, 페이지를 열 때부터 있는 보이지 않는 `aria-live="polite"` 영역에 "프로필 저장 중" 같은 글자를 로딩 중일 때만 넣으라고 한다. 버튼의 보이는 글자가 바뀌는 경우에는 그 변화도 보조 기술에 전해야 하며, 이름이 `aria-label` 에서 온다면 `aria-label` 도 함께 바꾸라고 쓴다. 오류가 나면 오류 배너의 제목처럼 관련된 곳으로 포커스를 옮기라고 한다.

```html
<button type="submit" aria-disabled="true">
  <span class="spinner" aria-hidden="true"></span>
  저장 중
</button>
<!-- 페이지를 열 때는 비어 있고, 로딩 중에만 아래처럼 글자가 들어간 모습 -->
<div aria-live="polite" class="visually-hidden">프로필 저장 중</div>
```

버튼 이름이 바뀌었을 때 스크린 리더가 그 변화를 늘 읽어 주는지는 이번에 확인하지 못했다(확인 필요). 그래서 이름 바꾸기에만 기대지 않고 라이브 영역을 함께 두는 편이 안전하다(내 판단).

## 낙관적 업데이트 (Optimistic Update)
### 이름의 뜻
optimistic의 사전적 의미는 낙관적인, 일이 잘될 것이라고 믿는이다. 화면 용어로는 서버의 응답을 기다리지 않고, 요청이 성공할 것이라 가정해 결과를 먼저 화면에 반영하는 방식을 말한다. 이런 화면을 낙관적 UI(Optimistic UI)라고도 부른다. 실패하면 원래대로 되돌리고 사용자에게 알린다. 로딩 표시를 잘 보여 주는 방법이 아니라 기다림을 거의 보여 주지 않는 방법이다. 필요하면 아래 예처럼 저장 중이라는 작은 표시만 조용히 붙인다.

### 쓰임과 동작
좋아요 버튼을 누르면 하트가 바로 채워지고, 서버 요청은 뒤에서 진행된다. React 19에서 정식으로 들어온 `useOptimistic` 의 공식 문서 설명이 이 흐름을 그대로 보여 준다. 작업이 실제로는 시간이 걸리지만 그 결과를 사용자에게 즉시 보여 주는 값이라서 낙관적 상태라고 부르고, 작업이 진행되는 동안에만 임시로 쓰인다. 작업이 실패하면 실제 값이 바뀌지 않았으므로 화면은 낙관적 업데이트 전 모습으로 돌아가고, 오류를 잡아 사용자에게 메시지를 보여 줄 수 있다고 쓴다. 같은 문서의 할 일 목록 예시는 확정되지 않은 항목 옆에 "(Adding...)"을 붙여, 아직 저장 중이라는 것을 조용히 표시한다.

React는 구현 예시일 뿐이고, 개념 자체는 특정 라이브러리와 상관없다. 바꾸기 전 상태를 기억해 두고, 화면을 먼저 바꾸고, 요청을 보내고, 성공하면 그대로 두고 실패하면 기억해 둔 상태로 돌린다.

친구와 약속을 잡을 때 확답을 받기 전에 달력에 연필로 먼저 적어 두는 것과 같다. 대부분 그대로 확정되고, 취소 연락이 오면 지우개로 지운다.

### 언제 쓰고 언제 피하나
좋아요, 즐겨찾기, 목록 항목 순서 바꾸기처럼 거의 실패하지 않고, 실패해도 되돌리기 쉬우며, 되돌려도 큰 피해가 없는 작업에 맞다(내 판단). 결제, 송금, 예약 확정처럼 실패 가능성이 있고 결과가 중요한 작업에는 맞지 않는다. 성공했다고 보여 준 뒤 실패로 뒤집히면 사용자는 이미 다음 행동을 했을 수 있다(내 판단).

### 접근성
화면이 바로 바뀌므로 성공했을 때는 따로 알릴 것이 적다. 문제는 실패해서 되돌릴 때다. 눈으로 보는 사람도 하트가 슬쩍 비워지는 것을 놓치기 쉽고, 스크린 리더 사용자는 더 모르기 쉽다. 되돌릴 때는 "좋아요를 반영하지 못했습니다" 같은 메시지를 [알림과 피드백](../알림과%20피드백(Notifications%20and%20Feedback)/README.md) 노트의 status나 alert 방식으로 알린다(내 판단).

## 준비된 것부터 보여 주기 (Progressive Loading)
### 무엇인가
progressive의 사전적 의미는 점진적인, 단계적으로 나아가는이다. 화면 전체가 준비될 때까지 한꺼번에 기다리지 않고, 먼저 준비된 부분부터 보여 주고 나머지는 준비되는 대로 채우는 방식이다. 서버가 HTML을 다 만들기 전에 앞부분부터 보내는 것을 스트리밍(Streaming)이라 한다. stream의 사전적 의미는 시냇물, 끊이지 않는 흐름이다.

### 쓰임과 동작
React의 `Suspense` 문서가 이 방식을 구체적으로 보여 준다. 화면을 여러 경계로 나눠 두면 각 경계는 자기 안의 내용이 준비될 때까지 대체 화면(fallback)을 보이고, 준비되는 대로 대체 화면을 실제 내용으로 바꾼다. 예시에서 가수의 소개 글은 앨범 목록을 기다리지 않고 먼저 나타난다. 스트리밍 서버 렌더링에서는 대체 화면이 들어간 뼈대를 먼저 보내고, 각 경계의 HTML이 도착하는 대로 바꿔 끼운다고 쓴다. 이때 대체 화면 자리에 스켈레톤이나 스피너가 들어가므로, 이 방식은 앞의 패턴들을 영역별로 나눠 쓰는 방법이기도 하다.

같은 문서는 경계를 컴포넌트마다 두지 말라고 한다. 경계는 사용자가 겪기를 바라는 로딩 순서보다 잘게 나누면 안 된다. 경계가 너무 잘면 화면 여기저기가 따로 깜빡이며 채워진다.

여럿이 시킨 음식이 나오는 대로 먼저 먹기 시작하는 것과 같다. 마지막 접시가 나올 때까지 모두가 수저를 들고 기다리지 않는다.

### 이미 보이는 내용은 숨기지 않기
새 데이터를 불러올 때 이미 보이던 내용을 지우고 로딩 표시로 바꾸면, 사용자는 읽던 것을 잃는다. React 문서는 이미 드러난 내용을 숨기지 않고 이전 화면을 계속 보여 주는 방법과, 새 검색 결과가 준비될 때까지 이전 결과를 보여 주면서 흐리게 처리해 오래된 내용임을 알리는 방법을 든다. 프레임워크와 상관없이, 새로 고치는 동안에는 기존 내용을 남겨 두고 바뀌는 중이라는 표시만 더하는 편이 대개 낫다(내 판단).

### 접근성
영역마다 따로 채워질 때 스크린 리더가 조각마다 끼어들어 읽으면 혼란스럽다. MDN은 라이브 영역의 여러 부분을 다 불러온 뒤에 알리고 싶으면 그동안 `aria-busy="true"` 를 두었다가 끝나면 `false` 로 돌리라고 쓴다. 채워지는 영역마다 `aria-busy` 를 두는 것은 스켈레톤 화면 절과 같다.

## 움직임과 접근성
### 2.2.2 일시 정지, 정지, 숨기기
WCAG 2.2.2(Pause, Stop, Hide, A 수준)는 저절로 시작해 5초 넘게 움직이거나 깜빡이며 다른 콘텐츠와 함께 보이는 것에 멈추거나 숨길 방법을 두라고 요구한다. 활동에 꼭 필요한(essential) 움직임은 예외다. 이해 문서는 5초가 사용자의 주의를 끌 만큼 길지만, 사용자가 그 산만함을 견디며 기다릴 수 있을 만큼 짧아서 골랐다고 설명한다.

로딩 표시는 이 기준과 어떻게 엮일까. 이해 문서의 주석은 모든 사용자가 아무것도 할 수 없는 미리 불러오기 단계의 애니메이션은, 진행을 보여 주지 않으면 사용자가 멈췄거나 고장 났다고 여길 수 있다면 꼭 필요한 것으로 볼 수 있다고 쓴다. 또 애니메이션만 있는 화면에서 동영상이 불러와지는 동안 기다리라고 알리는 예를 들며, 다른 콘텐츠와 함께 보이는 것이 아니므로 느린 연결에서 5초를 넘겨도 멈춤 방법이 필요 없다고 설명한다.

거꾸로 읽으면, 이미 볼 수 있는 콘텐츠 옆에서 5초 넘게 도는 애니메이션은 이 기준의 대상이 될 수 있다. 일부 영역만 불러오는 스피너나 반짝이는 스켈레톤이 계속 돈다면 확인해 볼 일이다(내 판단, 이해 문서가 로딩 스피너를 직접 다루지는 않는다).

### 2.3.3 상호작용으로 생기는 애니메이션
WCAG 2.3.3(Animation from Interactions, AAA 수준)은 상호작용으로 생기는 움직임 애니메이션을 끌 수 있게 하라고 요구한다. 이해 문서는 사용자의 동작 없이 저절로 시작되는 애니메이션은 2.2.2가 다룬다고 구분한다. 버튼을 누른 뒤 나타나는 스피너가 상호작용으로 생긴 애니메이션인지는 이해 문서가 다루지 않는다(확인 필요). 이 기준의 충족 기법으로 CSS의 `prefers-reduced-motion` 미디어 쿼리를 쓰는 방법(C39)이 있다.

### 동작 줄이기 설정 (prefers-reduced-motion)
MDN에 따르면 `prefers-reduced-motion` 은 사용자가 기기에서 꼭 필요하지 않은 움직임을 줄여 달라고 설정했는지를 알려 준다. 값은 설정이 없음을 뜻하는 `no-preference` 와 줄이기를 켰음을 뜻하는 `reduce` 두 가지다. Windows 11의 애니메이션 효과, macOS와 iOS의 동작 줄이기, Android의 애니메이션 삭제 같은 운영체제 설정이 이 값을 바꾼다. MDN은 움직임 기반 애니메이션이 전정 기관 장애(vestibular motion disorders)가 있는 사람에게 불편을 일으킬 수 있다고 쓴다.

로딩 표시에서 까다로운 점은 움직임을 아예 없애면 안 된다는 것이다. Apple HIG가 쓰듯 멈춘 진행 표시는 작업이 멈춘 것처럼 보인다. 그래서 동작 줄이기가 켜져 있으면 회전을 느리게 하거나, 크기와 위치가 바뀌지 않는 투명도 변화로 바꾸거나, 글자 표시로 대신하는 쪽이 자연스럽다(내 판단). MDN의 예시도 크기가 바뀌는 맥박 애니메이션을 투명도만 바뀌는 애니메이션으로 바꾼다. 2.3.3 이해 문서도 색이나 투명도 변화는 크기, 모양, 위치가 바뀌어 보이지 않는 한 움직임 애니메이션으로 보지 않는다.

```css
.spinner {
  animation: spin 1s linear infinite;
}

/* 동작 줄이기가 켜져 있으면 회전 대신 천천히 흐려졌다 진해지게 한다 */
@media (prefers-reduced-motion: reduce) {
  .spinner {
    animation: fade 2s ease-in-out infinite;
  }
}
```

`spin` 과 `fade` 의 `@keyframes` 정의는 생략했다. 이 코드 조각 자체는 실행하지 않았고, 같은 방식(동작 줄이기에서 회전을 투명도 변화로 바꾸기)은 아래 예제 절의 example.html에서 실행해 확인했다.

### 고르는 순서
아래는 이 노트의 지침을 묶어 본 내 판단이다.

1. 1초 안에 끝나는가. 그러면 로딩 표시는 띄우지 않고 버튼이 눌린 반응만 준다. 응답 시간이 들쭉날쭉하면 지연과 최소 표시 시간을 둔다
2. 거의 실패하지 않고 되돌리기 쉬운 작업인가. 그러면 낙관적 업데이트로 기다림 자체를 없앤다
3. 사용자가 버튼을 눌러 시작한 짧은 작업인가. 그러면 버튼 안의 로딩 상태를 쓴다
4. 전체 양을 셀 수 있거나 10초 넘게 걸리는가. 그러면 확정형 진행 표시줄과 취소 방법을 둔다
5. 페이지나 목록의 모양을 미리 알 수 있는가. 그러면 스켈레톤 화면을 쓴다. 영역마다 준비 시간이 다르면 준비된 것부터 보여 준다
6. 위에 해당하지 않으면 무엇을 기다리는지 글자와 함께 스피너를 쓴다

어느 쪽을 고르든 표시는 일이 끝나면 사라지는 임시 장치다. Apple HIG도 진행 표시를 일이 끝나면 사라지는 일시적인 것으로 설명한다. 그래서 로딩 표시를 다듬기 전에 실제 응답 속도를 줄일 수 있는지 먼저 본다(내 판단, NN/g가 스켈레톤이 최적화를 대신하지 못한다고 쓴 것과 같은 방향).

## 예제
### 여는 방법
[example.html](./example.html)은 HTML, CSS, 약간의 자바스크립트만 든 파일 하나다. 설치나 빌드 없이 탐색기에서 더블클릭해 브라우저로 열면 된다. 요청은 실제로 보내지 않고 `setTimeout` 으로 기다리는 시간만 흉내 낸다.

화면 위쪽에서 응답 속도를 0.3초와 3초 가운데 고를 수 있다. 스피너, 스켈레톤, 버튼, 좋아요 예제가 이 값을 쓴다. 이 네 예제와 준비된 것부터 보여 주기 예제의 표시는 spin-delay의 기본값을 따라 0.5초가 지나도 끝나지 않을 때만 띄우고, 한 번 띄우면 0.2초 이상 남겨 둔다. 그래서 0.3초를 고르면 스피너와 스켈레톤이 아예 나타나지 않고, 3초를 고르면 0.5초 뒤에 나타난다. 너무 짧은 로딩이 깜빡이지 않게 하는 절의 내용을 두 속도를 번갈아 눌러 비교해 볼 수 있다.

### 어느 부분이 어떤 내용을 보여 주나
스피너 예제는 댓글을 불러오는 동안 목록에 `aria-busy="true"` 를 두고, 0.5초가 지나 스피너가 나타날 때 처음부터 비어 있던 `role="status"` 영역에 "댓글 불러오는 중"을 넣는다. 스피너 그림 자체는 `aria-hidden` 으로 숨긴다. 끝나면 `aria-busy` 를 `false` 로 돌리고 "댓글 3개를 불러왔습니다"를 남겨, 표시가 사라진 것을 볼 수 없는 사용자에게도 끝났다는 사실을 전한다. 다시 불러올 때는 이미 보이던 댓글을 지우지 않는다.

진행 표시줄 예제는 HTML의 `progress` 요소를 쓴다. 파일 개수를 세는 1초 동안은 `value` 속성이 없는 비확정형이고, 개수를 알게 되면 `max` 와 `value` 를 주어 확정형으로 바꾼다. 다시 시작할 때 비확정형으로 돌리려고 `value` 속성을 지운다. 진행률 메시지는 25%, 50%, 75%에서만 넣어 값이 바뀔 때마다 읽히지 않게 했다. 시작과 끝에도 한 번씩 알린다. 취소 버튼도 두었다. 노트에서는 10초 넘는 작업에 확정형을 쓴다고 했지만, 예제는 보기 편하도록 전체를 5초 정도로 줄였다.

스켈레톤 예제는 실제로 들어올 글 세 개와 같은 개수, 같은 높이로 회색 상자를 그린다. 상자는 `aria-hidden="true"` 로 숨기고, 목록 영역에는 `aria-busy="true"` 와 함께 `aria-describedby` 로 화면에서 감춘 비확정형 `progress` 를 가리킨다. 다시 불러올 때는 스켈레톤으로 바꾸지 않고 기존 글을 흐리게 남겨 둔다. 흐리게 하는 것도 로딩 표시라서 같은 지연을 둔다.

버튼 예제는 누르는 즉시 글자를 "저장 중"으로 바꾸고 `disabled` 대신 `aria-disabled="true"` 를 붙인다. `aria-disabled` 는 동작을 막지 않으므로 제출 처리 첫머리에서 이 값을 보고 로딩 중의 클릭과 Enter를 무시한다. 버튼 안의 작은 스피너는 다른 예제와 같이 0.5초가 지난 뒤에만 나타난다. 로딩 상태는 페이지를 열 때부터 있는 보이지 않는 `aria-live="polite"` 영역으로도 알린다. 화면의 "실제로 저장된 횟수"로 여러 번 눌러도 한 번만 저장되는지 볼 수 있다. 화면에서 막는 것과 별개로 서버에서도 중복 요청을 막아야 한다는 점은 예제가 보여 주지 못한다.

낙관적 업데이트 예제는 좋아요를 누르면 `aria-pressed` 와 숫자를 바로 바꾸고, 저장이 0.5초를 넘기면 옆에 "저장 중"을 작게 붙인다. "다음 저장을 실패하게 하기"를 켜고 누르면 바꾸기 전 상태로 되돌리고 `role="alert"` 영역에 반영하지 못했다는 메시지를 띄운다. 실패는 한 번만 일어나고 체크가 풀린다. 예제를 단순하게 하려고 저장이 끝나기 전에 다시 누르는 것은 무시한다.

준비된 것부터 보여 주기 예제는 세 영역을 0.4초, 1.2초, 2.4초 뒤에 따로 채운다. 영역마다 `aria-busy` 를 두고 준비된 영역부터 `false` 로 돌린다. 처음 불러올 때는 0.5초가 지나도 비어 있는 영역에만 스켈레톤을 그리므로, 0.4초 만에 채워지는 첫 영역에는 스켈레톤이 나타나지 않는다. 새로 고칠 때는 이전 내용을 지우지 않고 같은 지연 뒤에 흐리게 처리한다. 이 예제의 시간은 응답 속도 선택과 상관없이 고정이다.

동작 줄이기 설정이 켜져 있으면 스피너, 비확정형 진행 표시줄, 스켈레톤의 움직임을 모두 2초 주기의 투명도 변화로 바꾼다. 움직임을 없애지 않고 크기와 위치가 바뀌지 않는 변화로 바꾼다는 앞 절의 방법을 따랐다.

### 확인한 것과 못 한 것
2026-11-02에 이 PC에 설치된 Chrome(Chromium 계열)을 Playwright로 띄워 파일을 직접 열어 확인했다. 콘솔 오류는 없었다. 0.3초 응답에서는 스피너, 스켈레톤, 버튼 안 스피너가 한 번도 나타나지 않았고, 3초 응답에서는 0.5초 뒤에 나타났다. 화면에 없는 0.6초 응답은 라디오 버튼 값을 스크립트로 600으로 바꿔 시험했는데, 스피너가 0.2초 남짓 보인 뒤 사라져 최소 표시 시간이 지켜졌다. 각 영역의 `aria-busy` 가 `true` 였다가 `false` 로 돌아오는 것, 진행 표시줄이 처음에 값이 없는 비확정형이었다가 확정형으로 바뀌는 것, 상태 메시지가 "파일 변환 준비 중", "파일 20개 변환 시작", 25%, 50%, 75%, 완료 순으로 바뀌는 것을 확인했다. 버튼은 저장 중에 클릭과 Enter를 다섯 번 넣어도 한 번만 저장됐고 포커스가 버튼에 남았다. 좋아요는 실패를 켜면 원래 값으로 돌아오고 경고 메시지가 나왔다. 준비된 것부터 보여 주기는 첫 영역이 준비됐을 때 나머지 두 영역이 아직 `aria-busy="true"` 였고, 첫 영역에는 스켈레톤이 그려지지 않았다. 스켈레톤의 높이와 실제 글 목록의 높이는 1픽셀 안으로 같았다. 화면 너비 375픽셀에서 가로 스크롤이 생기지 않았고, 동작 줄이기를 켠 상태에서는 세 표시의 애니메이션이 투명도 변화로 바뀐 것을 계산된 스타일로 확인했다.

실제 스크린 리더(NVDA, VoiceOver 등)로 상태 메시지와 `aria-busy` 가 어떻게 읽히는지는 확인하지 못했다. Firefox와 Safari에서 `progress` 막대의 모양, 특히 비확정형 막대의 애니메이션이 같게 보이는지도 확인하지 못했다.
