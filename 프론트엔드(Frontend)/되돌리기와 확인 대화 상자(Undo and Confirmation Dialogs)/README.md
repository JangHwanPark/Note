## 되돌리기와 확인 대화 상자란 ?
- 되돌리기(Undo)는 사용자가 방금 한 행동을 없던 일로 돌리는 기능이고, 확인 대화 상자(Confirmation Dialog)는 결과가 큰 행동을 실행하기 전에 정말 할지 한 번 더 묻는 창이다
- 둘 다 지우기, 보내기, 버리기처럼 실수하면 손해가 나는 행동에서 사용자를 지키는 장치다. 되돌리기는 행동한 뒤에, 확인 대화 상자는 행동하기 전에 지킨다
- 이 노트는 둘 가운데 무엇을 고를지, 되돌리기를 만드는 방식, 확인 대화 상자에 담을 것, `<dialog>` 로 만드는 법, 저장하지 않은 변경 사항을 지키는 법, 접근성을 다룬다. 모달 자체의 포커스 규칙과 스낵바라는 그릇은 [알림과 피드백](../알림과%20피드백(Notifications%20and%20Feedback)/README.md) 노트에 있다

undo는 do(하다)에 거꾸로 돌린다는 뜻의 접두사 un-이 붙은 말로, 이미 한 일을 풀어 원래대로 돌린다는 뜻이다. 매듭을 푸는 것도 undo다. confirm은 라틴어 cōnfirmāre에서 왔고, 함께(con-)와 단단하게 하다(firmāre)가 합쳐진 말이다(Wiktionary). 확인 대화 상자는 사용자가 내린 결정을 한 번 더 다져 단단하게 만드는 창이라는 뜻이 된다.

종이에 연필로 쓰는 것과 볼펜으로 쓰는 것의 차이와 같다. 연필로 쓰면 틀려도 지우개로 지우면 되니 마음 편히 쓴다. 볼펜으로 계약서에 서명할 때는 쓰기 전에 한 번 더 읽어 본다. 되돌리기는 화면을 연필로 만드는 일이고, 확인 대화 상자는 볼펜으로밖에 쓸 수 없는 곳에서 펜을 대기 전에 멈추게 하는 일이다.

<br/>

## 왜 확인 대화 상자만으로는 부족할까
### 묻는 횟수가 늘면 읽지 않는다
가장 쉬운 방법은 지우기 버튼마다 "정말 삭제하시겠습니까?"를 띄우는 것이다. Raskin(2007)은 사람이 같은 경고에서 "확인"을 여러 번 누르면 습관이 생겨, 정작 취소하려던 순간에도 생각 없이 확인을 누른다고 쓴다. 그래서 경고를 더 크게 만들거나 닫기 어렵게 만들어도 이 문제는 풀리지 않는다고 본다. 그의 원칙은 "되돌리기를 뜻할 때 경고를 쓰지 말라(Never use a warning when you mean undo)"다.

Nielsen(2018)도 같은 방향이다. 확인 대화 상자는 결과가 심각한 행동 앞에서는 오류를 막아 주지만, 사람에게 너무 자주 경고하면 주의를 기울이지 않게 된다고 쓰고, 일상적인 행동에는 확인 대화 상자를 쓰지 말라고 한다. 그리고 확인 대화 상자를 잘 만들어도 실수는 생기므로 되돌리기를 만드는 데 최대한 공을 들이라고 덧붙인다.

### 실수는 누른 뒤에야 보인다
확인 대화 상자는 사용자가 자기 행동의 결과를 미리 상상해야 한다. 되돌리기는 결과를 눈으로 본 뒤에 판단하게 한다. 목록에서 다른 메일이 사라진 것을 보고 나서야 잘못 눌렀다는 것을 아는 경우가 많다(내 판단). Nielsen Norman Group(이하 NN/g)의 사용성 원칙 3번 사용자 통제와 자유(User control and freedom)도 사용자는 자주 실수하므로, 긴 대화를 거치지 않고 원치 않는 상태에서 빠져나올 수 있는 분명한 "비상구"가 필요하다고 하면서 되돌리기와 다시 하기를 지원하라고 한다(Rosala 2020).

## 어떻게 고를까
### 한눈에 비교
아래는 위 자료를 바탕으로 한 정리다. 어느 칸에 넣을지는 결국 그 서비스에서 행동이 얼마나 자주 일어나고 결과가 얼마나 무거운지에 달려 있다.

| 상황 | 예 | 고를 것 |
|---|---|---|
| 흔하고 되돌릴 수 있는 행동 | 메일을 휴지통으로, 목록에서 항목 빼기, 보관 | 묻지 않고 실행한 뒤 실행 취소를 준다 |
| 드물고 되돌릴 수 없는 행동 | 휴지통 비우기, 영구 삭제, 계정 탈퇴 | 확인 대화 상자로 결과를 구체적으로 알리고 묻는다 |
| 되돌릴 수 없고 결과가 아주 큰 행동 | 저장소 삭제, 조직 전체 데이터 삭제 | 확인 대화 상자에 대상 이름을 직접 입력하게 한다 |
| 저장하지 않은 내용을 잃는 행동 | 편집 중 취소, 편집 중 페이지 떠나기 | 고친 내용이 있을 때만 묻는다 |

Apple Human Interface Guidelines(이하 HIG)의 Alerts 문서는 흔하고 되돌릴 수 있는 행동에는 그 행동이 파괴적이어도 경고를 띄우지 말라고 쓴다. 첫 줄과 같은 판단이다.

### 되돌릴 수 있게 만들 수 있는지 먼저 본다
"이 행동은 되돌릴 수 없으니 확인을 받자"보다 "이 행동을 되돌릴 수 있게 만들 수 없을까"를 먼저 묻는 편이 낫다(내 판단). 지우기를 휴지통으로 옮기기로 바꾸면 되돌릴 수 없는 행동이 되돌릴 수 있는 행동이 되고, 확인 대화 상자는 휴지통을 비울 때 한 번만 남는다. 아래 되돌리기 절은 이렇게 바꾸는 방법을 본다.

<br/>

## 되돌리기 (Undo)
### 두 가지 만드는 방식
화면에서는 같은 "실행 취소" 버튼이라도, 뒤에서 일이 일어나는 순서는 둘로 나뉜다.

첫째는 바로 실행하고 되돌릴 때 복원하는 방식이다. 지우기를 누르면 서버에 바로 요청을 보내고, 실행 취소를 누르면 복원 요청을 다시 보낸다. 서버가 지운 것을 일정 기간 남겨 두어야(휴지통, 지운 표시만 해 두는 소프트 삭제(Soft Delete)) 복원할 수 있다. 다른 기기나 다른 사람 화면에도 바로 반영되고, 페이지를 닫아도 요청이 사라지지 않는다.

둘째는 잠시 미뤘다가 실행하는 방식이다. 화면에서는 바로 사라진 것처럼 보이지만 요청은 몇 초 기다렸다가 보내고, 그 안에 실행 취소를 누르면 요청을 아예 보내지 않는다. 서버에 복원 기능이 없어도 되돌리기를 만들 수 있다. Gmail의 보내기 취소(Undo Send)가 이 모양으로 보인다. Gmail 도움말은 보낸 직후 짧은 시간 안에 취소할 수 있고, 그 시간(Send cancellation period)을 5, 10, 20, 30초 가운데 고를 수 있다고 쓴다. 이미 받는 사람에게 간 메일은 되돌릴 수 없으니 보내기를 미루는 수밖에 없다는 점에서, 미루는 방식이 맞는 대표적인 예다(Gmail이 내부에서 실제로 미루는지는 공식 문서로 확인하지 못했다, 확인 필요).

미루는 방식에는 대가가 있다(내 판단). 기다리는 동안 페이지를 닫거나 연결이 끊기면 사용자는 지웠다고 생각했는데 실제로는 지워지지 않는다. 기다리는 동안 다른 기기에서는 아직 보인다. 정해진 시간이 지나면 되돌릴 수 없으므로 실행 취소에 시간 제한이 생긴다. 이 시간 제한이 WCAG 2.2.1 시간 조절(Timing Adjustable)의 대상인지는 이번에 확인하지 못했다(확인 필요). 예제는 조작판에서 두 방식을 바꿔 가며, 서버로 보낸 요청 기록이 어떻게 달라지는지 볼 수 있게 했다.

### 휴지통 (Trash)
되돌리기의 시간 제한을 늘리는 가장 흔한 방법이 휴지통이다. 스낵바의 실행 취소를 놓쳐도 휴지통에서 복원할 수 있다. Raskin(2007)도 Gmail이 지운 메일을 바로 되돌릴 수 있게 하고, 휴지통에 남겨 나중에 복원할 수 있게 한다는 점을 좋은 예로 든다. GitHub 문서는 저장소를 지울 때 저장소 이름을 입력하게 하면서도, 일부 지운 저장소는 90일 안에 복원할 수 있다고 쓴다. 확인을 받은 행동에도 복원할 길을 함께 남겨 둔 셈이다.

### 여러 단계와 단축키
NN/g의 Rosala(2020)는 사용자가 여러 행동을 잇달아 할 가능성이 크면 마지막 하나만이 아니라 여러 단계의 되돌리기와 다시 하기를 지원하라고 한다. 데스크톱에서는 흔히 쓰는 단축키도 지원하되, 사용자가 단축키로 되돌리기를 찾아낼 거라고 가정하지 말고 메뉴나 도구 모음처럼 사용자가 기대하는 곳에 보이는 되돌리기를 두라고 한다. 같은 글은 빨리 사라지는 맥락 속 되돌리기 안내는 놓치기 쉽다고도 쓴다.

예제는 휴지통으로 옮긴 순서를 쌓아 두고, Ctrl+Z(Mac은 Cmd+Z)를 누를 때마다 가장 최근 것부터 하나씩 되돌린다. 되돌린 파일의 버튼으로 포커스도 옮긴다. 다만 메모나 조작판처럼 입력 요소(`textarea`, `input`) 안에서 누른 Ctrl+Z와 대화 상자가 열려 있을 때의 Ctrl+Z는 가로채지 않는다. 글자를 고치던 사람이 Ctrl+Z를 눌렀는데 파일이 되살아나면 안 되기 때문이다. 휴지통에서 복원했거나 영구 삭제한 파일은 쌓아 둔 기록에서도 지운다.

### 실행 취소를 어디에 보여 줄까
행동 직후의 실행 취소는 보통 스낵바에 담는다. 스낵바의 동작과 접근성은 [알림과 피드백](../알림과%20피드백(Notifications%20and%20Feedback)/README.md) 노트의 스낵바 절에 있다. 그 노트에서 본 것처럼 Material Design 3는 행동 버튼이 있는 스낵바는 사용자가 누르거나 닫을 때까지 남겨야 한다고 쓴다. 예제의 바로 실행하는 방식은 이를 따라 스낵바를 닫거나 다음 행동이 덮을 때까지 남긴다. 미루는 방식은 이 지침에서 벗어난다. 8초가 지나면 요청을 보내고 스낵바를 닫는다. 스낵바 문구에 "8초 안에 실행 취소할 수 있습니다"라고 시간을 밝혔고, 파일은 휴지통으로 가므로 스낵바를 놓쳐도 휴지통에서 복원할 수 있다. 8초는 이 예제에서 임의로 정한 값이다. 요청을 보내면서 목록을 다시 그릴 때, 포커스가 목록 안 버튼에 있었다면 같은 파일의 버튼으로 돌려주고 스낵바에 있었다면 파일 목록 제목으로 옮긴다.

실행 취소를 누른 뒤의 결과도 알려 준다. 예제는 되돌린 파일을 원래 자리에 다시 넣고, 키보드 포커스를 그 파일의 버튼으로 옮기며, 화면에 보이지 않는 `role="status"` 문단으로 "되돌렸습니다"를 알린다.

## 확인 대화 상자 (Confirmation Dialog)
### 언제 쓰나
Nielsen(2018)은 결과가 심각한 행동을 실행하기 전에 확인 대화 상자를 쓰고, 일상적인 행동에는 쓰지 말라고 한다. 앞의 비교 표에서 되돌릴 수 없는 줄이 여기에 해당한다. 확인 대화 상자는 모달이므로, 모달을 쓸지 고르는 일반 기준은 [알림과 피드백](../알림과%20피드백(Notifications%20and%20Feedback)/README.md) 노트의 모달 절을 따른다.

### 무엇이 일어나는지 구체적으로 쓴다
Nielsen(2018)은 행동과 그 결과를 구체적으로 알리라고 하고, "정말 하시겠습니까?" 같은 막연한 질문은 사용자가 판단할 거리를 주지 않는다고 쓴다. 제목에는 무엇을 하려는지 대상까지 넣고, 본문에는 그러면 무엇이 사라지는지, 되돌릴 수 있는지를 쓴다. 여러 개를 한꺼번에 지운다면 몇 개인지, 가능하면 무엇인지도 보여 준다(내 판단).

피할 예와 고친 예를 나란히 보면 아래와 같다.

```text
피할 예   제목: 확인        본문: 정말 삭제하시겠습니까?      버튼: 아니요 / 예
고친 예   제목: 휴지통을 비울까요?
          본문: 아래 파일 2개가 영구 삭제되고 되돌릴 수 없습니다. (파일 이름 목록)
          버튼: 취소 / 파일 2개 영구 삭제
```

### 버튼에는 동사를 쓴다
Nielsen(2018)은 응답 버튼이 각각 무엇이 일어나는지 요약하게 하라고 하면서, "Delete file"과 "Keep file" 같은 예를 든다. Apple HIG도 버튼 제목에는 경고 문구와 바로 이어지는 동사나 동사구를 쓰라고 하고, "예"와 "아니요"는 피하며, "OK"는 순수하게 정보만 전하는 경고에서만 쓰라고 한다. "예/아니요"는 질문을 다시 읽어야 뜻이 정해지지만, "영구 삭제"는 버튼만 봐도 무엇이 일어나는지 안다.

Apple HIG는 파괴적인 행동이 있으면 사용자가 안전하게 피할 수 있는 취소 버튼을 함께 두고, 그 버튼 제목은 항상 "Cancel"(취소)로 하라고 쓴다. 다만 예제의 메모 편집 취소처럼 "취소"라는 말이 이미 행동 이름에 들어간 경우에는 "취소"가 무엇을 취소하는지 헷갈릴 수 있어서, 예제는 그 대화 상자만 "계속 편집"과 "변경 사항 버리기"로 두었다(내 판단).

### 처음 포커스는 덜 위험한 쪽에
WAI-ARIA 작성 지침(APG, ARIA Authoring Practices Guide)은 되돌릴 수 없는 행동을 묻는 대화 상자에서는 처음 포커스를 덜 파괴적인 버튼에 두는 예를 든다([알림과 피드백](../알림과%20피드백(Notifications%20and%20Feedback)/README.md) 노트의 모달 접근성 절). Apple HIG는 취소 버튼을 기본 버튼으로 만들지 말라고 쓰면서도, 사람들이 Return 키로 넘기지 않고 경고를 읽기를 원한다면 어떤 버튼도 기본 버튼으로 두지 말라고 한다. 처음 포커스와 기본 버튼은 다른 개념이지만, 두 자료 모두 습관처럼 누르는 키 하나로 파괴적인 행동이 실행되지 않게 하려는 방향이다. 예제는 취소 쪽 버튼에 `autofocus` 를 두었다.

### 이름을 입력하게 하는 확인
GitHub는 저장소를 지울 때 지우려는 저장소 이름을 입력하게 한다. 습관처럼 누르는 것으로는 넘어갈 수 없게 만든 장치다. Raskin(2007)은 입력하게 하는 확인도 사용자의 주의를 흩뜨리고 느리며, 결국 작업을 잃게 하는 것은 같다고 비판한다. 이 방식은 드물고 결과가 아주 큰 행동에만 남겨 두는 편이 맞다(내 판단). 예제에는 넣지 않았다.

## `<dialog>` 로 만들기
### 모달로 열기
HTML의 `<dialog>` 요소는 `showModal()` 로 열면 모달, `show()` 로 열면 모달이 아닌 대화 상자가 된다. 모달로 열면 뒤의 내용은 조작할 수 없게 되고, `::backdrop` 가상 요소로 뒤를 어둡게 칠할 수 있다. MDN은 `<dialog>` 가 2022년 3월부터 주요 브라우저에서 쓸 수 있다고 쓴다.

MDN은 모달로 연 대화 상자는 기본적으로 Esc 키로 닫을 수 있고, Esc로 닫을 때는 먼저 `cancel` 이벤트가 일어나 코드가 닫기를 막을 기회가 있다고 쓴다. `closedby` 속성으로 닫는 방법(Esc 같은 플랫폼 동작, 바깥 누르기)을 정할 수 있고, 값을 주지 않으면 `showModal()` 로 연 대화 상자는 `closerequest` 처럼 동작한다. MDN 페이지에는 `closedby` 의 브라우저 지원 정보가 없었다. Chrome 156.0.8078.48에서는 `HTMLDialogElement.prototype` 에 `closedBy` 가 있었고(2026-11-03), 다른 브라우저는 확인하지 못했다(확인 필요).

### 어느 버튼으로 닫혔는지 받기
MDN은 `<dialog>` 안의 `<form method="dialog">` 를 제출하면 대화 상자가 닫히고, 누른 버튼의 `value` 가 `returnValue` 에 들어간다고 쓴다. 예제는 이것으로 확인 대화 상자를 `Promise` 로 감쌌다.

```js
function confirmDialog({ title, okLabel, cancelLabel }) {
  const dlg = document.getElementById('confirm');
  // 제목, 본문, 버튼 글자 채우기 생략
  dlg.returnValue = '';
  dlg.showModal();
  return new Promise((resolve) => {
    dlg.addEventListener('close', () => resolve(dlg.returnValue === 'confirm'), { once: true });
  });
}

// 쓰는 쪽 (async 함수 안에서)
if (await confirmDialog({ title: '휴지통을 비울까요?', okLabel: '파일 2개 영구 삭제', cancelLabel: '취소' })) {
  // 영구 삭제
}
```

`returnValue` 를 열 때마다 비우는 데는 이유가 있다. 2026-11-03에 Chrome 156.0.8078.48에서 비우는 줄이 없는 별도 페이지로 확인해 보니, 확인 버튼으로 한 번 닫은 대화 상자를 `showModal()` 로 다시 열었을 때 `returnValue` 는 여전히 `"confirm"` 이었다. 같은 실험에서 Esc로 닫으면 `cancel` 이벤트가 일어나고 `returnValue` 는 빈 문자열이 되었지만, 다른 브라우저도 그런지는 확인하지 못했다(확인 필요). 열 때 비워 두면 지난번 확인이 이번 결과로 새어 들어올 일이 없다.

### 포커스
예제는 `role="alertdialog"` 를 `<dialog>` 에 직접 주고, 제목과 본문을 `aria-labelledby`, `aria-describedby` 로 이었다. `showModal()` 로 열면 브라우저가 모달로 알리므로 `aria-modal` 은 따로 두지 않았다(확인 필요). 같은 날 Chrome에서 확인한 동작은 이렇다. 열면 `autofocus` 를 둔 취소 버튼에 포커스가 갔다. Esc나 취소로 닫으면 포커스는 대화 상자를 연 버튼으로 돌아갔다. 마지막 버튼에서 Tab을 누르면 포커스가 대화 상자 앞쪽 버튼으로 돌아오지 않고 `document.activeElement` 가 `body` 가 되었다. 포커스가 문서 밖(주소창 같은 브라우저 화면)으로 나간 것으로 보인다. 뒤의 내용은 비활성이어서 포커스를 받지 않았다. 알림과 피드백 노트에서 본 APG 패턴은 Tab이 대화 상자 안에서 돌게 하라고 하는데, Chrome의 기본 동작은 그와 달랐다. 이것을 문제로 볼지는 이번에 판단하지 못했다(확인 필요). 알림과 피드백 노트의 예제도 같은 `showModal()` 로 열었으므로 같은 동작일 것으로 보인다(확인 필요).

확인한 뒤 대상이 사라지면 대화 상자를 연 버튼도 함께 사라진다. 예제는 영구 삭제한 뒤 포커스를 이웃 파일의 버튼으로, 이웃이 없으면 휴지통 제목으로 옮긴다.

## 저장하지 않은 변경 사항 지키기
### 화면 안에서 버리려 할 때
고치던 내용을 버리는 "편집 취소"는 고친 내용이 있을 때만 묻는다. 고친 것이 없는데 묻는 것은 Nielsen이 말한 일상적인 행동에 확인을 붙이는 경우가 된다. 예제의 메모는 저장한 값과 지금 값이 다를 때만 "저장하지 않은 변경 사항을 버릴까요?"를 띄우고, 같으면 아무것도 묻지 않는다.

### 페이지를 떠나려 할 때
탭을 닫거나 다른 주소로 가려 할 때는 `beforeunload` 이벤트로 브라우저의 확인 창을 띄울 수 있다. MDN은 이벤트 객체의 `preventDefault()` 를 부르고, 예전 브라우저(MDN 예제 주석은 Chrome과 Edge 119 미만을 든다)를 위해 `returnValue` 도 함께 설정하라고 한다.

```js
function onBeforeUnload(e) {
  e.preventDefault();
  e.returnValue = true;
}
// 고친 내용이 있을 때만 걸고, 저장하면 뗀다
window.addEventListener('beforeunload', onBeforeUnload);
window.removeEventListener('beforeunload', onBeforeUnload);
```

MDN이 밝힌 제약은 둘이고 권고가 하나다. 요즘 브라우저는 확인 창에 브라우저가 정한 일반 문구만 보여 주고 페이지가 문구를 바꿀 수 없다. 사용자가 페이지와 한 번이라도 상호작용해야(sticky activation) 창이 뜬다. 그리고 권고로, 저장하지 않은 변경 사항이 있을 때만 이 이벤트를 듣고 필요 없어지면 리스너를 떼라고 한다. 예제도 메모를 고치면 리스너를 걸고, 저장하거나 변경을 버리면 뗀다.

이 창은 페이지를 떠나는 경우만 막는다. 페이지를 새로 불러오지 않고 화면만 바꾸는 앱에서 앱 안의 링크로 다른 화면에 갈 때는 `beforeunload` 가 일어나지 않으므로, 그 경우는 앱의 라우터에서 따로 막아야 한다(내 판단, 확인 필요).

## 접근성
### 관련된 WCAG 기준
WCAG 2.2의 3.3.4 오류 예방(법률, 금융, 데이터)(Error Prevention (Legal, Financial, Data), AA)은 [오류 상태](../오류%20상태(Error%20State)/README.md) 노트의 WCAG 기준 절에 정리했다. 결과가 무거운 제출에서 되돌릴 수 있게 하거나(Reversible), 입력 오류를 검사해 고칠 기회를 주거나(Checked), 마지막으로 검토하고 확인할 수 있게 하는(Confirmed) 것 가운데 하나를 요구한다. 3.3.6 오류 예방(전체)(Error Prevention (All), AAA)은 같은 세 가지 가운데 하나를 사용자가 정보를 제출하는 모든 페이지로 넓힌다.

두 기준 모두 되돌리기와 확인을 같은 무게의 선택지로 나란히 둔다. 어느 쪽을 골라도 기준은 채울 수 있으니, 앞에서 본 사용성 기준으로 고르면 된다. 오류 상태 노트에서 확인할 기회를 먼저 주라고 한 것은 되돌릴 수 없는 작업 이야기이고, 되돌릴 수 있게 바꿀 수 있다면 그쪽이 먼저다(내 판단).

### 예제에 넣은 것
줄마다 같은 글자의 버튼(휴지통으로, 복원, 영구 삭제)이 있으므로 버튼 이름에 파일 이름을 넣어 "계약서.pdf 영구 삭제"처럼 읽히게 했다. 행동의 결과는 화면에 보이지 않는 `role="status"` 문단으로 알린다. 지우거나 옮겨서 포커스가 있던 버튼이 사라지면 이웃 줄의 버튼으로, 목록이 비면 목록 제목으로 포커스를 옮긴다. 파괴적인 버튼은 빨간색과 함께 "영구 삭제", "휴지통 비우기"처럼 무엇을 하는지 글자로 써서 색만으로 구분하지 않았다.

## 예제
[example.html](./example.html)은 가짜 파일 보관함에서 이 노트의 내용을 눌러 보는 예제다. HTML, CSS, 약간의 자바스크립트만 한 파일에 담았으므로 파일을 더블클릭하거나 브라우저 창에 끌어다 놓으면 바로 열린다. 서버로 실제 요청을 보내지 않고, 보냈어야 할 요청을 조작판의 "서버로 보낸 요청"에 기록만 한다.

### 무엇을 보여 주나
파일 목록의 "휴지통으로"는 묻지 않고 바로 옮긴 뒤 스낵바에 실행 취소를 준다. 조작판에서 요청을 바로 보내는 방식과 8초 미뤘다가 보내는 방식을 고를 수 있다. 바로 보내는 방식에서 실행 취소하면 기록에 "복원" 요청이 하나 더 남고, 미루는 방식에서 8초 안에 실행 취소하면 기록에 아무것도 남지 않는다. 여러 파일을 옮긴 뒤 Ctrl+Z를 누르면 최근 것부터 하나씩 되돌아온다.

휴지통의 "복원"은 묻지 않는다. 다시 옮기면 되니 되돌릴 수 있는 행동이다. "영구 삭제"와 "휴지통 비우기"는 확인 대화 상자를 띄운다. 제목에는 대상 파일 이름을, 본문에는 되돌릴 수 없다는 것을 쓰고, 휴지통 비우기는 지워질 파일 목록과 개수를 보여 준다. 확인 버튼은 "영구 삭제", "파일 2개 영구 삭제"처럼 동사로 썼고, 처음 포커스는 취소에 있다.

메모는 고친 내용이 있으면 "저장하지 않은 변경 사항이 있습니다"를 보여 주고, 그때만 편집 취소에서 확인 대화 상자를, 페이지를 떠날 때 브라우저 확인 창을 띄운다.

### 확인한 것과 못 한 것
2026-11-03에 Playwright로 Chromium 계열 브라우저(설치된 Chrome 156.0.8078.48)를 띄워 파일을 file:// 주소로 열고 55가지를 확인했다. 콘솔 오류는 없었다. 휴지통으로 옮길 때 대화 상자가 뜨지 않는 것, 실행 취소로 원래 순서대로 돌아오고 포커스가 되돌린 파일로 가는 것, Ctrl+Z가 최근 것부터 차례로 되돌리며 포커스를 되돌린 파일로 옮기고, 더 없으면 "되돌릴 이동이 없습니다"를 알리는 것, 메모 칸 안의 Ctrl+Z는 파일을 되돌리지 않는 것을 확인했다. 확인 대화 상자가 `alertdialog` 로 열리고 처음 포커스가 취소에 가는 것, Esc가 취소로 처리되고 포커스가 연 버튼으로 돌아가는 것, 확인한 뒤 한 번 더 열어 Esc를 눌러도 지난 확인 값이 섞이지 않는 것, 미루는 방식에서 8초 안의 실행 취소는 요청을 남기지 않고 8초 뒤에는 요청이 남으며, 그때 목록을 다시 그려도 포커스가 같은 버튼에 남는 것도 확인했다. 메모를 고친 채 페이지를 닫으면 `beforeunload` 확인 창이 뜨고, 저장한 뒤에는 뜨지 않았다. 375px 너비에서 대화 상자를 열어도 가로 스크롤이 생기지 않았다.

실제 스크린 리더(NVDA, VoiceOver, TalkBack 등)로 듣는 확인은 하지 않았다. `<dialog>` 에 준 `alertdialog` 역할과 설명이 실제로 어떻게 읽히는지, 스낵바와 상태 알림이 겹칠 때 어떤 순서로 읽히는지는 확인하지 못했다(확인 필요). Chrome 외의 브라우저, 실제 휴대폰 터치 조작, 미루는 방식에서 기다리는 동안 페이지를 닫는 경우는 시험하지 않았다. 예제는 미루는 중인 요청을 페이지를 닫을 때 보내지 않으므로, 그 사이에 닫으면 파일이 옮겨지지 않은 채 남는다.
