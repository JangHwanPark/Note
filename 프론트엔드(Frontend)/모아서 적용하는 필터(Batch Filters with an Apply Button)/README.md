## 무엇이 문제인가
- 필터를 고를 때마다 결과가 바로 바뀌는 화면이 있고, 여러 개를 고른 뒤 적용 버튼을 눌러야 바뀌는 화면이 있다. 이 노트는 뒤쪽, 모아서 적용하는 필터를 다룬다
- 모아서 적용하면 누르기 전까지 결과가 그대로라서, 사용자는 지금 고른 조합이 몇 개를 돌려줄지, 0개는 아닌지 모른 채 버튼을 누르게 된다. 그래서 적용 전에 결과 수를 미리 보여 주는 방법을 함께 정리한다
- 고르는 중인 조건과 이미 적용된 조건을 어떻게 나눠 들고 있을지, 적용 버튼은 어디에 둘지, 적용한 뒤 주소와 포커스와 알림은 어떻게 할지, 좁은 화면에서 필터를 대화 상자로 띄울 때 무엇이 달라지는지를 본다

[같은 화면에서 주소만 바뀔 때](../같은%20화면에서%20주소만%20바뀔%20때(URL%20Changes%20Within%20a%20Screen)/README.md) 노트는 고를 때마다 바로 적용하는 필터를 다뤘다. 주소에 조건을 담는 방법, `pushState` 와 `replaceState`, 결과 수를 상태 메시지로 알리는 방법은 그 노트에 있고, 이 노트는 그 위에 적용 단계가 하나 끼었을 때 달라지는 것을 본다.

옷 가게 탈의실과 같다. 옷을 여러 벌 골라 들고 들어가 입어 보는 동안에는 아직 산 것이 아니고, 계산대에서 계산해야 내 것이 된다. 고르는 중인 옷과 계산한 옷이 따로 있고, 고른 옷을 내려놓고 나가면 산 것은 하나도 바뀌지 않는다. 입어 보는 동안 거울 옆에 지금 고른 옷이 몇 벌인지 바로 떠서, 계산대에 가기 전에 너무 많거나 하나도 없다는 것을 아는 것이 결과 수 미리 보기다.

## 바로 적용과 모아서 적용
### 두 방식
NN/g의 Sherwin(2016)은 필터를 하나 고를 때마다 결과를 다시 불러오는 바로 적용(interactive filtering)과, 사용자가 여러 필터를 다 고를 때까지 기다렸다가 결과를 불러오는 모아서 적용(batch filtering)을 나눈다. batch의 사전적 의미는 한 번에 처리하는 한 묶음으로, 빵을 한 판씩 굽는 것처럼 일을 모아 두었다가 한꺼번에 처리한다는 뜻이다.

같은 글은 바로 적용이 무엇이 있는지 둘러보는 사용자에게 맞고, 모아서 적용은 찾는 조건이 분명한 사용자나 적어도 가끔 느려지는 사이트에 맞는다고 쓴다. 모아서 적용할 때는 "적용" 버튼을 두어 사용자가 다 골랐다고 알리게 하라고 하고, 모바일에서는 이동 중 페이지 불러오기가 느린 경우가 많아 모아서 적용을 권한다. 단점도 든다. 모아서 적용하면 결과가 0개인 조합을 고를 위험이 있고, 어떤 필터가 남아 있는지를 계속 보여 주기 어렵다.

eBay 디자인 시스템(Playbook)의 필터 패턴도 같은 둘을 바로 적용(Immediate apply)과 명시적 적용(explicit apply)으로 나눈다. 결과가 눈에 띄는 지연 없이 바뀔 수 있는 단순한 필터(필터 칩, 하나만 고르는 메뉴)는 바로 적용하고, 결과를 바꾸기 전에 여러 개를 골라야 하는 경우(고급 필터 시트)는 명시적으로 적용하라고 쓴다. 가격 범위나 위치 입력도 명시적으로 적용해서, 값을 다 넣은 뒤에만 결과가 바뀌게 한다고 쓴다. 가격 범위와 슬라이더의 적용 시점은 [가격 범위와 슬라이더 필터](../가격%20범위와%20슬라이더%20필터(Price%20Range%20and%20Slider%20Filters)/README.md) 노트에 따로 정리했다.

### 고르는 기준
위 자료를 모으면 아래처럼 정리할 수 있다. 세 번째 줄은 이 노트가 다루는 방식으로, 모아서 적용하면서 결과 수를 미리 보여 주어 단점을 줄인 것이다(정리는 내 판단).

| 방식 | 결과가 바뀌는 때 | 맞는 경우 | 약점 |
|---|---|---|---|
| 바로 적용 | 고를 때마다 | 둘러보는 사용자, 결과가 빨리 오는 화면, 단순한 필터 | 고를 때마다 결과가 움직이고 요청이 나간다. 여러 개를 고르려면 기다려야 한다 |
| 모아서 적용 | 적용 버튼을 누를 때 | 조건이 분명한 사용자, 느린 화면, 모바일, 범위 입력 | 누르기 전까지 결과를 모른다. 0개 조합을 고를 수 있다 |
| 모아서 적용과 결과 수 미리 보기 | 적용 버튼을 누를 때(수는 고를 때마다) | 모아서 적용이 맞는 경우 대부분 | 수를 세는 요청이 고를 때마다 나간다 |

Baymard의 지침 목록에도 "모바일 필터링 화면의 적용 버튼"과 "필터 선택지마다 결과 수 표시"라는 항목이 있다. 공개된 부분에는 자동으로 적용되는 필터가 여러 선택지를 고르려는 사용자를 느리게 할 수 있다는 것, 선택지마다 결과 수를 보여 주지 않으면 사용자가 그 필터를 적용했을 때의 효과를 모른다는 것만 나와 있다. 권고 본문은 유료라 읽지 못했다.

## 고르는 중인 조건과 적용된 조건
### 상태를 둘로 나눈다
모아서 적용하는 화면은 조건을 두 벌 들고 있어야 한다. 하나는 이미 적용되어 결과 목록과 주소에 반영된 조건이고, 다른 하나는 사용자가 폼에서 고르는 중인 조건이다. 이 노트와 예제는 앞쪽을 적용된 조건(`applied`), 뒤쪽을 초안(`draft`)이라고 부른다. 둘을 한 벌로 두면 체크박스를 누르는 순간 결과 쪽도 함께 바뀌어 버려서 결국 바로 적용과 같아진다.

예제는 `applied` 와 `draft` 두 변수를 두고, 폼의 `change` 이벤트에서는 `draft` 만 바꾼다. 적용 버튼을 누를 때만 `draft` 를 `applied` 로 복사하고 주소를 바꾼다. 주소에서 화면을 그릴 때는 `applied` 를 주소에서 읽고 `draft` 는 그것을 복사해 시작한다.

```js
form.addEventListener('change', () => {
  draft = readForm();       // 고르는 중인 조건만 바꾼다. 결과와 주소는 그대로
  afterDraftChange();       // 미리 보기 수를 다시 세고, 적용하지 않은 변경 표시를 갱신
});
form.addEventListener('submit', (e) => {
  e.preventDefault();
  if (!same(draft, applied)) {
    applied = copy(draft);
    history.pushState(null, '', toQuery(applied) || location.pathname);
    loadResults();
  }
});
```

### 적용하지 않은 변경을 보여 준다
옆 칸에 필터를 늘 펼쳐 두는 넓은 화면에서는 고르는 중인 조건이 화면에 그대로 남는다. 체크박스는 "키보드, 마우스"로 되어 있는데 결과는 아직 전체라면, 사용자는 결과가 조건과 맞는지 헷갈릴 수 있다. 예제는 두 조건이 다르면 적용 버튼 위에 "적용하지 않은 변경이 있습니다"와 "변경 취소" 버튼을 보여 준다. 변경 취소는 `draft` 를 `applied` 로 되돌리고 폼을 다시 적는다. 이 표시 방식은 자료에서 가져온 것이 아니라 내 판단이다.

## 결과 수를 미리 보여 준다
### 적용 버튼에 수를 넣는다
eBay 필터 패턴은 주 버튼(primary call to action)이 숫자로 된 전체 결과 수를 함께 보여 주도록 바뀐다고 쓰고, "See 120 results", 큰 수는 "See 5,000+ results"처럼 상한을 둔 예를 든다. 예제는 버튼 글자를 "상품 20개 보기"로 바꾸고, 0개면 "결과 보기 (0개)"로 쓴다. 0개일 때도 버튼을 막지 않았다. 눌러도 빈 결과와 필터 지우기 안내가 나올 뿐 해가 없고, [폼 설계](../폼%20설계(Form%20Design)/README.md) 노트에서 본 것처럼 막힌 버튼은 왜 막혔는지 알려 주지 못하기 때문이다(내 판단).

### 선택지마다 수를 넣는다
패싯(facet)의 사전적 의미는 보석을 깎은 여러 면, 또는 일의 한 측면이다. 공학에서는 분류, 브랜드, 가격처럼 결과를 서로 다른 측면에서 좁히는 필터 묶음을 패싯이라 하고, 이런 필터로 찾는 방식을 패싯 검색(faceted search)이라고 부른다. Sherwin(2016)은 바로 적용하는 패싯이 필터마다 항목이 몇 개 있는지를 흔히 보여 주고, 이것이 결과 0개 검색을 피하게 돕는다고 쓴다(원문을 요약 도구로 읽어 확인했고, 정확한 문장은 확인 필요). 모아서 적용할 때도 이 수를 고를 때마다 새로 세면 같은 도움을 받을 수 있다.

이때 수를 무엇으로 셀지 정해야 한다. 예제의 필터는 같은 묶음 안에서는 "또는"(키보드 또는 마우스), 묶음 사이에서는 "그리고"(그리고 가람 브랜드)로 거른다. 선택지 옆의 수를 지금 조건 전체로 세면, 키보드를 고른 순간 마우스 옆의 수가 0이 된다. 마우스는 키보드와 함께 고를 수 있는 선택지인데 0으로 보이면 고를 수 없는 것처럼 읽힌다. 그래서 예제는 선택지마다 "자기 묶음의 조건은 빼고, 다른 묶음의 조건은 지금 고른 그대로"에 그 선택지를 더해 센다. 분류에서 키보드와 마우스를 골라도 모니터 옆에는 여전히 10개가 나오고, 브랜드 옆의 수는 고른 분류에 맞게 줄어든다.

아래에서 `f` 는 고르는 중인 조건(`draft`)이다.

```js
// 선택지마다 "이 묶음은 이 값만, 나머지 묶음은 지금 조건 그대로"일 때의 수
const facet = (group, test) => PRODUCTS.filter((p) => matches(p, f, group) && test(p)).length;
```

`matches(p, f, group)` 의 세 번째 인자는 건너뛸 묶음이다. 실제 서비스에서는 이 계산을 검색 서버가 한다. 상품 분류처럼 한 상품이 한 값만 갖는 묶음이라면, 이렇게 센 수는 그 선택지를 더 골랐을 때 늘어나는 결과 수와 같다.

### 0개인 선택지
지금 조건에서 0개인 선택지를 숨길지, 막을지, 흐리게만 둘지도 정해야 한다. 숨기면 선택지 목록이 고를 때마다 바뀌어 자리가 흔들리고, 막으면(`disabled`) 키보드로 닿지 않아 왜 없는지 알 수 없다. 예제는 글자색만 흐리게 하고 고를 수는 있게 두었다. 다른 묶음의 선택을 바꾸면 다시 수가 생길 수 있기 때문이다. 이 선택은 내 판단이고, 공개된 자료에서 기준을 찾지 못했다(확인 필요).

### 세는 요청과 늦은 응답
수를 세려면 고를 때마다 서버에 물어야 한다. 체크박스를 빠르게 여러 개 누르면 요청이 여러 개 나가고, 앞 요청의 응답이 뒤 요청보다 늦게 와서 화면의 수를 낡은 값으로 덮을 수 있다. 예제는 두 가지를 한다. 마지막 조작 뒤 0.2초 동안 다른 조작이 없을 때만 묻고(0.2초는 임의로 정한 값), 조건이 바뀔 때마다 번호를 올려 응답이 왔을 때 가장 최근 번호가 아니면 버린다. 번호를 요청을 보낼 때 올리면, 요청 하나가 나간 뒤 다시 고르고 다음 요청이 0.2초를 기다리는 사이에 앞 응답이 도착했을 때 그 낡은 수가 그려진다. 처음 쓴 코드가 이랬고, 리뷰에서 찾았다. [화면 전환 시 제목과 포커스 옮기기](../화면%20전환%20시%20제목과%20포커스%20옮기기(Title%20and%20Focus%20on%20Route%20Change)/README.md) 노트의 늦게 도착한 화면 버리기와 같은 방법이다. 예제의 가짜 서버는 응답 시간을 450ms, 150ms, 300ms로 돌려 가며 써서 일부러 순서를 뒤섞는다. 세는 동안에는 적용 버튼 아래에 "개수를 세는 중"을 보여 준다.

```js
function scheduleCount() {
  clearTimeout(countTimer);
  const seq = ++countSeq;                       // 조건이 바뀔 때마다 번호를 올린다
  countTimer = setTimeout(() => requestCount(seq), 200);
}
async function requestCount(seq) {
  const r = await fakeCount(copy(draft));
  if (seq !== countSeq) return;   // 그 사이 조건이 또 바뀌었다면 이 응답은 낡았다
  paintCounts(r);
}
```

### 미리 보기 수를 알린다
화면을 보는 사용자는 버튼의 수가 바뀌는 것을 보지만, 스크린 리더 사용자는 체크박스에 포커스를 둔 채로는 버튼 글자가 바뀐 것을 듣지 못한다. 예제는 적용 버튼 바로 위에 `role="status"` 문단을 두고 "이 조건이면 상품 20개"를 넣는다. 글이 그대로면 다시 넣지 않아서, 수가 바뀌지 않은 조작에서는 읽히지 않는다. 체크박스를 누를 때마다 수가 읽히는 것이 도움이 될지 소음이 될지는 들어 보지 않아 모른다(확인 필요). 상태 메시지와 라이브 영역의 동작은 [알림과 피드백](../알림과%20피드백(Notifications%20and%20Feedback)/README.md) 노트에 있다.

## 적용 버튼을 두는 곳
MOJ(영국 법무부) 디자인 시스템의 필터 컴포넌트는 고른 필터를 맨 위에 모아 보여 주고, 선택지를 고른 뒤 "Apply filters" 버튼을 눌러 적용한다. 같은 문서는 사용자가 선택을 마친 뒤 적용하려면 컴포넌트 위쪽으로 돌아가야 해서 키보드 사용자에게 어려울 수 있다고 적는다. 이것이 WCAG 위반은 아니라고 하면서, 접근성 성명(accessibility statement)에 언급하라고 제안한다. 버튼이 고른 필터 묶음의 위인지 아래인지는 원문 그림으로 확인하지 못했다.

키보드 사용자는 위에서 아래로 선택지를 지나가므로, 고르기를 마친 자리 바로 다음에 적용 버튼이 있으면 다시 거슬러 올라가지 않아도 된다. 예제는 모든 선택지 아래, 폼의 맨 끝에 적용 버튼을 둔다. 좁은 화면의 대화 상자 안에서는 선택지가 길어 화면을 넘으므로 적용 버튼 묶음에 `position: sticky; bottom: 0` 을 주어 늘 아래에 보이게 했다(내 판단).

<br/>

## 적용한 뒤
### 주소는 한 번만 쌓는다
같은 화면 노트에서 필터를 바꿀 때마다 기록을 쌓았던 것과 달리, 모아서 적용하면 사용자가 내린 결정은 "적용" 한 번이다. 그래서 적용을 누를 때 `pushState` 로 한 번 쌓고, 고르는 동안에는 주소를 건드리지 않는다. 뒤로 가기를 누르면 직전에 적용했던 조건으로 돌아가고, 고르던 것은 그 조건으로 덮인다.

적용을 눌렀는데 조건이 적용된 것과 같다면 주소도 결과도 그대로 둔다. 그렇지 않으면 뒤로 가기를 눌러도 같은 화면이 나오는 기록이 생긴다. 같은 화면 노트의 `commit()` 함수가 주소가 같으면 쌓지 않던 것과 같은 이유다.

### 포커스와 알림
넓은 화면에서 적용을 누르면 포커스는 적용 버튼에 그대로 둔다. 결과 목록이 옆에서 바뀌므로 포커스를 결과로 옮길 수도 있지만, 조건을 조금 더 바꿔 다시 적용하려는 사용자는 다시 필터로 돌아와야 한다. 대신 결과 목록 쪽의 `role="status"` 문단이 "키보드, 마우스 조건으로 상품 20개를 보여 줍니다"로 바뀌어 적용된 결과를 알린다. 이 예제는 분류마다 상품이 10개씩이라 키보드를 적용했다가 마우스로 바꿔 적용해도 수가 같다. 수만 넣으면 알림 글이 그대로라 읽히지 않을 수 있어서, 같은 화면 노트가 정렬 이름을 넣었던 것처럼 적용된 조건을 함께 넣었다. 어느 쪽이 나은지는 사용자에 따라 다를 수 있다(내 판단).

<br/>

## 적용된 필터를 보여 주고 지운다
### 칩으로 보여 준다
필터를 적용하면 무엇이 적용되어 있는지를 결과 위에 따로 보여 준다. MOJ 필터 컴포넌트는 고른 필터를 묶음별로 맨 위에 보여 주고, 하나하나를 지울 수 있는 태그로 만들어 누르면 그 필터만 빠진 채 페이지를 다시 불러온다. 모두 지우는 "Clear filters" 링크도 둔다. eBay 패턴은 여러 선택을 한 번에 지우거나 기본값으로 돌리는 동작(clear, reset)을 두라고 하면서, 고른 필터가 하나뿐이라 그것을 바로 지울 수 있는 경우에는 이 동작을 두지 말라고 쓴다. 예제가 칩이 둘 이상일 때만 모두 지우기를 붙이는 것은 이 때문이다.

칩(chip)의 사전적 의미는 나무나 돌에서 떨어져 나온 작은 조각이다. 화면에서는 작은 조각처럼 생긴 둥근 단추 하나에 값 하나를 담아 보여 주는 요소를 칩이라고 부른다. 예제는 적용된 조건마다 "키보드 ×" 칩을 두고, 칩이 둘 이상이면 "모두 지우기"를 붙인다. 칩 버튼의 접근 가능한 이름은 `aria-label="키보드 필터 지우기"` 로 주어, ×가 무엇을 하는지 말로 들리게 했다.

### 칩은 바로 적용한다
칩을 누르는 것은 조건 하나를 빼고 다시 보여 달라는 하나의 결정이라서, 적용 버튼을 다시 누르게 하지 않고 그 자리에서 적용한다(MOJ도 누르면 바로 다시 불러온다). 예제는 칩을 누르면 `applied` 와 `draft` 양쪽에서 그 값을 빼고 기록을 하나 쌓는다. 폼에서 고르는 중이던 다른 변경은 그대로 남긴다. 칩 하나를 지웠다고 아직 적용하지 않은 다른 선택까지 사라지면 놀랄 것이기 때문이다(내 판단). 가격처럼 하나만 고르는 묶음은, 적용된 "5만 원 미만"을 두고 폼에서 "10만 원 이상"으로 바꿔 둔 채 가격 칩을 지우면 고르던 "10만 원 이상"을 남긴다. 고르던 값이 지우는 칩의 값과 같을 때만 전체로 돌린다.

### 칩을 지운 뒤 포커스
누른 칩은 지워져 사라지므로 포커스를 어딘가로 옮겨야 한다. 그대로 두면 포커스가 `body` 로 떨어진다. 다음 Tab이 어디서 시작하는지는 브라우저마다 다를 수 있고(확인 필요), 스크린 리더 사용자는 자기가 어디에 있는지 놓치기 쉽다. 예제는 같은 자리에 온 다음 칩으로, 마지막 칩이었다면 앞 칩으로, 칩이 하나도 남지 않으면 결과 제목(`tabindex="-1"`)으로 옮긴다. 모두 지우기도 결과 제목으로 옮긴다. 이 순서는 내 판단이다.

<br/>

## 좁은 화면에서는 대화 상자로
### 트레이와 대화 상자
NN/g의 Whitenton(2015)은 모바일에서 필터를 결과 위에 덮이는 트레이(tray)로 띄우는 방식을 소개한다. 트레이의 사전적 의미는 물건을 담아 나르는 납작한 쟁반으로, 화면 가장자리에서 밀려 나오는 판 위에 필터를 담는다는 뜻이다. 이 글이 본 트레이는 열려 있는 동안에도 뒤의 결과가 보이고 고를 때마다 바뀌며, 긴 필터 목록을 내려도 전체 결과 수가 늘 보인다. 즉 이 글의 예는 바로 적용 쪽이다. 같은 글은 트레이도 결과 화면의 일부만 보여서 사용자가 필터를 닫았다 다시 열어야 할 수 있다고 쓴다.

예제는 넓은 화면에서는 필터를 옆 칸에 펼쳐 두고, 1100px보다 좁으면 "필터" 버튼으로 `<dialog>` 를 띄운다. 폼은 하나만 두고 대화 상자를 열 때 안으로 옮기고, 닫을 때 옆 칸으로 돌려놓는다. 대화 상자 자체는 [되돌리기와 확인 대화 상자](../되돌리기와%20확인%20대화%20상자(Undo%20and%20Confirmation%20Dialogs)/README.md) 노트에서 본 `showModal()` 로 연다. 트레이와 달리 모달 대화 상자라서 열려 있는 동안 뒤의 결과를 조작할 수 없고, 휴대폰 너비에서는 결과가 거의 가려진다. 그래서 고를 때 결과가 바뀌는 것을 볼 수 없고, 결과 수 미리 보기가 더 중요해진다. 필터 버튼 글자는 적용된 필터 수에 따라 "필터 (1개 적용)"처럼 바뀐다.

### 적용하지 않고 닫으면 버린다
대화 상자를 닫기 버튼이나 Esc로 닫는 것은 고르던 것을 그만둔다는 뜻으로 읽는 편이 자연스럽다. 예제는 `close()` 에 넘긴 값(`returnValue`)이 `'apply'` 가 아니면 `draft` 를 `applied` 로 되돌린다. 되돌리기 노트에서 확인했듯 Esc로 닫으면 `returnValue` 는 빈 글자가 되므로 이 경우도 되돌린다. 탈의실에서 고른 옷을 내려놓고 나오는 것과 같다. eBay 패턴과 NN/g 글 모두 적용하지 않고 닫았을 때 고른 것을 남길지 버릴지는 적지 않았다. 버리는 쪽은 내 판단이다. 고른 것이 많을 때 실수로 닫는 경우를 막으려면 확인을 받을 수도 있는데, 예제에는 넣지 않았다.

열린 채로 화면이 넓어지면 폼을 옆 칸으로 돌려놓아야 하는데, 이때는 사용자가 그만둔 것이 아니므로 고르던 것을 그대로 둔다. 예제는 이 경우 `close('resize')` 로 닫아 구분한다. 되돌리기 노트에서 확인했듯 `returnValue` 는 다시 열어도 앞 값이 남아 있어서(Chrome 156에서 확인, 다른 브라우저도 같은지는 확인 필요) 열 때마다 빈 글자로 비운다. 넓어지며 닫힐 때는 포커스를 돌려받을 필터 버튼이 숨겨져 있으므로 옆 칸의 적용 버튼으로 옮기고, 반대로 옆 칸에 포커스가 있던 채로 좁아지면 필터 버튼으로 옮긴다. Chrome 156에서 해 보니 화면 너비 변화 이벤트(`matchMedia` 의 `change`)가 올 때는 숨겨진 체크박스의 포커스가 이미 `body` 로 떨어져 있어서, 지금 포커스 대신 마지막으로 포커스가 있던 곳이 폼 안이었는지로 판단했다.

### 닫은 뒤 포커스
APG 모달 대화 상자 패턴은 대화 상자가 닫히면 연 요소로 포커스를 돌려보내되, 연 요소가 사라졌거나, 사용자가 곧바로 대화 상자를 다시 열 일이 거의 없고 대화 상자에서 마친 일이 다음 단계로 바로 이어지는 경우에는 다른 요소가 더 맞을 수 있다고 쓴다. 필터는 적용한 뒤 결과를 보다가 조건을 다시 바꾸는 일이 흔하다고 보고, 예제는 적용했든 그냥 닫았든 "필터" 버튼으로 돌려보낸다. 2026-11-04에 Chrome 156에서 확인해 보니 `<dialog>` 를 닫으면 브라우저가 연 버튼으로 포커스를 돌려주어 따로 코드를 쓰지 않았다. 결과 수는 결과 쪽 상태 문단이 알린다.

## 예제
[example.html](./example.html)은 가짜 상품 40개를 분류, 브랜드, 가격, 재고로 거르는 예제다. HTML, CSS, 약간의 자바스크립트만 한 파일에 담았으므로 파일을 더블클릭하거나 브라우저 창에 끌어다 놓으면 바로 열린다. 적용된 조건은 쿼리스트링(`?cat=키보드,마우스&stock=1`)에 담는다. 실제 주소는 한글과 쉼표가 인코딩되어 있고, 조작판은 풀어 쓴 값을 보여 준다. 브라우저 창을 1100px보다 좁히면 필터가 대화 상자로 바뀐다.

### 무엇을 보여 주나
조작판에는 주소의 쿼리스트링, 적용된 조건, 고르는 중인 조건, 방문 기록 항목 수, 포커스가 있는 곳, 미리 보기 알림 글자, 결과 알림 글자, 개수 요청을 보낸 횟수와 늦게 와서 버린 횟수가 나온다. 체크박스를 누르면 고르는 중인 조건과 선택지 옆의 수, 적용 버튼의 수만 바뀌고, 주소와 결과와 기록 수는 그대로다. 체크박스를 빠르게 여러 개 누르면 버린 횟수가 늘어난다. 적용을 누르면 주소와 결과가 바뀌고 기록 수가 하나 늘며, 결과 위에 칩이 생긴다.

### 확인한 것과 못 한 것
2026-11-04에 Playwright로 Chromium 계열 브라우저(설치된 Chrome 156.0.8078.48)를 띄워 파일을 file:// 주소로 열고 70가지를 확인했다. 콘솔 오류는 없었다.

- 고르기만 하면 주소, 결과, 기록 수가 그대로이고 포커스가 체크박스에 남는다. 키보드와 마우스를 고르면 적용 버튼이 "상품 20개 보기"가 되고, 분류 옆의 수는 10개 그대로이며, 브랜드 옆의 수는 합이 20이 되게 줄어든다
- 재고, 가격, 브랜드를 0.25초 간격으로 바꾸면 늦은 응답이 버려지고, 마지막에 보이는 수가 마지막 조건으로 직접 센 수와 같다. 요청 하나가 나간 뒤 다시 골라 다음 요청이 기다리는 사이에 앞 응답이 도착해도 그 수는 그려지지 않는다
- 적용하면 주소가 바뀌고 기록이 하나만 늘며, 결과 수와 적용된 조건이 들어간 알림 글자, 칩이 맞게 나온다. 같은 조건으로 다시 적용하면 기록이 늘지 않는다. 변경 취소는 폼을 적용된 조건으로 되돌리고 포커스를 적용 버튼으로 옮긴다
- 칩을 지우면 바로 적용되어 기록이 하나 늘고, 포커스가 다음 칩으로 간다. 마지막 칩이면 앞 칩으로 간다. 고르는 중이던 다른 변경은 칩을 지워도 남고, 가격 칩을 지워도 폼에서 다르게 고르던 가격은 남는다. 모두 지우기는 포커스를 결과 제목으로 옮긴다
- 뒤로 가기로 직전 조건의 결과, 폼, 칩이 돌아온다. 조건이 담긴 주소로 바로 열면 그 조건대로 그려진다. 0개인 선택지는 흐리지만 고를 수 있다
- 375px 너비에서 가로 스크롤이 없고, 필터 대화 상자 안의 적용 버튼이 화면 안에 보인다. Esc와 닫기 버튼은 고르던 것을 버리고, 적용은 대화 상자를 닫고 주소와 결과를 바꾼다. 어느 쪽이든 포커스는 필터 버튼으로 돌아온다. 대화 상자가 열린 채로 1280px로 넓히면 폼이 옆 칸으로 돌아가고 고르던 것이 남으며, 포커스가 적용 버튼으로 간다. 넓은 화면에서 체크박스에 포커스를 둔 채 375px로 좁히면 포커스가 필터 버튼으로 간다

실제 스크린 리더(NVDA, VoiceOver, TalkBack 등)로 듣는 확인은 하지 않았다. 체크박스 상태와 미리 보기 수가 어떤 순서로 읽히는지, 폼을 대화 상자 안으로 옮긴 뒤에도 폼 안의 `role="status"` 문단이 그대로 알림을 내는지, 대화 상자가 닫히면서 필터 버튼 포커스와 결과 수 알림이 겹칠 때, 칩을 지울 때 다음 칩 포커스와 결과 알림과 미리 보기 알림이 거의 함께 바뀔 때 어떻게 읽히는지는 확인하지 못했다(확인 필요). Chrome 외의 브라우저, 실제 휴대폰의 화면 키보드와 스크롤, 실제 서버의 응답 시간도 시험하지 않았다.
