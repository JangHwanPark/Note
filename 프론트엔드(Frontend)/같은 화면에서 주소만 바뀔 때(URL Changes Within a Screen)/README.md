## 무엇이 문제인가
- 검색어, 분류 필터, 정렬, 페이지 번호, 탭처럼 같은 화면 안에서 조건만 바꾸는 조작도 주소에 담는 경우가 많다. 그래야 새로 고침, 공유, 뒤로 가기가 그 조건을 기억한다
- 그런데 이 경우는 다른 화면으로 옮겨 가는 것과 다르게 다뤄야 한다. 사용자는 같은 자리에서 조작을 이어 가므로, 화면 이동처럼 포커스를 제목으로 옮기면 방금 누른 컨트롤에서 멀어진다
- 이 노트는 주소에 무엇을 담을지, 기록을 쌓을지 고쳐 쓸지, 포커스와 스크롤을 어떻게 둘지, 바뀐 결과를 어떻게 알릴지를 정리한다. 화면이 통째로 바뀌는 경우는 [화면 전환 시 제목과 포커스 옮기기](../화면%20전환%20시%20제목과%20포커스%20옮기기(Title%20and%20Focus%20on%20Route%20Change)/README.md) 노트에 있다

주소의 `?` 뒤에 조건을 붙이는 쿼리스트링(Query String)은 [쿼리스트링](../../CS_Basic/WEB/쿼리스트링(Query%20String)/README.md) 노트에서 다뤘다. 이 노트는 그 주소를 화면 쪽에서 언제 어떻게 바꾸는지를 본다.

도서관 검색대와 같다. 검색 조건을 "소설"에서 "소설, 2020년 이후"로 좁히는 것은 같은 검색대 앞에서 하는 일이라서, 사서가 그때마다 손님을 다른 층으로 데려가지 않는다. 대신 "이제 34권입니다" 하고 결과만 알려 준다. 다른 층의 열람실로 옮겨 갈 때와는 안내 방식이 달라야 한다.

## 주소에 무엇을 담을까
### 담을 것과 담지 않을 것
주소에 담는다는 것은 그 상태를 북마크하고, 공유하고, 새로 고침해도 되살리겠다는 뜻이다. 검색어, 필터, 정렬, 페이지 번호, 고른 탭은 다른 사람에게 그대로 보내고 싶은 상태라서 담을 만하다. 열려 있는 드롭다운, 마우스를 올린 항목, 입력 중인 폼의 값처럼 잠깐 있다 사라지는 상태는 담지 않는다(내 판단).

### 화면은 언제나 주소에서 그린다
주소에 상태를 담았다면 화면을 그릴 때도 주소에서 읽는 편이 안전하다. 버튼을 눌렀을 때, 뒤로 가기를 눌렀을 때, 공유받은 주소로 처음 열었을 때가 모두 "주소를 읽어 그린다"는 한 길을 지나므로, 어느 경로로 와도 화면이 같아진다(내 판단). 예제는 화면의 상태를 주소에서 읽는 함수와 그리는 함수를 하나씩만 두고, 모든 조작이 주소를 바꾼 뒤 그 함수를 부르게 했다. `?page=9` 처럼 범위를 넘는 페이지 번호로 열면 마지막 쪽을 그리고 주소도 그 쪽으로 고쳐 써서, 주소와 화면이 어긋나지 않게 했다.

## 기록을 쌓을까, 고쳐 쓸까
### pushState와 replaceState
History API에는 주소를 바꾸는 방법이 둘 있다. push는 밀어 넣다, replace는 바꿔 놓다라는 뜻이다. `history.pushState()` 는 방문 기록(history) 위에 새 항목을 밀어 넣고, `history.replaceState()` 는 지금 항목을 바꿔 놓는다. MDN은 `replaceState()` 가 지금 기록 항목을 넘겨받은 상태와 주소로 바꾼다고 쓰고, 새 주소는 지금 주소와 출처(origin)가 같아야 하며 그렇지 않으면 예외가 난다고 쓴다. 쌓은 항목 하나는 뒤로 가기 한 번이 된다.

```js
history.pushState(null, '', '?cat=input');   // 기록 항목을 하나 쌓는다. 뒤로 가기로 돌아올 곳이 하나 생긴다
history.replaceState(null, '', '?q=키보드'); // 지금 기록 항목을 고쳐 쓴다. 뒤로 가기 횟수는 그대로다
```

### 무엇을 쌓을까
뒤로 가기는 사용자가 "방금 전 상태"로 돌아가려고 누르는 버튼이다. 그래서 사용자가 의도를 갖고 한 단계로 여기는 조작은 쌓고, 그 사이의 중간 상태는 쌓지 않는다(내 판단).

| 조작 | 예제의 선택 | 이유 |
|---|---|---|
| 검색어 입력 | 고쳐 쓴다(replace) | 글자마다 쌓으면 뒤로 가기를 글자 수만큼 눌러야 한다 |
| 분류 필터, 정렬 | 쌓는다(push) | 한 번 고르면 하나의 결정이다. 뒤로 가기로 직전 조건으로 돌아갈 수 있다 |
| 페이지 번호 | 쌓는다(push) | 페이지를 새로 여는 것과 같은 일이라 뒤로 가기로 앞 쪽에 돌아가길 기대한다 |
| 탭 | 쌓는다(push) | GOV.UK 탭 컴포넌트는 탭을 바꾸면 주소의 `#` 뒤가 바뀌고, 뒤로 가기가 이전 탭으로 가야 한다고 쓴다 |

이 선택은 서비스마다 다를 수 있다. 예를 들어 필터를 여러 개 고른 뒤 "적용"을 누르는 방식이라면 적용 한 번만 쌓으면 된다.

### 뒤로 가기는 popstate로 받는다
pop은 꺼내다라는 뜻으로, 뒤로 가기나 앞으로 가기로 기록 사이를 옮겨 갈 때 `popstate` 이벤트가 일어난다. MDN은 이 이벤트가 뒤로 가기, 앞으로 가기 같은 브라우저 동작(또는 `history.back()`)으로 일어나고, `pushState()` 나 `replaceState()` 를 부르는 것만으로는 일어나지 않는다고 쓴다. 그래서 내가 주소를 바꾼 뒤에는 직접 다시 그리고, 뒤로 가기로 주소가 바뀌었을 때는 `popstate` 에서 주소를 다시 읽어 그린다. 예제에서 뒤로 가기를 누르면 정렬 선택 상자와 분류 체크박스까지 그 시점의 값으로 돌아오는 것이 이 때문이다.

예제의 코드를 줄이면 아래와 같다. 주소가 그대로면 기록을 쌓지 않는 줄이 있어서, 이미 고른 조건을 다시 골라도 뒤로 가기 횟수가 늘지 않는다.

```js
function commit(next, how) {
  const url = toQuery(next);
  if (url === (location.search || location.pathname)) return;
  if (how === 'push') history.pushState(null, '', url);
  else history.replaceState(null, '', url);
  render();
}
window.addEventListener('popstate', render);
```

## 포커스는 그대로 둔다
### 화면 이동이 아니라 상태 변화다
필터를 고르거나 정렬을 바꾸는 사용자는 같은 자리에서 다음 조작을 이어 가려 한다. 체크박스를 하나 더 고르거나, 정렬을 다시 바꿀 수 있다. 이때 포커스를 결과 제목으로 옮기면 다시 컨트롤까지 Tab으로 돌아와야 한다. 예제는 검색 칸, 체크박스, 정렬 선택 상자에서 조건을 바꿔도 포커스를 그 자리에 둔다.

WCAG 2.2의 4.1.3 상태 메시지(Status Messages, AA) 이해 문서도 이 둘을 나눈다. 포커스를 가져가는 변화는 맥락의 변화(change of context)이고, 대화 상자처럼 포커스를 가져가면 상태 메시지가 아니다. 반대로 포커스를 옮기지 않고 결과만 바뀌는 경우에는 그 결과를 상태 메시지로 알려야 한다(다음 절).

### 페이지 번호는 예외로 본다
페이지 번호를 누르는 것은 지금 목록을 다 보고 다음 목록을 읽으려는 행동이다. 목록 아래의 "2"를 눌렀을 때 포커스를 그대로 두면, 링크를 유지하는 구현에서는 포커스가 목록 아래에 남아 새 목록을 읽으려면 위로 거슬러 올라가야 한다. 예제처럼 페이지 링크를 다시 그리는 구현에서는 누른 링크가 사라져 포커스가 `body` 로 떨어진다. 어느 쪽이든 새 목록을 처음부터 읽기 어렵다. 예제는 페이지 번호를 누를 때만 포커스를 결과 제목(`tabindex="-1"`)으로 옮기고 그 제목이 보이도록 스크롤한다(내 판단).

### 스크롤을 맨 위로 튀게 하지 않는다
NN/g의 Sherwin(2016)은 필터를 고를 때마다 결과 페이지를 맨 위로 올리면, 사용자가 의도하지 않은 필터를 잘못 누를 수 있다고 쓴다. 다만 결과가 적거나 페이지가 비어 보이게 되는 경우에는 결과 목록 맨 위로 옮기는 편이 낫다고도 쓴다. 예제는 필터와 정렬에서는 스크롤을 건드리지 않고, 결과가 적어져 화면이 비어 보이는 예외도 따로 처리하지 않았다.

## 바뀐 결과를 알린다
### 결과 수를 상태 메시지로
포커스를 옮기지 않으면 스크린 리더 사용자는 결과가 바뀌었는지 알 수 없다. WCAG 4.1.3 이해 문서는 "Searching...", "18 results returned", "No results returned" 같은 검색 상태 글을 상태 메시지의 예로 들고, 검색 버튼을 누르면 결과와 함께 "5 results returned"가 나타나는 예를 든다. 예제는 결과 제목 옆에 `role="status"` 문단을 두고 "상품 7개, 이름순, 1/2쪽"처럼 결과 수와 정렬, 쪽을 넣는다. 정렬만 바꾸면 결과 수가 같아서, 정렬 이름을 넣지 않으면 알림 글자가 그대로라 아무것도 읽히지 않는다. 라이브 영역의 동작은 [알림과 피드백](../알림과%20피드백(Notifications%20and%20Feedback)/README.md) 노트에 있다.

같은 글을 다시 넣었을 때 다시 읽힐지는 스크린 리더마다 다를 수 있다(확인 필요). 알림과 피드백 노트의 예제는 같은 글도 다시 읽히게 하려고 영역을 잠깐 비운 뒤 넣는다. 이 예제는 반대로, 조건을 바꿨어도 결과가 같다면 다시 알릴 필요가 없다고 보고 알림 글이 달라졌을 때만 바꾼다(내 판단). 검색어는 치는 동안 0.4초 멈췄을 때 반영하므로 글자마다 결과 수가 읽히지 않는다. 0.4초는 이 예제에서 임의로 정한 값이다.

### 0개일 때
조건에 맞는 결과가 없으면 상태 메시지는 "조건에 맞는 상품 0개"로 알리고, 목록 자리에는 무엇을 하면 되는지(검색어 줄이기, 분류 선택 풀기)를 보여 준다. 결과가 없는 화면을 어떻게 꾸밀지는 [빈 상태](../빈%20상태(Empty%20State)/README.md) 노트의 "검색이나 필터 결과 없음" 절에, 결과 없음을 알리는 접근성 이야기는 같은 노트의 "검색 결과 없음을 알린다" 절에 있다.

### 제목에 페이지 번호를 담는다
GOV.UK 페이지 나누기(Pagination) 컴포넌트는 스크린 리더 사용자가 다른 페이지로 옮겨 왔다는 것을 알 수 있도록 페이지 `<title>` 에 페이지 번호를 넣으라고 하면서 "Search results (page 1 of 4)"를 예로 든다. 같은 컴포넌트의 예제 코드는 페이지 링크를 `aria-label="Pagination"` 이 붙은 `<nav>` 로 감싸고 지금 페이지 링크에 `aria-current="page"` 를 둔다. 예제는 제목을 `상품 목록 2/2쪽 - 예제 상점`, 검색 중에는 `"키보드" 검색 결과 - 예제 상점` 처럼 단다. 필터와 정렬까지 제목에 넣으면 너무 길어져서 넣지 않았다(내 판단).

## 바로 적용과 모아서 적용
NN/g의 Sherwin(2016)은 필터를 고를 때마다 결과가 바로 바뀌는 방식(interactive filtering)과 여러 필터를 고른 뒤 한꺼번에 적용하는 방식(batch filtering)을 나눈다. 무엇이 있는지 둘러보는 사용자에게는 바로 적용을, 조건이 분명한 사용자나 사이트가 자주 느린 경우에는 모아서 적용을 권하고, 모아서 적용하는 방식에는 "적용" 버튼을 두어 사용자가 다 골랐다고 알리게 하라고 한다. 모아서 적용하면 결과가 0개인 조합을 고를 위험이 있다는 점도 함께 든다.

이 노트의 주제와 이어 보면, 바로 적용은 고를 때마다 주소와 결과가 바뀌므로 결과 수 알림이 고를 때마다 필요하고, 모아서 적용은 "적용"을 누를 때 한 번만 주소를 쌓고 알리면 된다(내 판단). 예제는 바로 적용 방식이다.

## 탭
### 역할과 키보드
WAI-ARIA 작성 지침(APG, ARIA Authoring Practices Guide)의 탭 패턴은 탭 묶음에 `role="tablist"`, 각 탭에 `role="tab"`, 내용 영역에 `role="tabpanel"` 을 주고, 고른 탭에 `aria-selected="true"`, 나머지에 `false` 를 두며, 각 탭의 `aria-controls` 로 내용 영역을 가리키라고 한다. 키보드로는 탭 묶음에 들어오면 지금 고른 탭에 포커스가 가고, 왼쪽과 오른쪽 화살표로 탭 사이를 옮기며, Tab 키를 누르면 탭 묶음을 벗어나 내용 영역으로 간다. 내용 영역의 처음에 포커스를 받을 요소가 있으면 그 요소로 간다(예제의 상품 탭에서는 검색 칸).

APG는 내용이 눈에 띄는 지연 없이 나타난다면 탭에 포커스가 가는 순간 바로 바꾸는 자동 활성화를 권한다. 그렇지 않으면 자동 활성화가 포커스 이동을 느리게 해 탭 사이를 오가기 어렵게 만든다고 쓰고, 그 경우를 위해 Space나 Enter로 바꾸는 수동 활성화를 둔다. 서버에서 내용을 받아야 하는 탭이라면 미리 받아 두지 않는 한 수동 활성화가 맞아 보인다(내 판단).

### 탭과 주소
GOV.UK 탭 컴포넌트는 탭을 바꾸면 주소에 `#탭의 id` 가 붙고 뒤로 가기가 이전 탭으로 간다고 쓴다. 같은 문서는 탭을 페이지 이동 수단으로 쓰지 말고, 사용자가 탭 사이 내용을 비교해야 하거나 순서대로 다 읽어야 하는 경우에도 쓰지 말라고 한다.

예제는 화살표로 탭을 옮기면 바로 바꾸고(자동 활성화) 기록을 하나 쌓는다. 화살표를 누를 때마다 기록이 쌓이는 셈이라, 탭이 많다면 뒤로 가기를 여러 번 눌러야 할 수 있다. 탭이 두 개뿐인 예제에서는 이대로 두었다.

## 늦게 도착한 결과
검색어를 빠르게 바꾸면 앞 요청의 결과가 뒤 요청보다 늦게 와서 화면을 덮을 수 있다. [화면 전환 시 제목과 포커스 옮기기](../화면%20전환%20시%20제목과%20포커스%20옮기기(Title%20and%20Focus%20on%20Route%20Change)/README.md) 노트의 "늦게 도착한 화면은 버린다" 절과 같은 방법(요청마다 번호를 붙이고 최신이 아니면 버리기)이 여기에도 필요하다. 이 예제는 데이터를 화면 안에서 바로 걸러 내므로 요청이 없어 넣지 않았다.

<br/>

## 예제
[example.html](./example.html)은 가짜 상품 목록에서 검색, 분류, 정렬, 페이지, 탭을 바꿔 보는 예제다. HTML, CSS, 약간의 자바스크립트만 한 파일에 담았으므로 파일을 더블클릭하거나 브라우저 창에 끌어다 놓으면 바로 열린다. 조건은 쿼리스트링(`?q=키보드&cat=input`)에 담는다. 2026-11-04에 Chrome 156에서 확인해 보니 file:// 주소에서도 `pushState` 로 쿼리스트링을 바꿀 수 있었다. 다른 브라우저에서는 확인하지 못했다(확인 필요). 상품 16개를 한 쪽에 5개씩 보여 준다.

### 무엇을 보여 주나
조작판에는 지금 주소의 쿼리스트링, 이 탭의 방문 기록 항목 수(`history.length`), 탭 제목, 포커스가 있는 곳, 상태 알림 글자가 나온다. 주소는 실제로는 인코딩되어 있어서(검색어 키보드는 `%ED%82%A4...`, 분류 사이 쉼표는 `%2C`) 조작판은 풀어 쓴 값을 보여 준다. 인코딩은 [쿼리스트링](../../CS_Basic/WEB/쿼리스트링(Query%20String)/README.md) 노트에 있다. 방문 기록 항목 수에는 예제를 열기 전의 기록도 들어가고, 뒤로 간 뒤에 조건을 바꾸면 앞으로 가기 기록이 버려져 수가 늘지 않을 수 있다. 검색 칸에 글자를 치면 0.4초 멈춘 뒤 주소와 결과가 바뀌지만 기록 수는 그대로다. 앞으로 가기 기록이 없는 상태에서 분류, 정렬, 페이지, 탭을 바꾸면 기록 수가 하나씩 늘고, 뒤로 가기를 누르면 직전 조건으로 돌아가며 선택 상자와 체크박스도 그 값으로 돌아온다.

검색, 분류, 정렬을 바꾸면 포커스는 그 컨트롤에 남고, 결과 제목 옆의 `role="status"` 문단이 "상품 3개, 이름순", "상품 7개, 가격 낮은 순, 1/2쪽"처럼 바뀐다. 조건을 바꾸면 1쪽으로 돌아간다. 페이지 번호를 누르면 포커스가 결과 제목으로 가고 그 제목이 화면에 보이도록 스크롤된다. 지금 페이지 링크에는 `aria-current="page"` 가 붙고, 탭 제목에는 "2/2쪽"이 붙는다. 결과가 없으면 "조건에 맞는 상품 0개"를 알리고 목록 자리에 할 일을 보여 주며 페이지 링크를 숨긴다.

탭은 APG 패턴을 따라 화살표로 옮기고, 고르지 않은 탭은 `tabindex="-1"` 로 Tab 순서에서 뺐다. 배송 안내 탭의 내용 영역에는 포커스를 받을 요소가 없어서 영역 자체에 `tabindex="0"` 을 주었다. 그 영역에 포커스가 있을 때 뒤로 가기로 상품 탭이 돌아오면 영역이 숨겨지므로, 포커스를 고른 탭으로 옮긴다.

### 확인한 것과 못 한 것
2026-11-04에 Playwright로 Chromium 계열 브라우저(설치된 Chrome 156.0.8078.48)를 띄워 파일을 file:// 주소로 열고 41가지를 확인했다. 콘솔 오류는 없었다. 검색어가 치는 도중에는 반영되지 않고 멈춘 뒤 반영되며 기록 수가 늘지 않는 것, 검색 중 포커스가 검색 칸에 남는 것, 분류와 정렬과 페이지가 기록을 하나씩 쌓는 것, 체크박스와 선택 상자에 포커스가 남는 것, 결과 수 알림 글자가 조건마다 맞게 바뀌고 정렬만 바꿔도 바뀌는 것을 확인했다. 목록 아래까지 스크롤한 상태에서 2쪽을 누르면 포커스가 결과 제목으로 가고 제목이 화면 안에 들어오는 것, 뒤로 가기 세 번에 페이지, 정렬, 분류가 차례로 되돌아가는 것, 결과 0개일 때의 알림과 안내, 화살표로 탭을 바꾸면 내용과 주소와 제목이 바뀌고 Tab이 내용 영역으로 가는 것, 뒤로 가기로 이전 탭이 돌아오고 숨겨진 탭 영역에 있던 포커스가 고른 탭으로 가는 것, 범위를 넘는 `?page=9` 로 열면 주소가 `?page=4` 로 고쳐지는 것, 조건이 담긴 주소로 바로 열면 그 조건대로 그려지는 것, 375px 너비에서 가로 스크롤이 생기지 않는 것도 확인했다.

실제 스크린 리더(NVDA, VoiceOver, TalkBack 등)로 듣는 확인은 하지 않았다. 결과 수 알림이 언제 어떤 말투로 읽히는지, 체크박스를 고른 직후 체크박스 상태와 결과 수 알림이 어떤 순서로 읽히는지, 페이지 번호를 누를 때 결과 제목 포커스와 결과 수 알림이 함께 일어나면 어떤 순서로 읽히고 하나가 다른 하나를 끊는지는 확인하지 못했다(확인 필요). Chrome 외의 브라우저, 실제 휴대폰, 실제 서버 요청이 있을 때의 늦은 결과 처리는 시험하지 않았다.
