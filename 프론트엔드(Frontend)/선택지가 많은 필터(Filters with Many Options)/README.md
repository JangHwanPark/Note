## 무엇이 문제인가
- 분류나 재고처럼 선택지가 서너 개인 필터는 체크박스를 다 펼쳐 두면 된다. 그런데 브랜드, 제조사, 저자처럼 선택지가 수십 개에서 수백 개가 되는 묶음은 다 펼치면 필터 칸이 화면 몇 장을 차지하고, 원하는 하나를 찾으려면 끝까지 훑어야 한다
- 이 노트는 그런 묶음을 줄여 보여 주는 더 보기, 묶음 안에서 찾는 목록 안 검색, 이름을 쳐서 고르는 자동 완성(autocomplete, 여기서는 콤보박스로 만든다)을 정리한다. 각각의 키보드와 스크린 리더 처리, 고른 것이 가려지지 않게 하는 방법, 한글 검색에서 신경 쓸 것을 함께 본다

필터를 고르는 시점(바로 적용과 모아서 적용)과 선택지마다 결과 수를 붙이는 방법은 [모아서 적용하는 필터](../모아서%20적용하는%20필터(Batch%20Filters%20with%20an%20Apply%20Button)/README.md) 노트에 있다. 이 노트는 묶음 하나의 선택지가 많을 때만 본다.

동네 서점과 대형 서점의 차이와 같다. 동네 서점은 책장 하나를 훑으면 되지만, 대형 서점은 매대에 많이 찾는 책을 내놓고(더 보기), 서가 앞 안내판에서 저자 이름을 찾아 그 칸만 보게 하고(목록 안 검색), 안내 단말기에 제목 몇 글자를 치면 위치를 알려 준다(자동 완성). 책이 많아지면 훑는 대신 찾는 길을 여러 개 둔다.

<br/>

## 얼마나 많으면 손을 쓸까
Baymard의 Olah(2024)는 B2B 전자 부품 사이트를 다룬 글에서, 저항 값처럼 선택지가 수백 개인 필터를 사용자가 어떻게 다루는지 관찰한 결과를 썼다. 대상이 B2B 전자 부품이라 일반 쇼핑몰의 브랜드 필터와 꼭 같지는 않다. 일부 사용자는 긴 목록이 보이는 방식 때문에 애를 먹었고, 작은 스크롤 상자 안을 위아래로 굴리는 것을 어려워했으며, 선택지가 두어 개만 보이도록 상자를 작게 만든 사이트도 있었다고 쓴다. 필터 하나를 아예 포기한 참가자도 있었다. 같은 글은 선택지가 많을 때(예: 15~20개 이상) 그 묶음 안에서 검색할 수 있게 하라고 권하고, 벤치마크한 사이트의 46%가 필터 묶음 안을 믿을 만하게 검색할 수 있게 하지 않았다고 쓴다. 사용자 시험 결과가 아니라 사이트를 평가한 수치다.

몇 개부터 접어 둘지는 찾은 자료에 기준이 없었다. 예제는 처음에 8개를 보여 주는데, 이는 임의로 정한 값이다.

<br/>

## 방법 고르기
| 방법 | 어떻게 동작하나 | 맞는 경우 | 약점 |
|---|---|---|---|
| 작은 스크롤 상자 | 목록 전체를 높이가 고정된 상자 안에 넣는다 | 없음(쓰지 않는다) | Olah(2024)가 지적한 것처럼 몇 개밖에 안 보이고, 상자 안 스크롤이 어렵다 |
| 더 보기 | 처음에는 몇 개만 보이고 버튼으로 나머지를 펼친다 | 수십 개, 둘러보며 고르는 사용자 | 펼치면 결국 긴 목록이다. 찾는 이름이 있을 때 느리다 |
| 목록 안 검색 | 묶음 위의 검색 칸에 치면 체크박스 목록이 좁혀진다 | 15~20개 이상, 이름을 아는 사용자 | 검색 칸, 지우기 버튼, 결과 알림을 함께 만들어야 한다 |
| 자동 완성(콤보박스) | 입력란에 치면 추천 목록이 뜨고, 골라서 하나씩 더한다 | 수백 개 이상, 이름을 아는 사용자 | 무엇이 있는지 둘러보기 어렵다. 키보드와 스크린 리더 처리가 가장 손이 많이 간다 |

맞는 경우의 개수 가운데 15~20개만 Olah(2024)가 든 예이고, 수십 개와 수백 개로 나눈 것은 내 판단이다. Olah의 글은 수백 개짜리 목록에 묶음 안 검색을 권하는 글이므로, 수백 개라도 목록 안 검색이 맞을 수 있다.

예제는 더 보기와 목록 안 검색을 함께 둔 방식과 자동 완성 방식을 조작판에서 바꿔 볼 수 있게 했다. 수십 개라면 더 보기와 목록 안 검색을 함께 두는 편이 둘러보는 사용자와 이름을 아는 사용자를 다 받는다고 보았다(내 판단).

MOJ(영국 법무부) 디자인 시스템의 필터 컴포넌트는 선택지가 긴 목록에 접근 가능한 자동 완성을 권한다. 맞춤 기준으로는 대소문자를 가리지 않고, 문장 부호와 남는 띄어쓰기를 무시하고, "&"와 "and"를 같게 보라고 한다. 예제는 이 가운데 대소문자와 띄어쓰기만 처리하고, 띄어쓰기는 남는 것뿐 아니라 모두 지운다.

<br/>

## 더 보기
### 펼치고 접는 버튼
W3C의 ARIA 작성 지침(APG, ARIA Authoring Practices Guide)에 있는 디스클로저(Disclosure) 패턴은 내용을 접어(숨겨) 두거나 펼쳐(보여) 두는 위젯이다. disclose의 사전적 의미는 드러내다, 밝히다로, 숨어 있던 것을 드러낸다는 뜻이 그대로 이름이 되었다. 버튼은 Enter나 Space로 펼침과 접힘을 바꾸고, 내용이 보이면 버튼의 `aria-expanded` 가 `true`, 숨겨지면 `false` 다. 버튼이 가리키는 내용 영역을 `aria-controls` 로 이을 수 있다(선택 사항).

예제의 버튼은 접혀 있을 때 "브랜드 32개 더 보기", 펼치면 "브랜드 접기"라고 쓴다. 몇 개가 더 있는지 버튼 글자에 넣어 두면, 펼치기 전에 얼마나 긴 목록인지 알 수 있다.

### 무엇을 먼저 보여 줄까
접혀 있을 때는 "상품이 많은 브랜드"라는 제목 아래 상품이 많은 브랜드 8개를 많은 순으로 보여 준다. 많이 찾을 것 같은 쪽을 먼저 내놓는 것이다(내 판단). 펼치면 나머지 32개는 "나머지 브랜드 (가나다순)"이라는 제목 아래 가나다순으로 붙인다. Olah(2024)는 선택지를 묶음의 성격에 맞게 논리적으로 늘어놓으라고 하면서, 제조사는 알파벳순, 온도는 숫자순을 예로 든다. 이름으로 찾는 긴 목록은 이름 순서여야 눈으로 찾기 쉽다. 한글 이름은 `localeCompare(b, 'ko')` 로 가나다순 정렬한다.

### 펼친 뒤 포커스
APG 디스클로저 패턴은 펼친 뒤 포커스를 어디에 둘지 말하지 않는다. 예제의 버튼은 목록 아래에 있어서, 펼치면 새 선택지가 버튼 위에 생긴다. 포커스를 버튼에 그대로 두면 다음 Tab은 펼친 목록이 아니라 그 아래로 가고, 새로 생긴 브랜드를 고르려면 Shift+Tab으로 32개를 거슬러 올라가야 한다. 그래서 예제는 펼치면 새로 보인 첫 브랜드로 포커스를 옮기고, 접으면 버튼에 둔다. [무한 스크롤과 더 보기 버튼](../무한%20스크롤과%20더%20보기%20버튼(Infinite%20Scroll%20and%20Load%20More)/README.md) 노트에서 더 보기를 누르면 새로 붙은 첫 상품으로 옮긴 것과 같은 이유다(내 판단).

대가도 있다. 다시 접으려면 Tab으로 나머지 32개를 지나 버튼까지 내려가야 하고, 포커스가 버튼을 떠나므로 펼쳐졌다는 버튼 상태(`aria-expanded`)는 들리지 않는다. 몇 개만 훑어보고 바로 접으려는 사용자에게는 버튼에 남는 편이 낫다.

<br/>

## 고른 것이 가려지지 않게
접거나 검색으로 좁히면, 이미 고른 브랜드가 목록에서 안 보이게 될 수 있다. 펼쳐서 "가람"을 고른 뒤 접으면 가람은 다시 숨겨지고, 사용자는 가람이 골라져 있다는 것을 잊기 쉽다. 예제는 묶음 맨 위에 "고른 브랜드 2개: 가람, 초롱"을 늘 적어 둔다.

고른 체크박스를 목록 맨 위로 끌어올리는 사이트도 있다. 다만 체크하는 순간 그 체크박스를 옮기면, 포커스가 있던 요소가 자리를 옮겨 키보드 사용자가 어디에 있는지 놓치고 마우스 사용자는 누른 자리에서 항목이 사라진다. 그래서 예제는 체크할 때는 목록을 그대로 두고 맨 위의 글로만 알린다(내 판단).

<br/>

## 목록 안 검색
### Olah(2024)가 꼽은 것
Olah(2024)는 묶음 안 검색에서 사용자가 "1K", "1.2K"처럼 정확한 값을 칠 수 있게 하고, 검색 칸이 내놓는 제안(suggestion)마다 맞는 결과 수를 보여 주며, 검색 칸에 "X" 같은 지우기 수단을 두고, 제안에서 사용자가 치지 않은 부분을 강조하라고 쓴다. 강조 지침은 Baymard의 자동 완성 글을 근거로 들고 있어서, 원래는 자동 완성 제안에 가까운 권고다. 예제는 이것을 좁혀진 체크박스 목록에 옮겨 적용했다.

예제는 검색 칸 옆에 "검색어 지우기" 버튼(×)을 두고, 이름으로 맞은 경우 친 부분은 보통 굵기로, 치지 않은 부분은 굵게 보여 준다. "솔"을 치면 "솔**빛**", "**은**솔", "**해**솔"이 된다. 수는 원래 체크박스마다 붙어 있다.

### 무엇을 맞는 것으로 볼까
예제는 사용자가 친 글을 소문자로 바꾸고 띄어쓰기를 지운 뒤 비교한다. 그래서 "GA RAM"으로도 가람(Garam)을 찾는다. 한글 이름에 더해 영문 이름으로도 찾고, 영문으로 맞은 경우는 "가람 (Garam)"처럼 영문을 함께 보여 준다. 왜 그 브랜드가 나왔는지 알 수 있게 하려는 것이다.

한글은 초성(첫소리)으로 찾게 할 수 있다. 첫소리는 한 글자의 맨 앞 자음으로, "해솔"의 초성은 "ㅎㅅ"이다. 한글 음절은 유니코드에서 `0xAC00`(가)부터 `0xD7A3`(힣)까지 초성, 중성, 종성 순서대로 놓여 있어서, `(코드 - 0xAC00) / 588` 의 몫이 초성 번호가 된다. 588은 중성 21개와 종성 28개(종성 없음 포함)를 곱한 수다. 예제는 친 글이 모두 자음이면 초성끼리 비교한다. 초성 검색은 국내 서비스에서 흔히 보이지만, 사용자 조사나 지침으로 확인한 것은 아니다(확인 필요).

```js
const CHO = 'ㄱㄲㄴㄷㄸㄹㅁㅂㅃㅅㅆㅇㅈㅉㅊㅋㅌㅍㅎ';
function chosung(text) {
  return [...text].map((ch) => {
    const c = ch.charCodeAt(0);
    return c >= 0xac00 && c <= 0xd7a3 ? CHO[Math.floor((c - 0xac00) / 588)] : ch;
  }).join('');
}
chosung('해솔');   // 'ㅎㅅ'
```

### 처음부터 맞는 것을 앞에
글자가 이름 어디에 있든 맞는 것으로 치면, "ㄷ"으로 다솜, 단비, 도담, 들꽃 말고도 바다, 버들, 이든이 함께 나온다. 예제는 이름의 처음부터 맞는 것을 앞에, 중간에서 맞는 것을 뒤에 두고, 각각을 가나다순으로 늘어놓는다. 처음 만든 예제는 맞는 것을 모두 가나다순으로만 늘어놓아서, 영문 "bo"를 치면 이름 중간에 "bo"가 있는 늘봄(Neulbom)이 보람(Boram)보다 앞에 나왔다. 시험을 돌리다 찾았다.

### 결과 수 알림과 없을 때
검색 중에는 접힘과 상관없이 맞는 것을 모두 보여 주고, 더 보기 버튼은 숨긴다. 맞는 수는 숨긴 `role="status"` 문단에 "브랜드 3개"로 알린다. 치는 동안 글자마다 알리지 않도록 0.5초 멈췄을 때 넣는다(0.5초는 임의로 정한 값). 맞는 것이 없으면 목록 자리에 "'없는브랜드'에 맞는 브랜드가 없습니다. 검색어를 줄여 보세요."를 보여 주고 "맞는 브랜드 없음"을 알린다. 검색어의 끝 글자에 받침이 있든 없든 맞도록 조사는 "와/과" 대신 "에"를 쓴다. 검색어 지우기 버튼은 누르면 숨겨지므로 포커스를 검색 칸으로 옮기고 "검색어를 지웠습니다"를 알린다. 이때 기다리던 결과 수 알림이 이 글을 덮어쓰지 않게 먼저 버린다. `type="search"` 입력란은 Chrome이 자체 지우기 버튼을 그려 ×가 두 개 보이므로, 기본 버튼은 CSS로 숨겼다.

## 자동 완성(콤보박스)
### 콤보박스란
combo의 사전적 의미는 조합, 묶음이다. 콤보박스(combobox)는 입력란과 목록 상자를 묶은 것이라 이런 이름이 붙었다. APG 콤보박스 패턴은 콤보박스를 팝업이 딸린 입력 위젯이라고 정의한다. 예제처럼 친 글에 맞는 추천이 목록 상자(listbox) 팝업으로 뜨는 형태를 본다.

### 역할과 속성
APG가 정한 것을 예제에 대 보면 아래와 같다.

- 값을 치는 입력란에 `role="combobox"` 를 준다
- 팝업이 보이지 않으면 `aria-expanded="false"`, 보이면 `true` 다
- `aria-controls` 는 팝업을 가리키며, 팝업이 보일 때만 두면 된다
- `aria-autocomplete="list"` 는 추천이 친 글을 완성하거나 친 글과 논리적으로 맞는 값이라는 뜻이다. 남은 글자를 입력란 안에 미리 채워 보이는 `both`, 친 글과 상관없이 같은 추천을 보이는 `none` 도 있다
- 팝업 안의 선택지에 포커스가 간 것처럼 보이게 할 때는 입력란의 `aria-activedescendant` 를 그 선택지의 id로 둔다. 목록 상자 팝업에서는 실제 DOM 포커스가 입력란에 그대로 있고, 보조 기술의 포커스만 이 속성으로 목록 안을 옮겨 다닌다

```html
<input role="combobox" aria-autocomplete="list" aria-expanded="true"
       aria-controls="combo-list" aria-activedescendant="opt-b5">
<ul role="listbox" id="combo-list">
  <li role="option" id="opt-b4" aria-selected="false">다솜 4개</li>
  <li role="option" id="opt-b5" aria-selected="true">단비 12개</li>
</ul>
```

### 키보드
APG의 목록 상자 팝업 키보드 조작은 아래 화살표가 다음 선택지로, 위 화살표가 이전 선택지로 포커스를 옮기고 고르며, Enter가 포커스된 선택지를 받아들여 팝업을 닫고 값을 입력란에 넣는 것이다. Esc는 팝업을 닫고 포커스를 콤보박스로 돌려준다. 예제는 팝업이 닫혀 있을 때 아래 화살표를 누르면 열고 첫 선택지로 가며, 팝업이 닫힌 상태에서 Esc를 한 번 더 누르면 입력란을 비운다.

팝업이 열려 있고 고른 선택지가 없을 때 위 화살표를 누르면 예제는 첫 선택지로 간다. 이 경우 마지막 선택지로 보내는 구현도 있다.

한글은 입력기(IME)로 자모를 조합해 글자를 만든다. 조합하는 중에 누른 화살표와 Enter는 입력기가 먼저 처리해야 하므로, 예제는 keydown에서 `e.isComposing` 이 참이면 아무것도 하지 않는다.

마우스로 선택지를 누를 때는 `mousedown` 의 기본 동작을 막는다. 그러지 않으면 누르는 순간 입력란이 포커스를 잃어 팝업이 먼저 닫히고, 클릭이 선택지에 닿지 않는다.

### 여러 개 고르기는 칩으로
APG는 콤보박스를 하나만 고르는 위젯으로 보고, 팝업 안에서는 포커스가 가는 선택지가 곧 고른 것(selection follows focus)이라고 쓴다. 여러 브랜드를 고르는 필터에는 그대로 맞지 않는다. 예제는 Enter로 받아들일 때마다 그 브랜드를 아래 "고른 브랜드" 목록에 칩으로 더하고(칩은 [모아서 적용하는 필터](../모아서%20적용하는%20필터(Batch%20Filters%20with%20an%20Apply%20Button)/README.md) 노트에서 본, 값 하나를 담은 둥근 단추다), 입력란을 비우고 팝업을 닫는다. 고른 브랜드는 다음 추천에서 뺀다. 칩은 모아서 적용하는 필터 노트와 같이 "단비 필터 지우기"라는 이름의 버튼이고, 지우면 다음 칩, 없으면 앞 칩, 그것도 없으면 입력란으로 포커스를 옮긴다. 이 구성은 APG에 있는 것이 아니라 내 판단이고, 여러 개를 고르는 콤보박스에 대한 지침은 찾지 못했다(확인 필요).

### 추천 수 알림
추천이 몇 개 떴는지는 숨긴 `role="status"` 문단에 "추천 브랜드 6개. 아래 화살표로 고르세요"로 알린다. 목록 안 검색과 같이 0.5초 멈췄을 때 넣는다. APG 콤보박스 패턴은 이 알림을 요구하지 않는다. 팝업이 열렸다는 것은 `aria-expanded` 로 표시되지만 입력 중에 이것이 읽히는지는 들어 보지 않았고(확인 필요), 몇 개인지와 어떻게 고르는지는 이 속성으로 전해지지 않으므로 넣었다(내 판단). 팝업이 닫히면 기다리던 알림은 버리고 알림 글도 비운다. 처음 만든 예제는 "ㄷ"을 치고 0.5초 안에 지우면, 팝업이 닫힌 뒤에 "추천 브랜드 7개"가 나왔다(리뷰에서 찾았다). 글을 비워 두면 다시 열었을 때 수가 같아도 다시 읽힌다.

## 예제
[example.html](./example.html)은 가상의 브랜드 40개(가람, 단비, 해솔 등, 영문 이름 포함)에서 고르는 예제다. HTML, CSS, 약간의 자바스크립트만 한 파일에 담았으므로 파일을 더블클릭하거나 브라우저 창에 끌어다 놓으면 바로 열린다. 고른 결과는 화면 안에서 바로 적용한다. 주소에 담는 방법은 [같은 화면에서 주소만 바뀔 때](../같은%20화면에서%20주소만%20바뀔%20때(URL%20Changes%20Within%20a%20Screen)/README.md) 노트에 있어 이 예제에는 넣지 않았다.

### 무엇을 보여 주나
조작판에서 "더 보기와 목록 안 검색"과 "자동 완성(콤보박스)"을 바꿀 수 있다. 두 방식은 고른 브랜드를 함께 쓰므로, 한쪽에서 고른 것이 다른 쪽에도 체크나 칩으로 나온다. 방식을 바꿔도 목록 쪽의 검색어와 펼침 상태는 그대로 남고, 숨겨지는 쪽의 기다리던 알림은 버린다. 조작판에는 고른 브랜드, 지금 보이는 선택지 수, 포커스가 있는 곳, 입력란의 `aria-activedescendant` 값, 상태 알림 글자가 나온다. 자동 완성에서 화살표를 누르면 포커스가 있는 곳은 입력란 그대로이고 `aria-activedescendant` 만 바뀌는 것을 볼 수 있다.

### 확인한 것과 못 한 것
2026-11-04에 Playwright로 Chromium 계열 브라우저(설치된 Chrome 156.0.8078.48)를 띄워 파일을 file:// 주소로 열고 56가지를 확인했다. 콘솔 오류는 없었다.

- 처음에는 "상품이 많은 브랜드" 제목 아래 8개가 상품 많은 순으로 보이고 버튼이 "브랜드 32개 더 보기", `aria-expanded="false"` 다. 펼치면 40개가 보이고 나머지는 가나다순이며, 포커스가 새로 보인 첫 브랜드로 간다. 접으면 포커스가 버튼에 남고, 펼쳐서 고른 브랜드가 숨겨져도 맨 위 글에 남는다
- "솔"은 솔빛, 은솔, 해솔을 찾고 "빛"이 굵게 나온다. "ㅎㅅ"은 해솔, 햇살, 호수를, "GA RAM"은 가람 (Garam)을 찾는다. 결과 수 알림은 치는 즉시가 아니라 멈춘 뒤 "브랜드 3개"로 나온다. 맞는 것이 없으면 안내와 "맞는 브랜드 없음"이 나온다. 지우기 버튼은 포커스를 검색 칸으로 돌려주고, 직전에 친 검색어의 알림이 "검색어를 지웠습니다"를 덮어쓰지 않는다. 검색 결과에서 고른 것은 검색을 지워도 남는다
- 체크박스의 접근 가능한 이름 사이에 띄어쓰기가 있다("가람 1개")
- 콤보박스는 `role="combobox"` 이고, 치면 `aria-expanded` 가 `true` 가 되고 `aria-controls` 가 생긴다. "ㄷ"은 다솜, 단비, 도담, 들꽃, 바다, 버들, 이든 순으로, 처음부터 맞는 것이 앞에 나온다. 아래 화살표로 `aria-activedescendant` 와 `aria-selected` 가 옮겨 가고, DOM 포커스는 입력란에 남는다. Enter로 고르면 팝업이 닫히고 입력란이 비며, 고른 브랜드는 다음 추천에 나오지 않는다. Esc 한 번은 닫기만, 두 번은 입력란을 비운다. 마우스로 선택지를 눌러도 고르고 포커스가 입력란에 남는다. 칩을 지우면 다음 칩으로 포커스가 간다. "ㅂ"을 치고 0.15초 만에 지우면 0.7초 뒤에도 추천 수 알림이 나오지 않는다
- 방식을 바꾸면 숨겨지는 목록 쪽의 알림 글이 비워진다. 콤보박스에서 고른 것이 목록 방식의 체크와 맞고, 375px 너비에서 두 방식 모두 가로 스크롤이 없다

시험을 돌리다 예제 버그 둘을 찾아 고쳤다. 앞에 쓴 정렬 문제와, 검색이 끝난 뒤 숨긴 검색 결과 목록이 남아 같은 브랜드의 체크박스가 두 벌 있던 문제다. 리뷰에서는 닫힌 뒤 나오는 추천 수 알림, 덮어써지는 지우기 알림, 겹쳐 보이는 지우기 버튼, 받침에 따라 틀리는 조사, 한글 조합 중 키 처리를 찾아 고쳤다.

실제 스크린 리더(NVDA, VoiceOver, TalkBack 등)로 듣는 확인은 하지 않았다. `aria-activedescendant` 로 옮겨 간 선택지가 읽히는지, 추천 수 알림과 선택지 읽기가 겹칠 때 어떻게 들리는지, 펼친 뒤 첫 브랜드로 포커스가 옮겨 갈 때 무엇이 읽히는지는 확인하지 못했다(확인 필요). 휴대폰의 화면 자판으로 초성을 칠 때, 데스크톱 한글 입력기로 조합하는 중에 화살표나 Enter를 누를 때의 실제 동작도 시험하지 않았다. Playwright의 글자 입력은 입력기를 거치지 않기 때문이다(확인 필요). Chrome 외 브라우저도 시험하지 않았다.
