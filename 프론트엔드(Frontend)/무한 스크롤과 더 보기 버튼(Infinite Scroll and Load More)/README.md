## 무한 스크롤과 더 보기 버튼이란 ?
- 무한 스크롤(Infinite Scroll)은 목록 끝에 가까워지면 다음 묶음을 저절로 불러와 이어 붙이는 방식이고, 더 보기 버튼(Load More)은 사용자가 버튼을 눌렀을 때만 다음 묶음을 이어 붙이는 방식이다
- 둘 다 쪽 번호 링크로 목록을 나눠 보여 주는 방식(이 노트에서는 페이지 번호 방식이라 부른다)과 달리, 불러온 묶음을 한 화면에 계속 쌓는다. 차이는 다음 묶음을 누가 부르느냐, 화면이냐 사용자냐다. 서버에서 묶음을 끊어 받는 일은 세 방식 모두 페이지네이션(Pagination)이다
- 이 노트는 둘을 고르는 기준, 그리고 이어 붙일 때 주소, 포커스, 알림, 돌아오기, 바닥글을 어떻게 다룰지를 정리한다. 서버 쪽에서 묶음을 나누는 방법(오프셋, 커서)은 [페이지네이션](../../CS_Basic/WEB/페이지네이션(Pagination)/README.md) 노트에 있다

scroll의 사전적 의미는 두루마리다. 종이를 길게 이어 말아 두고, 읽을 만큼 풀어 가며 보는 책이다. 화면에서 스크롤은 창보다 긴 내용을 두루마리처럼 위아래로 밀어 가며 보는 일이 되었다. 무한 스크롤은 끝없이 풀려 나오는 두루마리다. 다 풀었다 싶으면 뒤에 종이가 더 붙어 나온다.

회전 초밥집과 일반 식당의 차이와 같다. 회전 초밥은 앉아 있기만 하면 접시가 계속 지나가서 둘러보기에는 좋지만, 몇 접시가 더 나올지는 알 수 없다. 더 보기 버튼은 "한 접시 더 주세요"라고 말할 때만 나오는 방식이다. 원하는 만큼 먹고, 그만 먹고 싶으면 말하지 않으면 된다.

## 어떻게 고를까
### 무한 스크롤이 맞는 곳과 맞지 않는 곳
NN/g의 Neusesser(2022)는 무한 스크롤이 특별한 목표 없이 비슷한 항목을 훑어보는 상황(오락, 뉴스, 소셜 미디어)에 가장 잘 맞는다고 쓴다. 반대로 특정한 것을 찾아야 하거나, 긴 목록에서 항목을 비교해야 하거나, 위쪽 몇 개만 보면 되는 경우에는 권하지 않는다. 느린 연결을 쓰는 사용자가 많거나 접근성이 필요한 사용자가 자주 쓰는 사이트에도 맞지 않는다고 쓴다.

같은 글은 더 보기 버튼을 절충안으로 소개한다. 더 보기 버튼을 두면 무한 스크롤의 사용성 문제 일부가 줄어든다고 하면서, 바닥글에 닿을 수 있고, 더 있다는 것이 보이며, 데이터가 제한된 사용자에게도 낫다는 점을 든다. 대신 한 번씩 눌러야 하는 비용이 늘어난다.

### 한눈에 비교
아래는 위 글과 아래 절들의 내용을 모은 정리다. 예제에서 세 방식을 바꿔 가며 같은 목록으로 비교할 수 있다.

| 기준 | 페이지 번호 | 더 보기 버튼 | 무한 스크롤 |
|---|---|---|---|
| 다음 묶음을 부르는 쪽 | 사용자(쪽 번호) | 사용자(버튼) | 화면(스크롤 위치) |
| 바닥글에 닿기 | 언제나 | 언제나(버튼 바로 뒤) | 목록을 다 불러와야 |
| 특정 위치로 건너뛰기 | 쪽 번호로 가능 | 어렵다 | 어렵다 |
| 지금 어디쯤인지 | 쪽 번호가 알려 준다 | 직접 표시해야 한다 | 직접 표시해야 한다 |
| 둘러보기의 편함 | 쪽마다 끊긴다 | 한 번씩 누른다 | 가장 매끄럽다 |

## 무한 스크롤이 남기는 문제
### 바닥글에 닿을 수 없다
NN/g는 더 보기 버튼이 없는 무한 스크롤이 웹사이트 바닥글(Footer)에 닿는 것을 불가능하게 만들 수 있다고 쓴다. 바닥글에는 고객센터, 이용약관 같은 링크가 있는 경우가 많다. Roselli(2014)는 사용자가 닿을 수 없는 바닥글을 보여 주는 것은 닿을 수 있다고 거짓말하는 셈이라고 쓴다.

예제에서 이것을 키보드로 재 보았다. 목록의 첫 상품에서 Tab만 눌러 바닥글의 "고객센터"까지 가는 데, 더 보기 모드는 11번(나머지 상품 9개, 버튼, 고객센터)이면 닿았다. 무한 스크롤 모드는 Tab으로 상품을 지날 때마다 포커스를 따라 화면이 내려가고 그때마다 다음 묶음이 붙어서, 상품 60개를 모두 불러오고 60번(나머지 상품 59개, 고객센터)을 눌러서야 닿았다(2026-11-04, Chrome 156). 이 측정은 묶음을 다 불러오기를 기다린 뒤 다음 Tab을 눌렀다. 불러오는 0.4초 사이에 마지막 상품에서 Tab을 누르면 바닥글로 넘어갈 수도 있지만, 불러오기를 기다리며 Tab을 누르는 사용자라면 목록이 끝나지 않는 한 닿지 못한다.

### 돌아왔을 때 제자리가 아니다
상품을 눌러 상세를 보고 뒤로 가기를 누르면, 사용자는 보던 자리로 돌아오기를 기대한다. NN/g는 목록과 상세를 오가는 동안 목록의 위치를 저장하지 않으면 사용자가 맨 위로 돌아가 다시 스크롤해야 한다고 쓴다. 이어 붙인 목록은 처음 열 때의 첫 묶음만 다시 그려지기 쉬워서, 30번째를 보다 돌아오면 10개만 있는 목록의 맨 위에 서게 된다(내 판단). Roselli(2014)의 점검 목록 첫 질문도 사용자가 뒤로 가기를 눌러 정확히 같은 자리로 돌아올 수 있는가다.

### 끝인지 알 수 없다
NN/g는 아래에서 내용을 불러오는 동안 사용자가 내용의 끝에 닿았다고 착각할 수 있다고 쓴다. 불러오는 중이라는 표시와, 정말 끝났을 때의 "모든 상품을 보았습니다" 같은 표시가 둘 다 필요한 이유다.

### 스크린 리더와 키보드
NN/g는 키보드 사용자가 끝에 닿으려면 긴 목록을 Tab으로 다 지나야 하고, 스크린 리더 사용자는 목록의 첫 묶음만 알게 된다고 쓰면서, ARIA의 feed 역할로 스크린 리더 지원이 나아졌다고 덧붙인다. feed는 아래 접근성 절에서 본다.

### 그 밖의 점검 질문
Roselli(2014)는 무한 스크롤을 만들었다면 스스로 물어볼 질문 열한 가지를 든다. 뒤로 가기로 같은 자리에 돌아오는가, 바닥글이 있는가, 키보드 사용자가 페이지의 다른 내용에 모두 닿을 수 있는가는 위 절들에서 보았다. 자동으로 불러오기를 끄고 일반 쪽 나누기로 바꿀 방법이 있는가는 아래 "자동으로 계속 불러오지 않게 하기" 절에서 본다. 나머지 가운데 화면 쪽과 관련된 것은 자바스크립트가 깨졌을 때 쪽 나누기가 있는가, 페이지의 특정 위치를 주소로 공유할 수 있는가, 몇 쪽 앞으로 빠르게 건너뛸 수 있는가, 묶음 몇 개만 불러와도 메모리 사용량이 크게 늘지 않는가다. 마지막 셋은 사용자 시험을 했는가, 실제 요구에서 나왔는가, 성공을 잴 분석 도구가 있는가를 묻는다.

## 더 보기 버튼을 만들 때
### 누른 뒤 포커스
더 보기 버튼을 누르면 버튼 위에 새 항목이 붙고 버튼은 아래로 밀려난다. 포커스가 버튼에 남으면, 키보드 사용자는 새로 붙은 항목을 보려고 Shift+Tab으로 거슬러 올라가야 하고, 스크린 리더 사용자는 무엇이 붙었는지 모른 채 버튼에 머문다. 예제는 새로 붙은 묶음의 첫 항목(상품 11)으로 포커스를 옮긴다. 이 방식은 [같은 화면에서 주소만 바뀔 때](../같은%20화면에서%20주소만%20바뀔%20때(URL%20Changes%20Within%20a%20Screen)/README.md) 노트에서 페이지 번호를 누를 때 결과 제목으로 포커스를 옮긴 것과 같은 판단이다. 사용자가 다음 내용을 읽으려고 누른 버튼이기 때문이다(내 판단).

반대로 포커스를 버튼에 남기고 상태 메시지로만 알리는 방식도 쓰인다. 몇 묶음을 연달아 불러오려는 사용자에게는 버튼에 남는 편이 빠르다. 어느 쪽이 나은지 다룬 연구나 지침은 이번에 찾지 못했다(확인 필요).

### 몇 개를 보았는지 보여 준다
NN/g는 전체 가운데 몇 개를 보았는지 보여 주는 예(Asos)를 좋은 사례로 든다. 예제는 목록 위에 "전체 60개 가운데 1~20번째"를, 버튼에 "상품 더 보기 (20/60)"를 보여 준다. 다 불러오면 버튼을 숨기고 "모든 상품을 보았습니다."를 보여 준다.

### 불러오는 중과 두 번 누르기
불러오는 동안 버튼에는 `disabled` 대신 `aria-disabled="true"` 를 두고 버튼 아래에 "불러오는 중"을 보여 주며, 그동안 들어온 클릭은 무시한다. 방금 누른 버튼에 `disabled` 를 걸면 포커스가 버튼을 떠날 수 있다(브라우저별 동작은 확인 필요). 버튼을 막지 않는 일반적인 이유는 [폼 설계](../폼%20설계(Form%20Design)/README.md) 노트의 제출 버튼을 비활성화하지 않는다 절에 있다. 예제에서 불러오는 중에 한 번 더 눌러도 한 묶음만 붙었다.

## 무한 스크롤을 만들 때
### 끝에 가까워졌는지 알아채기
목록 끝에 눈에 보이지 않는 요소를 하나 두고, 그 요소가 화면 가까이 오면 다음 묶음을 부른다. 이런 요소를 흔히 sentinel이라고 부르는데, 사전적 의미는 보초다. 목록 끝에 세워 둔 보초가 화면에 들어왔다고 알려 주는 셈이다. 스크롤 이벤트로 매번 위치를 재는 대신 `IntersectionObserver` 를 쓴다. 스크롤 이벤트는 스크롤하는 동안 아주 자주 일어나서 그때마다 위치를 재면 계산이 반복되지만, 관찰자는 겹침 상태가 바뀔 때만 알려 준다(내 판단). MDN은 이 API가 대상 요소가 조상 요소나 화면(viewport)과 겹치는 변화를 비동기로 지켜보는 방법이라고 설명하고, 쓰임의 예로 스크롤할수록 내용을 불러와 그리는 무한 스크롤을 든다. `rootMargin` 은 겹침을 계산하기 전에 기준 영역을 늘리거나 줄이는 여백이다. 2019년 3월부터 주요 브라우저에서 쓸 수 있다고 MDN은 쓴다.

```js
const observer = new IntersectionObserver((entries) => {
  if (entries.some((e) => e.isIntersecting)) loadMore();
}, { rootMargin: '0px 0px 300px 0px' }); // 화면 아래 300px 앞에서 미리 부른다
observer.observe(document.getElementById('sentinel'));
```

예제는 아래쪽 여백을 300px로 두어, 보초가 화면에 들어오기 300px 전에 다음 묶음을 부른다. 300px는 이 예제에서 임의로 정한 값이다. 관찰자는 겹침 상태가 바뀔 때만 알려 주므로, 한 묶음을 붙인 뒤에도 보초가 여전히 화면 가까이 있으면(세로로 긴 화면, 축소한 화면) 다시 알려 주지 않는다. 그러면 버튼이 없는 무한 스크롤은 그 자리에서 멈춘다. 예제는 묶음을 붙일 때마다 보초의 위치를 직접 재서, 아직 가까우면 한 묶음을 더 부른다. 높이 2600px 화면에서 열었을 때 상품 60개를 모두 불러올 때까지 이어서 불렀다.

모드를 바꾸거나 상세에서 돌아와 목록을 다시 그리는 동안에는 관찰자를 떼어 두었다가 다 그린 뒤에 붙인다. 목록을 비운 순간 보초가 화면에 들어와 관찰자가 다음 묶음을 부르면, 다시 그린 목록과 겹치거나 사이가 빠지기 때문이다. 이런 경쟁 상태(race condition)는 페이지 번호에서 무한 스크롤로, 더 보기로 30개를 본 뒤 무한 스크롤로 바꾸는 경로에서 드러나므로, 두 경로를 시험에 넣었다.

### 포커스는 옮기지 않는다
무한 스크롤은 사용자가 부르지 않았는데 저절로 붙는다. 이때 포커스를 새 항목으로 옮기면 읽던 자리를 빼앗는다. 예제는 무한 스크롤에서는 포커스를 건드리지 않고, 상태 메시지로 몇 개를 더 불러왔는지만 알린다.

### 자동으로 계속 불러오지 않게 하기
Roselli(2014)는 자동으로 불러오기를 끄고 일반 쪽 나누기로 바꿀 방법이 있는지를 묻는다. 흔한 절충은 처음 몇 번은 자동으로 붙이다가 그 뒤로는 더 보기 버튼을 보여 주는 방식이다(내 판단, 이번에 이 방식을 다룬 1차 자료는 확인하지 못했다). 그러면 바닥글에도 닿을 수 있다. 예제는 세 방식을 조작판에서 바꾸게만 했고, 이 섞은 방식은 만들지 않았다.

WCAG 2.2의 2.2.2 일시 정지, 정지, 숨기기(Pause, Stop, Hide, A)는 저절로 시작되고 다른 내용과 함께 보이는 자동 갱신 정보를 멈추거나 숨기거나 갱신 빈도를 조절할 방법을 요구한다. 이해 문서는 자동 갱신 내용을 정해진 시간 간격에 따라 바뀌는 내용으로 정의하고, 무한 스크롤을 이름으로 다루지는 않는다. 스크롤에 따라 붙는 무한 스크롤이 이 기준의 대상인지는 이번에 판단하지 못했다(확인 필요).

## 주소와 돌아오기
### 몇 개까지 보았는지를 주소에 남긴다
상세에 다녀오거나 새로 고침해도 같은 만큼 보이게 하려면, 지금 몇 개까지 보았는지를 어딘가에 남겨야 한다. 예제는 묶음을 붙일 때마다 `history.replaceState` 로 주소를 `?count=20` 처럼 고쳐 쓴다. 기록을 쌓지 않고 고쳐 쓰는 이유는 [같은 화면에서 주소만 바뀔 때](../같은%20화면에서%20주소만%20바뀔%20때(URL%20Changes%20Within%20a%20Screen)/README.md) 노트의 pushState와 replaceState 절과 같다. 묶음마다 기록을 쌓으면 뒤로 가기를 묶음 수만큼 눌러야 목록을 벗어날 수 있다.

주소를 열면 그 개수만큼 한 번에 다시 받아 그린다. 실제 서비스에서 개수가 아주 많으면 한 번에 다시 받기 무거우므로, 다른 방법(받아 둔 목록을 기억해 두기 등)이 필요할 수 있다(내 판단).

### 스크롤 위치와 포커스를 되살린다
상세로 떠나기 직전에 스크롤 위치와 누른 상품을 지금 기록 항목에 적어 두고, 뒤로 가기로 돌아오면 목록을 다시 그린 뒤 그 위치로 스크롤하고 누른 상품 링크로 포커스를 돌려준다. 예제에서 상품 25를 눌렀다가 뒤로 가기를 누르면 30개가 다시 그려지고, 떠날 때의 위치(951px)로 돌아오며 포커스가 상품 25에 간다. 그 노트처럼 `history.scrollRestoration = 'manual'` 로 브라우저의 자동 복원을 끄고, 목록을 다 그린 뒤 코드가 위치를 옮긴다. 스크롤 위치를 직접 되살리는 방법은 [화면 전환 시 제목과 포커스 옮기기](../화면%20전환%20시%20제목과%20포커스%20옮기기(Title%20and%20Focus%20on%20Route%20Change)/README.md) 노트의 스크롤 위치 절에 있다. 그 노트는 뒤로 가기 때 떠났던 링크로 포커스를 되돌리는 방법을 본문에 적기만 하고 만들지 않았는데, 이 예제가 그 방식이다.

## 접근성
### 불러온 결과를 알린다
더 보기든 무한 스크롤이든 새 항목이 붙은 것은 눈으로만 보인다. 예제는 화면에 보이지 않는 `role="status"` 문단에 "상품 10개를 더 불러왔습니다. 전체 60개 가운데 20개"를, 마지막 묶음에서는 "모든 상품 60개를 보았습니다"를 넣는다. 상태 메시지의 기준(WCAG 4.1.3)은 [같은 화면에서 주소만 바뀔 때](../같은%20화면에서%20주소만%20바뀔%20때(URL%20Changes%20Within%20a%20Screen)/README.md) 노트에 있다.

### 불러오는 동안 aria-busy
예제는 묶음을 받아 붙이는 동안 목록에 `aria-busy="true"` 를 걸었다가 다 붙이면 뗀다. 아래 feed 패턴이 이렇게 하라고 쓰는데, 예제는 feed 역할 없이 일반 목록(`ul`)에 같은 속성만 빌려 썼다. 일반 목록에서 `aria-busy` 가 스크린 리더에 어떤 차이를 만드는지는 확인하지 못했다(확인 필요).

### feed 패턴
feed의 사전적 의미는 먹이를 대 주다, 공급하다이다. 새 글이 계속 공급되는 목록을 피드라고 부른다. WAI-ARIA 작성 지침(APG, ARIA Authoring Practices Guide)의 feed 패턴은 스크롤하면 새 내용 묶음을 저절로 불러오는 페이지 영역을 위한 것이다. 목록을 감싼 요소에 `role="feed"`, 각 내용 단위에 `role="article"` 을 준다. 각 article에는 `aria-posinset` 으로 몇 번째인지, `aria-setsize` 로 전체가 몇 개인지(모르면 `-1`)를 주고, 여러 번에 걸쳐 article을 더하거나 뺄 때는 feed에 `aria-busy="true"` 를 두었다가 끝나면 `false` 로 되돌린다. 되돌리지 않으면 일부 보조 기술 사용자가 바뀐 내용을 알지 못할 수 있다고 쓴다.

feed 안에 포커스가 있을 때의 키보드 조작도 정해 둔다. Page Down과 Page Up은 다음과 이전 article로, Control+End는 feed 뒤의 첫 포커스 요소로, Control+Home은 feed 앞의 첫 포커스 요소로 포커스를 옮긴다. Control+End가 무한 스크롤의 바닥글 문제를 키보드 사용자에게 풀어 주는 장치다. APG는 스크린 리더처럼 읽기 모드가 있는 보조 기술이 feed 안에서 읽기 모드로 움직여도 새 article을 믿을 만하게 불러올 수 있게 하는 것이 이 패턴의 약속이라고 쓴다.

예제는 상품 목록이 짧은 항목의 목록이라 feed가 아니라 `ul` 로 만들었다. feed는 소셜 미디어 글처럼 하나하나가 읽을거리인 article에 맞는 패턴으로 보인다(내 판단).

## 예제
[example.html](./example.html)은 가짜 상품 60개를 한 묶음에 10개씩 불러오는 예제다. HTML, CSS, 약간의 자바스크립트만 한 파일에 담았으므로 파일을 더블클릭하거나 브라우저 창에 끌어다 놓으면 바로 열린다. 묶음은 0.4초 걸리는 가짜 요청으로 받는다. 목록 아래에는 고객센터 링크가 있는 바닥글이 있다.

### 무엇을 보여 주나
조작판에서 목록을 이어 보는 방식을 페이지 번호, 더 보기 버튼(기본), 무한 스크롤 가운데 하나로 고른다. 조작판 아래에는 주소의 쿼리스트링, 포커스가 있는 곳, 상태 알림 글자, 가짜 요청을 보낸 횟수(이어 붙이기, 쪽 넘기기, 다시 그리기를 모두 센다)가 나온다.

더 보기 모드에서는 버튼을 누르면 10개가 붙고 포커스가 새 묶음의 첫 상품으로 가며, 주소가 `?count=20` 으로 고쳐 써진다. 상품을 눌러 상세를 본 뒤 뒤로 가기를 누르면 보던 개수, 스크롤 위치, 포커스가 돌아온다. 새로 고침해도 개수가 유지된다. 무한 스크롤 모드에서는 아래로 스크롤하면 저절로 묶음이 붙고 바닥글이 계속 밀려나며, 포커스는 움직이지 않는다. 불러오는 동안에는 목록 아래에 "불러오는 중"이 보인다. 페이지 번호 모드는 [같은 화면에서 주소만 바뀔 때](../같은%20화면에서%20주소만%20바뀔%20때(URL%20Changes%20Within%20a%20Screen)/README.md) 노트의 예제와 같게, 범위를 넘는 쪽 번호로 열면 주소를 마지막 쪽으로 고쳐 쓰고, 쪽 번호를 누르면 기록을 쌓고 목록 제목으로 포커스를 옮기며 탭 제목에 쪽을 붙인다.

조작 방식은 주소에 담지 않았다. 방식을 바꾸면 목록을 처음부터 다시 그린다.

### 확인한 것과 못 한 것
2026-11-04에 Playwright로 Chromium 계열 브라우저(설치된 Chrome 156.0.8078.48)를 띄워 파일을 file:// 주소로 열고 44가지를 확인했다. 콘솔 오류는 없었다. 더 보기 버튼이 불러오는 동안 목록에 `aria-busy` 가 걸리고 버튼에 `disabled` 가 붙지 않는 것, 불러오는 중에 한 번 더 눌러도 한 묶음만 붙는 것, 포커스가 새 묶음의 첫 상품으로 가는 것, 상태 알림 글자, 주소가 기록을 쌓지 않고 `?count=` 로 고쳐 써지는 것을 확인했다. 상세에 다녀오면 개수(30개), 스크롤 위치(951px), 누른 상품의 포커스가 돌아오는 것, 새로 고침 뒤에도 개수가 남는 것, 60개를 다 불러오면 버튼이 사라지고 끝 안내가 나오는 것, 더 보기 모드에서 버튼 바로 뒤 Tab으로 바닥글에 닿는 것도 확인했다. 무한 스크롤 모드에서 처음 열면 저절로 한 묶음이 더 붙고, 높이 2600px 화면에서는 보초가 화면 밖으로 밀려날 때까지(이 경우 60개 전부) 이어서 불러오며, 페이지 번호나 더 보기 30개에서 무한 스크롤로 바꿔도 상품이 1번부터 빠짐없이 겹치지 않게 이어지고, 무한 스크롤에서 상세를 다녀와도 순서가 맞으며, 아래로 스크롤하면 더 붙으며 바닥글이 밀려나고, 포커스가 움직이지 않고, 끝까지 가면 60개와 끝 안내가 나오는 것, 페이지 번호 모드의 동작과 범위를 넘는 `?page=9` 가 `?page=6` 으로 고쳐지는 것, 375px 너비에서 가로 스크롤이 생기지 않는 것도 확인했다. 바닥글까지의 Tab 횟수(더 보기 11번, 무한 스크롤 60번)는 별도 스크립트로 쟀다.

실제 스크린 리더(NVDA, VoiceOver, TalkBack 등)로 듣는 확인은 하지 않았다. 새 묶음의 첫 상품으로 포커스를 옮기는 것과 상태 알림이 함께 일어날 때 어떤 순서로 읽히는지, 무한 스크롤에서 스크린 리더의 읽기 모드로 목록을 따라 내려갈 때 새 묶음이 불리는지는 확인하지 못했다(확인 필요). Chrome 외의 브라우저, 실제 휴대폰의 터치 스크롤, 느린 연결, 아주 긴 목록의 메모리 사용량은 시험하지 않았다.
