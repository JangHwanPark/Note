## 무엇이 문제인가
- 페이지를 새로 불러오지 않고 화면만 바꾸는 앱에서는, 브라우저가 페이지를 열 때 해 주던 일(탭 제목 바꾸기, 새 페이지 알리기, 포커스와 스크롤을 처음으로 되돌리기)이 저절로 일어나지 않는다
- 그래서 화면 이동이 눈에는 보여도 스크린 리더 사용자와 키보드 사용자에게는 아무 일도 없었던 것처럼 느껴질 수 있다
- 이 노트는 화면이 바뀔 때 제목, 포커스, 화면 이름 알림, 스크롤을 어떻게 다룰지와 프레임워크가 무엇을 대신해 주는지를 정리한다. 특정 라우터의 구현은 다루지 않는다

이런 앱을 단일 페이지 애플리케이션(SPA, Single Page Application)이라고 부른다. 처음 한 번만 HTML 문서를 받고, 이후에는 자바스크립트가 주소와 내용을 바꾼다. 이렇게 브라우저 안에서 주소에 맞는 화면을 골라 그리는 일을 클라이언트 쪽 라우팅(Client-side Routing)이라고 한다. route의 사전적 의미는 길, 노선이다. 라우팅은 들어온 주소를 보고 어느 길(어느 화면)로 보낼지 정하는 일이다.

focus의 사전적 의미는 초점이다. 렌즈의 초점이 맞은 한 곳만 또렷하게 보이듯, 화면에서 포커스(Focus)는 지금 키보드 입력을 받는 단 하나의 요소다. 스크린 리더는 대개 포커스가 간 요소를 읽고, Tab 키는 포커스가 있는 곳에서부터 다음 요소로 간다. 그래서 화면이 바뀌었을 때 포커스가 어디 있느냐가 다음에 무엇을 듣고 어디서부터 움직이느냐를 정한다.

엘리베이터와 같다. 층에 서면 "3층입니다" 하는 안내 방송이 나오고 문이 열린다. 방송 없이 문만 조용히 열리면, 눈으로 층 표시를 볼 수 없는 사람은 내려야 할 층인지 알 수 없다. 화면을 바꿀 때 제목을 바꾸고 화면 이름을 알리는 일은 이 안내 방송을 직접 만들어 넣는 일이다.

## 페이지를 새로 열 때 브라우저가 해 주던 일
### 셋이 함께 일어난다
링크를 눌러 새 HTML 문서를 받으면 세 가지가 함께 일어난다. 탭 제목이 새 문서의 `<title>` 로 바뀌고, 스크린 리더가 그 제목을 읽어 페이지가 바뀌었다는 것을 알리며, 포커스와 스크롤이 새 문서의 처음에서 시작한다. Next.js 문서도 서버가 그린 페이지 사이를 오갈 때는 페이지가 열리면서 스크린 리더 같은 보조 기술이 페이지 제목을 읽어 바뀌었다는 것을 알게 한다고 쓴다.

SPA에서 화면을 바꾸는 것은 문서 안의 내용 일부를 바꿔 끼우는 일이라서 이 셋 가운데 어느 것도 저절로 일어나지 않는다(내 판단, 아래 예제에서 Chrome으로 확인). 아래 절들은 이 셋을 하나씩 직접 해 주는 방법이다.

### 아무것도 하지 않으면
예제의 조작판에서 "내용만 바꾼다"를 고르고 화면을 옮겨 보면 두 가지가 드러난다. 첫째, 탭 제목이 처음 연 화면의 제목("홈 - 예제 상점")에 그대로 머문다. 둘째, 포커스가 어디로 갈지가 우연에 맡겨진다. 머리글 메뉴의 링크를 눌렀다면 포커스는 그 링크에 남아 있어, Tab을 누르면 새 화면의 처음이 아니라 메뉴의 다음 링크로 간다. 본문 안의 상품 링크를 눌렀다면 그 링크가 새 화면으로 바뀌며 사라지므로 포커스가 `body` 로 떨어진다. 어느 쪽이든 스크린 리더는 새 화면에 대해 아무것도 읽지 않을 수 있다.

## 제목 바꾸기
### 화면마다 제목을 단다
WCAG 2.2의 2.4.2 페이지 제목(Page Titled, A)은 웹 페이지에 주제나 목적을 설명하는 제목을 두라고 요구한다. 이해 문서는 같은 주소 아래에서 내용이 동적으로 바뀌는 단일 페이지 애플리케이션이라면, 지금 보이는 화면의 내용이나 주제를 반영하도록 제목도 동적으로 바꿔야 한다고 쓴다. 제목은 사용자가 페이지 내용을 읽지 않고도 지금 어디 있는지 알게 해 준다고 설명한다.

```js
document.title = '무선 키보드 - 상품 목록 - 예제 상점';
```

### 순서는 구체적인 것부터
WCAG 이해 문서는 제목 안의 순서를 규칙으로 정하지 않는다. 예로 든 제목도 WAI-ARIA 작성 지침(APG, ARIA Authoring Practices Guide)의 예제 페이지는 "Alert Dialog Example | APG | WAI | W3C"처럼 구체적인 것을 앞에 두고, 은행 예는 "Bank XYZ, December 2005 statement..."처럼 사이트 이름을 앞에 둔다. 이 노트의 예제는 구체적인 것을 앞에 두었다. 탭이 여러 개 열려 좁아지면 앞부분만 보이고, 스크린 리더도 앞에서부터 읽으니 화면마다 다른 부분이 먼저 나오는 편이 낫다(내 판단).

### 데이터를 받은 뒤에 단다
상품 상세처럼 제목에 들어갈 이름을 서버에서 받아야 아는 화면은, 받기 전에 제목을 바꾸면 "상품 상세"처럼 뭉뚱그린 제목이 되거나 이전 화면의 제목이 남는다. 예제는 데이터를 받아 내용을 그린 다음에 제목, 포커스, 알림을 한꺼번에 처리한다. 화면을 그리기 전에 포커스를 옮기면 옮길 `h1` 이 아직 없기 때문이기도 하다.

### 오류 화면도 제목을 바꾼다
찾을 수 없는 주소, 권한 없음 같은 오류 화면으로 바뀔 때도 제목을 바꾼다. [오류 상태](../오류%20상태(Error%20State)/README.md) 노트의 "페이지 제목에 오류를 드러낸다" 절과 그 예제가 이 경우를 다룬다.

## 포커스 옮기기
### 어디로 옮길까
Gatsby의 Marcy Sutton은 2019년에 Fable Tech Labs와 함께, 장애가 있는 테스터 다섯 명(NVDA, JAWS, 화면 확대, Dragon 음성 입력과 키보드, 스위치 접근 사용자)과 화면 이동 뒤 포커스를 둘 곳을 시험했다(Sutton 2019). 건너뛰기 링크(Skip Link)는 페이지 맨 앞에 두는 링크로, 누르면 반복되는 머리글을 건너뛰고 본문이나 메뉴로 바로 가게 해 준다. 라이브 영역(Live Region)은 [알림과 피드백](../알림과%20피드백(Notifications%20and%20Feedback)/README.md) 노트에서 본, 내용이 바뀌면 포커스가 없어도 읽히는 영역이다. 시험 결과는 이렇다.

| 포커스를 둔 곳 | 시험에서 본 것 |
|---|---|
| 새 화면의 제목(`h1`) | 가장 나은 경험이었다. 시간을 아끼고 화면이 바뀐 것이 분명했다 |
| 본문을 감싼 요소 | 그런대로 동작했지만 제목보다 덜 눈에 띄었다. 그래도 페이지 맨 위로 되돌리는 것보다는 나았다 |
| 화면 이동 때 포커스를 받는 건너뛰기 링크 + 라이브 영역 알림 | 글의 최종 권고. 건너뛰기 링크 글자는 "주요 메뉴로 건너뛰기"처럼 하는 일을 설명하게 한다 |

제목이 가장 나았다는 것은 스크린 리더 사용자의 경험이고, 최종 권고는 다른 사용자의 결과를 함께 본 것이다. 글은 바꾼 이유를 한 문장으로 밝히지는 않지만, 시험에서 나온 문제를 이렇게 든다. 키보드만 쓰는 테스터에게 영역에 포커스를 주면 닿을 수는 있어도 조작할 수는 없고, 그래서 건너뛰기 링크가 가장 자연스러운 선택이라고 쓴다. 화면 확대 사용자에게는 가로로 넓은 제목에 포커스가 가면 휴대폰 Chrome이 제목 가운데로 스크롤해 앞뒤 글자가 잘렸다. 스위치 사용자는 조작할 수 없는 요소의 포커스 테두리가 헷갈린다고 했다. 그래서 확대해도 잘리지 않을 만큼 작고 실제로 누를 수 있는 건너뛰기 링크에 포커스를 두고, 스크린 리더 사용자를 위한 화면 이름은 라이브 영역으로 넘긴 것으로 읽힌다(내 해석). 다섯 명, 한 번의 시험이라는 점도 함께 봐야 한다.

프레임워크와 브라우저는 또 다른 기본값을 쓴다. SvelteKit은 화면을 옮길 때마다 `<body>` 에 포커스를 두어 페이지를 새로 연 것처럼 흉내 내고, `autofocus` 속성이 있는 요소가 있으면 그 요소에 둔다. 새 Navigation API(아래 절)의 `focusReset` 기본값도 같아서, 화면을 바꾼 뒤 `autofocus` 가 있는 첫 요소에, 없으면 `<body>` 에 포커스를 둔다. `body` 에 두는 것은 Tab을 눌렀을 때 문서 처음부터 다시 시작해 새 페이지를 연 것과 같아지기를 노린 것이다. 브라우저마다 실제로 그런지는 이번에 확인하지 못했다(확인 필요). 다만 스크린 리더가 새 화면에 대해 무엇을 읽을지는 따로 알림을 주지 않으면 정해지지 않는다(내 판단).

정리하면 정답이 하나로 모이지 않는다. 이 노트의 예제는 구현이 가장 단순하고 스크린 리더 사용자에게 가장 나았던 `h1` 을 기본으로 두었다. 최종 권고와 비슷하게, 화면 이름을 알리고 건너뛰기 링크에 포커스를 두는 방식도 고를 수 있게 했다. 다만 예제의 링크는 Sutton 글의 예처럼 메뉴로 보내는 링크가 아니라 본문으로 건너뛰는 링크다. `h1` 을 쓴다면 확대 사용자를 위해 제목이 지나치게 넓어지지 않게 하는 편이 낫다(내 판단).

### 제목에 포커스를 주려면
`h1` 은 원래 포커스를 받지 않는 요소다. `tabindex="-1"` 을 주면 Tab 키 순서에는 들어가지 않으면서 스크립트의 `focus()` 로는 포커스를 받을 수 있다. 포커스를 받은 제목에 테두리가 보여야 키보드 사용자도 지금 어디 있는지 안다. 예제는 `[tabindex="-1"]:focus` 에도 노란 테두리를 그렸다.

```html
<h1 tabindex="-1">상품 목록</h1>
```

```js
main.querySelector('h1').focus();
```

### 옮기지 않아야 할 때
포커스를 옮기는 것은 사용자가 화면을 바꾸려고 한 행동에 대한 응답이다. 같은 화면 안에서 필터를 바꾸거나 탭을 고르는 것처럼 주소가 바뀌어도 사용자가 같은 자리에서 계속 조작하는 경우에 포커스를 `h1` 으로 빼앗으면, 방금 누른 컨트롤에서 멀어진다(내 판단). 이 경우는 [같은 화면에서 주소만 바뀔 때](../같은%20화면에서%20주소만%20바뀔%20때(URL%20Changes%20Within%20a%20Screen)/README.md) 노트에서 따로 다룬다. 처음 페이지를 열 때도 옮기지 않는다. 그때는 브라우저가 페이지를 연 것이므로 브라우저의 기본 동작에 맡긴다. 예제도 처음 열 때는 제목만 맞추고 포커스는 건드리지 않는다.

### 뒤로 가기에서
뒤로 가기로 돌아올 때는 아래 스크롤 절처럼 이전 스크롤 위치를 되살리는 것이 보통이다. 이때 `h1` 에 포커스를 주면, 스크롤은 목록 중간에 있는데 포커스는 화면 밖 맨 위 제목에 가 있게 된다. 예제는 `focus({ preventScroll: true })` 로 스크롤이 제목으로 튀지 않게 했지만, 그 결과 포커스 테두리가 화면에 보이지 않는다. 알림 모드의 건너뛰기 링크는 화면 기준(`position: fixed`)으로 띄워서 스크롤이 내려가 있어도 화면 위쪽에 보인다. 뒤로 가기에서는 누르고 떠났던 링크로 포커스를 되돌리는 방법도 생각할 수 있다(내 판단). 이 예제는 이것까지 만들지 않았고, [무한 스크롤과 더 보기 버튼](../무한%20스크롤과%20더%20보기%20버튼(Infinite%20Scroll%20and%20Load%20More)/README.md) 노트의 예제가 이 방식이다.

## 화면 이름 알리기
### 라이브 영역으로 알린다
포커스를 옮기지 않거나, 옮긴 곳(건너뛰기 링크, `body`)이 화면 이름을 담고 있지 않다면 라이브 영역으로 화면 이름을 알린다. 라이브 영역은 [알림과 피드백](../알림과%20피드백(Notifications%20and%20Feedback)/README.md) 노트의 라이브 영역 절에서 다뤘다. Sutton(2019)은 페이지를 처음 열 때 라이브 영역을 넣어 두고, 화면이 바뀌면 "포트폴리오 페이지"처럼 지금 화면을 알리는 글자를 넣으라고 쓴다.

Next.js와 SvelteKit은 이 일을 기본으로 한다. Next.js는 `next/link` 로 화면을 옮길 때도 보조 기술이 알 수 있도록 라우트 알림 장치(route announcer)를 기본으로 넣고, 알릴 이름을 `document.title`, `<h1>`, 주소 경로 순서로 찾는다고 쓴다. SvelteKit은 화면을 옮길 때마다 새 페이지 이름을 읽어 주는 라이브 영역을 넣고, 그 이름은 `<title>` 에서 가져온다. 두 문서 모두 화면마다 겹치지 않고 내용을 설명하는 제목을 달라고 한다. 프레임워크가 알림을 해 주더라도 그 재료는 결국 제목이다.

### 두 번 읽히지 않게
`h1` 에 포커스를 주면서 같은 이름을 라이브 영역으로도 알리면, 스크린 리더가 같은 말을 두 번 읽을 수 있다(내 판단, 확인 필요). 예제는 `h1` 으로 포커스를 옮기는 방식과, 알림을 주고 건너뛰기 링크로 포커스를 옮기는 방식을 따로 두었다. Next.js처럼 알림이 기본으로 켜진 프레임워크에서 `h1` 포커스를 함께 쓸 때 실제로 어떻게 들리는지는 이번에 확인하지 못했다.

## 스크롤 위치
### 새로 가면 맨 위로, 돌아오면 그 자리로
페이지를 새로 열면 맨 위에서 시작하고, 뒤로 가기로 돌아오면 브라우저가 떠날 때의 스크롤 위치를 되살린다. MDN은 `history.scrollRestoration` 이 `auto` 면 사용자가 스크롤했던 위치가 되살아나고, `manual` 이면 되살아나지 않는다고 쓴다. SPA는 돌아왔을 때 내용을 다시 그리느라 시간이 걸리므로, 브라우저가 위치를 되살리는 순간에는 아직 목록이 그려지지 않았을 수 있다(내 판단, 확인 필요).

예제는 자동 복원을 `manual` 로 끄고 직접 처리한다. 링크를 누르는 순간 지금 기록 항목에 스크롤 위치를 `history.replaceState` 로 적어 두고, 새 화면으로 가면 맨 위로, 뒤로 가기로 돌아오면 그 기록 항목에 적힌 위치로 내용을 다 그린 뒤 옮긴다.

```js
history.scrollRestoration = 'manual';

// 링크를 누를 때 지금 위치를 기록해 둔다
history.replaceState({ scrollY: window.scrollY }, '');

// 화면을 다 그린 뒤
const saved = history.state?.scrollY ?? 0;
window.scrollTo(0, saved);
```

### Navigation API
Navigation API는 이 일들을 브라우저가 맡게 하려는 새 API다. 화면 이동을 가로채는 `NavigateEvent.intercept()` 에 `focusReset` 과 `scroll` 옵션이 있다. 기본값인 `"after-transition"` 은 처리 함수가 끝나면 포커스를 `autofocus` 가 있는 첫 요소나 `<body>` 에 두고, 스크롤은 주소에 조각 식별자(`#`)가 있으면 그곳으로 가고, 다시 불러오거나 뒤로 가기, 앞으로 가기로 찾아온 기록이면 지난 위치로 되살린다. `"manual"` 은 이 기본 동작을 끈다. MDN은 이 기능을 2026년 1월부터 최신 브라우저에서 쓸 수 있는 Baseline 2026(새로 사용 가능)으로 표시한다. 오래된 브라우저에서는 동작하지 않을 수 있다고 쓴다. 예제는 이 API를 쓰지 않았다.

## 그 밖에 맞춰 둘 것
### 늦게 도착한 화면은 버린다
상품 목록을 누르고 데이터가 오기 전에 회사 소개를 누르면, 늦게 도착한 상품 목록이 회사 소개 화면을 덮고 제목과 포커스까지 가져갈 수 있다. 예제는 화면 이동마다 번호를 붙이고, 데이터가 왔을 때 번호가 최신이 아니면 결과를 버린다. 데이터를 받는 동안에는 본문에 `aria-busy="true"` 를 걸고 "불러오는 중"을 보여 준다. 기다리는 동안의 표시는 [로딩 상태 표시](../로딩%20상태%20표시(Loading%20Indicators)/README.md) 노트에 있다.

### 메뉴에 지금 위치를 표시한다
머리글 메뉴에서 지금 화면의 링크에 `aria-current="page"` 를 둔다. 굵은 글씨나 밑줄로 보이는 표시와 함께, 스크린 리더 사용자에게도 메뉴 가운데 어느 것이 지금 화면인지 알린다. 상품 상세처럼 메뉴에 없는 화면이라면 예제는 그 화면이 속한 메뉴(상품 목록)를 굵게만 표시하고 `aria-current` 는 두지 않았다. `page` 는 그 링크가 지금 페이지라는 뜻이라 상위 메뉴에 두면 사실과 달라지기 때문이다. 상위 메뉴를 보조 기술에 어떻게 알릴지(`aria-current="true"` 등)는 이번에 1차 자료로 확인하지 못했다(확인 필요).

## 프레임워크가 해 주는 것
아래는 각 공식 문서에서 이번에 확인한 내용만 적었다. 문서에 없는 것은 해 주지 않는다는 뜻이 아니라 확인하지 못했다는 뜻이다.

| 프레임워크 | 제목 | 화면 이름 알림 | 포커스 |
|---|---|---|---|
| Next.js | 화면마다 겹치지 않는 제목을 달라고 권한다 | 라우트 알림 장치가 기본으로 들어 있다. `document.title`, `<h1>`, 주소 경로 순서로 이름을 찾는다 | 문서에서 확인하지 못했다 |
| SvelteKit | `<svelte:head>` 로 화면마다 `<title>` 을 단다 | 라이브 영역이 기본으로 들어 있고 `<title>` 을 읽는다 | 화면 이동 뒤 `<body>` 에, `autofocus` 가 있으면 그 요소에 둔다. `afterNavigate` 로 바꿀 수 있다 |
| Angular | 라우트의 `title` 속성으로, 라우트가 활성화되면 제목을 자동으로 바꾼다. `TitleStrategy` 로 규칙을 바꿀 수 있다 | 확인하지 못했다 | 확인하지 못했다 |
| React | 컴포넌트 어디서든 `<title>` 을 그리면 `<head>` 로 옮겨 준다. 한 번에 하나만 그려야 한다 | 라우터에 따라 다르다(확인 필요) | 라우터에 따라 다르다(확인 필요) |

React 문서는 `<title>` 의 자식이 하나의 문자열이어야 한다고 쓴다. `<title>Results page {pageNumber}</title>` 은 자식이 문자열 하나가 아니라 두 개짜리 배열이 되므로(React 문서는 이를 문제로 들고 오류가 난다고 쓴다) `` <title>{`Results page ${pageNumber}`}</title> `` 처럼 템플릿 문자열 하나로 넘긴다. 컴포넌트 어디서든 `<title>` 을 그리는 기능이 들어온 React 버전을 문서 페이지에서는 찾지 못했다. React 19에서 들어온 것으로 알고 있지만 이번에 확인하지 못했다(확인 필요).

## 예제
[example.html](./example.html)은 가짜 상점에서 화면을 옮기며 제목과 포커스가 어떻게 바뀌는지 보는 예제다. HTML, CSS, 약간의 자바스크립트만 한 파일에 담았으므로 파일을 더블클릭하거나 브라우저 창에 끌어다 놓으면 바로 열린다. 파일로 연 페이지에서도 동작하도록 주소의 `#` 뒤를 바꾸는 방식(`#/products`)으로 화면을 옮긴다. 상품 목록과 상품 상세는 0.3초 걸리는 가짜 요청으로 데이터를 받는다.

### 무엇을 보여 주나
조작판에서 화면이 바뀔 때 할 일을 네 가지 가운데 하나로 고를 수 있다. 내용만 바꾼다, 제목도 바꾼다, 제목을 바꾸고 새 화면의 `h1` 으로 포커스를 옮긴다(기본), 제목을 바꾸고 화면 이름을 알린 뒤 건너뛰기 링크로 포커스를 옮긴다. 조작판 아래에는 지금 탭 제목, 포커스가 있는 요소, 라이브 영역의 글자가 나와서, 스크린 리더 없이도 화면을 옮길 때마다 무엇이 바뀌는지 볼 수 있다.

건너뛰기 링크는 평소에는 화면 밖에 있다가 포커스를 받으면 왼쪽 위에 나타나고, 누르면 주소는 그대로 둔 채 본문의 `h1` 으로 포커스를 옮긴다. 상품 상세의 제목은 받은 상품 이름으로 "무선 키보드 - 상품 목록 - 예제 상점"처럼 단다. 상품 목록에서 아래로 스크롤한 뒤 상품을 눌렀다가 뒤로 가기를 누르면 떠날 때의 위치로 돌아온다. 머리글 메뉴의 지금 화면에는 `aria-current="page"` 가 붙고(상품 상세에서는 상품 목록이 굵게만 표시된다), 없는 주소로 가면 "페이지를 찾을 수 없음" 화면과 제목이 나온다.

### 확인한 것과 못 한 것
2026-11-04에 Playwright로 Chromium 계열 브라우저(설치된 Chrome 156.0.8078.48)를 띄워 파일을 file:// 주소로 열고 29가지를 확인했다. 콘솔 오류는 없었다. 내용만 바꾸면 제목이 처음 화면에 머물고, 메뉴 링크로 옮기면 포커스가 그 링크에 남으며, 본문 안 링크로 옮기면 포커스가 `body` 로 떨어지는 것을 확인했다. 제목만 바꾸는 모드에서 제목이 바뀌고 포커스는 링크에 남는 것, `h1` 모드에서 새 화면의 `h1` 에 포커스가 가는 것, 알림 모드에서 라이브 영역에 "홈 화면"이 들어가고 건너뛰기 링크가 포커스를 받아 화면에 보이며(뒤로 가기로 스크롤이 386px 내려간 상태에서도) 누르면 주소를 바꾸지 않고 `h1` 으로 가는 것도 확인했다. 상품 상세의 제목이 데이터를 받은 뒤 상품 이름으로 바뀌는 것, 새 화면은 맨 위에서 시작하고 뒤로 가기는 떠날 때의 스크롤 위치(386px)로 돌아오는 것, 상품 목록을 누르고 곧바로 회사 소개를 누르면 회사 소개만 남는 것, 첫 화면의 데이터가 오기 전에 다른 화면으로 옮겨도 포커스가 새 `h1` 으로 가는 것, 지금 화면의 링크를 다시 누르면 주소가 바뀌지 않아 아무 일도 일어나지 않는 것, 주소를 직접 `#/products` 로 열면 데이터를 받은 뒤 상품 목록 제목으로 바뀌는 것, 375px 너비에서 가로 스크롤이 생기지 않는 것도 확인했다.

실제 스크린 리더(NVDA, VoiceOver, TalkBack 등)로 듣는 확인은 하지 않았다. 그래서 각 모드에서 화면을 옮긴 뒤 실제로 무엇이 어떤 순서로 읽히는지, `h1` 포커스와 라이브 영역 알림을 함께 쓰면 두 번 읽히는지는 확인하지 못했다(확인 필요). Chrome 외의 브라우저, 실제 휴대폰의 스크린 리더 조작, `#` 대신 History API의 `pushState` 로 주소를 바꾸는 방식, Navigation API는 시험하지 않았다.
