## 오류 상태란 ?
- 오류 상태(Error State)는 화면이나 화면 안의 한 영역이 내용을 불러오지 못했거나 사용자가 시킨 일을 끝내지 못했을 때의 상태, 그리고 그때 대신 보여 주는 화면을 말한다
- 연결이 끊겨 목록을 받지 못한 화면, 서버가 고장 나 저장이 안 된 화면, 없는 주소로 들어온 화면, 권한이 없는 페이지가 모두 오류 상태다
- 이 노트는 화면이 구분해야 할 실패의 종류, 오류를 보여 주는 범위, 오류 상태에 담을 것, 다시 시도 설계, 문구, 404와 500 페이지, 오류 경계, 접근성을 다룬다. 특정 프레임워크 구현은 다루지 않는다

error의 사전적 의미는 잘못, 틀림이다. 라틴어 error(헤맴)에서 왔고, 그 뿌리인 동사 errō는 길을 잃고 헤매다라는 뜻이다(Wiktionary). 컴퓨팅에서는 작업을 끝내지 못하고 중간에 멈춘 실패를 가리킨다. 화면 용어로 오류 상태는 사용자가 가려던 길이 막혔다는 것을 알리고, 다시 길을 찾게 돕는 화면이다. 길을 잃었다는 원래 뜻처럼, 오류 화면이 할 일은 잘못을 꾸짖는 것이 아니라 어디서 막혔고 어디로 가면 되는지 알려 주는 것이다.

[빈 상태](../빈%20상태(Empty%20State)/README.md) 노트는 비어 보이는 세 상태를 "지금 아는 것이 무엇인가"로 나눴다. 로딩 상태는 아직 모른다는 뜻이고, 빈 상태는 확인했더니 없다는 뜻이며, 오류 상태는 확인하지 못했다는 뜻이다. 이 노트는 그 세 번째, 확인하지 못했거나 끝내지 못한 상태를 화면과 영역 단위로 어떻게 보여 줄지를 본다. 입력란 옆의 인라인 오류, 토스트와 스낵바, 배너 같은 그릇 자체는 [알림과 피드백](../알림과%20피드백(Notifications%20and%20Feedback)/README.md) 노트에, 기다리는 동안의 표시는 [로딩 상태 표시](../로딩%20상태%20표시(Loading%20Indicators)/README.md) 노트에 있다.

여행 중 길이 막혔을 때 "통행 불가"라고만 적힌 팻말과 "낙석으로 통제, 2km 앞에서 우회, 오후 6시 개통 예정"이라고 적힌 팻말의 차이와 같다. 앞의 팻말 앞에서는 서 있을 수밖에 없고, 뒤의 팻말을 보면 돌아갈지 기다릴지 정할 수 있다.

## 왜 "오류가 발생했습니다" 하나로 끝내면 안 될까
### 실패마다 사용자가 할 일이 다르다
연결이 끊겼다면 사용자는 와이파이를 확인하면 된다. 서버가 고장 났다면 사용자가 할 수 있는 일은 잠시 뒤 다시 해 보는 것뿐이다. 로그인이 풀렸다면 다시 로그인하면 되고, 권한이 없다면 관리자에게 요청해야 한다. 같은 "오류가 발생했습니다"를 보여 주면 사용자는 이 가운데 무엇을 해야 하는지 모른다. 결국 아무 버튼이나 다시 누르거나, 고칠 수 없는 일을 고치려고 애쓰거나, 떠난다.

NN/g(Nielsen Norman Group)의 오류 메시지 지침(Error-Message Guidelines, 2023)은 문제를 정확히 설명하라고 하면서 "An error occurred"(오류가 발생했습니다) 같은 막연한 문구를 피하라고 쓴다. 동시에 사용자가 이해하지 못할 만큼 기술적으로 쓰지도 말라고 한다. 1998년 Jakob Nielsen이 404 페이지를 두고 쓴 글도 오류 메시지의 기본 원칙 세 가지로 쉬운 말, 정확한 설명, 해결로 이끄는 조언을 들었다. 25년이 지나도 원칙이 거의 같다(내 판단).

### 누구 탓인지에 따라 말투가 달라진다
사용자가 고칠 수 있는 오류(입력 형식이 틀림, 로그인 만료)와 사용자가 어떻게 해도 고칠 수 없는 오류(서버 고장, 점검)를 같은 말투로 쓰면 둘 다 어색해진다. 서버 고장을 "입력을 확인해 주세요"로 알리면 사용자는 자기가 뭘 잘못했는지 한참 찾는다. 반대로 입력 오류를 "시스템 문제입니다"로 알리면 고칠 기회를 놓친다(내 판단).

### 모르는 원인은 지어내지 않는다
그렇다고 원인을 늘 정확히 알 수 있는 것은 아니다. Atlassian 디자인 시스템(이하 Atlassian)의 오류 메시지 지침은 원인을 모르면 원인을 지어내지 말고, 무언가 잘못됐다고 말한 뒤 다음 단계를 주라고 쓴다. 정리하면 아는 만큼은 구분해서 말하고, 모르는 부분은 모른다고 말하되 다음에 할 일은 꼭 준다.

## 화면이 구분해야 할 실패의 종류
아래 상태 코드의 뜻은 HTTP 의미론 표준인 RFC 9110을 따랐다. 상태 코드 자체는 [HTTP 메서드와 상태 코드](../../CS_Basic/WEB/HTTP%20메서드와%20상태%20코드(HTTP%20Methods%20and%20Status%20Codes)/README.md) 노트에 정리했고, 여기서는 그 코드를 받았을 때 화면이 무엇을 말해야 하는지만 본다. 상태 코드는 화면이 실패를 구분하는 단서일 뿐이고, 사용자에게 그대로 보여 줄 말은 아니다.

### 네트워크 끊김과 오프라인
요청이 서버에 닿지도 못한 경우다. 응답이 아예 없으므로 상태 코드도 없다. 사용자 쪽 연결 문제일 가능성이 크고, 사용자가 연결을 확인하거나 연결이 돌아온 뒤 다시 시도하면 풀리는 경우가 많다.

브라우저는 `navigator.onLine` 과 `online`, `offline` 이벤트로 연결 상태를 알려 준다. 다만 MDN은 이 값이 믿을 만하지 않다고 경고한다. 브라우저와 운영체제마다 판단 방식이 다른데, 대체로 인터넷이 안 되는 사내망(LAN)에 연결만 되어 있어도 온라인으로 보고, Windows에서는 Microsoft 서버에 닿을 수 있는지로 판단해서 방화벽이나 VPN 때문에 인터넷이 되는데도 오프라인으로 볼 수 있다. 그래서 MDN은 이 값으로 기능을 끄지 말고, 오프라인인 것 같을 때 힌트를 주는 데만 쓰라고 한다. 실제로 요청이 실패했다는 사실이 이 값보다 더 확실한 증거다(내 판단).

오프라인은 대개 여러 화면에 걸쳐 계속되는 상태라서, 화면마다 오류를 띄우기보다 [알림과 피드백](../알림과%20피드백(Notifications%20and%20Feedback)/README.md) 노트의 배너처럼 연결이 돌아올 때까지 남는 표시 하나로 알리는 편이 맞다. 이미 받아 둔 내용은 지우지 말고 그대로 보여 준다(내 판단).

엘리베이터 안에서 휴대폰이 안 터지는 것과 같다. 상대방 전화가 고장 난 것이 아니라 내가 있는 자리의 문제이고, 밖으로 나가면 다시 걸 수 있다.

### 시간 초과 (Timeout)
time out의 사전적 의미는 정해 둔 시간이 다 됐다는 것이다. 화면에서는 요청을 보냈는데 정해 둔 시간 안에 응답이 오지 않아 기다리기를 그만둔 상태를 말한다.

시간 초과는 어디서 기다렸느냐에 따라 여러 모습으로 나타난다. RFC 9110의 408(Request Timeout)은 서버가 기다린 시간 안에 요청을 다 받지 못했다는 뜻이고, 504(Gateway Timeout)는 중간 서버(게이트웨이, 프록시)가 그 뒤의 서버에게서 제때 응답을 받지 못했다는 뜻이다. 화면 쪽에서 스스로 시간을 정해 두고 그 시간이 지나면 기다리기를 멈추는 경우도 있다. 이때는 상태 코드가 없다.

시간 초과에서 까다로운 점은 일이 처리됐는지 모른다는 것이다. 결제 요청이 시간 초과로 끝났다면 결제가 안 된 것인지, 됐는데 응답만 늦은 것인지 화면은 알 수 없다. 그래서 시간 초과 문구에는 "처리되지 않았습니다"라고 단정하지 말고, 결과를 확인하는 길(주문 내역 보기 등)을 함께 준다(내 판단). 같은 요청을 다시 보내도 안전한지는 아래 다시 시도 설계에서 본다.

### 서버 오류 (5xx)
5xx는 서버 쪽 문제다. RFC 9110에 따르면 500(Internal Server Error)은 서버가 예상하지 못한 상황 때문에 요청을 처리하지 못했다는 뜻이고, 502(Bad Gateway)는 중간 서버가 뒤의 서버에게서 잘못된 응답을 받았다는 뜻이며, 503(Service Unavailable)은 과부하나 예정된 점검으로 지금은 처리할 수 없지만 얼마 뒤에는 풀릴 가능성이 크다는 뜻이다. 503에는 언제 다시 시도하면 좋을지 알려 주는 `Retry-After` 헤더를 붙일 수 있다.

사용자 잘못이 아니고, 사용자가 고칠 수도 없다. 그래서 문구의 초점은 사용자 탓이 아니라는 것, 입력한 내용이 어떻게 됐는지, 잠시 뒤 다시 해 보거나 다른 길로 갈 수 있다는 것이다. GOV.UK 디자인 시스템(이하 GOV.UK)은 예상하지 못한 고장과 일부러 닫은 점검을 다른 페이지로 나눈다. 아래 404와 500 페이지 절에서 다시 본다.

### 찾을 수 없음 (404)
RFC 9110의 404(Not Found)는 서버가 요청한 대상을 찾지 못했거나, 있다는 사실을 밝히고 싶지 않다는 뜻이다. 없어진 것이 잠깐인지 영원인지는 알려 주지 않는다. 주소를 잘못 쳤거나, 오래된 링크를 눌렀거나, 이미 지워진 게시물을 열었을 때 생긴다.

사용자 실수일 수도 있고 사이트의 링크 관리 문제일 수도 있다. 그래서 문구는 누구 탓도 하지 않고, 주소를 확인하는 방법과 원하는 것을 찾아갈 길(검색, 주요 메뉴)을 준다.

### 로그인 필요와 권한 없음 (401, 403)
RFC 9110에서 401(Unauthorized)은 대상에 맞는 인증 정보가 없어서 요청을 처리하지 않았다는 뜻이고, 403(Forbidden)은 요청을 이해했지만 들어주지 않겠다는 뜻이다. [HTTP 메서드와 상태 코드](../../CS_Basic/WEB/HTTP%20메서드와%20상태%20코드(HTTP%20Methods%20and%20Status%20Codes)/README.md) 노트의 비유로는 401은 신분증을 안 보여 준 것이고, 403은 신분증은 확인했는데 출입 명단에 없는 것이다.

화면에서 할 말도 다르다. 401은 대개 로그인이 풀렸다는 뜻이므로 다시 로그인하게 하고, 로그인한 뒤에는 하던 곳으로 돌려보내며 입력하던 내용을 잃지 않게 한다(내 판단). 403은 다시 로그인해도 풀리지 않으므로 권한을 요청하는 길이나 누구에게 물어야 하는지를 준다. RFC 9110은 서버가 금지된 대상의 존재를 숨기고 싶으면 403 대신 404를 보내도 된다고 쓴다. 그래서 404 화면에서 "이 페이지는 없습니다"라고 단정하기보다 "찾을 수 없거나 볼 권한이 없습니다"처럼 쓰는 편이 맞는 서비스도 있다(내 판단).

### 제출한 폼의 검증 실패
사용자가 폼을 제출했는데 서버가 입력 내용을 받아들이지 않은 경우다. 형식은 맞지만 내용상 처리할 수 없을 때 422(Unprocessable Content)를 쓰는 서비스가 있고, 400을 쓰는 서비스도 있다. 어느 칸이 왜 틀렸는지는 각 입력란의 인라인 오류로 알리고(알림과 피드백 노트의 인라인 오류 절), 페이지 단위에서는 오류가 있다는 것과 몇 개인지를 폼 위의 오류 요약으로 모아 보여 준다. 오류 요약은 아래 접근성 절에서 자세히 본다.

이 경우는 사용자가 입력을 고쳐서 풀 수 있는 오류라서, 입력한 값을 반드시 남겨 두어야 한다. GOV.UK 검증(Validation) 패턴은 오류가 나면 사용자가 입력한 값을 그대로 둔 채 페이지를 다시 보여 주어, 무엇이 틀렸는지 보고 고칠 수 있게 하고 처음부터 다시 치지 않게 하라고 쓴다.

### 일부만 실패
대시보드의 위젯 다섯 개 가운데 하나만 불러오지 못했거나, 상품 상세 페이지에서 리뷰 목록만 실패한 경우다. 이때 페이지 전체를 오류 화면으로 바꾸면 멀쩡히 불러온 나머지까지 사용자가 잃는다. 실패한 영역만 오류 상태로 바꾸고 나머지는 그대로 쓰게 해야 한다. 이 생각은 아래 오류 경계 절과 이어진다.

| 로그인 필요 | 401 | 아님(로그인 만료 등, 다시 로그인하면 풀림) | 다시 로그인하면 이어서 할 수 있다는 것 | 로그인 뒤 원래 자리로 |
| 권한 없음 | 403 | 아님 | 이 계정으로는 볼 수 없다는 것, 누구에게 요청하는지 | 권한 요청, 다른 계정으로 로그인 |
| 제출한 폼 검증 실패 | 400, 422 등 | 대개 입력 실수(입력을 고치면 풀림) | 어느 칸이 왜 틀렸고 어떻게 고치는지 | 입력란으로 가서 고치기 |
| 일부만 실패 | 영역 하나의 요청 실패 | 경우에 따라 다름 | 그 영역만 못 불러왔다는 것 | 그 영역만 다시 시도 |

<br/>

## 오류를 보여 주는 범위
같은 실패라도 얼마나 넓은 자리를 차지해 보여 줄지 정해야 한다. 기준은 실패가 막아 버린 범위만큼만 차지한다는 것이다(내 판단).

### 페이지 전체
페이지의 주된 내용 자체를 보여 줄 수 없을 때다. 없는 주소, 볼 권한이 없는 페이지, 페이지의 핵심 데이터를 불러오지 못한 경우가 여기에 든다. 이때는 원래 내용 자리를 오류 페이지가 대신한다. 머리글과 주요 메뉴는 남겨 두어 다른 곳으로 갈 길을 열어 두는 것이 흔하다(내 판단). GOV.UK는 이런 오류 페이지에 이동 경로(Breadcrumbs)를 두지 말라고 쓴다.

### 영역 (섹션, 위젯)
페이지의 한 부분만 실패했을 때다. 실패한 카드나 목록 자리에 짧은 문구와 다시 시도 버튼을 두고, 나머지 영역은 정상으로 둔다. IBM Carbon 디자인 시스템(이하 Carbon)은 이런 화면을 오류 관리 빈 상태(Error Management Empty State)라 부르며 빈 상태 안에 넣는다([빈 상태](../빈%20상태(Empty%20State)/README.md) 노트). 이 시리즈의 기준으로는 확인하지 못한 상태이므로 오류 상태로 본다. 같은 노트에서 본 것처럼, 대시보드에서 여러 위젯이 한꺼번에 실패하면 그림 없이 글자만 쓰는 편이 반복이 적다.

```html
<section aria-labelledby="reviews-title">
  <h2 id="reviews-title">리뷰</h2>
  <p>리뷰를 불러오지 못했습니다. 상품 정보와 주문은 그대로 이용할 수 있습니다.</p>
  <button type="button">리뷰 다시 불러오기</button>
</section>
```

### 입력란
특정 입력란의 값이 문제일 때는 그 입력란 바로 옆의 인라인 오류로 알린다. [알림과 피드백](../알림과%20피드백(Notifications%20and%20Feedback)/README.md) 노트의 인라인 오류 절에 정리했다.

### 잠깐 지나가는 오류
화면 전체를 바꿀 정도는 아닌 일시적 실패, 예를 들어 좋아요가 반영되지 않았거나 자동 저장이 한 번 실패한 경우다. 스낵바나 토스트, 해결될 때까지 남는 배너로 알린다. 그릇을 고르는 기준은 [알림과 피드백](../알림과%20피드백(Notifications%20and%20Feedback)/README.md) 노트에 있다. 다만 같은 노트에서 본 것처럼 Atlassian은 경고와 오류를 저절로 사라지게 하지 말라고 하므로, 사용자가 꼭 알아야 하는 실패는 저절로 사라지는 토스트에만 맡기지 않는다.

<br/>

## 오류 상태에 담을 것
여러 지침을 겹쳐 보면 오류 상태에는 대략 아래 여섯 가지가 들어간다. 모든 오류에 여섯 가지가 다 필요하지는 않고, 실패의 종류에 맞춰 고른다(내 판단).

### 무슨 일이 있었는지
쉬운 말로 짧게 쓴다. NN/g는 핵심 정보를 앞에 두라고 하고, Atlassian은 본문을 한두 문장으로 쓰라고 한다. "결제를 완료하지 못했습니다"처럼 사용자가 하려던 일을 주어로 쓰면 무엇이 실패했는지 바로 알 수 있다(내 판단).

### 누구 탓인지
사용자 탓이 아니면 그렇다는 것을 분명히 한다. NN/g 채점표는 책임을 사용자가 아니라 시스템에 두는 긍정적인 말투를 기준으로 삼고, Atlassian은 "당신" 대신 "저희"를 주어로 쓰라고 한다. 사용자와 문제를 묶어 말하면 사용자가 책임을 느끼기 때문이다.

### 다음에 할 일
NN/g는 문제만 말하지 말고 해결 방법을 주라고 쓴다. Atlassian은 원인이 여러 가지일 수 있으면 가장 그럴듯한 원인이나 가장 쉬운 해결을 먼저 쓰고, 두 번째 문장에서 다른 방법을 주라고 한다. 행동 버튼은 "확인" 같은 막연한 말 대신 "다시 시도", "로그인"처럼 무엇을 하는지 드러나는 동사로 쓴다.

### 다시 시도 버튼
일시적일 수 있는 실패(연결, 시간 초과, 서버 오류)에는 다시 시도 버튼을 둔다. 사용자가 고칠 수 없는 영구적인 실패(권한 없음, 없는 페이지)에 다시 시도 버튼만 두면 같은 실패를 계속 겪게 된다(내 판단).

### 입력한 내용 지키기
NN/g는 사용자가 입력한 값이 틀렸더라도 지우지 말고 남겨 두어 고칠 수 있게 하라고 쓰고, 임시 저장을 예로 든다. GOV.UK의 서비스 문제 페이지는 거래 중간에 문제가 났다면 사용자가 입력한 답이 어떻게 됐는지 알려 주라고 한다. 저장했다면 "답을 저장했습니다. 30일 동안 볼 수 있습니다"처럼, 저장하지 못했다면 다시 시작해야 한다고 쓴다. 긴 글을 쓰다 저장에 실패했는데 그 글이 사라진다면, 문구를 아무리 잘 써도 사용자는 그 서비스를 다시 믿기 어렵다(내 판단).

### 문의 경로와 오류 코드
사용자가 스스로 풀 수 없는 문제라면 누구에게 어떻게 물어야 하는지 준다. GOV.UK는 연락처가 실제로 있고 사용자에게 도움이 될 때만 넣고, 전화번호와 운영 시간을 모두 적거나 그런 정보가 있는 페이지로 연결하라고 한다.

오류 코드는 조심해서 쓴다. NN/g는 오류 코드와 약어를 진단에 쓰이는 경우가 아니면 숨기라고 하고, GOV.UK는 오류 페이지에 "404", "500" 같은 말을 쓰지 말라고 한다. 내가 작업할 때 따르는 규칙도 같은 이유로 UI 문구에 API, 백엔드, ID 같은 내부 구현 용어를 넣지 않고, 내부 사정은 코드 주석에 둔다. 다만 고객센터가 문제를 추적하려면 무언가 단서가 필요할 수 있다. 그럴 때는 쉬운 말의 설명을 먼저 쓰고, 그 아래에 "문의하실 때 이 번호를 알려 주세요" 같은 짧은 안내와 함께 문의 번호를 보조로 둔다. 내부 식별자나 오류 내용 원문을 그대로 노출하지 않고, 번호만 덩그러니 보여 주지도 않는다(내 판단).

## 다시 시도 설계
### 직접 누르는 다시 시도
가장 기본은 사용자가 누르는 다시 시도 버튼이다. 누르면 그 영역은 다시 로딩 상태로 돌아가고, 성공하면 내용으로, 또 실패하면 오류 상태로 돌아온다. 다시 시도할 때 페이지 전체를 새로 고치지 않고 실패한 영역만 다시 불러오면, 사용자가 다른 영역에서 하던 일을 잃지 않는다(내 판단).

몇 번을 다시 시도해도 계속 실패한다면 같은 문구를 반복하기보다 다른 길(나중에 다시 오기, 문의하기)을 함께 보여 주는 편이 낫다(내 판단). 같은 버튼을 열 번 누르게 만드는 화면은 막다른 길과 다르지 않다.

### 자동 재시도와 백오프
일시적인 실패는 사용자가 누르기 전에 화면이 알아서 몇 번 다시 시도하기도 한다. 이때 실패하자마자 바로 다시 보내면 이미 힘든 서버에 요청이 더 몰린다. 그래서 기다리는 시간을 실패할 때마다 늘려 가는 지수 백오프(Exponential Backoff)와, 여러 클라이언트가 같은 순간에 몰리지 않게 기다리는 시간을 조금씩 흩뜨리는 지터(Jitter)를 쓴다. 두 개념은 [멱등 키](../../CS_Basic/WEB/멱등%20키(Idempotency%20Key)/README.md) 노트의 재시도의 예의 절에 정리했다. 503 응답에 `Retry-After` 가 붙어 있다면 그 시간을 따르는 것이 자연스럽다(내 판단).

자동 재시도에는 횟수 상한을 둔다. 상한에 닿으면 조용히 계속 시도하지 말고 오류 상태와 수동 다시 시도 버튼으로 넘어간다(내 판단). 자동 재시도 중이라는 것을 알릴지는 걸리는 시간에 따라 다르다. 짧으면 로딩 표시 안에 묻어 두고, 길어지면 "연결을 다시 시도하는 중"처럼 지금 무슨 일을 하는지 보여 준다(내 판단).

### 다시 보내도 안전한가
조회는 몇 번을 다시 보내도 서버 상태가 바뀌지 않지만, 결제나 주문은 두 번 처리되면 곤란하다. 그래서 자동 재시도는 다시 보내도 안전한 요청에만 쓰고, 그렇지 않은 요청은 서버가 같은 요청을 알아볼 수 있게 멱등 키를 함께 보내거나 사용자에게 결과를 확인하게 한다. 이 부분도 [멱등 키](../../CS_Basic/WEB/멱등%20키(Idempotency%20Key)/README.md) 노트에 있다.

### 끝없는 스피너 대신 시간 초과
실패 중에서 가장 나쁜 모습은 오류 화면이 아니라 영원히 도는 스피너다. [로딩 상태 표시](../로딩%20상태%20표시(Loading%20Indicators)/README.md) 노트에서 본 것처럼 NN/g는 스피너가 끝없이 돌면 사용자가 시스템이 아직 일하는지 멈췄는지 알 수 없어 작업을 포기할 수 있다고 쓰고, Apple Human Interface Guidelines(이하 HIG)는 멈춘 진행 표시가 앱이 얼어붙은 것처럼 보인다고 쓴다. 응답이 오지 않으면 화면은 언젠가 기다리기를 멈추고 오류 상태로 넘어가야 한다.

얼마나 기다린 뒤 포기할지는 정해진 표준이 없고, 서비스의 평소 응답 속도와 작업의 성격을 보고 정한다(내 판단). 기다리는 시간이 길어지면 바로 포기하기 전에 중간 단계를 두는 것도 방법이다. 예를 들어 평소보다 오래 걸리면 "평소보다 오래 걸리고 있습니다"를 덧붙이고, 그래도 응답이 없으면 시간 초과 오류로 넘어간다(내 판단).

전화를 걸었는데 신호만 계속 가면, 몇 번 울린 뒤 "지금은 전화를 받을 수 없습니다"라는 안내가 나오는 편이 낫다. 수화기를 들고 무작정 기다리게 하지 않는다.

## 오류 문구 쓰는 법
### 지침이 모이는 곳
NN/g는 오류 메시지 지침을 보이게 하기(Visibility), 전달하기(Communication), 효율(Efficiency) 세 묶음으로 나누고, 이 열두 가지를 1점에서 4점으로 매기는 채점표(Error-Message Scoring Rubric)도 냈다. 채점표의 전달하기 묶음은 전문 용어 없는 쉬운 말, 짧고 정확한 문제 설명, 적은 수고로 따라 할 수 있는 해결 조언, 사용자가 아닌 시스템에 책임을 두는 긍정적인 말투로 이루어진다. 효율 묶음은 흔한 실수를 미리 막기, 사용자가 입력한 값을 남기고 가리키기, 성공 가능성이 높은 쉬운 해결책, 짧은 맥락 도움말이다.

GOV.UK의 오류 메시지 컴포넌트는 무엇이 일어났고 어떻게 고치는지를 쉬운 말과 긍정적인 표현으로 쓰라고 하면서, 피할 말을 구체적으로 든다. 사용자를 탓하거나 거칠게 들리는 말(illegal, forbidden, you forgot), 선택처럼 들리는 please와 문제 해결에 도움이 안 되는 sorry, 아무 정보도 더하지 않는 valid와 invalid, "oops" 같은 가벼운 말이다. NN/g도 invalid, illegal, incorrect처럼 사용자 잘못을 암시하는 말을 피하고, 같은 오류를 여러 번 보면 질리는 유머도 피하라고 쓴다. Atlassian은 please와 sorry가 오류를 실제보다 심각하게 보이게 하거나 꼭 해야 하는 단계를 선택처럼 보이게 할 수 있다며, 결과가 심각하고 되돌릴 수 없을 때가 아니면 쓰지 말라고 한다.

이 지침들은 영어 문구를 기준으로 쓰였다. 한국어에서는 "죄송합니다"가 영어 sorry보다 훨씬 흔한 인사말에 가깝고, "해 주세요"도 명령을 부드럽게 만드는 기본 어미라서 그대로 옮기기 어렵다. 한국어 문구에서는 사과를 한 번 넘게 반복하지 않고, 사과보다 할 일을 먼저 쓰는 정도로 적용하는 것이 자연스럽다(내 판단).

### 피할 문구와 고친 문구
아래는 위 지침을 한국어 문구에 적용해 본 예다(내 판단).

- "오류가 발생했습니다"는 무엇이 실패했고 무엇을 하면 되는지 말하지 않는다. "주문을 완료하지 못했습니다. 잠시 뒤 다시 시도해 주세요. 입력하신 배송 정보는 그대로 남아 있습니다"처럼 고친다
- "잘못된 요청입니다(400)"는 사용자를 탓하는 데다 코드만 보여 준다. 어느 칸이 문제인지를 인라인 오류로 알리고, 폼 위에는 "입력 내용 2곳을 확인해 주세요"처럼 쓴다
- "API 서버 응답 없음"은 내부 용어다. "서버에 연결하지 못했습니다" 정도도 사용자에게는 여전히 낯설 수 있으므로 "지금 정보를 불러올 수 없습니다. 잠시 뒤 다시 시도해 주세요"처럼 사용자가 겪는 일로 쓴다
- "권한이 없습니다"만 쓰면 다음에 할 일이 없다. "이 문서는 팀 관리자만 볼 수 있습니다. 관리자에게 접근 권한을 요청하세요"처럼 누구에게 무엇을 하면 되는지 붙인다

### 오류처럼 보이지 않아야 할 것
NN/g의 적대적인 오류 메시지 패턴(Hostile Patterns in Error Messages, 2022) 글은 두 가지를 경계한다. 사용자가 실수했다고 보기 전에, 예를 들어 아직 입력하는 중에 오류를 띄우는 것과, 오류가 아닌 평범한 안내에 빨간 배경이나 경고 기호 같은 오류 모양을 입히는 것이다. 오류 모양은 정말로 흐름을 끊어야 하는 메시지에만 남겨 두어야 사용자가 그 모양을 믿는다. 글은 사용자를 꾸짖지 말고 도우라는 말로 정리된다.

## 404 페이지와 500 페이지
### 찾을 수 없는 페이지 (404)
Nielsen의 1998년 글은 웹 서버가 기본으로 보여 주는 "404 Not Found" 화면이 오류 메시지의 기본 원칙을 어긴다고 보고, 직접 만든 404 페이지를 권한다. 요청한 주소를 찾을 수 없다는 짧은 안내, 자주 틀리는 주소 형태, 비슷한 주소를 찾아 링크로 보여 주는 맞춤법 검사, 사이트 검색창을 넣으라고 한다.

GOV.UK의 페이지를 찾을 수 없음(Page not found) 패턴은 제목을 "Page not found"(페이지를 찾을 수 없음)로 두고, 주소를 직접 쳤다면 맞는지 확인하고 붙여 넣었다면 주소 전체를 복사했는지 확인하라는 안내를 본문으로 든다. 이동 경로, "404" 같은 기술 용어, "oops" 같은 가벼운 말, 경고용 빨간 글자를 피하고, 사용자를 탓하지 말라고 쓴다. 서비스 안의 링크와 버튼, 편지나 양식에 적은 주소가 실제 페이지로 이어지는지 시험해 보라고도 한다. 404 페이지를 잘 만드는 것보다 404가 덜 나게 하는 것이 먼저라는 뜻이다.

### 서비스에 문제가 있는 페이지 (500)
GOV.UK는 예상하지 못한 고장에는 "Sorry, there is a problem with the service"(서비스에 문제가 있습니다) 페이지를 쓰고, 모든 고장에 같은 페이지를 쓰라고 한다. 본문에는 "나중에 다시 시도하세요"를 두고, 거래 중이었다면 입력한 답이 저장됐는지 알려 주며, 도움이 되면 연락처와 같은 일을 할 수 있는 다른 서비스 링크를 둔다. "500" 같은 전문 용어와 "기술적인 문제를 겪고 있습니다" 같은 막연한 표현은 피한다. 원인을 모르므로 언제 다시 된다는 말도 하지 않는다. 이 페이지는 잠깐만 보여야 하고, 빨리 고칠 수 없으면 서비스를 닫고 아래의 서비스 이용 불가 페이지로 바꾸라고 한다.

### 서비스 이용 불가 페이지 (503)
GOV.UK는 서비스를 일부러 닫았을 때(점검, 종료)를 503 페이지, 셔터(Shutter) 페이지로 따로 둔다. 셔터는 가게 문을 내리는 덧문이다. 제목은 "Sorry, the service is unavailable"(서비스를 이용할 수 없습니다)이고, 언제 다시 여는지 요일, 날짜, 시간까지 알려 주며, 영영 닫았다면 대신 무엇을 하면 되는지 쓴다. "점검", "개선" 같은 막연한 말은 피하라고 한다. 고장 페이지와 달리 원인과 재개 시점을 아는 경우이므로 더 구체적으로 쓸 수 있다.

## 오류 경계 (Error Boundary)
### 이름의 뜻
boundary의 사전적 의미는 경계, 경계선이다. 오류 경계는 화면 안에 선을 그어 두고, 그 선 안에서 일어난 오류가 선 밖으로 번지지 않게 막는 장치를 말한다. 선 안쪽이 실패하면 그 자리만 대체 화면(Fallback UI, 실패했을 때 대신 보여 줄 화면)으로 바꾸고, 선 밖의 화면은 그대로 둔다.

오류 경계라는 이름은 이 노트에서 확인한 자료 가운데 React 문서에서 쓰는 이름이다. 여기서는 실패를 한 영역에 가둔다는 생각을 설명하려고 빌려 쓴다.

건물의 방화문과 같다. 방 하나에 불이 나도 방화문이 닫히면 불이 그 방에 머물고, 나머지 층은 계속 쓸 수 있다.

### 왜 필요할까
화면을 그리는 코드 한 곳의 오류가 앱 전체를 하얗게 지워 버리면, 사용자는 멀쩡하던 부분까지 모두 잃는다. 오류 경계는 화면을 그리다 난 예외가 앱 전체를 지우지 않게 하는 장치다. 데이터 요청이 실패한 경우는 위의 일부만 실패 절처럼 그 영역의 상태로 따로 다룬다. 둘 다 실패를 실패한 영역 안에 가둔다는 같은 생각에서 나온다. 어디에 경계를 그을지는 어디까지가 함께 실패해도 되는 단위인지를 정하는 일이다.

### 예: React의 오류 경계
React 문서는 렌더링 중에 오류가 나면 React가 기본으로 그 UI를 화면에서 지운다고 쓰고, 이를 막으려면 UI의 일부를 오류 경계로 감싸 고장 난 부분 대신 오류 메시지 같은 대체 화면을 보여 주라고 한다. 경계를 얼마나 잘게 둘지에 대해서는 모든 컴포넌트를 감쌀 필요는 없고, 오류 메시지를 보여 주는 것이 말이 되는 자리를 생각하라고 한다. 메시지 앱이라면 대화 목록 전체나 메시지 하나하나를 감싸는 것은 말이 되지만, 프로필 사진 하나하나를 감싸는 것은 그렇지 않다는 예를 든다.

같은 문서는 오류 경계가 잡지 못하는 오류도 밝힌다. 이벤트 핸들러, 서버 렌더링, `setTimeout` 같은 비동기 코드(예외는 `startTransition` 에 넘긴 함수), 오류 경계 자신에서 난 오류다. 그래서 버튼을 눌러 보낸 요청의 실패 같은 것은 오류 경계와 별도로 그 자리에서 오류 상태로 바꿔 보여 줘야 한다. 구현 방법은 [React 문서](https://react.dev/reference/react/Component#catching-rendering-errors-with-an-error-boundary)를 본다. 다른 프레임워크에도 비슷한 장치가 있는지는 이 노트에서 확인하지 않았다(확인 필요).

## 접근성
### 진행을 막는 오류는 알리거나 포커스를 옮긴다
화면 한쪽에 오류가 새로 나타나도 스크린 리더는 포커스 자리를 따라 읽으므로 알려 주지 않는다. 사용자가 더 나아갈 수 없게 막는 오류라면 둘 중 하나를 한다. 오류로 포커스를 옮기거나, 포커스는 두고 `role="alert"` 로 알린다.

MDN은 폼을 채우는 중 스크립트로 오류 메시지를 붙이는 경우를 `alert` 역할이 딱 맞는 상황으로 들고, alert 요소는 포커스를 받을 필요가 없다고 쓴다. 주의할 점도 함께 든다. alert는 페이지를 열 때부터 있던 내용이 아니라 나중에 나타나는 내용에 쓴다. 메시지가 이미 들어 있는 alert 요소를 새로 만들어 붙이면 내용 변화가 아니라서 대개 읽히지 않으므로, 비어 있는 컨테이너를 미리 두고 나중에 글자를 넣는다. 또 alert에는 글자만 넣고 링크나 버튼 같은 조작 요소는 넣지 말라고 한다. 그래서 다시 시도 버튼은 alert 영역 밖에 둔다. 라이브 영역과 `status`, `alert` 의 차이는 [알림과 피드백](../알림과%20피드백(Notifications%20and%20Feedback)/README.md) 노트에 있다.

```html
<!-- 처음에는 비워 두었다가, 실패하면 글자를 넣는다 -->
<p role="alert" id="orders-error"></p>
<!-- 버튼은 alert 밖에 둔다 -->
<button type="button" hidden>주문 목록 다시 불러오기</button>
```

WCAG 4.1.3 상태 메시지(Status Messages) 이해 문서는 대화 상자 안의 오류처럼 포커스를 가져가는 것은 맥락 변화라서 이 기준의 대상이 아니고, 새 페이지로 넘어가는 것도 맥락 변화라고 쓴다. alert 역할은 맥락 변화가 없는 경우에만 필요하다고도 쓴다. 정리하면 페이지 전체를 오류 페이지로 바꾸거나 포커스를 오류로 옮겼다면 따로 alert를 붙일 필요가 없고, 포커스를 두고 영역 하나만 오류로 바뀔 때 라이브 영역이 필요하다. 같은 문서는 입력란 위에 붙는 "Invalid entry", 폼에 붙는 "5 errors on page" 같은 글자를 상태 메시지의 예로 든다.

### 폼 위의 오류 요약
GOV.UK의 오류 요약(Error summary) 컴포넌트는 검증 오류가 하나뿐이어도 항상 오류 요약을 보여 주라고 한다. 위치는 본문(`main`)의 맨 위, 이동 경로나 뒤로 가기 링크가 있으면 그 아래이고 페이지 제목(`h1`) 위다. 제목은 "There is a problem"(문제가 있습니다)으로 두고, 요약의 각 항목은 해당 입력란으로 가는 링크로 만든다. 날짜처럼 여러 칸으로 된 질문은 오류가 있는 첫 칸으로, 라디오 버튼이나 체크박스는 첫 번째 선택지로 연결한다. 요약의 문구는 입력란 옆 오류 메시지와 똑같이 써서 보기에도 듣기에도 같은 뜻이 되게 한다.

GOV.UK의 스크립트는 페이지를 다시 보여 줄 때 키보드 포커스를 오류 요약으로 자동으로 옮긴다. 이 컴포넌트는 `role="alert"` 를 컴포넌트 바깥 요소가 아니라 안쪽 요소에 둔다. GOV.UK Frontend 4.4.0(2022년 11월)에서 JAWS 스크린 리더가 요약 전체를 읽지 않던 문제를 고치려고 이렇게 바꿨다고 쓴다.

아래 예는 앞의 MDN 주의와 어긋나 보인다. 요약은 페이지를 다시 그릴 때부터 내용이 들어 있고, alert 안에 링크 목록이 있다. GOV.UK 방식에서 요약이 읽히는 것은 주로 스크립트가 포커스를 요약으로 옮기기 때문이고, alert 안에 링크를 둔 것은 GOV.UK가 정한 구조다. 이 구조가 스크린 리더마다 어떻게 읽히는지는 이번에 확인하지 못했다(확인 필요). 직접 만들 때는 GOV.UK처럼 포커스를 옮기는 방식과, MDN처럼 비워 둔 alert에 글자만 넣는 방식 가운데 하나를 골라 일관되게 쓰는 편이 낫다(내 판단).

```html
<div class="error-summary">
  <div role="alert">
    <h2>문제가 있습니다</h2>
    <ul>
      <li><a href="#email">이메일 주소를 입력하세요</a></li>
      <li><a href="#phone">휴대폰 번호를 숫자로 입력하세요</a></li>
    </ul>
  </div>
</div>
```

GOV.UK 오류 메시지 컴포넌트는 입력란 옆 오류 메시지 앞에 화면에는 보이지 않는 "Error:"(오류:)를 붙여, 스크린 리더 사용자가 그 글이 오류라는 것을 듣게 한다. 다만 GOV.UK는 이 컴포넌트를 사용자가 고칠 수 없는 자격, 권한, 서비스 용량 문제에는 쓰지 말고, 앞에서 본 서비스 문제 페이지나 페이지를 찾을 수 없음 페이지를 쓰라고 한다. 오류 요약은 입력란에 붙은 오류를 모으는 도구이고, 서버 고장 같은 페이지 단위 실패를 담는 그릇은 아니다.

### 페이지 제목에 오류를 드러낸다
GOV.UK 검증 패턴은 검증 오류가 있으면 페이지 `title` 앞에 "Error: "를 붙이라고 하고, 오류 요약 컴포넌트 문서는 그 이유를 스크린 리더가 최대한 일찍 알리게 하려는 것이라고 쓴다. 스크린 리더는 페이지가 열리면 제목부터 읽으므로, 제목만 들어도 제출이 받아들여지지 않았다는 것을 안다. 404 페이지와 서비스 문제 페이지도 제목 자체가 "Page not found", "Sorry, there is a problem with the service"다.

```html
<title>오류: 연락처 입력 - 서비스 이름</title>
```

페이지를 새로 불러오지 않고 화면만 바꾸는 앱에서는 브라우저가 제목을 알아서 바꿔 주지 않으므로, 오류 화면으로 바뀔 때 제목도 함께 바꿔야 한다(내 판단).

### 색만으로 알리지 않는다
WCAG 1.4.1 색 사용(Use of Color, A 수준)은 색을 정보 전달의 유일한 시각적 수단으로 쓰지 말라고 요구한다. 이해 문서는 필수 입력란을 빨간색으로만 표시하는 것을 색에만 기댄 예로 들고, 빨간 라벨에 아이콘을 함께 붙이면 빨간색을 구분하지 못하는 사용자도 알 수 있다고 쓴다. 필수 입력란이나 오류가 난 입력란을 색 차이로만 표시하는 것은 실패 사례 F81로 따로 정리돼 있다. 오류 상태도 빨간 테두리만 두지 말고 글자와 아이콘을 함께 둔다. NN/g 채점표도 오류와 경고에만 쓰는 눈에 띄고 접근 가능한 표시를 세 가지 이상 쓰라고 한다.

### 오류와 관련된 WCAG 기준
알림과 피드백 노트에서 본 3.3.1을 다시 짚고, 오류 상태와 바로 이어지는 3.3.3과 3.3.4를 더하면 아래와 같다. 모두 WCAG 2.2 기준이다.

- 3.3.1 오류 식별(Error Identification, A 수준)은 입력 오류를 자동으로 찾아냈다면 어느 항목이 틀렸는지 알리고 오류를 글자로 설명하라고 요구한다
- 3.3.3 오류 수정 제안(Error Suggestion, AA 수준)은 입력 오류를 자동으로 찾아냈고 고치는 방법을 안다면, 보안이나 목적을 해치지 않는 한 그 방법을 알려 주라고 요구한다. 이해 문서는 오류를 알리기만 해서는 인지 장애나 시각 장애가 있는 사용자가 어떻게 고칠지 몰라 폼을 포기할 수 있다고 설명하고, 월 이름을 넣어야 하는 칸에 12를 넣으면 "December"(12월)를 말한 것인지 묻는 예를 든다
- 3.3.4 오류 예방(법률, 금융, 데이터)(Error Prevention (Legal, Financial, Data), AA 수준)은 법적 약속이나 금융 거래를 일으키는 페이지, 사용자가 관리하는 저장 데이터를 고치거나 지우는 페이지, 시험 답안을 제출하는 페이지에 적용된다. 이런 페이지는 제출을 되돌릴 수 있거나, 입력 오류를 검사해 고칠 기회를 주거나, 최종 제출 전에 검토하고 확인하고 고칠 방법을 주는 것 가운데 적어도 하나를 지켜야 한다. 이해 문서는 모든 일상적인 저장마다 확인 단계를 둘 필요는 없다고 쓴다

3.3.4는 오류가 난 뒤가 아니라 나기 전을 다룬다는 점이 다르다. 결제나 삭제처럼 실패하면 되돌리기 어려운 작업일수록, 오류 화면을 잘 만드는 것보다 오류가 나기 전에 확인할 기회를 주는 것이 먼저다(내 판단).

## 예제
[example.html](./example.html)은 가짜 주문 상세 페이지에서 이 노트의 실패 종류와 보여 주는 범위를 눌러 보는 예제다. HTML, CSS, 약간의 자바스크립트만 한 파일에 담았으므로 파일을 더블클릭하거나 브라우저 창에 끌어다 놓으면 바로 열린다. 서버나 빌드 과정은 필요 없고, 실제로 서버에 요청을 보내지도 않는다. 조작판(넓은 화면에서는 왼쪽, 좁은 화면에서는 위)에서 페이지 불러오기 결과(성공, 네트워크 끊김, 시간 초과, 서버 오류, 찾을 수 없음, 권한 없음, 일부만 실패)와 배송지 저장 결과를 고르면, `setTimeout` 으로 만든 가짜 요청이 그 결과대로 끝난다.

### 무엇을 보여 주나
가짜 요청은 연결 끊김이면 상태 코드 없이 실패하고, 찾을 수 없음, 권한 없음, 서버 오류는 404, 403, 500(추천 상품은 503)을 담아 실패한다. 시간 초과는 화면이 정한 시간이 지나 스스로 기다리기를 멈추는 실패라서 상태 코드가 없다. 화면은 이 코드를 실패 종류를 가르는 단서로만 쓰고 문구에는 숫자를 넣지 않는다. 한눈에 비교 표를 따라 연결 끊김은 연결을 확인한 뒤 다시 불러오라고, 시간 초과는 응답이 늦어 기다리기를 멈췄다고, 서버 오류는 "저희 쪽 문제로"를 앞세워 사용자 탓이 아니라고 쓴다. 그리기 중에 난 예외처럼 어느 쪽에도 들지 않는 실패는 원인을 지어내지 않고 다시 불러오라고만 쓴다. 로그인 필요(401)와 서버가 돌려준 검증 실패(400, 422)는 이 예제에 넣지 않았다.

배송 현황과 추천 상품은 각각 하나의 영역이다. 영역마다 요청과 그리기를 하나의 try로 감싸서, 한 영역이 실패해도 그 자리만 오류 상태로 바뀌고 다른 영역과 배송지 폼은 그대로 쓸 수 있다. React 없이 오류 경계 절의 생각만 옮긴 것이다. 일부만 실패를 고르면 추천 상품만 실패한다. 오류 문구는 처음부터 비어 있는 `role="alert"` 문단에 글자만 넣고, 다시 불러오기 버튼과 고객센터 링크는 그 밖에 둔다. 다시 불러오기는 그 영역만 다시 요청하고, 전에 받아 둔 목록은 지우지 않은 채 "마지막으로 불러온 배송 현황은 아래에 그대로 있습니다"처럼 덧붙인다. 같은 영역이 세 번 연달아 실패하면 나중에 다시 오거나 문의하라는 다른 길을 함께 보여 준다.

시간 초과를 고르면 가짜 서버는 10초 뒤에야 응답한다. 화면은 1.5초가 지나면 "평소보다 오래 걸리고 있습니다"를 보여 주고, 4초가 되면 기다리기를 멈추고 시간 초과 오류로 넘어간다. 늦게 도착한 응답은 무시한다. 이 예제는 기다리기만 멈추고 요청 자체를 취소하지는 않는다. 실제로 요청을 끊는 방법은 TODO의 화면 쪽 시간 제한 항목으로 남겨 두었다. 배송지 저장이 시간 초과로 끝나면 "저장하지 못했습니다"라고 단정하지 않고, 바뀌었는지 아직 알 수 없다고 쓴 뒤 주문 정보에서 지금 배송지를 확인하는 링크를 준다. 다만 이 예제의 주문 정보는 다시 불러오지 않는 고정 값이라서, 링크는 확인할 자리로 데려가는 데까지만 보여 준다. 실제 서비스라면 그 자리에서 배송지를 새로 불러와야 사용자가 같은 저장을 두 번 하지 않는다. 시간 기준 4초는 이 예제에서 임의로 정한 값이다.

찾을 수 없음과 권한 없음은 영역이 아니라 주문 자체를 볼 수 없는 경우로 보고 페이지 전체를 바꾼다. 머리글과 주요 메뉴는 남기고 본문만 오류 페이지로 바꾸며, 화면만 바뀌는 페이지이므로 `document.title` 을 직접 바꾸고 포커스를 새 `h1` 으로 옮긴다. 404 화면은 GOV.UK 패턴처럼 주소를 확인하는 방법과 주문 목록으로 가는 길을 주고, 숫자와 빨간 글자와 이동 경로는 넣지 않았다. 권한 없음 화면은 주문한 계정으로 다시 로그인하거나 고객센터에 묻는 길을 준다. 두 화면 모두 다시 해도 풀리지 않는 실패라서 다시 시도 버튼을 두지 않았다. 예제에는 주문 목록 화면이 따로 없어서 주문 목록으로 가기를 누르면 주문 상세로 돌아오고, 비어 있는 영역은 조작판에서 성공을 골라 다시 불러와야 채워진다.

배송지 폼은 제출할 때 입력을 검사한다. 오류가 있으면 본문 맨 위 `h1` 위에 오류 요약을 보여 주고 포커스를 요약으로 옮기며, 페이지 제목 앞에 "오류: "를 붙인다. 요약의 각 항목은 입력란으로 가는 링크이고, 누르면 라벨이 보이게 스크롤한 뒤 그 입력란에 포커스를 둔다. 입력란 옆에는 요약과 같은 문구를 두고, 화면에는 보이지 않는 "오류:"를 앞에 붙였다. 요약은 접근성 절에서 말한 두 방식 가운데 포커스를 옮기는 쪽을 골랐기 때문에 요약 안에는 `role="alert"` 를 두지 않았다. 반대로 검사를 통과한 뒤 저장이 연결 끊김이나 서버 오류로 실패하면 포커스는 저장 버튼에 그대로 두고, 비워 둔 `role="alert"` 문단에 "입력하신 내용은 그대로 남아 있습니다"를 담아 알린다. 저장 실패 문구에는 문의 경로를 넣지 않았는데, 여러 번 실패할 때 고객센터 링크를 보여 주는 것은 영역에만 만들었기 때문이다. 어느 경우든 입력한 값은 지우지 않는다.

오프라인 흉내 내기를 켜면 연결이 돌아올 때까지 남는 배너가 뜨고, 고른 결과와 상관없이 모든 요청이 연결 끊김으로 실패하지만 받아 둔 내용은 그대로 보인다. 브라우저의 `offline`, `online` 이벤트도 같은 배너를 켜고 끄되, MDN의 경고에 따라 기능을 막지는 않고 힌트로만 쓴다. 오류 표시는 빨간색에, 오프라인 배너는 노란 안내색에 느낌표 기호와 글자를 함께 두어 색만으로 알리지 않는다. 운영체제에서 동작 줄이기를 켜면(`prefers-reduced-motion`) 로딩 표시의 회전을 끈다.

### 확인한 것과 못 한 것
2026-11-02에 Playwright로 Chromium 계열 브라우저(설치된 Chrome)를 띄워 파일을 file:// 주소로 열고 모든 결과를 하나씩 골라 눌러 봤다. 콘솔 오류와 처리되지 않은 예외는 없었다. 실패 종류마다 다른 문구가 나오는 것, 시간 초과가 약 4.1초 만에 오류로 바뀌고 10초 뒤 늦은 응답이 화면을 덮지 않는 것, 다시 불러오기 뒤 성공하면 오류가 사라지는 것, 한 영역이 실패한 동안 다른 영역 버튼과 폼이 동작하는 것을 확인했다. 오류 요약이 포커스를 받고 링크가 각 입력란에 포커스를 주는 것, 제목 앞의 "오류: "가 붙었다가 검사를 통과하면 빠지는 것, 실패 뒤 입력값이 남는 것, 404와 권한 없음 화면에서 제목이 바뀌고 포커스가 `h1` 으로 가는 것도 확인했다. 오프라인 배너는 조작판 체크와 Playwright의 오프라인 전환 양쪽에서 나타났다가 사라졌다. 375px 너비에서 가로 스크롤이 생기지 않는 것과 동작 줄이기 설정에서 회전이 꺼지는 것도 확인했다.

실제 스크린 리더(NVDA, VoiceOver, TalkBack 등)로 듣는 확인은 하지 않았다. 그래서 `role="alert"` 문단과 오류 요약이 실제로 어떤 순서로 읽히는지, 포커스를 받은 요약이 제목부터 읽히는지는 이 예제로 확인하지 못했다(확인 필요). 요청은 모두 가짜라서 실제 네트워크 끊김, 실제 서버의 응답 지연, `Retry-After` 처리는 시험하지 않았다. 자동 재시도와 백오프는 이 예제에 넣지 않았다. Chrome 외의 브라우저와 실제 휴대폰 터치 조작도 확인하지 않았다.
