## 퍼센트 인코딩이란 ?
- 주소(URI, Uniform Resource Identifier)에 그대로 쓸 수 없는 글자를 `%`와 16진수 두 자리로 바꿔 적는 규칙. 치킨은 `%EC%B9%98%ED%82%A8`이 된다. 이 노트에서는 URI와 URL을 구분하지 않고 주소라고 부른다
- 글자를 먼저 UTF-8 바이트로 바꾸고, 바이트 하나하나를 `%XX`로 적는다. 받는 쪽은 같은 규칙을 거꾸로 따라 원래 글자로 되돌린다
- 주소의 문법을 정한 RFC 3986의 2.1절에 정해져 있다. 흔히 URL 인코딩이라고도 부른다

[쿼리스트링](../쿼리스트링(Query%20String)/README.md#특수-문자와-한글은-인코딩해서-보낸다) 노트에서 값 안의 `&`를 `%26`으로 바꿔야 하는 이유와 띄어쓰기가 `%20`과 `+` 두 가지로 적힌다는 것까지 봤다. 이 노트는 그 뒤를 다룬다. 어떤 글자를 바꿔야 하는지는 누가 정하는지, 같은 글자인데 자리에 따라 왜 다르게 다루는지, 그리고 자주 하는 실수를 본다.

### 인코딩 (Encoding)
사전적 의미는 부호(code)로 바꾸는 일이다. en-은 무엇으로 만든다는 뜻의 접두사다.
공학적으로는 정보를 정해진 규칙에 따라 다른 표현으로 바꾸는 일을 말한다. 반대로 원래 표현으로 되돌리는 일은 디코딩(Decoding)이다. 암호화와 달리 규칙이 공개되어 있어서 누구나 되돌릴 수 있다. 숨기려는 것이 아니라 상대가 읽을 수 있는 모양으로 바꾸는 것이 목적이다.

### 퍼센트 인코딩 (Percent-Encoding)
바꾼 글자 앞에 퍼센트 기호 `%`를 붙여서 붙은 이름이다.
공학적으로는 바이트 하나를 `%`와 그 바이트 값을 나타내는 16진수 두 자리로 적는 방식이다. 16진수는 0~9와 A~F 열여섯 글자로 수를 적는 방식이고, 앞에 붙은 0x는 16진수라는 표시다. 바이트 하나는 0부터 255까지의 값이라 16진수 두 자리(00~FF)에 딱 맞게 적힌다. 바이트 값이 0x26이면 `%26`, 0xEC이면 `%EC`로 적는다.

쿼리스트링 노트에서는 외국으로 편지를 보낼 때 한글 주소를 그쪽 우편 체계가 읽을 수 있는 글자로 바꿔 적는 것에 빗댔다. 퍼센트 인코딩은 여기서 한 걸음 더 나가서, 글자마다 바꿔 적을 모양이 표로 정해져 있다. 그래서 받는 쪽은 같은 표를 보고 원래 글자를 정확히 되찾는다.

<br/>

## 왜 주소에 쓸 수 있는 글자가 제한될까
RFC 3986은 주소에 쓰는 글자를 US-ASCII의 일부로 한정한다. 영문자, 숫자, 그리고 몇몇 기호뿐이다. 한글, 띄어쓰기, `"`나 `<` 같은 기호는 이 목록에 없다.

이유는 크게 두 가지다.

첫째, 주소는 아주 많은 곳을 거친다. 브라우저, 서버, 중간의 프록시, 로그 파일, 이메일 본문, 종이 인쇄물까지 지나간다. 이 중 어딘가가 한글이나 띄어쓰기를 제대로 다루지 못하면 주소가 깨진다. 누구나 같은 모양으로 읽고 옮겨 적을 수 있는 좁은 글자 집합만 쓰면 이런 사고가 줄어든다.

둘째, 주소 안의 몇몇 기호는 이미 다른 일을 하고 있다. `?`는 쿼리가 시작된다는 표시, `#`은 프래그먼트가 시작된다는 표시, `/`는 경로를 나누는 표시다. 값 안에 이 기호가 그대로 들어 있으면 받는 쪽은 그것이 데이터인지 구분 표시인지 알 수 없다.

그래서 목록 밖의 글자와, 구분 표시와 겹치는 글자를 데이터로 쓸 때는 퍼센트 인코딩으로 바꿔 적는다. 편지 봉투의 주소 칸 사이에 넣는 쉼표나 줄바꿈을 받는 사람 이름 안에 그대로 써 버리면 집배원이 어디서 이름이 끝나는지 헷갈리는 것과 같다.

<br/>

## 예약하지 않은 문자와 예약 문자
RFC 3986은 주소에 쓸 수 있는 글자를 두 무리로 나눈다. 구분 표시로 쓰려고 맡아 둔 글자와 그렇지 않은 글자다.

### 예약 문자 (Reserved Characters)
Reserved는 예약된, 따로 맡아 둔이라는 뜻이다.
공학적으로는 주소의 구분 표시로 쓰도록 맡아 둔 글자다. RFC 3986 2.2절은 이를 다시 두 무리로 나눈다.

- 일반 구분 문자(gen-delims): `:` `/` `?` `#` `[` `]` `@`
- 하위 구분 문자(sub-delims): `!` `$` `&` `'` `(` `)` `*` `+` `,` `;` `=`

delims는 delimiter(구분 기호)를 줄인 말이다. 일반 구분 문자는 주소 전체를 스킴, 호스트, 경로, 쿼리, 프래그먼트 같은 큰 부분으로 나누고, 하위 구분 문자는 그 부분 안을 다시 나누는 데 쓴다.

식당의 예약석과 비슷하다. 예약석에 누가 앉아 있으면 손님들은 그 자리를 예약한 사람이라고 읽는다. 아무나 앉으면 착각이 생긴다. 예약 문자도 그 자리에 있으면 받는 쪽은 구분 표시로 읽는다.

### 예약하지 않은 문자 (Unreserved Characters)
Unreserved는 예약 문자와 반대로 맡아 두지 않았다는 뜻이다.
공학적으로는 아무 특별한 역할이 없어서 어디에 써도 그대로 데이터로 읽히는 글자다. RFC 3986 2.3절이 정한 목록은 아래와 같다.

- 영문 대문자와 소문자 (A~Z, a~z)
- 숫자 (0~9)
- 기호 네 개: `-` `.` `_` `~`

이 글자들은 인코딩할 필요가 없다. 인코딩해도 뜻은 같아서, RFC 3986 6.2.2.2절은 이 글자를 인코딩한 `%41` 같은 값은 원래 글자(A)로 풀어서 정규화하라고 권한다.

### 각 예약 문자가 맡는 자리
일반 구분 문자는 주소의 큰 칸을 나눈다. 주소의 각 부분 이름은 [쿼리스트링 노트의 생김새와 규칙](../쿼리스트링(Query%20String)/README.md#생김새와-규칙)에 정리했다. 아래 도식에서 `=`와 `&`는 일반 구분 문자가 아니라 다음에 볼 하위 구분 문자다.

```
https://user@example.com:443/stores/3?sort=rating&page=2#review
     ://    @           :   /      / ?    =      &    = #
```

| 문자 | 맡는 자리 | 예 |
| --- | --- | --- |
| `:` | 스킴 끝, 호스트와 포트 사이 | `https:`, `example.com:443` |
| `/` | 경로의 칸 나누기. 두 개(`//`)는 호스트 부분의 시작 | `/stores/3` |
| `?` | 쿼리 시작 | `?sort=rating` |
| `#` | 프래그먼트 시작 | `#review` |
| `[` `]` | IPv6 주소를 감싸기 (IPv6 주소 안의 `:`와 포트의 `:`를 구분하려고) | `https://[2001:db8::1]/` |
| `@` | 사용자 정보와 호스트 사이 | `user@example.com` |

하위 구분 문자는 각 칸 안에서 쓰인다. 쿼리스트링의 `&`와 `=`가 대표적이다. 다만 RFC 3986은 쿼리 안을 `이름=값&이름=값`으로 쓰라고 정하지 않는다. 이 모양은 HTML 폼에서 굳어진 관례이고, `+`를 띄어쓰기로 읽는 것도 그 관례(뒤에서 볼 폼 방식)에서 나왔다. `;`이나 `,` 같은 나머지 글자도 스킴이나 프로그램이 칸 안을 나누고 싶을 때 쓰라고 맡아 둔 것이다. MDN은 이 중 `!` `'` `(` `)` `*` 는 실제로 정해진 구분 용도가 없다고 설명한다.

### 둘 다 아닌 글자
한글, 띄어쓰기, `"`, `<`, `>`, `%` 같은 글자는 두 목록 어디에도 없다. 이런 글자는 경로, 쿼리, 프래그먼트 어느 자리에 들어가든 인코딩해야 한다. 도메인 이름 자리의 한글은 사정이 달라서 마지막 절에서 따로 본다.

`%`는 따로 기억해 둔다. `%`는 인코딩이 시작된다는 표시이므로, 글자 `%` 자체를 데이터로 쓰려면 `%25`로 적어야 한다(RFC 3986 2.4절). 100%라는 값은 `100%25`가 된다.

<br/>

## 인코딩은 어떻게 할까
절차는 두 단계다.

1. 글자를 UTF-8 바이트로 바꾼다
2. 바꿔야 하는 바이트마다 `%`와 16진수 두 자리로 적는다

RFC 3986 2.5절은 새로 만드는 주소 체계라면 글자를 먼저 UTF-8로 바꾼 뒤, 예약하지 않은 문자가 아닌 바이트를 퍼센트 인코딩하라고 권한다. UTF-8은 세계의 글자를 바이트로 적는 규칙 중 하나이고(자세한 것은 별도 주제로 TODO에 남긴다), 지금 웹에서 가장 널리 쓴다. UTF-8은 영문자 하나를 1바이트로, 한글 한 글자를 3바이트로 적는다. 그래서 한글 한 글자는 `%XX`가 세 개 붙은 모양이 된다.

```js
console.log(Buffer.from('치', 'utf8'));  // <Buffer ec b9 98>
console.log(encodeURIComponent('치'));   // %EC%B9%98
console.log(encodeURIComponent('é'));    // %C3%A9
console.log(encodeURIComponent('A'));    // A
```

치는 UTF-8로 EC, B9, 98 세 바이트이고, 각각 앞에 `%`를 붙여 `%EC%B9%98`이 된다. é는 2바이트라 `%XX`가 두 개다. A는 예약하지 않은 문자라 바꾸지 않는다. (이 노트의 코드는 모두 Node.js v24.22.1, Windows에서 실행했다. Buffer는 Node.js에서 바이트를 보여 주는 도구다.)

디코딩은 거꾸로다. `%` 뒤의 16진수 두 자리를 바이트로 되돌리고, 모은 바이트를 UTF-8로 읽어 글자로 만든다.

<br/>

## 같은 글자라도 자리에 따라 다르다
예약 문자는 구분 표시로 쓰일 때와 데이터로 쓰일 때가 있다. 그래서 같은 `/`라도 어느 자리에 들어가느냐에 따라 그대로 둘지, 인코딩할지가 달라진다.

### 구분 표시일 때와 데이터일 때
파일 이름이 `a/b.txt`인 파일을 경로에 넣는다고 하자. 그대로 넣으면 `/files/a/b.txt`가 되어, 받는 쪽은 files 아래 a 폴더 안의 b.txt로 읽는다. 파일 이름 안의 `/`는 데이터인데 구분 표시로 오해받은 것이다. 데이터라는 것을 알리려면 `%2F`로 바꿔 `/files/a%2Fb.txt`로 보낸다.

```js
console.log('/files/' + 'a/b.txt');                     // /files/a/b.txt
console.log('/files/' + encodeURIComponent('a/b.txt')); // /files/a%2Fb.txt
```

RFC 3986 2.2절은 예약 문자를 그대로 쓴 주소와 그 글자를 퍼센트 인코딩한 주소를 같은 주소로 보지 않는다고 정한다. `/files/a/b.txt`와 `/files/a%2Fb.txt`를 같은 자원이라고 가정할 수 없다. 반면 예약하지 않은 문자는 인코딩해도 같은 주소로 본다. 예약 문자는 자리를 맡고 있으니 인코딩하면 뜻이 바뀌고, 예약하지 않은 문자는 맡은 자리가 없으니 뜻이 그대로다.

이 때문에 받는 쪽은 순서를 지켜야 한다. 먼저 구분 표시로 주소를 나누고, 나눈 조각 안에서 인코딩을 푼다(RFC 3986 2.4절). 먼저 풀어 버리면 `%2F`가 `/`로 바뀌어 구분 표시와 섞인다.

### 칸마다 허용하는 글자가 다르다
주소의 각 칸은 쓸 수 있는 글자가 조금씩 다르다. RFC 3986 3.4절은 쿼리 안에 `/`와 `?`를 그대로 쓸 수 있게 했다. 쿼리는 `#`이 나오거나 주소가 끝날 때까지이므로, 쿼리 안의 `?`는 이미 시작된 쿼리의 일부로 읽힌다. 반면 `#`은 쿼리 안에 그대로 두면 프래그먼트 시작으로 읽힌다.

```js
const a = new URL('https://example.com/?q=a/b?c');
console.log(a.searchParams.get('q')); // a/b?c

const b = new URL('https://example.com/?q=a#b');
console.log(b.searchParams.get('q')); // a
console.log(b.hash);                  // #b
```

경로에서는 사정이 다르다. 경로에 `?`가 그대로 나오면 그 자리에서 쿼리가 시작된다. 그래서 경로 안의 데이터 `?`는 `%3F`로 바꿔야 한다.

브라우저가 따르는 WHATWG URL 표준은 이 차이를 칸별 퍼센트 인코딩 집합(percent-encode set)으로 정해 두었다(1.3절). 경로용, 쿼리용, 프래그먼트용 집합이 따로 있고, 주소를 읽을 때 칸마다 맞는 집합에 든 글자만 인코딩한다. 자바스크립트의 `new URL()` 이 이 규칙을 따른다.

```js
const u = new URL('https://example.com/치킨 메뉴/a+b?q=양념 치킨&x=a+b#맛 집');
console.log(u.pathname); // /%EC%B9%98%ED%82%A8%20%EB%A9%94%EB%89%B4/a+b
console.log(u.search);   // ?q=%EC%96%91%EB%85%90%20%EC%B9%98%ED%82%A8&x=a+b
console.log(u.hash);     // #%EB%A7%9B%20%EC%A7%91
```

한글과 띄어쓰기는 어느 칸에서든 인코딩됐고, 예약 문자인 `+`와 `&`, `=`는 그대로 남았다. 주소를 읽는 쪽은 이 글자들이 구분 표시인지 데이터인지 알 수 없으니 손대지 않는 것이다. 값 안의 예약 문자를 인코딩하는 일은 주소를 만드는 쪽의 몫이다.

<br/>

## 두 번 인코딩하는 실수
이미 인코딩한 값을 한 번 더 인코딩하면 `%`가 `%25`로 바뀐다. `%EC`는 `%25EC`가 되고, 받는 쪽이 한 번 풀면 원래 글자가 아니라 `%EC`라는 문자열이 나온다.

편지를 봉투에 넣고, 그 봉투를 다시 큰 봉투에 넣어 보낸 것과 같다. 받는 사람은 봉투를 한 번만 뜯으니, 편지 대신 안쪽 봉투를 받게 된다.

```js
const once = encodeURIComponent('치킨 100%');
console.log(once);                                       // %EC%B9%98%ED%82%A8%20100%25
console.log(encodeURIComponent(once));                   // %25EC%25B9%2598%25ED%2582%25A8%2520100%2525
console.log(decodeURIComponent(encodeURIComponent(once))); // %EC%B9%98%ED%82%A8%20100%25
```

`%25`가 보이면 두 번 인코딩을 의심한다. 실제로는 이런 경우에 잘 생긴다.

- 값을 직접 인코딩한 뒤, 알아서 인코딩해 주는 도구에 다시 넘길 때. URLSearchParams는 값을 넣을 때 스스로 인코딩하므로, 미리 인코딩한 값을 넣으면 두 번 인코딩된다
- 이미 인코딩된 주소 전체를 encodeURI에 한 번 더 넣을 때. encodeURI는 `%`도 바꾼다

```js
const q = encodeURIComponent('양념 치킨');
console.log(new URLSearchParams({ q }).toString());
// q=%25EC%2596%2591%25EB%2585%2590%2520%25EC%25B9%2598%25ED%2582%25A8

console.log(encodeURI('%41')); // %2541
```

반대로 두 번 푸는 것도 문제다. `100%25`를 한 번 풀면 `100%`가 되는데, 이걸 다시 풀면 `%` 뒤에 16진수가 없어서 오류가 난다. 값 안에 원래 `%25`라는 글자가 있었다면 두 번 풀 때 `%`로 바뀌어 다른 값이 된다.

```js
console.log(decodeURIComponent('%2525'));                     // %25
console.log(decodeURIComponent(decodeURIComponent('%2525'))); // %
```

RFC 3986 2.4절은 같은 문자열을 두 번 이상 인코딩하거나 디코딩하지 말라고 정한다. 값이 지금 인코딩된 상태인지 아닌지를 한 곳에서만 정하고, 인코딩은 주소를 만들 때 한 번, 디코딩은 주소를 나눈 뒤 한 번만 한다.

<br/>

## 잘못된 %를 만났을 때
`%` 뒤에 16진수 두 자리가 오지 않으면 올바른 퍼센트 인코딩이 아니다. 이런 값을 만났을 때 어떻게 할지는 도구마다 다르다.

```js
try {
  decodeURIComponent('100%');
} catch (e) {
  console.log(String(e)); // URIError: URI malformed
}

console.log(new URLSearchParams('q=100%').get('q')); // 100%
console.log(new URLSearchParams('q=%ZZ').get('q'));  // %ZZ
console.log(new URL('https://example.com/100%').pathname); // /100%
```

decodeURIComponent는 URIError라는 오류를 던진다. 오류 문구는 자바스크립트 엔진마다 다르다. 위는 Node.js(V8 엔진)의 문구이고, MDN 예시에는 `malformed URI sequence` 라는 다른 문구가 나온다. 반면 URLSearchParams는 WHATWG URL 표준의 디코딩 절차(1.3절)를 따르는데, 이 절차는 `%` 뒤에 16진수 두 자리가 없으면 그 `%`를 그대로 둔다. `new URL()` 은 경로를 풀지 않고, 잘못된 `%`를 만나도 멈추지 않고 그대로 둔다. 그래서 둘 다 오류 없이 원래 글자를 남긴다.

사용자가 입력한 값이나 다른 곳에서 받은 주소를 decodeURIComponent로 풀 때는 이 오류를 잡아 둔다. 그렇지 않으면 `%` 하나 때문에 프로그램이 멈출 수 있다.

<br/>

## 대소문자: %2f와 %2F
16진수의 A~F는 대문자와 소문자 어느 쪽으로 써도 같은 값이다. RFC 3986 2.1절은 `%2f`와 `%2F`가 같다고 정하고, 일관성을 위해 인코딩할 때는 대문자를 쓰라고 권한다. 6.2.2.1절도 주소를 정규화(Normalization, 같은 주소를 한 가지 모양으로 맞추는 일)할 때 대문자로 맞추라고 한다.

디코딩하면 둘 다 같은 글자가 된다. 하지만 문자열로 비교하면 다르다.

```js
console.log(decodeURIComponent('%2f'), decodeURIComponent('%2F')); // / /
console.log(encodeURIComponent('/'));                              // %2F

console.log(new URL('https://example.com/a%2fb').href); // https://example.com/a%2fb
console.log(new URL('https://example.com/a%2Fb').href); // https://example.com/a%2Fb
```

`new URL()` 은 들어온 대소문자를 바꾸지 않고 그대로 둔다. 그래서 두 주소를 문자열로 비교하면 다르다고 나온다. 주소를 [캐시 키](../HTTP%20캐시(HTTP%20Caching)/README.md#캐시-키-cache-key)나 비교 기준으로 쓴다면, RFC가 같다고 본 주소도 프로그램은 다르게 다룰 수 있다. 직접 인코딩할 때는 대문자로 쓰고, 주소를 비교해야 하면 정규화한 뒤 비교한다. 자바스크립트의 인코딩 함수는 모두 대문자로 만든다.

<br/>

## 띄어쓰기: %20과 +
띄어쓰기는 퍼센트 인코딩으로 `%20`이다. 그런데 HTML 폼이 값을 보낼 때 쓰는 방식(application/x-www-form-urlencoded, 이하 폼 방식)은 띄어쓰기를 `+`로 적는다. 이 차이는 쿼리스트링 노트에서 봤다.

이 노트의 관점에서 짚을 것은 두 규칙이 서로 다른 문서에 있다는 점이다. RFC 3986에서 `+`는 하위 구분 문자일 뿐, 띄어쓰기라는 뜻이 없다. `+`를 띄어쓰기로 읽는 것은 WHATWG URL 표준 5장의 폼 방식이 정한 규칙이다. 5.1절의 읽는 절차에 `+`를 띄어쓰기로 바꾸는 단계가 있고, 5.2절의 쓰는 절차는 띄어쓰기를 `+`로 적는다. WHATWG 표준은 이 형식이 여러모로 기형적(aberrant monstrosity)이지만 HTML 폼 때문에 널리 쓰이고 있다고 적어 두었다.

그래서 같은 `a+b`도 어떤 규칙으로 읽느냐에 따라 값이 다르다. 앞의 `new URL()` 예시에서 경로의 `a+b`는 그대로 `a+b`였다. 쿼리의 `x=a+b`를 searchParams로 꺼내면 폼 방식으로 읽기 때문에 `a b`가 된다.

```js
const u = new URL('https://example.com/a+b?x=a+b');
console.log(u.pathname);              // /a+b
console.log(u.searchParams.get('x')); // a b
```

폼 방식이 POST 본문에서 어떻게 쓰이는지, 파일을 보낼 때 쓰는 multipart/form-data와 무엇이 다른지는 [폼 인코딩](../폼%20인코딩(Form%20Encoding)/README.md) 노트에 정리했다.

<br/>

## encodeURI, encodeURIComponent, URLSearchParams
자바스크립트에는 퍼센트 인코딩을 해 주는 도구가 여러 개 있다. 셋은 무엇을 남기고 무엇을 바꾸는지가 다르고, 그 차이는 앞에서 본 예약 문자와 폼 방식의 차이에서 나온다. 다른 언어에도 비슷한 구분이 있으니, 함수 이름보다 어느 규칙을 따르는지를 보면 된다.

같은 문자열을 셋에 넣어 보면 차이가 바로 보인다.

```js
const s = '치킨 a&b=c?d#e/f+g%h';

console.log(encodeURI(s));
// %EC%B9%98%ED%82%A8%20a&b=c?d#e/f+g%25h

console.log(encodeURIComponent(s));
// %EC%B9%98%ED%82%A8%20a%26b%3Dc%3Fd%23e%2Ff%2Bg%25h

console.log(new URLSearchParams({ q: s }).toString());
// q=%EC%B9%98%ED%82%A8+a%26b%3Dc%3Fd%23e%2Ff%2Bg%25h
```

encodeURI는 한글, 띄어쓰기, `%`만 바꾸고 `& = ? # / +`는 그대로 뒀다. encodeURIComponent는 이 문자열에 든 예약 문자를 모두 바꿨다. URLSearchParams는 encodeURIComponent와 비슷하지만 띄어쓰기를 `+`로 적었다.

기호만 따로 넣어 보면 남기는 글자가 더 분명해진다.

```js
console.log(encodeURI(";,/?:@&=+$#"));          // ;,/?:@&=+$#
console.log(encodeURIComponent(";,/?:@&=+$#")); // %3B%2C%2F%3F%3A%40%26%3D%2B%24%23

console.log(encodeURIComponent("-_.!~*'()"));                   // -_.!~*'()
console.log(new URLSearchParams({ q: "-_.!~*'()" }).toString()); // q=-_.%21%7E*%27%28%29
```

| 구분 | encodeURI | encodeURIComponent | URLSearchParams |
| --- | --- | --- | --- |
| 쓰는 곳 | 이미 모양이 갖춰진 주소 전체 | 주소에 넣을 값 하나 | 쿼리스트링 전체 |
| 따르는 규칙 | 퍼센트 인코딩 | 퍼센트 인코딩 | 폼 방식 (WHATWG 5장) |
| 그대로 두는 글자 | 영문, 숫자, `- _ . ! ~ * ' ( )`, 그리고 `; , / ? : @ & = + $ #` | 영문, 숫자, `- _ . ! ~ * ' ( )` | 영문, 숫자, `* - . _` |
| 띄어쓰기 | `%20` | `%20` | `+` |
| `%` | `%25`로 바꾼다 | `%25`로 바꾼다 | `%25`로 바꾼다 |

그대로 두는 글자 목록은 MDN의 encodeURI, encodeURIComponent 문서와 WHATWG URL 표준 1.3절의 폼 방식 집합 정의를 보고 적었고, 위 실행 결과와도 맞는다.

### encodeURI는 주소 전체에 쓴다
encodeURI는 주소의 모양을 유지하려고 예약 문자를 남긴다. 주소 전체를 넣어도 `://`, `?`, `#`이 살아 있다.

```js
console.log(encodeURI('https://example.com/치킨 메뉴?q=a&b#x'));
// https://example.com/%EC%B9%98%ED%82%A8%20%EB%A9%94%EB%89%B4?q=a&b#x
```

대신 값 안의 예약 문자도 함께 남긴다는 뜻이다. 위 결과에서 `q=a&b`의 `&`가 데이터였는지 구분 표시였는지는 이미 알 수 없다. MDN도 encodeURI는 이미 올바른 모양의 주소 전체에 쓰고, 값을 이어 붙여 주소를 만들 때는 값마다 encodeURIComponent를 쓰라고 안내한다.

### encodeURIComponent는 값 하나에 쓴다
이름의 Component는 구성 요소, 부품이라는 뜻이다. 주소 전체가 아니라 그 안에 들어갈 조각 하나를 인코딩한다는 의미다. 예약 문자를 대부분 바꾸므로(`! ' ( ) *` 는 남긴다. 아래에서 본다) 값이 어느 칸에 들어가도 구분 표시로 오해받지 않는다. 대신 주소 전체에 쓰면 구분 표시까지 바뀌어 주소가 망가진다.

```js
console.log(encodeURIComponent('https://example.com/치킨 메뉴?q=a&b#x'));
// https%3A%2F%2Fexample.com%2F%EC%B9%98%ED%82%A8%20%EB%A9%94%EB%89%B4%3Fq%3Da%26b%23x
```

이렇게 주소 전체를 바꾼 결과는 다른 주소의 쿼리 값으로 넣을 때 쓴다. 로그인 뒤 돌아갈 주소를 `?next=` 뒤에 붙이는 경우가 그렇다.

encodeURIComponent도 RFC 3986의 하위 구분 문자 중 `! ' ( ) *` 는 바꾸지 않는다. MDN은 RFC 3986이 이 글자들을 예약해 두었으므로, 더 엄격하게 맞추려면 이 글자들을 추가로 바꾸는 함수를 따로 쓰라고 소개한다.

### decodeURI와 decodeURIComponent
푸는 쪽도 짝이 있다. decodeURI는 예약 문자를 인코딩한 값은 풀지 않고 남긴다. 풀어 버리면 데이터였던 `/`가 구분 표시로 바뀌기 때문이다. decodeURIComponent는 모두 푼다.

```js
console.log(decodeURI('%2F%20%EC%B9%98'));          // %2F 치
console.log(decodeURIComponent('%2F%20%EC%B9%98')); // / 치
```

### URLSearchParams는 다른 규칙을 따른다
URLSearchParams는 퍼센트 인코딩이 아니라 폼 방식을 따른다. 띄어쓰기를 `+`로 적는 것 말고도 `!`, `'`, `(`, `)`, `~`까지 인코딩한다. 반대로 `*`는 남긴다. WHATWG URL 표준 1.3절은 폼 방식 집합을 영문, 숫자, `*`, `-`, `.`, `_`를 뺀 모든 글자라고 정한다.

`new URL()` 로 만든 주소의 searchParams도 같은 규칙이다. 주소를 읽을 때 쿼리의 띄어쓰기는 `%20`으로 적히지만, searchParams로 값을 하나라도 고치면 쿼리 전체를 폼 방식으로 다시 적는다. 그래서 원래 있던 값의 `%20`까지 `+`로 바뀐다.

```js
const u2 = new URL('https://example.com/?a=양념 치킨');
console.log(u2.href);
// https://example.com/?a=%EC%96%91%EB%85%90%20%EC%B9%98%ED%82%A8

u2.searchParams.append('b', '양념 치킨');
console.log(u2.href);
// https://example.com/?a=%EC%96%91%EB%85%90+%EC%B9%98%ED%82%A8&b=%EC%96%91%EB%85%90+%EC%B9%98%ED%82%A8
```

두 주소는 폼 방식으로 읽으면 같은 값이지만 문자열은 다르다. 앞의 대소문자 절처럼, 주소를 문자열로 비교할 때 이런 차이가 생길 수 있다.

정리하면, 주소를 통째로 다룰 때는 `new URL()`, 쿼리스트링을 만들 때는 URLSearchParams, 경로 조각처럼 값 하나를 끼워 넣을 때는 encodeURIComponent를 쓴다. 어느 쪽이든 한 값은 한 번만 인코딩한다.

<br/>

## 도메인 이름의 한글은 퓨니코드
주소 중 호스트 자리, 곧 도메인 이름에 들어간 한글은 보통 퍼센트 인코딩으로 보내지 않는다. 도메인 이름은 [DNS](../../Network/DNS(Domain%20Name%20System)/README.md)로 찾는 이름이고, 호스트 이름의 각 부분(레이블)에는 영문자, 숫자, 하이픈을 쓴다. RFC 3986 3.2.2절의 문법은 호스트에도 UTF-8 퍼센트 인코딩을 허용하지만, DNS로 찾을 이름이라면 찾기 전에 IDNA 형식으로 바꾸라고 정한다. 도메인 이름의 구조는 [주소체계](../../Network/주소체계(Addressing)/README.md#도메인-이름과-fqdn) 노트에 정리했다.

그래서 도메인 이름의 한글은 퓨니코드(Punycode)라는 다른 방식으로 바꾼다. RFC 3492는 퓨니코드를 국제화 도메인 이름(IDN, Internationalized Domain Name)을 응용 프로그램에서 다루는 방식인 IDNA(Internationalized Domain Names in Applications)에 쓰려고 만든 변환 방식이고, ASCII가 아닌 글자를 호스트 이름에 쓸 수 있는 글자(영문자, 숫자, 하이픈)로 나타낸다고 설명한다.

```js
console.log(new URL('https://한글.example.com/').hostname); // xn--bj0bj06e.example.com
```

같은 `new URL()` 이 경로의 한글은 `%XX`로 바꿨지만, 호스트의 한글은 `xn--`로 시작하는 이름으로 바꿨다. WHATWG URL 표준은 호스트를 읽을 때 도메인 이름을 ASCII로 바꾸는 절차를 거치게 한다(세부 절차는 TODO의 퓨니코드 주제로 미룬다). `xn--`는 퓨니코드로 바꾼 이름이라는 표시로 붙는 접두사(ACE prefix)이고, IDNA 표준 RFC 3490 5절이 이 값을 정했다. RFC 3490은 지금은 RFC 5890, 5891로 대체되었다.

<br/>

## 정리
- 퍼센트 인코딩은 글자를 UTF-8 바이트로 바꾸고 바이트마다 `%XX`로 적는 규칙이다. 16진수는 대문자로 쓴다
- 예약하지 않은 문자(영문, 숫자, `- . _ ~`)는 어디서든 그대로 쓴다
- 예약 문자는 구분 표시로 쓸 때는 그대로, 데이터로 쓸 때는 인코딩한다. 인코딩하면 다른 주소가 된다
- 받는 쪽은 먼저 구분 표시로 나누고, 그다음에 푼다. 인코딩도 디코딩도 한 번만 한다
- `%20`은 퍼센트 인코딩의 띄어쓰기, `+`는 폼 방식의 띄어쓰기다
- DNS로 찾는 도메인 이름의 한글은 퍼센트 인코딩이 아니라 퓨니코드로 바꾼다
