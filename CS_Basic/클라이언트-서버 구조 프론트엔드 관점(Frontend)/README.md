## 프론트엔드 관점의 클라이언트-서버란 ?
- 웹에서 클라이언트는 대부분 브라우저이고, 프론트엔드는 이 브라우저 안에서 동작하는 코드를 다룬다
- 브라우저는 서버에서 HTML, CSS, JavaScript를 받아 화면을 만들고, 이후에도 필요한 데이터를 서버에 계속 요청한다
- 일반 이론은 [클라이언트-서버 구조](../클라이언트-서버%20구조(Client-Server%20Architecture)/README.md) 문서에 정리했고, 이 문서는 웹 프론트엔드에서 그 구조가 어떻게 드러나는지를 다룬다

<br/>

## 브라우저라는 클라이언트
### 브라우저 (Browser)
사전적 의미는 둘러보는 사람. 동사 browse(이것저것 훑어보다)에서 왔다.
공학적으로는 웹 서버에서 문서를 받아 해석하고 화면에 보여주는 클라이언트 프로그램을 말한다. 사용자가 여러 페이지를 둘러보게 해 주는 도구라는 점에서 이름이 이어진다.

### 브라우저가 하는 일
1. URL을 해석하고 DNS로 서버의 IP 주소를 찾는다
2. 서버에 HTTP 요청을 보내 HTML을 받는다
3. HTML을 파싱하면서 필요한 CSS, JavaScript, 이미지를 추가로 요청한다
4. DOM과 CSSOM을 만들고 레이아웃을 계산해 화면에 그린다
5. JavaScript를 실행해 사용자 입력에 반응하고, 필요하면 서버에 데이터를 다시 요청한다

하나의 페이지를 보여주기 위해 요청이 한 번이 아니라 여러 번 오간다는 점이 핵심이다. 그래서 프론트엔드 성능 문제는 대부분 요청의 수, 크기, 순서 문제로 이어진다.

<br/>

## 서버와 통신하는 방식
### 문서 요청과 데이터 요청
초기의 웹은 링크를 누르거나 폼을 제출할 때마다 서버가 새 HTML 문서 전체를 내려주는 방식이었다. 화면 일부만 바꾸고 싶어도 페이지 전체를 다시 받아야 했다.

이후 JavaScript로 페이지를 유지한 채 데이터만 요청하는 방식(Ajax)이 자리 잡았다. 지금은 fetch API나 XMLHttpRequest로 서버의 API를 호출하고, JSON 같은 데이터만 받아 화면 일부를 갱신하는 방식이 일반적이다.

### API (Application Programming Interface)
사전적 의미에서 인터페이스는 경계면, 접점. 서로 다른 두 영역이 맞닿는 면이다.
공학적으로는 프로그램끼리 기능을 주고받기 위해 정해 둔 호출 규칙을 말한다. 웹에서는 클라이언트가 어떤 URL에 어떤 메서드로 요청하면 어떤 형식의 응답을 받는지를 정한 약속을 가리킨다.

<br/>

## 렌더링 위치
### 렌더링 (Rendering)
사전적 의미는 표현, 묘사. 무언가를 그려 내거나 다른 형태로 옮겨 나타내는 일이다.
공학적으로는 데이터와 코드를 바탕으로 사용자가 볼 화면을 만들어 내는 과정을 말한다. 웹에서는 HTML을 만드는 일과 브라우저가 그것을 화면에 그리는 일을 함께 가리킨다.

클라이언트-서버 구조에서 렌더링을 어느 쪽이 하느냐에 따라 방식이 나뉜다.

### CSR (Client-Side Rendering)
서버는 거의 빈 HTML과 JavaScript 번들만 보내고, 브라우저가 JavaScript를 실행해 화면을 만든다. 첫 화면이 뜨기까지 시간이 걸리고 검색 엔진이 내용을 읽기 어려울 수 있지만, 한 번 로드된 뒤에는 페이지 전환이 빠르다. 클라이언트에 처리를 많이 맡기는 팻 클라이언트에 가깝다.

### SSR (Server-Side Rendering)
요청이 올 때마다 서버가 데이터를 채운 HTML을 만들어 보낸다. 첫 화면이 빨리 보이고 검색 엔진에도 유리하지만, 요청마다 서버가 렌더링해야 하므로 서버 부담이 커진다.

### SSG (Static Site Generation)
빌드 시점에 HTML을 미리 만들어 두고, 요청이 오면 만들어 둔 파일을 그대로 보낸다. 가장 빠르고 서버 부담도 적지만, 내용이 자주 바뀌는 페이지에는 맞지 않는다.

### 하이드레이션 (Hydration)
사전적 의미는 수분 공급. 마른 것에 물을 채워 되살리는 일이다.
공학적으로는 서버가 보낸 정적인 HTML에 브라우저가 JavaScript 이벤트와 상태를 연결해 상호작용이 가능한 화면으로 만드는 과정을 말한다. SSR이나 SSG로 받은 화면은 하이드레이션이 끝나야 클릭 같은 입력에 반응한다.

| 구분 | CSR | SSR | SSG |
| --- | --- | --- | --- |
| HTML을 만드는 곳 | 브라우저 | 서버 (요청 시) | 서버 (빌드 시) |
| 첫 화면 속도 | 느림 | 빠름 | 가장 빠름 |
| 서버 부담 | 적음 | 큼 | 적음 |
| 검색 엔진 노출 | 불리 | 유리 | 유리 |
| 맞는 페이지 | 로그인 후 대시보드 | 자주 바뀌는 공개 페이지 | 블로그, 문서 |

## 상태 유지
HTTP는 무상태 프로토콜이라 서버는 같은 사용자가 보낸 요청끼리 이어 붙이지 못한다. 그래서 로그인 같은 상태를 유지하려면 클라이언트가 요청마다 자신을 증명할 정보를 함께 보내야 한다.

### 쿠키 (Cookie)
사전적 의미는 과자. 기술 용어로는 유닉스에서 프로그램끼리 주고받던 작은 데이터 조각을 부르던 매직 쿠키(Magic Cookie)라는 표현에서 왔다.
공학적으로는 서버가 응답 헤더로 내려주고 브라우저가 저장해 두었다가, 같은 서버에 요청할 때 자동으로 함께 보내는 작은 데이터를 말한다.

### 세션 기반 인증
로그인하면 서버가 사용자 정보를 서버 쪽 저장소에 두고, 그 정보를 찾을 수 있는 세션 ID만 쿠키로 내려준다. 서버가 상태를 들고 있는 상태 유지(Stateful) 방식이라 서버를 여러 대로 늘리면 세션 저장소를 공유해야 한다.

### 토큰 기반 인증
로그인하면 서버가 사용자 정보를 담고 서명한 토큰(JWT 등)을 내려주고, 클라이언트가 요청마다 이 토큰을 보낸다. 서버는 서명만 확인하면 되므로 상태를 저장하지 않아도 되지만, 이미 발급한 토큰을 중간에 무효화하기 어렵다.

### 브라우저 저장소
쿠키 외에도 localStorage, sessionStorage, IndexedDB가 있다. 이들은 요청에 자동으로 실리지 않고 JavaScript로만 읽고 쓴다. JavaScript로 읽을 수 있다는 것은 XSS 공격에도 노출된다는 뜻이라, 인증 정보를 어디에 둘지는 보안과 함께 판단해야 한다.

## 출처와 CORS
### 출처 (Origin)
사전적 의미는 기원, 근원. 무언가가 처음 나온 곳이다.
공학적으로는 리소스가 어디서 왔는지를 나타내는 프로토콜, 호스트, 포트의 조합을 말한다. 이 셋이 모두 같아야 같은 출처로 본다.

### 동일 출처 정책 (Same-Origin Policy)
브라우저는 기본적으로 한 출처에서 불러온 스크립트가 다른 출처의 응답을 읽지 못하게 막는다. 사용자가 로그인해 둔 다른 사이트의 정보를 악성 페이지가 몰래 읽어 가는 일을 막기 위해서다.

### CORS (Cross-Origin Resource Sharing)
프론트엔드와 API 서버의 출처가 다른 경우가 흔하기 때문에, 서버가 허용한 출처에는 예외를 두는 규칙이다. 서버가 응답 헤더로 어떤 출처의 요청을 허용하는지 알려 주면 브라우저가 그 응답을 스크립트에 넘겨준다. 특정 조건의 요청은 본 요청 전에 OPTIONS 메서드로 사전 요청(Preflight)을 먼저 보낸다.

CORS 오류는 서버가 요청을 거부한 것이 아니라 브라우저가 응답을 막은 것이다. 같은 요청을 서버끼리 보내면 문제가 생기지 않는 이유가 여기에 있다.

## 실시간 통신
요청-응답 모델에서는 클라이언트가 먼저 묻지 않으면 서버가 데이터를 보낼 수 없다. 채팅이나 알림처럼 서버에서 먼저 알려야 하는 기능을 위해 몇 가지 방식이 쓰인다.

### 폴링 (Polling)
사전적 의미는 여론 조사, 투표. 여기서는 주기적으로 상태를 물어보는 일을 뜻한다.
공학적으로는 클라이언트가 일정 간격으로 서버에 새 데이터가 있는지 반복해서 요청하는 방식을 말한다. 구현이 쉽지만 바뀐 것이 없어도 요청이 계속 나간다.

### 롱 폴링 (Long Polling)
클라이언트가 요청을 보내면 서버가 새 데이터가 생길 때까지 응답을 미뤘다가 보낸다. 응답을 받으면 클라이언트는 바로 다음 요청을 보낸다.

### SSE (Server-Sent Events)
하나의 HTTP 연결을 열어 두고 서버가 클라이언트로 이벤트를 계속 흘려보내는 방식. 서버에서 클라이언트로 가는 단방향 통신이다.

### 웹소켓 (WebSocket)
HTTP로 연결을 시작한 뒤 프로토콜을 전환해, 연결을 유지한 채 양쪽이 언제든 메시지를 주고받는 방식. 양방향 통신이라 채팅, 협업 도구, 실시간 대시보드에 쓰인다.
