## 소켓이란 ?
- 프로그램이 네트워크로 데이터를 주고받을 때 쓰는 출입구
- 운영체제가 만들어 주고, 프로그램은 이 출입구에 데이터를 넣고 꺼내기만 하면 실제 전송은 운영체제가 처리한다
- 클라이언트-서버 구조에서 클라이언트와 서버는 결국 소켓 두 개가 연결되어 대화하는 것이다. 구조 자체는 [클라이언트-서버 구조](../../클라이언트-서버%20구조(Client-Server%20Architecture)/README.md) 문서에 정리했다

### 소켓 (Socket)
사전적 의미는 콘센트, 꽂는 구멍. 플러그를 꽂아 전기를 연결하는 자리다.
공학적으로는 네트워크 통신의 끝점(Endpoint)을 말한다. 프로그램이 네트워크에 꽂히는 자리라는 뜻에서 이 이름이 왔다.

<br/>

## 전화로 이해하기
소켓은 전화기와 비슷하다. 회사에 전화를 건다고 생각해 보자.

| 전화 | 네트워크 |
| --- | --- |
| 전화기 | 소켓 |
| 회사 대표 전화번호 | IP 주소 (어느 컴퓨터인지) |
| 내선 번호 | 포트 번호 (그 컴퓨터의 어느 프로그램인지) |
| 전화 걸기 | 연결 요청 (connect) |
| 수화기 들기 | 연결 수락 (accept) |
| 통화 | 데이터 주고받기 |
| 전화 끊기 | 연결 종료 (close) |

회사 번호만 알면 회사까지는 연결되지만, 누구와 통화할지는 내선 번호로 정해진다. 컴퓨터도 마찬가지다. IP 주소로 컴퓨터를 찾고, 포트 번호로 그 안의 프로그램을 찾는다.

<br/>

## 왜 소켓이 필요할까
데이터를 네트워크로 보내려면 할 일이 많다. 데이터를 작은 묶음(패킷)으로 나누고, 주소를 붙이고, 빠진 것이 있으면 다시 보내고, 랜카드를 움직여야 한다. 프로그램마다 이걸 직접 하면 너무 복잡하다.

그래서 이런 일은 운영체제가 맡고, 프로그램에는 간단한 출입구 하나만 준다. 그 출입구가 소켓이다. 전화기를 쓰는 사람이 전화망이 어떻게 이어지는지 몰라도 되는 것과 같다. 프로그램은 소켓에 쓰기(write)와 읽기(read)만 하면 된다.

```mermaid
flowchart LR
    subgraph PC1["내 컴퓨터"]
        direction TB
        A1["프로그램 (브라우저)"] --> A2["소켓"] --> A3["운영체제가 전송 처리"]
    end
    subgraph PC2["서버 컴퓨터"]
        direction TB
        B3["운영체제가 수신 처리"] --> B2["소켓"] --> B1["프로그램 (웹 서버)"]
    end
    A3 -- "네트워크" --> B3
```

## IP 주소와 포트
### IP 주소
네트워크에서 컴퓨터 한 대를 찾아가기 위한 주소다. 전화 비유에서는 회사 대표 번호에 해당한다. 구조와 종류는 [주소체계](../주소체계(Addressing)/README.md#ip-주소) 문서에 정리했다.

### 포트 (Port)
사전적 의미는 항구, 배가 드나드는 문이다.
공학적으로는 한 컴퓨터 안에서 데이터가 어느 프로그램으로 들어갈지 구분하는 번호를 말한다. 전화 비유에서는 내선 번호에 해당한다. [ARP](../ARP(Address%20Resolution%20Protocol)/README.md#데이터에-붙는-주소-정리) 문서에서 4계층이 다룬다고 한 번호가 이 포트 번호다.

포트 번호는 0부터 65535까지 있다. 자주 쓰는 서비스는 번호가 관례로 정해져 있다.

| 포트 | 서비스 |
| --- | --- |
| 22 | SSH (원격 접속) |
| 80 | HTTP (웹) |
| 443 | HTTPS (보안 웹) |
| 3306 | MySQL (데이터베이스) |

브라우저 주소창에 포트를 쓰지 않아도 되는 이유가 이것이다. https로 접속하면 브라우저가 알아서 443번으로 연결한다. 관례 번호가 아닌 포트에 서버를 띄우면 주소 뒤에 :3000처럼 포트를 직접 붙여야 한다. 개발할 때 자주 보는 localhost:3000은 내 컴퓨터 자신(localhost)의 3000번 포트라는 뜻이다.

### 연결 하나를 구분하는 방법
서버 하나에 수많은 사용자가 동시에 접속해도 대화가 섞이지 않는다. 연결마다 다음 네 가지 조합이 다르기 때문이다.

- 내 IP 주소
- 내 포트 번호
- 상대 IP 주소
- 상대 포트 번호

서버의 443번 포트에 천 명이 접속해도, 각 사용자의 IP 주소나 포트 번호가 달라서 천 개의 서로 다른 연결로 구분된다. 같은 내선 번호로 걸려 온 전화라도 건 사람의 번호가 다르면 다른 통화인 것과 같다.

## TCP 소켓과 UDP 소켓
소켓은 어떤 방식으로 데이터를 보낼지에 따라 두 종류로 나뉜다.

### TCP 소켓 (스트림 소켓, Stream Socket)
스트림은 시냇물이라는 뜻이다. 데이터가 끊김 없이 순서대로 흘러온다는 데서 온 이름이다.
전화와 같다. 먼저 연결을 맺고, 통화하고, 끊는다. 보낸 데이터는 빠짐없이 순서대로 도착한다. 웹, 메일, 파일 전송처럼 데이터가 하나라도 빠지면 안 되는 곳에 쓴다. 다만 웹 중에서도 HTTP/3는 UDP 위에서 동작하는 전송 프로토콜인 QUIC(퀵)을 쓴다.

### UDP 소켓 (데이터그램 소켓, Datagram Socket)
데이터그램은 데이터(data)와 전보(telegram)를 합친 말로, 한 통씩 따로 보내는 데이터라는 뜻이다.
편지와 같다. 연결 없이 주소만 적어서 바로 보낸다. 확인 절차가 없어 빠르지만 도착하는지, 순서가 맞는지는 보장하지 않는다. 실시간 게임, 영상 통화처럼 조금 빠져도 빠른 게 중요한 곳에 쓴다. DNS처럼 짧은 질문 하나를 주고받을 때도 UDP를 쓴다.

아래 내용은 클라이언트-서버 구조에서 가장 많이 쓰는 TCP 소켓을 기준으로 한다.

<br/>

## 서버가 연결을 받는 과정
가게를 열고 전화 주문을 받는 과정과 같다.

### 서버 쪽
1. socket으로 소켓을 만든다. 전화기를 하나 사는 단계다.
2. bind로 소켓에 IP 주소와 포트 번호를 묶는다. bind는 묶다라는 뜻이다. 전화기에 번호를 등록하는 단계다.
3. listen으로 연결 요청을 기다린다. listen은 귀 기울이다라는 뜻이다. 벨이 울리길 기다리는 단계다.
4. accept로 들어온 연결을 받아들인다. accept는 받아들이다라는 뜻이다. 수화기를 드는 단계다.
5. read와 write로 데이터를 주고받는다. 통화하는 단계다.
6. close로 연결을 닫는다. 전화를 끊는 단계다.

### 클라이언트 쪽
1. socket으로 소켓을 만든다.
2. connect로 서버의 IP 주소와 포트 번호에 연결을 요청한다. 가게 번호로 전화를 거는 단계다. 클라이언트는 bind를 하지 않아도 된다. 운영체제가 연결할 때마다 비어 있는 포트 번호를 임시로 붙여 주기 때문이다(임시 포트, Ephemeral Port).
3. read와 write로 데이터를 주고받는다.
4. close로 연결을 닫는다.

```mermaid
sequenceDiagram
    participant C as 클라이언트
    participant S as 서버
    Note over S: socket: 소켓 만들기
    Note over S: bind: 포트 번호 붙이기 (예: 443)
    Note over S: listen: 연결 요청 기다리기
    Note over C: socket: 소켓 만들기
    C->>S: connect: 연결 요청
    Note over S: accept: 연결 수락 (이 클라이언트 전용 소켓 생성)
    C->>S: write: 요청 보내기
    S-->>C: write: 응답 보내기
    C->>S: close: 연결 종료
```

### accept가 새 소켓을 만드는 이유
accept는 연결을 받을 때마다 그 클라이언트 전용 소켓을 새로 만든다. 처음 listen하던 소켓은 계속 다음 손님을 기다린다.

고객센터 내선 하나(443번)에 전화가 몰리는 상황을 떠올리면 쉽다. 걸려 온 전화는 상담원에게 하나씩 넘어가 각자 통화하고, 그동안에도 그 내선으로는 다른 전화가 계속 들어온다. 내선 번호를 지키는 자리가 listen 소켓이고, 상담원과의 통화 하나하나가 accept로 만들어진 소켓이다.

```mermaid
flowchart LR
    C1["클라이언트 1"] --> L["listen 소켓 (443번 내선)"]
    C2["클라이언트 2"] --> L
    C3["클라이언트 3"] --> L
    L -- "accept" --> S1["클라이언트 1 전용 소켓"]
    L -- "accept" --> S2["클라이언트 2 전용 소켓"]
    L -- "accept" --> S3["클라이언트 3 전용 소켓"]
```

### 연결 대기열
운영체제는 연결 과정(핸드셰이크)이 끝난 연결을 대기열에 줄 세워 두고, 프로그램이 accept를 부르면 하나씩 꺼내 준다. 고객센터의 통화 대기와 같다. 핸드셰이크 과정은 [TCP 연결 과정](../TCP%20연결%20과정(TCP%20Handshake)/README.md#소켓-함수와-연결해-보기) 문서에 정리했다. listen을 할 때 대기열 크기를 정할 수 있다. 대기열이 꽉 찼을 때 새 요청을 거절할지 무시할지는 운영체제마다 다르다.

## 코드로 보기
Node.js의 net 모듈로 만든 간단한 TCP 서버와 클라이언트다. Node.js는 socket, bind, listen, accept를 하나하나 부르지 않고 한 번에 처리해 준다.

```js
// server.js
const net = require('net');

// 연결이 들어올 때마다(accept) 그 클라이언트 전용 소켓이 콜백으로 넘어온다
const server = net.createServer((socket) => {
  socket.on('data', (data) => {
    socket.write(`받은 메시지: ${data}`);
  });
});

// socket + bind + listen
server.listen(3000);
```

```js
// client.js
const net = require('net');

// socket + connect
const socket = net.createConnection({ port: 3000 }, () => {
  socket.write('안녕');
});

socket.on('data', (data) => {
  console.log(data.toString());
  socket.end(); // close
});
```

터미널 하나에서 `node server.js` 를 켜 두고 다른 터미널에서 `node client.js` 를 실행하면 클라이언트에 아래처럼 찍힌다(Node.js 22, 윈도우 11에서 실행).

```text
받은 메시지: 안녕
```

## 소켓과 웹소켓은 다를까
이름이 비슷해서 헷갈리지만 다른 개념이다.

소켓은 운영체제가 제공하는 통신 출입구이고, 웹, 메일, 게임 등 거의 모든 네트워크 프로그램이 내부적으로 소켓을 쓴다. 웹소켓(WebSocket)은 브라우저와 서버가 연결을 유지한 채 양방향으로 대화하기 위한 프로토콜이다. 기본 규격(RFC 6455)의 웹소켓은 내부에서 TCP 소켓 위에서 동작한다. HTTP/3 위에서 웹소켓을 여는 방법도 표준(RFC 9220)으로 정해져 있는데, 이때는 UDP 위의 QUIC을 쓴다. 브라우저가 이 방식을 얼마나 지원하는지는 확인 필요다.

전화기(소켓)와 그 전화기로 쓰는 특정 통화 방식(웹소켓)의 관계에 가깝다. 웹소켓 자체는 [클라이언트-서버 구조 프론트엔드 관점](../../클라이언트-서버%20구조%20프론트엔드%20관점(Frontend)/README.md#웹소켓-websocket) 문서에 정리했다.
