## 캐싱이란 ?
- 캐싱(Caching)은 자주 쓰는 데이터의 사본을 원래 자리보다 빨리 꺼낼 수 있는 곳에 두고, 다음에 같은 데이터가 필요할 때 사본을 쓰는 기법이다
- 사본을 두는 곳을 캐시(Cache)라고 한다. CPU 안의 작은 메모리부터 브라우저, 서버의 메모리 저장소, 전 세계에 흩어진 콘텐츠 전송 네트워크(CDN, Content Delivery Network) 서버까지 모두 캐시가 될 수 있다
- 원본을 다시 가져오는 시간과 비용을 줄이는 대신, 사본이 원본과 달라질 수 있다는 문제를 함께 떠안는다

<br/>

## 캐시 (Cache)
사전적 의미는 숨겨 둔 저장소다. 프랑스어 cacher(숨기다)에서 온 말로, 나중에 쓰려고 식량이나 도구를 숨겨 둔 곳을 가리킨다.
공학적으로는 나중에 다시 쓸 데이터를 빠른 곳에 따로 담아 둔 저장소를 말한다. CPU 캐시처럼 쓰는 쪽이 캐시가 있는지 몰라도 데이터가 빨리 나오는 경우가 많아서, 숨겨 둔 저장소라는 뜻과 이어진다. 다만 뒤에서 볼 캐시 어사이드처럼 프로그램이 캐시를 직접 다루는 방식도 있다.

책상 위에 자주 보는 책 몇 권을 꺼내 두는 것과 같다. 책은 원래 서재 책장에 있지만, 매번 서재까지 가지 않고 책상에서 바로 집는다. 책상은 좁아서 모든 책을 올려 둘 수는 없다.

<br/>

## 왜 필요할까
컴퓨터 안의 저장 장치는 빠를수록 비싸고 작다. CPU 레지스터와 CPU 캐시는 아주 빠르지만 작고, 메모리(RAM)는 그보다 느리지만 크고, 디스크는 더 느리지만 훨씬 크다. 네트워크 건너편의 서버는 그보다도 멀다. 이렇게 빠르고 작은 저장소부터 느리고 큰 저장소까지 층층이 놓인 구조를 메모리 계층(Memory Hierarchy)이라고 한다.

캐싱이 효과가 있는 이유는 프로그램이 데이터를 고르게 쓰지 않기 때문이다. 방금 쓴 데이터는 곧 다시 쓰는 경우가 많고(시간 지역성, Temporal Locality), 어떤 데이터를 쓰면 그 근처 데이터도 곧 쓰는 경우가 많다(공간 지역성, Spatial Locality). 이 성질을 지역성(Locality)이라고 한다. 방금 읽은 책은 곧 다시 펴 보고, 한 권을 꺼내면 같은 칸의 다음 권도 곧 찾게 되는 것과 같다. 그래서 자주 쓰는 일부만 빠른 곳에 두어도 대부분의 요청을 빠르게 처리할 수 있다.

캐시에서 원하는 데이터를 찾으면 캐시 적중(Cache Hit), 없어서 원본까지 가야 하면 캐시 미스(Cache Miss)라고 한다.

<br/>

## 캐시가 놓이는 곳
같은 원리가 여러 층에서 쓰인다.

- CPU 캐시: 메모리에서 읽은 데이터를 CPU 가까이에 둔다
- 브라우저 캐시: 한 번 받은 HTML, CSS, 이미지 같은 파일을 브라우저에 두고 다시 받지 않는다
- CDN 캐시: 정적 파일(누구에게나 같은 내용으로 보내는 이미지, CSS 같은 파일)을 사용자와 가까운 지역의 서버에 사본으로 둔다
- 서버 측 캐시: 데이터베이스 조회 결과 같은 값을 Redis, Memcached 같은 메모리 저장소(데이터를 디스크가 아닌 메모리에 두는 데이터 저장 프로그램)에 둔다

브라우저의 LocalStorage, SessionStorage는 자바스크립트가 직접 값을 넣고 꺼내는 저장소다. 캐시처럼 쓸 수는 있지만, 언제 버리고 언제 새로 받을지를 브라우저가 대신 관리해 주지는 않는다.

<br/>

## 캐시를 채우고 갱신하는 방식
### 캐시 어사이드 (Cache-Aside)
레이지 로딩(Lazy Loading)이라고도 한다. 애플리케이션이 먼저 캐시를 보고, 없으면 원본(데이터베이스 등)에서 읽어 와 캐시에 넣은 뒤 돌려준다. 실제로 요청된 데이터만 캐시에 들어간다는 장점이 있다. 대신 원본이 바뀌어도 캐시는 저절로 바뀌지 않아서 오래된 사본이 남을 수 있다. 그래서 원본을 고칠 때 캐시 항목을 지우는(무효화, Invalidation) 방식과 함께 쓴다.

### 리드 스루 (Read-Through)
읽는 흐름은 캐시 어사이드와 비슷하지만, 원본에서 읽어 와 채우는 일을 애플리케이션이 아니라 캐시 쪽이 맡는다. 애플리케이션은 늘 캐시에만 묻는다. 캐시 어사이드와 달리 애플리케이션 코드에 원본을 읽는 로직이 없다.

### 라이트 스루 (Write-Through)
데이터를 쓸 때 원본과 캐시에 함께 쓴다. 캐시가 늘 최신 값을 갖는 대신, 쓰기마다 두 곳에 써야 해서 쓰기가 느려지고, 한 번도 읽히지 않을 데이터까지 캐시에 들어갈 수 있다.

<br/>

## 캐시를 비우는 방식
### 만료 (Expiration)와 TTL
TTL(Time To Live)은 사본이 살아 있을 시간이다. TTL이 지난 항목은 없는 것으로 보고 다음 요청 때 원본에서 다시 가져온다. 위의 채우는 방식과 따로 고르는 것이 아니라 함께 붙여 쓰는 정책이다. 너무 짧으면 원본을 자주 다시 읽고, 너무 길면 오래된 사본을 오래 보여 준다.

### 축출 (Eviction)
캐시는 원본보다 작아서 가득 차면 무언가를 내보내야 한다. 이것을 축출이라고 한다. 가장 오래 쓰지 않은 항목부터 내보내는 LRU(Least Recently Used)가 흔히 쓰인다. 책상이 꽉 차면 가장 오래 펼쳐 보지 않은 책을 서재에 돌려놓는 셈이다.

<br/>

## 캐시를 쓸 때 생각할 것
캐시의 가장 큰 문제는 사본이 원본과 달라지는 것이다. 자주 바뀌는 데이터일수록 TTL을 짧게 잡거나 원본이 바뀔 때 캐시를 지워야 한다. 캐시 서버가 여러 대라면 서버마다 다른 사본을 들고 있을 수도 있다. 또 CDN처럼 여러 사용자가 함께 쓰는 캐시에는 개인 정보처럼 한 사람만 봐야 하는 데이터를 두면 안 된다.
