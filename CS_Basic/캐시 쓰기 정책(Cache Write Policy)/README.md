## 캐시 쓰기 정책이란 ?
- 캐시 쓰기 정책(Cache Write Policy)은 캐시를 거쳐 데이터를 쓸 때 그 변경을 원본에 언제 반영하고, 캐시에 없던 데이터라면 캐시에 넣을지를 정한 규칙이다
- 쓰기 적중(Write Hit) 때 원본에 바로 쓰는 라이트 스루(Write-Through)와 나중에 몰아서 쓰는 라이트 백(Write-Back)이 대표적이고, 쓰기 미스(Write Miss) 때 데이터를 캐시로 가져올지를 정하는 쓰기 할당(Write Allocate)과 쓰기 비할당(No-Write Allocate)이 짝을 이룬다
- 같은 생각이 CPU 캐시에서도, 데이터베이스 앞에 둔 애플리케이션 캐시에서도 쓰인다

캐시, 캐시 적중과 미스, 축출, 캐시 어사이드 같은 기본 개념은 [캐싱](../캐싱(Caching)/README.md)에, CPU 캐시의 구조는 [CPU 캐시](../CPU%20캐시(CPU%20Cache)/README.md)에, 원본이 바뀐 뒤 캐시를 지우는 이야기는 [캐시 무효화와 캐시 스탬피드](../캐시%20무효화와%20캐시%20스탬피드(Cache%20Invalidation%20and%20Cache%20Stampede)/README.md)에 정리했다. 이 노트는 그 사이에 비어 있던 쓰기 쪽 이야기를 다룬다.

<br/>

## 쓰기는 어디에, 언제 반영할까
### 정책 (Policy)
사전적 의미는 어떤 일을 해 나가는 방침이다. 정부나 회사가 같은 종류의 일을 매번 같은 방식으로 처리하려고 미리 정해 두는 원칙을 가리킨다.
공학적으로 캐시 정책은 캐시가 특정 상황에서 어떻게 움직일지 미리 정한 규칙이다. [캐싱](../캐싱(Caching)/README.md#축출-eviction)의 LRU가 꽉 찼을 때 무엇을 내보낼지 정한 축출 정책이었다면, 쓰기 정책은 값을 바꿀 때 무엇을 할지 정한 규칙이다.

### 왜 따로 정해야 할까
읽기는 간단하다. 캐시에 사본이 있으면 사본을 쓰고, 원본은 그대로 둔다. 사본과 원본은 여전히 같다.

쓰기는 다르다. 캐시에 있는 사본을 바꾸는 순간 사본과 원본이 달라진다. 그래서 두 가지를 정해야 한다.

첫째, 쓰려는 데이터가 캐시에 있을 때(쓰기 적중) 원본에는 언제 반영하나. 지금 바로 반영하면 라이트 스루, 나중에 반영하면 라이트 백이다.

둘째, 쓰려는 데이터가 캐시에 없을 때(쓰기 미스) 캐시로 가져와서 쓰나, 원본에만 쓰나. 가져오면 쓰기 할당, 원본에만 쓰면 쓰기 비할당이다.

워싱턴 대학교 CSE351 강의 자료도 쓰기를 이 두 질문, 쓰기 적중 정책과 쓰기 미스 정책으로 나눠 설명한다. 아래에서 하나씩 본다.

<br/>

## 라이트 스루 (Write-Through)
### 정의
Through의 사전적 의미는 무엇을 뚫고 지나서, 처음부터 끝까지다. 터널을 통과해 반대편으로 나가는 모습을 떠올리면 된다.
공학적으로 라이트 스루는 캐시에 쓰는 값을 캐시에서 멈추지 않고 그대로 원본까지 함께 쓰는 정책이다. 쓰기가 캐시를 통과해 원본에 닿는다는 뜻이다. Drepper의 글은 캐시 라인에 쓰면 프로세서가 그 캐시 라인을 곧바로 메인 메모리에도 쓰는 방식이라고 설명한다.

[캐싱](../캐싱(Caching)/README.md)의 책상 비유로 보면, 책상 위 책에 메모할 때마다 서재에 가서 원본 책에도 똑같이 적는 것과 같다. 서재의 원본은 언제 봐도 최신이지만, 한 줄 적을 때마다 서재까지 다녀와야 한다.

### 왜 쓸까
원본이 늘 캐시와 같다는 것이 가장 큰 장점이다. 그래서 캐시가 통째로 사라져도 잃는 데이터가 없다. 캐시에서 항목을 내보낼 때도 원본에 이미 같은 값이 있으므로 그냥 버리면 된다. Drepper의 글은 라이트 스루를 캐시와 메모리를 일치시키는 가장 단순한 방법이라고 부른다. 다만 코어가 여럿이면 다른 코어 캐시의 사본까지 맞추는 장치가 따로 필요하다(아래 CPU 캐시에서의 모습).

### 대가
쓰기마다 원본까지 다녀와야 해서 쓰기가 느리다. 캐시는 원본이 느려서 두는 것인데, 쓰기에 한해서는 그 느린 원본을 매번 기다린다. 같은 위치에 짧은 시간 동안 여러 번 쓰면 그 횟수만큼 원본에 쓴다. Drepper의 글은 지역 변수(함수 안에서만 쓰는 변수) 하나를 계속 고치기만 해도 메모리로 가는 통로(버스)가 붐빈다는 예를 든다. 캐시에서 원본으로 가는 이 부담은 아래 실험에서 숫자로 본다.

<br/>

## 라이트 백 (Write-Back)
### 정의
Back의 사전적 의미는 뒤로, 원래 자리로 되돌려서다. Write back은 원래 자리로 되돌려 쓴다는 말이 된다.
공학적으로 라이트 백은 쓰기를 캐시에만 하고 원본에는 나중에 되돌려 쓰는 정책이다. 가장 흔한 때는 그 항목이 캐시에서 축출될 때이고, 정해 둔 시간이 지나거나 한가할 때 미리 쓰기도 한다. 워싱턴 대학교 강의 자료는 이것을 다음 단계(원본)에 쓰는 일을 그 캐시 라인이 축출될 때까지 미루는 것이라고 정리한다. 애플리케이션 캐시에서는 같은 생각을 라이트 비하인드(Write-Behind)라고 부르는 경우가 많다. Behind는 뒤에, 뒤처져서라는 뜻으로, 원본 반영이 캐시보다 뒤처져 따라온다는 의미다.

책상 위 책에만 메모해 두었다가, 책상이 꽉 차 그 책을 서재에 돌려놓을 때 원본에 한 번에 옮겨 적는 것과 같다. 서재까지 가는 일은 크게 줄지만, 옮겨 적기 전에 책상 위 책을 잃어버리면 그동안 적은 메모가 사라진다.

### 더티 비트 (Dirty Bit)
Dirty의 사전적 의미는 더러운, 때가 묻은이다.
공학적으로 더티 비트는 캐시 항목이 원본과 달라졌는지, 즉 캐시에서 고친 뒤 아직 원본에 반영하지 않았는지를 표시하는 1비트 표시다. 고쳤으나 반영하지 않은 항목을 더티(Dirty)하다고 하고, 원본과 같은 항목을 깨끗하다(Clean)고 한다.

라이트 백은 원본에 쓰는 일을 미루므로, 어느 항목을 나중에 원본에 써야 하는지 기억해야 한다. 더티 비트가 그 기억이다. 책상 위 책 중 원본에 아직 옮기지 않은 메모가 있는 책에 포스트잇을 붙여 두는 것과 같다.

### 축출될 때 원본에 쓴다
라이트 백 캐시도 [축출](../캐싱(Caching)/README.md#축출-eviction)로 항목을 내보낸다. 이때 더티 비트를 본다. Drepper의 글에 따르면 더티한 캐시 라인을 내보낼 때는 그 내용을 메모리에 써야 하고, 깨끗한 캐시 라인은 그냥 버리면 된다. 원본에 쓰는 일이 쓰기마다 일어나지 않고 축출 때 한 번 일어나는 것이다.

그래서 같은 항목에 짧은 시간 동안 여러 번 쓸수록(쓰기의 시간 지역성이 좋을수록) 라이트 백이 유리하다. 1000번을 고쳐도 축출될 때 마지막 값만 원본에 한 번 쓰면 된다. Drepper의 글은 프로세서가 메모리 통로가 한가할 때 더티한 캐시 라인을 미리 써 두고 더티 비트를 지워, 나중에 축출할 때 쓰기 없이 버릴 수 있게 하기도 한다고 적는다.

### 장애 때 유실될 수 있다
라이트 백의 대가는 원본이 잠시 옛 값을 들고 있다는 점이다. 더티한 항목이 원본에 쓰이기 전에 캐시가 사라지면 그 변경은 원본에 닿지 못하고 사라진다. 애플리케이션 캐시라면 캐시를 들고 있던 프로세스나 캐시 서버가 죽을 때다. 쓰기를 요청한 쪽은 이미 성공이라는 답을 받았는데 실제로는 저장되지 않은 것이다. CPU 캐시는 사정이 다르다. 원본인 메인 메모리도 전원이 끊기면 함께 지워지므로, 정전에 대비하는 문제는 디스크에 쓰는 단계에서 따로 다룬다(TODO의 페이지 캐시와 fsync).

애플리케이션 캐시에서 라이트 스루는 쓰기마다 원본에 쓰므로 캐시가 사라져도 이런 유실이 없다. 둘 중 무엇을 고를지는 쓰기 속도와 원본 쓰기 부담을 줄이는 대신 이 위험을 받아들일 수 있느냐로 정해진다.

## 직접 보기
2026-10-29에 Windows 11 Pro, Node.js v24.22.1에서 실행했다. 원본은 몇 번 쓰였는지 세는 Map으로, 캐시는 두 가지 정책으로 흉내 냈다. 라이트 백 캐시는 두 칸만 두고 꽉 차면 가장 오래 쓰지 않은 항목(LRU)을 내보낸다. 게시글 A의 좋아요 수를 1000번 올리는 사이에 게시글 B와 C에 한 번씩 쓴다.

```js
// write-policy.js
// 원본: 느린 저장소라고 가정하고, 몇 번 썼는지 센다
class Store {
  constructor() {
    this.data = new Map();
    this.writes = 0;
  }
  write(key, value) {
    this.writes += 1;
    this.data.set(key, value);
  }
}

// 라이트 스루: 캐시에 쓸 때마다 원본에도 바로 쓴다
class WriteThroughCache {
  constructor(store) {
    this.store = store;
    this.cache = new Map();
  }
  set(key, value) {
    this.cache.set(key, value);
    this.store.write(key, value);
  }
}

// 라이트 백: 캐시에만 쓰고 더티 표시를 남긴다. 쫓겨날 때나 flush 때 원본에 쓴다
class WriteBackCache {
  constructor(store, capacity) {
    this.store = store;
    this.capacity = capacity;
    this.cache = new Map(); // 키 -> { value, dirty }. Map은 넣은 순서를 기억한다
  }
  set(key, value) {
    if (!this.cache.has(key) && this.cache.size >= this.capacity) this.evict();
    this.cache.delete(key); // 지웠다 다시 넣어 가장 최근에 쓴 항목으로 만든다
    this.cache.set(key, { value, dirty: true });
  }
  evict() {
    // 맨 앞 항목이 가장 오래 쓰지 않은 항목이다 (LRU)
    const [key, entry] = this.cache.entries().next().value;
    if (entry.dirty) this.store.write(key, entry.value); // 더티면 원본에 쓰고 내보낸다
    this.cache.delete(key);
    console.log(`  축출 ${key}=${entry.value}, ${entry.dirty ? '더티라서 원본에 씀' : '깨끗해서 그냥 버림'}`);
  }
  flush() {
    for (const [key, entry] of this.cache) {
      if (entry.dirty) {
        this.store.write(key, entry.value);
        entry.dirty = false;
      }
    }
  }
}

// 게시글 A의 좋아요가 1000번 오르는 동안 B, C에 한 번씩 쓴다
function workload(cache) {
  let likesA = 0;
  for (let i = 0; i < 500; i++) cache.set('A', ++likesA);
  cache.set('B', 1);
  for (let i = 0; i < 500; i++) cache.set('A', ++likesA);
  cache.set('C', 1);
  return likesA + 2; // 요청한 쓰기 횟수 (A 1000번, B와 C 한 번씩)
}

const show = (store) => JSON.stringify(Object.fromEntries(store.data));

console.log('[라이트 스루]');
const s1 = new Store();
const n1 = workload(new WriteThroughCache(s1));
console.log(`  쓰기 요청 ${n1}번, 원본 쓰기 ${s1.writes}번, 원본 ${show(s1)}`);

console.log('[라이트 백, 캐시 두 칸, 끝에 flush]');
const s2 = new Store();
const c2 = new WriteBackCache(s2, 2);
const n2 = workload(c2);
console.log(`  flush 전 원본 쓰기 ${s2.writes}번, 원본 ${show(s2)}`);
c2.flush();
console.log(`  flush 후 원본 쓰기 ${s2.writes}번, 원본 ${show(s2)} (쓰기 요청 ${n2}번)`);

console.log('[라이트 백, flush 전에 프로세스가 죽었다고 가정]');
const s3 = new Store();
const c3 = new WriteBackCache(s3, 2);
workload(c3);
// 캐시는 프로세스 메모리에 있으므로 죽으면 함께 사라진다. 원본만 남는다
const lost = [...c3.cache].filter(([, e]) => e.dirty).map(([k, e]) => `${k}=${e.value}`);
console.log(`  남은 원본 ${show(s3)}, 원본에 닿지 못한 값 ${lost.join(', ')}`);
```

```text
[라이트 스루]
  쓰기 요청 1002번, 원본 쓰기 1002번, 원본 {"A":1000,"B":1,"C":1}
[라이트 백, 캐시 두 칸, 끝에 flush]
  축출 B=1, 더티라서 원본에 씀
  flush 전 원본 쓰기 1번, 원본 {"B":1}
  flush 후 원본 쓰기 3번, 원본 {"B":1,"A":1000,"C":1} (쓰기 요청 1002번)
[라이트 백, flush 전에 프로세스가 죽었다고 가정]
  축출 B=1, 더티라서 원본에 씀
  남은 원본 {"B":1}, 원본에 닿지 못한 값 A=1000, C=1
```

여러 번 실행해도 같은 출력이 나왔다. 무작위 요소가 없는 코드라서 그렇다. 이 실험에는 읽기가 없어 캐시의 모든 항목이 더티이고, 깨끗한 항목을 그냥 버리는 경우는 나오지 않는다.

라이트 스루는 쓰기 요청 1002번에 원본 쓰기도 1002번이다. 원본은 처음부터 끝까지 캐시와 같다.

라이트 백은 같은 1002번의 쓰기를 원본 쓰기 3번으로 끝냈다. A에 1000번 쓰는 동안 A는 계속 캐시에 머물며 더티 표시만 유지했고, C가 들어올 때 캐시가 꽉 차서 가장 오래 쓰지 않은 B가 축출되며 원본에 한 번 쓰였다. 남은 A와 C는 마지막 flush(캐시에 남은 더티 항목을 원본에 모두 쓰는 일)에서 한 번씩 쓰였다.

세 번째 경우가 유실이다. flush 전에 프로세스가 죽으면 원본에는 축출되면서 쓰인 B만 남는다. A의 좋아요 1000번과 C의 쓰기는 요청한 쪽이 모두 성공으로 받았지만 원본에 없다. 뒤에서 볼 Oracle Coherence는 항목이 바뀐 뒤 정해 둔 지연 시간이 지나면 원본에 써서, 원본이 그 시간 이상 뒤처지지 않게 한다. 위 코드는 그런 장치 없이 끝에 flush를 한 번만 부르는 가장 단순한 모양이라 유실 범위가 크다.

## 쓰기 미스 정책
쓰려는 데이터가 캐시에 없을 때의 선택이다. 위 실험의 라이트 백 캐시는 B와 C처럼 캐시에 없던 키를 쓸 때도 캐시에 넣었다. 이것이 쓰기 할당이다. 값을 통째로 덮어쓰는 이 실험에서는 원본에서 가져올 것이 없어 자리만 내주었다. CPU 캐시처럼 캐시 라인의 일부만 고치는 경우에는 아래처럼 나머지 부분을 먼저 가져와야 한다.

### 쓰기 할당 (Write Allocate)
할당(Allocate)의 사전적 의미는 몫을 나누어 정해 주는 것이다. 공학적으로는 메모리나 자리를 어떤 용도에 떼어 주는 일을 말한다.
쓰기 할당은 쓰기 미스가 나면 캐시에 자리를 내주고, 그 데이터를 원본에서 캐시로 가져온 뒤, 캐시에서 쓰기 적중처럼 처리하는 정책이다. 워싱턴 대학교 강의 자료는 이를 쓰기 때 가져오기(Fetch on Write)라고도 부르고, 그 위치에 이어서 쓰거나 읽을 일이 많을 때 좋다고 적는다.

CPU 캐시는 캐시 라인 단위로 데이터를 주고받으므로([CPU 캐시](../CPU%20캐시(CPU%20Cache)/README.md#캐시-라인-cache-line) 참고), 쓰기 할당에서는 4바이트만 쓰더라도 그 4바이트가 들어 있는 캐시 라인 전체를 메모리에서 가져온 뒤 그 일부를 고친다.

고칠 책을 서재에서 책상으로 가져와서 고치는 것과 같다. 한 번 가져오는 수고가 들지만, 그 책을 또 고치거나 읽을 때는 책상에서 바로 한다.

### 쓰기 비할당 (No-Write Allocate)
쓰기 비할당은 쓰기 미스가 나면 캐시는 건드리지 않고 원본에만 바로 쓰는 정책이다. 캐시를 돌아서 지나간다는 뜻에서 라이트 어라운드(Write Around)라고도 부른다.

책상으로 가져오지 않고 서재에 가서 그 자리에서 고치고 오는 것과 같다. 책상 자리를 차지하지 않지만, 다음에 그 책을 볼 때는 다시 서재까지 가야 한다.

### 보통 짝지어지는 조합
워싱턴 대학교 강의 자료는 라이트 백과 쓰기 할당을 짝짓는 것이 보통이고, 라이트 스루와 쓰기 비할당을 짝짓는 경우도 있다고 정리한다.

각 정책이 노리는 것을 보면 이유를 알 수 있다. 라이트 백은 같은 곳에 여러 번 쓰는 것을 캐시에서 받아 내 원본 쓰기를 줄이려는 정책이다. 그러려면 쓴 데이터가 캐시에 있어야 하므로 미스 때 가져오는 쓰기 할당과 맞는다. 라이트 스루는 어차피 쓰기마다 원본까지 가므로, 쓰기를 위해 데이터를 캐시에 가져와도 원본 쓰기는 줄지 않는다. 그래서 미스 때는 원본에만 쓰는 쓰기 비할당과 잘 어울린다. 다만 이것은 흔한 짝일 뿐이고, 라이트 스루에 쓰기 할당을 붙이는 조합도 가능하다. 위 실험의 라이트 스루 캐시도 캐시에 값을 넣었으니 그런 경우다.

## CPU 캐시에서의 모습
[CPU 캐시](../CPU%20캐시(CPU%20Cache)/README.md)는 프로그램이 직접 다루지 않고 하드웨어가 알아서 채우고 비운다. 쓰기 정책도 하드웨어가 정한다.

Drepper의 글(3.3.3절)은 라이트 스루를 단순하지만 느린 방식으로, 라이트 백을 성능이 훨씬 나을 수 있는 방식으로 설명한다. 라이트 백에서는 위에서 본 대로 고친 캐시 라인에 더티 표시를 하고, 그 캐시 라인이 축출될 때 메모리에 쓴다. 지금 쓰이는 개별 CPU 모델이 단계마다 어떤 정책을 쓰는지는 이 노트에서 제조사 문서로 확인하지 않았다(확인 필요).

라이트 백에는 코어가 여러 개일 때 생기는 문제가 하나 더 있다. 한 코어의 캐시에 더티한 캐시 라인이 있으면 메모리에는 옛 값이 있다. 이때 다른 코어가 같은 주소를 읽으면 메모리가 아니라 첫 번째 코어의 캐시에서 값을 받아야 한다. Drepper의 글은 이것을 라이트 백의 큰 문제로 꼽고, 다음 절에서 MESI로 푸는 방법을 설명한다. [CPU 캐시의 MESI](../CPU%20캐시(CPU%20Cache)/README.md#캐시-일관성과-mesi)에서 본 수정됨(Modified) 상태는 이 노트의 더티에, 다른 코어에는 사본이 없다는 뜻이 더해진 상태다.

Drepper의 글은 이 두 정책 말고도 그래픽 카드 같은 장치의 메모리에 여러 쓰기를 모아 한 번에 보내는 쓰기 결합(Write-Combining), 장치 레지스터처럼 아예 캐시하면 안 되는 주소에 쓰는 캐시 불가(Uncacheable)를 함께 소개한다. 입문 범위를 넘어서 TODO로 넘긴다.

## 애플리케이션 캐시에서의 모습
여기서 애플리케이션 캐시는 데이터베이스 앞에 Redis나 Memcached 같은 메모리 저장소를 두는 [서버 측 캐시](../캐싱(Caching)/README.md#캐시가-놓이는-곳)를 말한다. CPU 캐시와 원리는 같지만, 원본이 데이터베이스이고 캐시를 다루는 쪽이 하드웨어가 아니라 프로그램이라는 점이 다르다.

### 라이트 스루
[캐싱](../캐싱(Caching)/README.md#라이트-스루-write-through)에서 본 것처럼 데이터를 쓸 때 데이터베이스와 캐시에 함께 쓴다. AWS 문서의 예시는 데이터베이스를 고친 뒤 그 결과를 캐시에 넣는다. Oracle Coherence 문서는 캐시에 값을 넣는 호출이 데이터베이스에 저장을 마칠 때까지 끝나지 않으므로 쓰기 성능은 전혀 나아지지 않는다고 적는다.

AWS 문서는 라이트 스루의 단점도 두 가지 든다. 캐시 서버를 새로 띄우면 그 뒤로 쓰기가 일어나기 전까지 데이터가 캐시에 없다. 또 대부분의 데이터는 한 번도 읽히지 않는데도 쓰는 족족 캐시에 들어가 자리를 낭비한다. 그래서 캐시 어사이드와 TTL을 함께 쓰라고 권한다.

### 라이트 비하인드
Oracle Coherence 문서의 설명은 아래와 같다. 애플리케이션은 캐시에만 쓰고 바로 다음 일로 넘어간다. 바뀐 항목은 쓰기 대기열에 들어가고, 정해 둔 지연 시간이 지나면 다른 스레드가 데이터베이스에 쓴다. 지연 시간 안에 같은 항목이 여러 번 바뀌면 대기열의 항목만 바꿔치기되어 데이터베이스에는 한 번만 쓰인다. 위 실험에서 A에 1000번 쓴 것이 원본 쓰기 한 번이 된 것과 같은 효과다. 여러 항목의 쓰기를 데이터베이스 트랜잭션 하나로 묶을 수도 있다.

대신 문서는 미리 따져야 할 점도 적는다.

- 데이터베이스 쓰기가 캐시 쓰기가 끝난 뒤에 따로 일어나므로, 데이터베이스 쓰기가 실패해도 애플리케이션은 이미 성공으로 알고 있다
- 데이터베이스에 쓰는 순서가 바뀔 수 있다
- 다른 프로그램이 같은 데이터베이스를 직접 고치면 대기열의 쓰기와 충돌할 수 있다
- 대기열이 데이터베이스에 쓰이기 전까지는 캐시에만 있는 값이 유일한 최신 값이다

문서는 지연 시간이 연속된 변경 중 첫 변경부터 센다고 적는다. 그래서 데이터베이스는 캐시보다 지연 시간 이상 뒤처지지 않는다. 캐시 서버가 죽을 때 대기열을 어떻게 지키는지는 제품마다 다르고 이 노트에서는 다루지 않는다(TODO). 위 실험처럼 캐시가 프로세스 하나의 메모리에만 있다면 그 프로세스가 죽는 순간 대기열도 사라진다.

### 캐시 어사이드와 비교
[캐시 어사이드](../캐싱(Caching)/README.md#캐시-어사이드-cache-aside)에서 쓰기는 데이터베이스에만 하고, 캐시는 그 항목을 지우기만 한다. 캐시는 끝까지 사본일 뿐이고, 데이터의 기준은 늘 데이터베이스다. 세 방식을 쓰기 기준으로 비교하면 아래와 같다.

| 방식 | 쓸 때 데이터베이스 | 쓸 때 캐시 | 쓰기 응답 시간 | 캐시를 잃으면 |
| --- | --- | --- | --- | --- |
| 캐시 어사이드 | 바로 씀 | 항목을 지움 | 데이터베이스 쓰기만큼 | 다음 읽기에서 다시 채움, 잃는 데이터 없음 |
| 라이트 스루 | 바로 씀 | 새 값을 넣음 | 데이터베이스와 캐시 쓰기만큼 | 쓰기가 다시 올 때까지 비어 있음, 잃는 데이터 없음 |
| 라이트 비하인드 | 나중에 몰아서 씀 | 새 값을 넣음 | 캐시 쓰기만큼 | 아직 쓰이지 않은 변경을 잃을 수 있음 |

## 무효화와의 관계
[캐시 무효화](../캐시%20무효화와%20캐시%20스탬피드(Cache%20Invalidation%20and%20Cache%20Stampede)/README.md)는 원본이 바뀌었을 때 캐시의 옛 사본을 지우는 일이었다. 쓰기 정책은 그 원본을 바꾸는 쪽의 이야기라서 둘은 맞물린다.

### 라이트 스루는 지우기 대신 갱신을 고른 것이다
캐시 어사이드는 쓸 때 캐시를 지우고, 라이트 스루는 쓸 때 캐시에 새 값을 넣는다. 무효화 노트의 [쓸 때 지우기와 갱신](../캐시%20무효화와%20캐시%20스탬피드(Cache%20Invalidation%20and%20Cache%20Stampede)/README.md#쓸-때-지우기와-갱신)에서 본 두 선택지 중 갱신 쪽이다. 그래서 그 절에서 본 문제를 그대로 안는다. 두 요청이 거의 동시에 같은 항목을 고치면, 데이터베이스에 쓴 순서와 캐시에 쓴 순서가 엇갈려 캐시에 옛 값이 남을 수 있다. 또 서버마다 메모리에 캐시를 따로 두었다면 쓰기를 처리한 서버의 캐시만 새 값을 갖고, 다른 서버의 사본은 옛 값으로 남는다. 라이트 스루를 쓰더라도 TTL을 함께 걸어 두는 이유다.

### 라이트 백에서는 함부로 지울 수 없다
라이트 백(비하인드) 캐시의 더티 항목은 원본에 아직 없는 유일한 최신 값이다. 이것을 무효화한다고 그냥 지우면 그 변경이 사라진다. 그래서 더티 항목은 지우기 전에 원본에 먼저 써야 한다. 축출 때 더티 항목을 원본에 쓰고 내보내는 것과 같은 이유다. 캐시 어사이드에서 지우기가 몇 번을 해도 안전한 동작이었던 것은 캐시가 사본일 뿐이었기 때문인데, 라이트 백에서는 그 전제가 깨진다.

반대 방향도 있다. 원본이 캐시보다 늦으므로, 캐시를 거치지 않고 데이터베이스를 직접 읽는 프로그램은 옛 값을 본다. 데이터베이스를 직접 고치는 프로그램이 있으면 위 Coherence 문서의 지적처럼 나중에 도착한 대기열의 쓰기가 그 변경을 덮을 수 있다. 라이트 비하인드를 쓸 때는 모든 읽기와 쓰기가 캐시를 거치도록 하는 것이 전제가 된다.

### CPU 캐시에서는 하드웨어가 무효화한다
CPU 캐시에서는 다른 코어의 사본을 무효로 만드는 일을 하드웨어가 한다. [MESI](../CPU%20캐시(CPU%20Cache)/README.md#캐시-일관성과-mesi)에서 본 것처럼 한 코어가 공유된 캐시 라인에 쓰려면 다른 코어의 사본을 먼저 무효로 만든다. 라이트 백이라 메모리가 늦더라도, 다른 코어는 낡은 사본 대신 수정됨 상태의 캐시 라인을 가진 코어에서 값을 받는다. 애플리케이션 캐시에서 프로그램이 직접 챙겨야 했던 사본 무효화를 CPU는 하드웨어 일관성 규칙으로 처리한다. 그 규칙의 세부, 그리고 여러 주소에 쓴 순서가 다른 코어에 어떻게 보이는지(메모리 순서)는 별개 문제라서 TODO로 넘긴다.

- 메모리 순서 (여러 주소에 쓴 순서가 다른 코어에 보이는 방식)
- 운영체제 페이지 캐시의 지연 쓰기와 fsync (디스크 쓰기에서의 라이트 백, 확인 필요)
- 리프레시 어헤드 (Refresh-Ahead, 만료 전에 미리 다시 읽어 두기)
