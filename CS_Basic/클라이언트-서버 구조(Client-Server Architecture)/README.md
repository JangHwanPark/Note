## 클라이언트-서버 구조란 ?
- 네트워크로 연결된 시스템에서 서비스를 요청하는 쪽(클라이언트)과 서비스를 제공하는 쪽(서버)으로 역할을 나눈 분산 시스템 모델
- 클라이언트가 요청(Request)을 보내면 서버가 처리한 뒤 응답(Response)을 돌려주는 요청-응답 방식으로 동작한다
- 웹, 메일, 파일 전송, 데이터베이스 접속 등 대부분의 네트워크 서비스가 이 구조를 따른다

<br/>

## 등장 배경
초기에는 메인프레임(Mainframe) 한 대가 연산과 데이터를 모두 맡고, 사용자는 입출력만 하는 단말기(Terminal)로 접속했다. 모든 처리가 중앙 컴퓨터 한 대에 몰리기 때문에 비용이 크고 확장이 어려웠다.

이후 개인용 컴퓨터가 보급되면서 단말기 쪽도 연산 능력을 갖게 됐다. 그래서 화면 표시와 입력 처리 같은 일은 사용자 쪽 컴퓨터에 맡기고, 공유해야 하는 데이터와 핵심 처리만 서버에 두는 방식이 자리 잡았다. 처리 부담을 나누면서도 데이터는 한곳에서 관리할 수 있다는 점이 이 구조의 출발점이다.

<br/>

## 구성 요소
### 클라이언트 (Client)
사전적 의미는 의뢰인, 고객. 전문가에게 일을 맡기고 결과를 받는 사람이다.
공학적으로는 서비스를 요청하는 주체를 말한다. 일을 맡기는 쪽이므로 통신을 먼저 시작하며, 맡길 곳인 서버의 주소를 알고 있어야 한다.
요청을 보낼 때만 연결하고, 여러 서버에 동시에 요청할 수도 있다.

### 서버 (Server)
사전적 의미는 시중드는 사람, 음식을 내어 주는 사람. 동사 serve(제공하다, 시중들다)에서 왔다.
공학적으로는 요청을 기다렸다가 처리하고 결과를 돌려주는 주체를 말한다. 손님을 기다리는 점원처럼 클라이언트가 언제 요청할지 모르기 때문에 항상 실행 중이어야 하고, 클라이언트가 찾아올 수 있도록 고정된 주소(IP 주소와 포트 번호)를 가진다.
여러 클라이언트의 요청을 동시에 처리해야 하므로 멀티 프로세스, 멀티 스레드, 이벤트 루프 같은 동시성 처리 방식을 사용한다.

### 네트워크와 프로토콜 (Protocol)
프로토콜의 사전적 의미는 외교 의례, 의정서. 국가 간에 지켜야 할 형식과 절차를 정해 둔 약속이다.
공학적으로는 통신하는 양쪽이 지켜야 할 메시지 형식과 절차의 규칙을 말한다. 클라이언트와 서버는 서로 다른 하드웨어, 운영체제, 언어로 만들어져도 통신할 수 있어야 한다. 이를 위해 메시지 형식과 주고받는 순서를 미리 약속해 두는데, 이 약속이 프로토콜이다.
웹은 HTTP, 메일은 SMTP, 파일 전송은 FTP처럼 서비스마다 프로토콜이 있고, 대부분 TCP/IP 위에서 동작한다.

<br/>

## 동작 방식
### 요청-응답 모델 (Request-Response)
1. 서버가 특정 포트를 열어 두고 요청을 기다린다 (Listen)
2. 클라이언트가 서버의 IP 주소와 포트로 연결을 요청한다
3. 연결이 맺어지면 클라이언트가 프로토콜 형식에 맞춰 요청 메시지를 보낸다
4. 서버가 요청을 해석하고 처리한다
5. 서버가 처리 결과를 응답 메시지로 돌려준다
6. 통신이 끝나면 연결을 닫거나, 다음 요청을 위해 유지한다

### 소켓 (Socket)
사전적 의미는 콘센트, 꽂는 구멍. 플러그를 꽂아 전기를 연결하는 자리다.
공학적으로는 운영체제가 제공하는 네트워크 통신의 끝점(Endpoint). IP 주소와 포트 번호의 조합으로 식별된다. 프로그램이 네트워크에 연결되는 자리라는 점에서 콘센트에 비유할 수 있다.
서버는 소켓을 만들어 포트에 묶고(bind) 연결을 기다리며(listen), 요청이 오면 받아들인다(accept). 클라이언트는 소켓을 만들어 서버에 연결한다(connect). 이후 양쪽은 소켓을 통해 데이터를 읽고 쓴다.

<br/>

## 상태 유지 방식
### 무상태 (Stateless)
서버가 이전 요청의 정보를 기억하지 않는 방식. 매 요청이 독립적이므로 어떤 서버가 요청을 받아도 같은 결과를 낼 수 있어 확장이 쉽다. 대신 클라이언트가 필요한 정보를 요청마다 함께 보내야 한다. HTTP가 대표적이다.

### 상태 유지 (Stateful)
서버가 클라이언트별 상태를 저장하고 이어서 사용하는 방식. 요청마다 정보를 다시 보낼 필요가 없지만, 서버가 상태를 들고 있어 서버를 늘리거나 장애가 났을 때 상태를 옮기기 어렵다. FTP, 텔넷 같은 연결 지향 프로토콜이 해당된다.

<br/>

## 클라이언트 유형
### 씬 클라이언트 (Thin Client)
대부분의 처리를 서버에 맡기고 클라이언트는 입출력 위주로만 동작한다. 클라이언트 관리가 쉽지만 서버 부담과 네트워크 의존도가 높다.

### 팻 클라이언트 (Fat/Thick Client)
클라이언트가 상당한 처리를 직접 수행한다. 서버 부담이 줄고 오프라인 동작도 가능하지만, 클라이언트마다 프로그램을 설치하고 갱신해야 한다.

<br/>

## 계층 구조 (Tier)
### 2-Tier
클라이언트와 서버 두 계층. 클라이언트가 화면과 로직을 갖고 데이터베이스 서버에 직접 접속하는 형태가 많다. 구조가 단순하지만 클라이언트 수가 늘면 DB 연결이 몰리고, 로직이 바뀌면 모든 클라이언트를 갱신해야 한다.

### 3-Tier
표현 계층(Presentation), 응용 계층(Application), 데이터 계층(Data)으로 나눈 구조. 클라이언트는 응용 서버하고만 통신하고, 데이터 접근은 응용 서버가 맡는다. 계층마다 독립적으로 교체하고 확장할 수 있으며 DB가 외부에 직접 노출되지 않는다.

### N-Tier
3-Tier에 로드 밸런서(Load Balancer), 캐시 서버, 메시지 큐 같은 계층을 더 둔 구조. 계층이 많아질수록 유연해지지만 구성과 운영이 복잡해진다.

<br/>

## 확장 방식
### 수직 확장 (Scale-up)
서버 한 대의 CPU, 메모리 같은 성능을 높이는 방식. 구조를 바꿀 필요가 없지만 하드웨어 한계가 있고 비용이 빠르게 늘어난다.

### 수평 확장 (Scale-out)
서버 대수를 늘리고 요청을 나눠 받는 방식. 이론상 계속 늘릴 수 있고 일부 서버가 죽어도 서비스가 유지된다. 대신 요청을 분배할 로드 밸런서가 필요하고, 서버 간 상태와 데이터 일관성을 맞추는 문제가 생긴다. 서버가 무상태일수록 수평 확장이 쉽다.

<br/>

## 장단점
### 장점
- 데이터와 자원을 서버에서 한 번에 관리하므로 일관성 유지, 백업, 접근 제어가 쉽다
- 역할이 나뉘어 있어 클라이언트와 서버를 독립적으로 수정할 수 있다
- 서버의 처리 방식을 바꾸면 모든 클라이언트에 바로 반영된다

### 단점
- 요청이 서버로 몰리므로 사용자가 늘면 서버가 병목이 된다
- 서버가 멈추면 서비스 전체가 멈춘다 (단일 장애 지점, SPOF: Single Point of Failure)
- 서버를 항상 운영해야 하므로 유지 비용이 든다

<br/>

## P2P 구조와 비교
P2P(Peer-to-Peer)는 고정된 서버 없이 참여한 모든 노드가 클라이언트이면서 서버 역할을 하는 구조다.

| 구분 | 클라이언트-서버 | P2P |
| --- | --- | --- |
| 역할 | 요청자와 제공자가 고정 | 모든 노드가 요청자이자 제공자 |
| 데이터 관리 | 서버에 집중 | 각 노드에 분산 |
| 확장성 | 사용자가 늘수록 서버 부담 증가 | 사용자가 늘수록 자원도 함께 증가 |
| 장애 영향 | 서버 장애 시 전체 중단 | 일부 노드가 빠져도 동작 |
| 관리와 보안 | 중앙에서 통제하기 쉬움 | 통제와 신뢰 확보가 어려움 |
| 예시 | 웹, 메일, DB | 토렌트, 블록체인 |
