## CPU 캐시란 ?
- CPU 캐시(CPU Cache)는 CPU 칩 안에 있는 작고 빠른 메모리로, 메인 메모리(RAM)에서 읽은 데이터와 명령어의 사본을 담아 둔다
- 보통 L1, L2, L3처럼 여러 단계로 나뉘고, 숫자가 작을수록 CPU 코어에 가깝고 빠르지만 작다
- 프로그램이 직접 다루지 않아도 하드웨어가 알아서 채우고 비운다. 다만 캐시는 메모리를 덩어리 단위로 가져오고 자리가 작아서, 같은 코드라도 메모리를 읽는 순서에 따라 속도가 크게 달라질 수 있다

캐시라는 말의 뜻, 캐시 적중(Cache Hit)과 캐시 미스(Cache Miss), 지역성(Locality), 메모리 계층(Memory Hierarchy)의 일반적인 설명은 [캐싱 노트](../캐싱(Caching)/README.md#왜-필요할까)에 있다. 이 노트는 그 원리가 CPU 안에서 어떻게 구현되는지를 다룬다.

## 왜 필요할까
### CPU와 메모리의 속도 차이
CPU는 1초에 수십억 번 계산하는데, 메인 메모리에서 값 하나를 가져오는 데는 그보다 훨씬 오래 걸린다. 걸리는 시간은 흔히 사이클(Cycle)로 센다. 사이클은 CPU가 일하는 가장 작은 박자 한 번이다. Drepper의 글에 실린 Intel Pentium M 기준 값을 보면 레지스터(CPU 안에서 계산 중인 값을 담는 아주 작은 자리)는 1사이클 이하, L1 데이터 캐시는 약 3사이클, L2는 약 14사이클, 메인 메모리는 약 240사이클이다. 메모리에서 값을 하나 기다리는 동안 CPU가 수백 번 계산할 수 있었다는 뜻이다.

Pentium M은 오래된 CPU라서 요즘 CPU의 측정값도 함께 본다. 7-cpu.com이 i7-6700(Skylake, 4.0GHz)에서 잰 값은 L1 데이터 캐시 4사이클, L2 12사이클, L3 42사이클, 메모리는 42사이클에 51ns를 더한 정도다. 4.0GHz에서 1사이클은 0.25ns이므로 L1은 약 1ns, 메모리는 약 61ns(42사이클 10.5ns + 51ns)로 60배쯤 느리다. 두 자료 모두 예시 값이고, 실제 값은 CPU 모델과 클럭, 메모리 종류에 따라 다르다. 제조사 공식 문서의 최신 CPU 지연 시간 값은 확인하지 못했다(확인 필요).

### 해결: CPU 가까이에 작은 사본을 둔다
메모리를 CPU만큼 빠르게 만들면 좋겠지만, 빠른 메모리는 비싸고 칩 안에 넣을 수 있는 크기도 작다. 그래서 CPU 안에 작고 빠른 캐시를 두고, 최근에 쓴 데이터와 그 근처 데이터를 담아 둔다. 프로그램이 같은 데이터를 다시 찾으면 메모리까지 가지 않고 캐시에서 바로 꺼낸다.

[캐싱 노트](../캐싱(Caching)/README.md)의 비유로 말하면, 서재(메모리)까지 매번 가지 않도록 자주 보는 책을 책상(캐시) 위에 올려 두는 것과 같다. CPU 캐시는 이 책상이 CPU 바로 앞에 붙어 있는 경우다.

## L1, L2, L3
### 레벨 (Level)
사전적 의미는 수준, 단계, 층이다. 건물의 층을 셀 때처럼 높낮이가 있는 단계를 가리킨다.
공학적으로 캐시의 레벨은 CPU 코어에서 얼마나 가까운지를 나타내는 단계다. CPU가 데이터를 찾을 때 L1을 먼저 보고, 없으면 L2, 그다음 L3, 마지막으로 메인 메모리를 본다. 레벨 숫자가 커질수록 코어에서 멀어지고 느려지지만 용량이 커진다.

책상 위(L1), 책상 옆 책꽂이(L2), 같은 방 사람들이 함께 쓰는 공용 책장(L3), 건물 지하의 서재(메모리) 순서로 책을 찾는 것과 같다. 가까울수록 빨리 집지만 놓을 자리가 적다.

### 코어별 캐시와 공유 캐시
요즘 CPU는 한 칩 안에 코어(Core, 실제로 명령을 실행하는 계산 장치)가 여러 개 있다. 2007년에 쓰인 Drepper의 글은 L1만 코어마다 두고 그 위 단계를 코어들이 함께 쓰는 구성을 예로 든다. 이 노트를 쓴 컴퓨터는 아래에서 보듯 L1과 L2를 코어마다 두고 L3만 모든 코어가 함께 쓴다. 어디까지를 코어별로 두고 어디부터 공유하는지는 CPU 설계마다 다르다.

코어별 캐시는 작고 코어 바로 옆에 있어 빠르고, 다른 코어와 자리를 나눌 필요가 없다. 공유 캐시는 크기가 커서 여러 코어가 같은 데이터를 쓸 때 한 번만 담아 두면 된다. 대신 여러 코어가 자리를 나눠 써야 한다.

### L1은 명령어와 데이터로 나뉜다
CPU가 메모리에서 읽는 것은 데이터만이 아니다. 실행할 명령어(프로그램 코드)도 메모리에서 읽어 온다. 그래서 L1은 보통 명령어 캐시(L1i, Instruction Cache)와 데이터 캐시(L1d, Data Cache)로 나뉜다. Drepper의 글에 따르면 Intel은 1993년부터 명령어 캐시와 데이터 캐시를 따로 두었다. L2와 L3는 둘을 구분하지 않고 함께 담는 통합(Unified) 캐시인 경우가 많다.

### 세 단계 비교
아래 용량은 이 노트를 쓴 컴퓨터(Intel Core i7-9700F)에서 확인한 값이고, 지연 시간은 위에서 본 7-cpu.com의 Skylake 측정값이다. i7-9700F(Coffee Lake Refresh)는 i7-6700과 같은 Skylake 마이크로아키텍처를 바탕으로 해서 비슷하리라 보지만 같은 칩은 아니다. L3 크기(12MB와 8MB)와 클럭이 달라 특히 L3 지연은 차이가 날 수 있다. 다른 CPU에서는 값이 다르다.

| 단계 | 누가 쓰나 | 이 컴퓨터의 용량 | 지연 시간 예시 |
| --- | --- | --- | --- |
| L1 | 코어마다 따로 | 명령어 32KB, 데이터 32KB | 4사이클 |
| L2 | 코어마다 따로 | 256KB | 12사이클 |
| L3 | 8개 코어가 함께 | 12MB (12,288KB) | 42사이클 |

## 이 컴퓨터의 캐시 확인하기
윈도우에서는 PowerShell로 CPU 정보를 읽을 수 있다. 2026-10-28에 Windows 11 Pro에서 아래 명령을 실행했다.

```powershell
Get-CimInstance Win32_Processor | Select-Object Name,NumberOfCores,NumberOfLogicalProcessors,L2CacheSize,L3CacheSize
```

```text
Name                      : Intel(R) Core(TM) i7-9700F CPU @ 3.00GHz
NumberOfCores             : 8
NumberOfLogicalProcessors : 8
L2CacheSize               : 2048
L3CacheSize               : 12288
```

단위는 KB다. 여기서 L2 2048KB는 코어 8개의 L2를 모두 더한 값이다. `Get-CimInstance Win32_CacheMemory` 도 실행해 봤는데, L1을 512KB(코어 8개의 L1i와 L1d를 모두 더한 값)로 보여 줄 뿐 코어마다의 크기나 캐시 라인 크기(캐시가 메모리에서 한 번에 가져오는 덩어리 크기, 바로 다음 섹션에서 본다)는 알려 주지 않았다.

코어마다 나눠진 크기와 캐시 라인 크기는 윈도우 API인 `GetLogicalProcessorInformation` 으로 확인했다. 파이썬의 ctypes로 이 함수를 불러 캐시 항목의 단계, 종류, 크기, 라인 크기, 연관도를 출력했다. 출력은 mask만 다른 같은 항목이 코어마다 반복되어 한 코어분과 L3만 옮긴다.

```text
L1 Data        size=32KB line=64B assoc=8 mask=00000001
L1 Instruction size=32KB line=64B assoc=8 mask=00000001
L2 Unified     size=256KB line=64B assoc=4 mask=00000001
...
L3 Unified     size=12288KB line=64B assoc=12 mask=11111111
```

mask는 이 캐시를 쓰는 논리 프로세서(운영체제가 보는 CPU 하나, 이 컴퓨터는 코어 하나가 논리 프로세서 하나다)를 비트로 표시한 값이다. L1과 L2는 비트가 하나만 켜져 있어 코어 하나 전용이고, L3는 여덟 비트가 모두 켜져 있어 여덟 코어가 함께 쓴다는 것을 알 수 있다. 캐시 라인 크기는 모든 단계에서 64바이트였다. assoc는 뒤에서 볼 연관도다.

## 캐시 라인 (Cache Line)
### 정의
라인(Line)의 사전적 의미는 줄, 선이다. 글에서는 한 줄을, 물건에서는 한 줄로 늘어선 묶음을 가리킨다.
공학적으로 캐시 라인은 캐시와 메모리가 데이터를 주고받는 최소 단위다. CPU가 1바이트만 필요해도 캐시는 그 바이트가 들어 있는 한 덩어리(요즘 흔히 64바이트)를 통째로 메모리에서 가져와 한 줄에 담는다. Drepper의 글은 초기 캐시는 라인이 32바이트였고 지금은 64바이트가 일반적이라고 쓴다. 이 컴퓨터에서도 64바이트였다. 다만 모든 CPU가 64바이트인 것은 아니다.

마트에서 달걀이 하나 필요해도 한 판으로 사 오는 것과 같다. 하나만 쓸 생각이었어도 곧 다음 달걀이 필요해지면 다시 마트에 가지 않아도 된다.

### 왜 한 덩어리씩 가져올까
위에서 본 것처럼 메모리까지 한 번 다녀오는 데는 오래 걸린다. 그래서 한 번 다녀올 때 근처 데이터까지 함께 가져오면, 프로그램이 이어서 옆 데이터를 쓸 때 메모리에 다시 가지 않아도 된다. 4바이트 정수라면 한 줄에 16개가 들어가므로, 배열을 처음부터 차례로 읽으면 프리페치(TODO)를 빼고 생각할 때 16개 중 첫 번째만 미스가 나고 나머지 15개는 적중한다.

## 지역성이 CPU 캐시에서 드러나는 모습
[캐싱 노트](../캐싱(Caching)/README.md#왜-필요할까)에서 본 두 가지 지역성이 CPU 캐시에서는 아래처럼 나타난다.

시간 지역성은 같은 데이터를 짧은 시간 안에 다시 쓰는 성질이다. 반복문 자체의 명령어, 반복문 안에서 여러 번 다시 읽는 작은 표가 그렇다. 한 번 캐시에 올라오면 반복이 끝날 때까지 L1에 머물며 계속 적중한다.

공간 지역성은 방금 쓴 데이터 근처를 곧 쓰는 성질이다. 배열을 앞에서부터 차례로 읽는 경우가 대표적이다. 위에서 본 대로 캐시 라인 하나를 가져오면 옆 칸들이 함께 올라오기 때문에, 차례로 읽는 코드는 캐시 라인을 남김없이 쓴다. 반대로 메모리를 멀리멀리 건너뛰며 읽으면 매번 새 캐시 라인을 가져오면서 그 안의 64바이트 중 몇 바이트만 쓰고 버린다.

## 직접 재 보기
아래 두 실험은 Windows 11 Pro, Intel Core i7-9700F(8코어 8스레드), Node.js v24.22.1에서 2026-10-28에 실행했다. 시간은 실행할 때마다 달라지고, 컴퓨터와 그때 함께 돌고 있던 프로그램, 자바스크립트 엔진의 최적화(자주 도는 코드를 실행 중에 기계어로 바꾸는 JIT 컴파일)에 따라서도 달라진다. 절대 값보다 두 경우의 차이를 본다.

### 행 순서와 열 순서
4096 x 4096 크기의 정수 표를 한 줄로 펼친 배열에 담고, 같은 값을 두 가지 순서로 모두 더한다. 표의 r번째 행 c번째 칸은 배열의 `r * N + c` 번째 자리에 있다. 그래서 한 행의 칸들은 메모리에 붙어 있고, 같은 열에서 아래 칸으로 가면 한 행 길이(4096칸 x 4바이트 = 16KB)만큼 건너뛴다.

```js
const N = 4096;
const a = new Int32Array(N * N); // N x N 표를 한 줄로 펼친 배열 (64MB)
a.fill(1);

function rowOrder() { // 행 순서: 메모리에 놓인 순서대로 읽는다
  let sum = 0;
  for (let r = 0; r < N; r++)
    for (let c = 0; c < N; c++) sum += a[r * N + c];
  return sum;
}

function colOrder() { // 열 순서: 한 번 읽을 때마다 16KB씩 건너뛴다
  let sum = 0;
  for (let c = 0; c < N; c++)
    for (let r = 0; r < N; r++) sum += a[r * N + c];
  return sum;
}

function time(fn) {
  const t = performance.now();
  const s = fn();
  return [(performance.now() - t).toFixed(0), s];
}

for (let i = 0; i < 5; i++) {
  const [rt, rs] = time(rowOrder);
  const [ct, cs] = time(colOrder);
  console.log(`행 순서 ${rt}ms, 열 순서 ${ct}ms (합계 ${rs}, ${cs})`);
}
```

한 번 실행한 출력은 아래와 같다.

```text
행 순서 19ms, 열 순서 239ms (합계 16777216, 16777216)
행 순서 16ms, 열 순서 239ms (합계 16777216, 16777216)
행 순서 17ms, 열 순서 207ms (합계 16777216, 16777216)
행 순서 18ms, 열 순서 223ms (합계 16777216, 16777216)
행 순서 17ms, 열 순서 206ms (합계 16777216, 16777216)
```

두 함수는 같은 칸을 같은 횟수만큼 읽고 합계도 같은데, 열 순서가 열 배 넘게 느렸다. 한 번 더 실행했을 때는 행 순서가 16~59ms, 열 순서가 208~440ms로 흔들렸지만 열 순서가 몇 배 느린 것은 같았다.

행 순서는 캐시 라인 하나를 가져오면 그 안의 정수 16개를 모두 쓴다. 열 순서는 한 칸 읽을 때마다 16KB를 건너뛰므로 매번 다른 캐시 라인을 건드린다. 한 열을 다 내려가는 동안 4096개의 캐시 라인을 가져오는데, 그 양(4096 x 64바이트 = 256KB)은 L1(32KB)보다 크다. 그래서 다음 열을 읽으러 돌아왔을 때 바로 옆 칸이 들어 있던 캐시 라인은 이미 L1에서 밀려나 있기 쉽다. 결국 열 순서는 캐시 라인을 가져와 4바이트만 쓰고 버리는 일을 반복한다.

게다가 16KB처럼 2의 거듭제곱 간격으로 건너뛰면 읽는 줄들이 캐시의 같은 세트(뒤의 연관도 참고)에 몰린다. 이 컴퓨터의 L1d(32KB, 8웨이)는 세트가 64개인데, 한 열을 내려가는 4096번의 읽기가 모두 한 세트에 몰려 8자리만 돌려 쓰게 된다. L2에서도 이렇게 몰리는지는 실제 메모리 위치(물리 주소)가 어떻게 배치되느냐에 달려 있어 확인하지 못했다. 매번 다른 페이지를 건드리므로 주소 변환 비용도 섞이고, 행 순서는 다음에 읽을 주소를 짐작하기 쉬워 프리페치의 도움도 받는다. 이 실험만으로 각 요인의 몫을 나누지는 못했다(확인 필요).

책장 한 칸을 통째로 책상에 옮겨 와야 책을 읽을 수 있고, 책상에는 몇 칸만 놓인다고 하자. 차례로 읽으면 옮겨 온 칸의 책을 다 읽고 다음 칸으로 간다. 칸마다 첫 권만 읽고 돌아오면, 두 번째 권을 읽으러 왔을 때 그 칸은 이미 서재로 돌아가 있어 다시 옮겨 와야 한다.

### 배열 크기에 따라 달라지는 읽기 시간
크기가 다른 배열을 만들고, 배열 안을 무작위 순서로 한 칸씩 따라가며 한 번 읽는 데 걸리는 평균 시간을 쟀다. 각 칸에는 다음에 갈 칸의 번호가 적혀 있어서, 앞 칸을 읽어야 다음 칸을 알 수 있다. 무작위 순서라 공간 지역성의 도움을 받지 못하고, 배열이 어느 캐시 단계에 들어가는지에 따라 시간이 달라진다.

```js
const STEPS = 20_000_000;

function makeCycle(len) {
  // 0..len-1 을 섞은 뒤, 각 칸에 다음에 갈 칸 번호를 적어 하나의 원을 만든다
  const order = new Int32Array(len);
  for (let i = 0; i < len; i++) order[i] = i;
  for (let i = len - 1; i > 0; i--) {
    const j = Math.floor(Math.random() * (i + 1));
    [order[i], order[j]] = [order[j], order[i]];
  }
  const next = new Int32Array(len);
  for (let i = 0; i < len; i++) next[order[i]] = order[(i + 1) % len];
  return next;
}

function chase(next) {
  let p = 0;
  for (let i = 0; i < STEPS; i++) p = next[p];
  return p;
}

for (const kb of [16, 128, 1024, 8 * 1024, 64 * 1024]) {
  const next = makeCycle((kb * 1024) / 4);
  chase(next); // 한 번 미리 돌려 캐시와 JIT를 데운다
  const t = performance.now();
  chase(next);
  const ns = ((performance.now() - t) * 1e6) / STEPS;
  console.log(`${String(kb).padStart(6)}KB  한 번 읽기 평균 ${ns.toFixed(1)}ns`);
}
```

세 번 실행한 결과를 정리하면 아래와 같다(단위 ns).

| 배열 크기 | 1회 | 2회 | 3회 |
| --- | --- | --- | --- |
| 16KB | 3.2 | 1.5 | 1.7 |
| 128KB | 3.9 | 3.7 | 3.5 |
| 1MB | 22.9 | 13.8 | 19.3 |
| 8MB | 151.0 | 168.3 | 120.0 |
| 64MB | 132.3 | 144.6 | 163.7 |

16KB는 L1(32KB)에, 128KB는 L2(256KB)에 들어가는 크기이고 둘 다 수 ns 안에 읽었다. 1MB는 L2보다 커서 L3에서 읽어야 하고 시간이 몇 배로 늘었다. 64MB는 L3(12MB)보다 훨씬 커서 대부분 메모리까지 가야 하고 100ns를 넘었다. 16KB에서 64MB로 가는 동안 한 번 읽는 시간이 수십 배에서 100배 남짓 늘었다.

8MB는 L3보다 작은데도 64MB와 비슷하게 느렸다. 무작위로 넓은 범위를 읽으면 주소 변환(가상 주소를 실제 메모리 위치로 바꾸는 일, [컨텍스트 스위칭 노트](../컨텍스트%20스위칭(Context%20Switching)/README.md#간접-비용-캐시와-tlb가-식는다)의 TLB 설명 참고) 비용 같은 다른 요인이 섞일 수 있지만, 이 실험만으로 원인을 가려내지는 못했다(확인 필요). 이 실험을 처음 돌렸을 때는 16KB가 16.0ns, 1MB가 140.0ns처럼 다른 회차와 동떨어진 값이 나오기도 했다. 측정값은 이렇게 흔들리므로 여러 번 돌려 보고 경향만 읽는다.

## 조금 더 깊은 주제
아래는 이름과 핵심만 짚는다. 자세한 내용은 별도 문서로 미룬다.

### 연관도 (Associativity)
연관(Associate)의 사전적 의미는 서로 관계를 맺어 짝짓는 것이다. 공학적으로 캐시의 연관도는 메모리의 한 위치를 캐시의 몇 자리와 짝지을 수 있는지를 말한다. 짝지을 수 있는 자리가 많을수록 연관도가 높다. 아무 자리에나 들어갈 수 있으면 완전 연관(Fully Associative), 정해진 한 자리에만 들어갈 수 있으면 직접 사상(Direct-Mapped), 정해진 몇 자리 묶음(세트) 안에서 고를 수 있으면 집합 연관(Set-Associative)이라고 한다. 완전 연관은 자리를 잘 쓰지만 찾을 곳이 많아 만들기 어렵고, 직접 사상은 찾기 쉽지만 같은 자리를 노리는 데이터끼리 서로 밀어낸다. 그래서 요즘 캐시는 대부분 그 중간인 집합 연관을 쓴다. 이 컴퓨터의 L1d는 8웨이(한 세트에 8자리), L2는 4웨이, L3는 12웨이였다.

학교 사물함을 번호 끝자리로 정한 구역에만 쓰게 하는 것과 같다. 구역 안의 몇 칸 중 빈 곳을 고를 수 있지만, 같은 구역 사람이 많으면 다른 구역이 비어 있어도 자리가 모자란다.

### 교체 정책 (Replacement Policy)
캐시 라인을 새로 가져올 자리가 꽉 차 있으면 하나를 내보내야 한다. Drepper의 글은 대부분의 캐시가 가장 오래 쓰지 않은 것(LRU, Least Recently Used)부터 내보낸다고 쓴다. [캐싱 노트의 축출](../캐싱(Caching)/README.md#축출-eviction)과 같은 생각을 하드웨어로 만든 것이다. 실제 CPU가 LRU를 정확히 따르는지, 비슷하게 흉내만 내는지는 설계마다 다르고 이 노트에서는 확인하지 않았다.

### 캐시 일관성과 MESI
코어마다 자기 캐시가 있으니, 두 코어가 같은 메모리 위치의 사본을 각자 들고 있을 수 있다. 한 코어가 값을 바꾸면 다른 코어의 사본은 낡은 값이 된다. 여러 캐시의 사본이 서로 어긋나지 않게 맞추는 것을 캐시 일관성(Cache Coherence)이라고 한다.

Drepper의 글이 설명하는 MESI는 대표적인 일관성 규칙으로, 캐시 라인마다 네 가지 상태 중 하나를 붙인다. 이름은 네 상태의 첫 글자다.

- 수정됨(Modified): 이 코어가 값을 바꿨고 메모리에는 아직 반영되지 않았다
- 배타적(Exclusive): 바뀌지 않았고 다른 코어의 캐시에는 없다
- 공유됨(Shared): 바뀌지 않았고 다른 코어의 캐시에도 있을 수 있다
- 무효(Invalid): 쓸 수 없는 캐시 라인이다

한 코어가 공유된 캐시 라인에 쓰려고 하면 다른 코어들의 사본을 무효로 만든 뒤에 쓴다. 여러 사람이 같은 문서를 한 부씩 복사해 들고 있다가, 누군가 고치려면 먼저 다른 사람들의 복사본을 걷어 가는 것과 같다.

### 거짓 공유 (False Sharing)
캐시 일관성은 변수 단위가 아니라 캐시 라인 단위로 움직인다. 그래서 두 스레드(한 프로그램 안에서 따로 실행되는 흐름)가 서로 다른 변수를 쓰더라도 그 두 변수가 같은 캐시 라인 안에 있으면, 한쪽이 쓸 때마다 다른 쪽 코어의 사본이 무효가 되고 캐시 라인이 두 코어 사이를 오간다. 실제로는 데이터를 함께 쓰지 않는데 함께 쓰는 것처럼 비용을 치르므로 거짓 공유라고 부른다. Drepper의 글은 같은 캐시 라인에 있는 변수를 여러 스레드가 고칠 때 따로 떨어진 경우보다 몇 배 느려지는 측정 결과를 보여 준다.

종이 한 장의 왼쪽 칸과 오른쪽 칸을 두 사람이 각자 채우는데, 종이가 한 장뿐이라 한 줄 쓸 때마다 서로 넘겨줘야 하는 것과 같다.
