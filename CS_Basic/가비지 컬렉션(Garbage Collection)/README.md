## 가비지 컬렉션이란 ?
- 가비지 컬렉션(Garbage Collection)은 프로그램이 힙(Heap)에 만든 값 가운데 더 이상 쓸 수 없게 된 것을 찾아, 그 메모리를 자동으로 돌려받는 일이다
- 이 일을 맡는, 프로그램 실행을 맡는 환경(런타임, Runtime)의 구성 요소를 가비지 컬렉터(Garbage Collector)라고 부른다
- 무엇을 쓰레기로 볼지(도달 가능성), 어떻게 찾을지(참조 카운팅, 마크 앤 스윕), 언제 얼마나 멈추고 치울지(세대별 수집, 증분 수집, 동시 수집)가 핵심이다

힙이 무엇이고 스택과 어떻게 다른지는 [변수 노트의 변수가 사는 곳](../변수(Variable)/README.md#변수가-사는-곳)과 [스택 프레임 노트의 스택과 힙 비교](../스택%20프레임(Stack%20Frame)/README.md#스택과-힙-비교)에서 다뤘다. 이 노트는 그 가운데 힙을 누가 어떻게 치우는지를 본다.

## 단어의 뜻
### 가비지 (Garbage)
사전적 의미는 쓰레기, 음식물 찌꺼기다. 쓸모가 다해 버려야 하는 것을 말한다.

공학적으로는 힙에 아직 자리를 차지하고 있지만 프로그램이 다시는 쓸 수 없는 값을 말한다. 값이 망가진 것이 아니라, 그 값에 닿을 길이 프로그램 안에 하나도 남지 않은 상태다. 아래 "무엇이 쓰레기인가"에서 이 기준을 자세히 본다.

### 컬렉션 (Collection)
사전적 의미는 모으기, 수거다. 쓰레기 수거(garbage collection)라고 하면 수거 차량이 쓰레기를 거둬 가는 일을 뜻한다.

공학적으로 가비지 컬렉션(Garbage Collection, 줄여서 GC)은 쓰레기가 된 값을 찾아 그 메모리를 다시 쓸 수 있는 빈자리로 돌려놓는 일이다. 아파트에 수거 차량이 정해진 때 와서 내놓은 쓰레기를 거둬 가듯, 가비지 컬렉터는 적당한 때 힙을 돌며 쓰레기를 치운다. 프로그래머는 쓰레기를 직접 버리러 가지 않는다.

## 힙 메모리는 누가 돌려주나
### 메모리의 한살이
어느 언어에서든 메모리는 필요한 만큼 잡고(할당), 읽고 쓰고(사용), 더 필요 없으면 돌려주는(해제) 순서를 밟는다. 스택에 놓인 값은 함수가 끝나면 프레임과 함께 사라지므로 해제를 고민할 필요가 없다. 문제는 함수가 끝나도 남아야 해서 힙에 만든 값이다. 힙의 값은 언제 필요 없어지는지가 코드마다 달라서, 누군가 그 시점을 판단해 돌려줘야 한다.

### 수동 해제 (Manual Memory Management)
프로그래머가 해제 시점을 직접 코드로 적는 방식이다. C에서는 `malloc` 으로 힙 메모리를 잡고 `free` 로 돌려준다.

```c
int *scores = malloc(sizeof(int) * 100); // 힙에 정수 100개 자리를 잡는다
// ... scores 사용
free(scores);                             // 다 썼으면 직접 돌려준다
```

메모리를 언제 돌려줄지 프로그래머가 정확히 알 수 있고, 치우는 일에 따로 드는 시간이 없다. 대신 실수가 바로 버그가 된다. 흔한 실수는 세 가지다.

- 해제를 잊는다. 쓰지 않는 메모리가 계속 쌓여 프로그램이 점점 많은 메모리를 차지한다. 이를 메모리 누수(Memory Leak)라고 한다.
- 너무 일찍 해제한다. 아직 그 자리의 주소를 담은 변수(포인터, Pointer)가 남아 있는데 메모리를 돌려주면, 그 포인터는 이미 다른 값에 다시 쓰일 수 있는 자리를 가리킨다. 이런 포인터를 허상 포인터(Dangling Pointer)라고 한다. 스택 프레임 노트에서 본 지역 변수 주소를 돌려주는 문제와 같은 종류다.
- 두 번 해제한다(Double Free). 이미 돌려준 자리를 또 돌려주면 메모리 관리 정보가 망가질 수 있다.

호텔 방을 직접 체크아웃하는 것과 같다. 깜빡하면 방값이 계속 나가고(누수), 체크아웃한 뒤에도 방 번호를 쥐고 다시 들어가면 이미 다른 손님이 쓰는 방이다(허상 포인터).

### 자동 해제 (Automatic Memory Management)
런타임이 해제 시점을 대신 판단하는 방식이다. 프로그래머는 값을 만들기만 하고, 더 이상 쓰지 않는 값은 가비지 컬렉터가 알아서 돌려받는다. Java, 파이썬, 자바스크립트, Go 같은 많은 언어가 이 방식을 쓴다.

너무 일찍 해제하거나 두 번 해제하는 실수는 코드로 쓸 수 없게 되고, 해제를 잊는 실수도 크게 줄어든다. 다만 누수가 완전히 없어지지는 않는다는 것을 뒤에서 본다. 대가는 두 가지다. 쓰레기를 찾는 일에 CPU 시간과 메모리가 더 들고, 언제 치울지를 프로그래머가 정확히 정할 수 없다.

가비지 컬렉션은 1959년 무렵 미국의 컴퓨터 과학자 존 매카시(John McCarthy)가 Lisp의 수동 메모리 관리를 덜기 위해 고안했다고 알려져 있다. 위키백과는 매카시가 1960년 Communications of the ACM에 실은 Lisp 논문을 출처로 든다.

## 무엇이 쓰레기인가
### 도달 가능성 (Reachability)
reach는 손이 닿다라는 뜻이다. 도달 가능성은 프로그램이 지금 가진 변수에서 출발해 참조를 따라가면 그 값에 닿을 수 있는지를 말한다. 닿을 수 있으면 살아 있는 값(도달 가능한 값), 어떤 길로도 닿을 수 없으면 쓰레기다.

가비지 컬렉터는 이 값이 앞으로 쓰일지를 미리 알 수 없다. 그래서 질문을 바꾼다. 앞으로 쓰일지 대신, 지금 이 값에 닿을 길이 있는지를 본다. 닿을 길이 없는 값은 프로그램이 다시 쓰고 싶어도 쓸 방법이 없으니 안전하게 치울 수 있다. 반대로 닿을 길은 있지만 다시는 안 쓰는 값은 쓰레기로 보지 않는다. 뒤에서 볼 메모리 누수가 여기서 생긴다.

### 루트 (Root)
사전적 의미는 뿌리다. 공학적으로 루트는 가비지 컬렉터가 도달 가능성을 따질 때 출발점으로 삼는, 처음부터 살아 있다고 보는 참조들이다. 보통 전역 변수, 그리고 지금 호출 스택에 쌓인 프레임들의 지역 변수와 매개변수가 루트가 된다. 실행 중인 함수가 쥐고 있는 값은 당연히 아직 쓰이는 값이기 때문이다.

손에 쥔 풍선 줄에 비유할 수 있다. 내가 줄을 쥔 풍선(루트), 그 풍선에 다시 묶인 풍선, 거기에 또 묶인 풍선은 모두 날아가지 않는다. 어느 손에도 이어지지 않은 풍선만 날아간다. 참조 카운팅과 마크 앤 스윕도 이 풍선으로 설명한다.

## 참조 카운팅 (Reference Counting)
### 동작
값마다 자신을 가리키는 참조가 몇 개인지 세어 두는 방식이다. 변수나 다른 값의 속성이 그 값을 가리키게 되면 수를 하나 올리고, 그 참조가 사라지거나 다른 값을 가리키게 되면 하나 내린다. 수가 0이 되는 순간 그 값을 가리키는 것이 하나도 없으니 바로 해제하고, 그 값이 가리키던 값들의 수도 하나씩 내린다.

풍선마다 매달린 줄이 몇 개인지 적어 두는 것과 같다. 줄이 하나 끊길 때마다 숫자를 내리고, 0이 되면 그 풍선을 치운다.

쓰레기가 생긴 그 자리에서 바로 치우므로 메모리가 쌓였다가 한꺼번에 치우는 일이 적고, 언제 해제될지 예측하기 쉽다. 대신 참조를 바꿀 때마다 수를 고쳐야 해서 그만큼 일이 늘어난다.

### 순환 참조 문제
두 값이 서로를 가리키면 수가 0이 되지 않는다. A가 B를, B가 A를 가리키는 상태에서 바깥의 변수가 둘 다 놓아 버리면, 둘은 어디에서도 닿을 수 없는 쓰레기가 된다. 그런데 A는 B가, B는 A가 가리키고 있으니 각자 수가 1로 남는다. 참조 카운팅만으로는 이 둘을 영원히 치우지 못한다. 이를 순환 참조(Circular Reference) 문제라고 한다.

두 풍선이 서로의 줄에 묶여 있는데 아무도 그 줄을 쥐고 있지 않은 상황이다. 각 풍선에는 줄이 하나씩 매달려 있으니 숫자만 보면 0이 아니다.

MDN은 지금의 자바스크립트 엔진 가운데 참조 카운팅으로 가비지 컬렉션을 하는 엔진은 없다고 적고 있다. 반면 파이썬의 기본 구현인 CPython은 참조 카운팅을 기본으로 쓰고, 순환 참조는 따로 돌리는 순환 탐지기(Cycle Detector)로 찾아 치운다. 실제로 수가 오르내리는 모습은 아래 "코드로 보기"에서 본다.

## 마크 앤 스윕 (Mark and Sweep)
### 동작
mark는 표시하다, sweep은 쓸어 내다라는 뜻이다. 이름대로 두 단계로 나뉜다.

1. 마크(Mark). 루트에서 출발해 참조를 따라가며 닿는 값마다 살아 있다고 표시한다. 표시한 값에서 다시 그 값이 가리키는 값으로 넘어가, 더 갈 곳이 없을 때까지 반복한다.
2. 스윕(Sweep). 힙 전체를 훑으며 표시가 없는 값의 자리를 빈자리로 돌려놓는다. 빈자리들은 다음에 값을 만들 때 쓰도록 빈자리 목록(Free List)에 모아 둔다.

풍선으로 보면, 손에 쥔 줄부터 따라가며 닿는 풍선마다 스티커를 붙이고(마크), 다 붙인 뒤 스티커가 없는 풍선을 모두 치우는(스윕) 것이다.

### 순환 참조도 치운다
마크 앤 스윕은 값을 가리키는 수가 아니라 루트에서 닿는지를 본다. 서로를 가리키는 두 값이라도 루트에서 이어지는 길이 없으면 스티커가 붙지 않으므로 스윕 단계에서 함께 치워진다. 참조 카운팅의 순환 참조 문제가 여기서는 생기지 않는다.

대신 쓰레기가 생긴 즉시 치우지 않고, 마크를 시작해야 비로소 쓰레기를 알게 된다. 힙 전체를 한 번 훑어야 하므로 힙이 클수록 한 번에 드는 일도 크다. MDN은 지금의 자바스크립트 엔진이 모두 마크 앤 스윕 계열의 가비지 컬렉터를 쓴다고 적고 있다.

## 단편화와 압축
### 단편화 (Fragmentation)
fragment는 조각이라는 뜻이다. 단편화는 빈자리가 여기저기 작은 조각으로 흩어져, 빈자리를 다 합치면 충분한데도 큰 값을 놓을 연속된 자리가 없는 상태를 말한다.

스윕은 죽은 값의 자리를 그 자리 그대로 비워 둘 뿐 살아 있는 값을 옮기지 않는다. 그래서 수집을 거듭할수록 살아 있는 값 사이사이에 크기가 제각각인 빈칸이 생긴다. 극장에 빈자리가 서른 개 있어도 한두 자리씩 흩어져 있으면 다섯 명 일행이 나란히 앉을 수 없는 것과 같다.

### 압축 (Compaction)
compact는 빽빽하게 채우다라는 뜻이다. 압축은 살아 있는 값을 힙의 한쪽으로 옮겨 붙여, 흩어진 빈자리를 하나의 큰 빈자리로 합치는 일이다. 관객에게 한쪽으로 당겨 앉아 달라고 부탁해 뒤쪽에 빈 줄을 통째로 만드는 것과 같다. V8 블로그는 이를 예전 PC에서 하드 디스크 조각 모음을 하던 일에 빗댄다.

값을 옮기면 주소가 바뀌므로, 그 값을 가리키던 참조도 모두 새 주소로 고쳐야 한다. 옮기고 고치는 일이 들기 때문에, V8은 매번 압축하지 않고 단편화가 심한 곳을 골라 압축한다. 수집기마다 압축하는 정도는 다르다. 마크와 스윕에 압축을 더한 방식을 마크 컴팩트(Mark-Compact)라고 부른다.

## 세대별 수집 (Generational Collection)
### 세대 가설 (Generational Hypothesis)
많은 프로그램에서 대부분의 값은 만들어지고 얼마 지나지 않아 쓰레기가 된다. 함수 안에서 잠깐 쓰고 버리는 중간 결과, 반복문 한 바퀴에서만 쓰는 임시 값이 그렇다. 반대로 한동안 살아남은 값은 그 뒤로도 오래 사는 경향이 있다. 이 관찰을 세대 가설이라고 하고, V8 블로그는 이를 대부분의 객체는 젊어서 죽는다(most objects die young)는 말로 요약한다.

### 동작
generation은 세대라는 뜻이다. 세대별 수집은 힙을 젊은 세대(Young Generation)와 늙은 세대(Old Generation)로 나누고, 세대마다 다른 주기로 치운다.

1. 새로 만든 값은 젊은 세대에 놓는다.
2. 젊은 세대는 작고 쓰레기가 많으므로 자주, 빠르게 치운다. 이를 마이너 GC(Minor GC)라고 한다.
3. 몇 번의 마이너 GC에서 살아남은 값은 오래 살 값으로 보고 늙은 세대로 옮긴다. 이를 승격(Promotion)이라고 한다.
4. 늙은 세대는 크고 쓰레기가 적으므로 가끔만, 마크 앤 스윕이나 마크 컴팩트로 크게 치운다. 이를 메이저 GC(Major GC)라고 한다.

부엌에 비유하면 일회용 컵은 싱크대 옆 작은 통에 모아 자주 비우고, 오래 쓰는 그릇이 든 찬장은 가끔만 정리하는 것과 같다. 매번 찬장까지 다 뒤질 필요가 없으니 정리가 빨라진다.

가설이 맞는 프로그램이라면 젊은 세대를 치울 때 살아남는 값이 적어서, 살아 있는 값만 따로 옮기는 식으로 아주 빠르게 치울 수 있다. 2019년 V8 블로그 기준으로 V8은 젊은 세대를 두 칸으로 나눠 살아 있는 값만 다른 칸으로 옮기는 방식을 쓴다. 구체적인 구현은 엔진마다 다르고, 이 노트에서는 다루지 않는다.

## 멈춤과 이를 줄이는 방법
### 멈춤 (Stop-the-World)
가비지 컬렉터가 마크를 하는 동안 프로그램이 계속 실행되면 참조가 바뀐다. 이미 표시를 마친 값에 아직 표시하지 않은 값을 새로 연결하면, 가비지 컬렉터는 그 값을 놓치고 살아 있는 값을 쓰레기로 치워 버릴 수 있다. 가장 단순한 해결은 수집하는 동안 프로그램을 통째로 멈추는 것이다. 세상을 멈춘다는 뜻으로 스톱 더 월드(Stop-the-World)라고 부른다.

가게를 청소하는 동안 문을 닫아 두는 것과 같다. 청소는 확실하지만 그동안 손님을 받지 못한다. 프로그램에서는 이 멈춤이 화면이 끊기거나 요청 응답이 늦어지는 것으로 드러난다. 그래서 가비지 컬렉터는 전체 일의 양만큼이나 한 번에 얼마나 오래 멈추는지를 중요하게 본다.

### 멈춤을 줄이는 세 가지 방법
멈춤을 줄이는 방법은 일을 잘게 나누거나, 다른 실행 흐름(스레드(Thread))에 맡기는 쪽으로 나뉜다. V8 블로그의 구분을 따라 세 가지로 정리하면 아래와 같다.

| 방법 | 어떻게 하나 | 프로그램은 그동안 |
|---|---|---|
| 병렬 수집 (Parallel) | 메인 스레드와 보조 스레드 여럿이 수집 일을 동시에 나눠 한다 | 멈춘다. 대신 일손이 많아 멈춤이 짧아진다 |
| 증분 수집 (Incremental) | 메인 스레드가 수집 일을 조금씩 나눠, 프로그램 실행 사이사이에 한다 | 짧게 여러 번 멈춘다 |
| 동시 수집 (Concurrent) | 보조 스레드가 수집 일을 하고, 메인 스레드는 그동안 프로그램을 계속 실행한다 | 거의 멈추지 않는다 |

가게 비유로 보면 병렬 수집은 문을 닫고 직원 여럿이 함께 청소해 빨리 끝내는 것, 증분 수집은 영업하면서 손님이 뜸할 때마다 한 구역씩 치우는 것, 동시 수집은 영업은 계속하고 청소 담당 직원이 따로 치우는 것이다.

증분 수집과 동시 수집은 수집하는 도중에 프로그램이 참조를 바꿀 수 있다는 앞의 문제를 그대로 안고 있다. 그래서 프로그램이 참조를 바꿀 때마다 가비지 컬렉터에게 알리는 장치를 함께 둔다. 이 장치를 쓰기 장벽(Write Barrier)이라고 부르는데, 세부 동작은 TODO로 넘긴다. V8 블로그는 V8이 세 방법을 함께 쓴다고 설명한다.

## 가비지 컬렉션이 있어도 생기는 메모리 누수
### 왜 생기나
가비지 컬렉터는 닿을 수 없는 값만 치운다. 프로그램이 다시는 쓰지 않을 값이라도 어딘가에서 참조가 남아 있으면 살아 있는 값으로 본다. 가비지 컬렉션이 있는 언어의 메모리 누수는 대부분 이렇게 잊힌 참조가 쓰레기가 될 값을 붙잡고 있는 경우다.

수거 차량은 문 앞에 내놓은 쓰레기만 가져간다. 버릴 물건을 서랍에 넣어 두면 아무리 오래 지나도 가져가지 않는다.

### 전역에 남은 참조
전역 변수는 루트이므로 거기서 닿는 값은 프로그램이 끝날 때까지 살아 있다. 처리한 요청을 기록해 두려고 전역 목록에 계속 넣기만 하면, 목록이 붙잡은 값은 모두 치워지지 않는다. 오래 남아야 하는 값이 아니라면 전역 대신 함수 안의 지역 변수에 두어, 함수가 끝나면 루트에서 떨어지게 한다.

### 지우지 않은 이벤트 리스너
이벤트 리스너(Event Listener)는 어떤 일이 생기면 불러 달라고 등록해 두는 함수다. 등록을 받는 쪽은 리스너 목록에 그 함수를 붙잡아 두고, 함수는 자기가 쓰는 값을 붙잡는다. 어떤 객체를 다 썼는데 그 객체가 등록한 리스너를 지우지 않으면, 등록받은 쪽이 살아 있는 한 리스너와 리스너가 쥔 값이 모두 남는다. 등록한 쪽이 일을 마칠 때 등록도 함께 해제해야 한다.

### 끝없이 커지는 캐시
캐시(Cache)는 다시 계산하지 않으려고 결과를 보관해 두는 곳이다. 넣기만 하고 지우는 규칙이 없으면 캐시가 붙잡은 값은 계속 늘어난다. 캐시는 대개 오래 사는 곳에 두므로 이 값들은 쓰레기가 되지 않는다. [캐싱 노트의 축출](../캐싱(Caching)/README.md#축출-eviction)에서 본 것처럼 크기 상한이나 만료 시간을 두어 오래된 것부터 내보내야 한다. 캐시가 계속 커지는 모습은 아래 "코드로 보기"에서 본다.

일부 언어는 약한 참조(Weak Reference)를 제공한다. 약한 참조로만 가리키는 값은 도달 가능성을 따질 때 없는 길로 보아 치울 수 있다. 캐시나 객체에 덧붙이는 정보를 보관할 때 쓴다. 다만 언제 치워질지는 보장하지 않아 쓸 때 주의할 점이 많으니, 쓰는 방법은 별도 문서로 넘긴다.

## 코드로 보기
자바스크립트 예시는 Windows 11(win32 x64), Node.js v24.22.1에서, 파이썬 예시는 같은 PC의 Python 3.13.14에서 2026-10-27에 실행했다. 힙 크기와 시간 같은 수치는 환경과 버전에 따라 다르고, 같은 환경에서도 실행할 때마다 조금씩 다를 수 있다. 여기서 Node.js는 가비지 컬렉터를 들여다보는 도구로만 쓴다.

### 참조를 끊으면 힙이 줄어든다
`node --expose-gc` 로 실행하면 `global.gc()` 로 가비지 컬렉션을 직접 부를 수 있다. 원래는 디버깅용 옵션이고, 보통 프로그램에서는 수집 시점을 코드로 정할 수 없다. `process.memoryUsage().heapUsed` 는 지금 힙에서 쓰고 있는 바이트 수다.

```js
const mb = () => (process.memoryUsage().heapUsed / 1024 / 1024).toFixed(1) + ' MB';

global.gc();
console.log('시작:', mb());

let list = [];
for (let i = 0; i < 1_000_000; i++) {
  list.push({ id: i });
}
global.gc();
console.log('객체', list.length, '개를 만든 뒤:', mb());

list = null; // 유일한 참조를 끊는다
global.gc();
console.log('참조를 끊고 수집한 뒤:', mb());
```

```
시작: 3.9 MB
객체 1000000 개를 만든 뒤: 44.6 MB
참조를 끊고 수집한 뒤: 4.1 MB
```

세 번 실행해 세 번 모두 같은 값이 나왔다. 객체 100만 개는 `list` 를 거쳐 루트에서 닿으므로 수집을 해도 남는다. `list = null` 로 길을 끊자 같은 수집에서 모두 치워졌다.

처음에는 두 번째 줄에 `list.length` 를 출력하지 않았는데, 그때는 만든 뒤 값도 4.1 MB로 나왔다. 그 뒤로 `list` 를 읽는 코드가 없어서 엔진이 수집 시점에 이미 쓸 수 없는 값으로 판단한 것으로 보이지만, 정확한 이유는 확인하지 못했다(확인 필요).

### 서로 가리키는 값도 치워진다
서로를 가리키는 객체 쌍을 50만 개 만든 뒤 바깥 참조만 끊었다. 쌍끼리의 참조는 그대로 둔다.

```js
const mb = () => (process.memoryUsage().heapUsed / 1024 / 1024).toFixed(1) + ' MB';

let pairs = [];
for (let i = 0; i < 500_000; i++) {
  const a = {};
  const b = {};
  a.other = b; // a가 b를 가리키고
  b.other = a; // b가 a를 가리킨다
  pairs.push(a);
}
global.gc();
console.log('서로 가리키는 쌍', pairs.length, '개:', mb());

pairs = null; // 바깥에서 들어오는 참조만 끊는다
global.gc();
console.log('바깥 참조를 끊고 수집한 뒤:', mb());
```

```
서로 가리키는 쌍 500000 개: 61.7 MB
바깥 참조를 끊고 수집한 뒤: 4.1 MB
```

참조 카운팅만 쓴다면 쌍마다 수가 1로 남아 치우지 못했을 값이다. 마크 앤 스윕 계열은 루트에서 닿는지를 보므로 순환 참조도 함께 치운다.

### 참조 수가 오르내리는 모습
CPython에서는 `sys.getrefcount()` 로 값의 참조 수를 볼 수 있다. Python 3.13에서는 이 함수에 값을 넘기는 순간 참조가 하나 더 생기므로 1을 빼서 출력했다. 이후 버전에서는 내부 최적화로 결과가 달라질 수 있다(확인 필요).

```python
import gc
import sys

class Node:
    pass

a = Node()
print(sys.getrefcount(a) - 1)  # 1
b = a
print(sys.getrefcount(a) - 1)  # 2
del b
print(sys.getrefcount(a) - 1)  # 1

gc.disable()      # 순환 탐지기의 자동 실행을 끈다
x = Node()
y = Node()
x.other = y
y.other = x
del x, y          # 이름은 사라졌지만 둘은 서로를 가리킨다
print(gc.collect())  # 2
gc.enable()       # 자동 실행을 다시 켠다
```

`b = a` 로 이름이 하나 더 가리키자 수가 2가 되고, `del b` 로 이름을 지우자 1로 돌아갔다. 아래쪽의 `x` 와 `y` 는 이름을 지운 뒤에도 서로 가리켜 수가 0이 되지 않는다. 자동 수집이 먼저 치워 버리지 않도록 `gc.disable()` 로 자동 실행만 끈 뒤, `gc.collect()` 로 순환 탐지기를 직접 돌렸다. `gc.collect()` 는 찾아낸 쓰레기 수를 돌려주고, 3.13에서는 이 두 객체에 해당하는 2가 나왔다. 버전에 따라 객체에 딸린 속성 사전까지 세어 더 큰 수가 나올 수 있다(확인 필요).

### 세대별 수집과 증분 수집 보기
`node --trace-gc` 로 실행하면 가비지 컬렉션이 일어날 때마다 한 줄씩 출력한다. 객체 300만 개를 만들면서 열 개 가운데 하나만 목록에 남기는 코드를 돌렸다.

```js
let keep = [];
for (let i = 0; i < 3_000_000; i++) {
  const temp = { i };                 // 대부분 바로 버려지는 객체
  if (i % 10 === 0) keep.push(temp);  // 열 개 가운데 하나만 오래 남긴다
}
console.log('남긴 객체 수:', keep.length);
```

출력 가운데 몇 줄만 옮겼다. 줄 앞의 프로세스 번호와 주소는 지웠다.

```
79 ms: Scavenge 4.9 (6.0) -> 4.1 (7.0) MB, pooled: 0 MB, 0.50 / 0.00 ms  (average mu = 1.000, current mu = 1.000) allocation failure;
148 ms: Scavenge 21.7 (30.6) -> 15.2 (47.4) MB, pooled: 0 MB, 5.60 / 0.00 ms  (average mu = 1.000, current mu = 1.000) allocation failure;
157 ms: Mark-Compact 16.6 (47.4) -> 11.5 (44.3) MB, pooled: 0 MB, 6.12 / 0.00 ms  (+ 1.0 ms in 23 steps since start of marking, biggest step 0.2 ms, walltime since start of marking 8 ms) (average mu = 0.951, current mu = 0.951) finalize incremental marking via stack guard; GC in old space requested
163 ms: Scavenge (interleaved) 27.5 (44.3) -> 13.1 (44.3) MB, pooled: 0 MB, 3.28 / 0.00 ms  (average mu = 0.951, current mu = 0.951) allocation failure;
```

V8 블로그의 설명에 따르면 `Scavenge` 는 V8의 젊은 세대 수집(마이너 GC)이고, `Mark-Compact` 는 힙 전체를 치우는 메이저 GC다. 이 실행에서는 79 ms부터 190 ms까지 약 0.1초 동안 `Scavenge` 가 19번, `Mark-Compact` 가 1번 나왔다. 젊은 세대를 훨씬 자주 치운다는 것을 볼 수 있다. `->` 앞뒤 숫자는 수집 전과 후의 힙 사용량으로 읽히고, 괄호 안 숫자는 엔진이 확보해 둔 힙 전체 크기로 보이지만 확인하지 못했다(확인 필요).

`Mark-Compact` 줄의 `in 23 steps since start of marking` 과 `finalize incremental marking` 은 마크를 한 번에 하지 않고 23번에 나눠 하다가 마지막에 마무리했다는 뜻으로 읽힌다. 앞에서 본 증분 수집이 실제로 쓰이는 모습이다.

### 끝없이 커지는 캐시
요청마다 결과를 캐시에 넣기만 하고 지우지 않는 코드다. 10만 건씩 세 번 돌리며 매번 가비지 컬렉션을 부른 뒤 힙을 쟀다.

```js
const mb = () => (process.memoryUsage().heapUsed / 1024 / 1024).toFixed(1) + ' MB';
const cache = new Map(); // 지우는 규칙이 없는 캐시

function handle(requestId) {
  const result = { id: requestId, data: new Array(100).fill(requestId) };
  cache.set(requestId, result); // 요청마다 새 키로 넣기만 한다
  return result;
}

for (let round = 1; round <= 3; round++) {
  for (let i = 0; i < 100_000; i++) handle(round * 1_000_000 + i);
  global.gc();
  console.log(`${round}회차 뒤 캐시 크기 ${cache.size}, 힙 ${mb()}`);
}
```

```
1회차 뒤 캐시 크기 100000, 힙 92.1 MB
2회차 뒤 캐시 크기 200000, 힙 180.5 MB
3회차 뒤 캐시 크기 300000, 힙 272.2 MB
```

`handle` 을 부른 쪽은 결과를 받아 바로 버리지만, 캐시가 붙잡고 있어 가비지 컬렉션을 해도 하나도 치워지지 않는다. 가비지 컬렉터는 제 일을 다 했는데도 힙이 회차마다 약 90 MB씩 늘었다.
