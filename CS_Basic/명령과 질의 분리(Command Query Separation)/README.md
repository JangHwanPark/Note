## 명령과 질의 분리란 ?
- 함수(메서드)를 상태를 바꾸는 명령과 값을 알려 주는 질의 두 종류로 나누고, 한 함수가 두 일을 함께 하지 않게 하자는 설계 원칙이다. 영어로는 Command Query Separation이라 하고 줄여서 CQS라고 부른다
- 질의는 몇 번을 불러도 바깥에서 보이는 상태가 바뀌지 않으므로 마음 놓고 부를 수 있다
- Bertrand Meyer가 책 Object-Oriented Software Construction에서 이름 붙인 원칙으로 알려져 있다(Martin Fowler의 글 기준, 원문은 확인 필요)

[함수 설계 원리](../함수%20설계%20원리(Function%20Design%20Principles)/README.md)에서 함수를 값 기반 함수와 효과 기반 함수로 나눠 보았다. 명령과 질의 분리는 그 구분을 한 걸음 더 밀고 나가, 한 함수 안에서 두 역할을 섞지 말자는 규칙으로 만든 것이다.

### 명령 (Command)
사전적 의미는 윗사람이 아랫사람에게 무엇을 하라고 시키는 말이다.
공학적으로는 시스템의 상태를 바꾸고 값을 돌려주지 않는 함수를 말한다. 일을 시키는 것이 목적이고, 결과를 알고 싶으면 따로 묻는다. Fowler는 명령(Command)이라는 말이 다른 곳에서도 많이 쓰여 헷갈린다며 수정자(Modifier)라는 이름을 더 좋아한다고 썼다.

자동차의 가속 페달과 같다. 밟으면 속도가 바뀌지만, 페달이 운전자에게 무언가를 돌려주지는 않는다.

### 질의 (Query)
사전적 의미는 모르는 것을 묻는 것이다. 데이터베이스에 보내는 조회 요청을 쿼리라고 부르는 것도 같은 뜻에서 왔다.
공학적으로는 값을 돌려주고, 바깥에서 관찰할 수 있는 상태를 바꾸지 않는 함수를 말한다. 즉 [부수효과](../함수%20설계%20원리(Function%20Design%20Principles)/README.md#부수효과-side-effect)가 없다.

자동차의 연료계와 같다. 몇 번을 쳐다봐도 기름이 줄지 않는다.

### 분리 (Separation)
사전적 의미는 서로 나누어 떨어지게 하는 것이다.
여기서는 함수 하나가 명령이거나 질의이거나 둘 중 하나만 되게 하라는 뜻이다. 상태를 바꾸면서 동시에 값을 돌려주는 함수를 만들지 않는다.

## 물었을 뿐인데 상태가 바뀌는 문제
도서관 사서에게 "이 책 지금 빌릴 수 있나요?"라고 물었는데, 사서가 "네" 하면서 그 책을 내 이름으로 대출 처리해 버렸다고 해 보자. 그냥 궁금해서 물어본 것인데 상태가 바뀌었다. 이제는 물어보는 것 자체가 조심스러워진다. 명령과 질의 분리는 묻는 일과 시키는 일을 서로 다른 창구로 나누자는 이야기다.

코드에서도 같은 일이 생긴다. 아래는 이름은 조회처럼 보이지만, 실제로는 번호를 하나 올리면서 그 번호를 돌려주는 함수다.

```js
let ticket = 0;
const getTicket = () => { ticket += 1; return ticket; }; // 바꾸면서 돌려준다

const a = getTicket();
console.log('확인용 출력', getTicket()); // 확인용 출력 2  (디버깅하려고 한 줄 넣었다)
const b = getTicket();
console.log(a, b); // 1 3
```

값을 확인하려고 출력 한 줄을 넣었을 뿐인데, b가 2에서 3으로 바뀌었다. 이름만 보면 값을 알려 주는 질의 같지만 실제로는 상태도 바꾸기 때문이다. 읽는 쪽이 이 사실을 모르면 이런 실수를 하기 쉽다.

둘로 나누면 아래처럼 된다.

```js
const counter = {
  value: 0,
  increase() { this.value += 1; },   // 명령: 상태를 바꾸고 돌려주지 않는다
  current() { return this.value; },  // 질의: 돌려주기만 하고 상태를 바꾸지 않는다
};

counter.increase();
console.log(counter.current()); // 1
console.log(counter.current()); // 1
```

`current()` 는 몇 번을 불러도 1이다. 디버깅용 출력을 몇 줄 넣어도 프로그램의 동작이 달라지지 않는다.

<br/>

## 왜 나누면 좋을까
### 질의는 마음 놓고 부를 수 있다
질의는 상태를 바꾸지 않으니 어디에 끼워 넣어도, 몇 번을 불러도, 질의끼리 순서를 바꿔 불러도 프로그램의 나머지 동작은 달라지지 않는다. 물론 질의가 돌려주는 값은 그 앞에 어떤 명령이 실행됐는지에 따라 달라진다. Fowler는 이 점을 들어 질의는 훨씬 자유롭게 쓸 수 있고, 명령은 더 조심해서 다뤄야 한다고 설명한다. 반대로 말하면 조심할 곳이 명령으로 좁혀진다. 원칙을 지킨 코드라면 상태가 바뀐 원인을 찾을 때 명령 쪽만 보면 된다.

### 테스트가 쉬워진다
질의는 상태를 맞춰 두고 부른 뒤 돌려받은 값만 확인하면 된다. 명령은 부른 뒤 질의로 상태를 물어 확인한다. 위 예시에서 `increase()` 를 부르고 `current()` 가 1인지 보는 식이다. 한 함수가 바꾸기와 돌려주기를 함께 하면, 돌려준 값과 바뀐 상태를 한 번에 모두 맞춰 봐야 해서 확인할 것이 늘어난다.

### 코드만 보고 짐작할 수 있다
값을 돌려받는 호출은 질의, 돌려받지 않는 호출은 명령이라고 믿을 수 있으면 함수 안을 열어 보지 않고도 무슨 일이 일어날지 짐작할 수 있다. Fowler는 반환 타입이 이 구분의 대략적인 신호가 된다고 썼다. 다만 대부분의 언어는 이 원칙을 강제하지 않는다. 지키는 것은 결국 코드를 쓰는 사람의 몫이다.

<br/>

## 관찰할 수 있는 상태
질의가 바꾸면 안 되는 것은 바깥에서 관찰할 수 있는 상태다. 질의가 안에서 계산 결과를 저장해 두었다가(캐싱) 다음에 다시 쓰는 것은 괜찮다. 호출하는 쪽에서 보면 돌려받는 값도, 그 뒤의 동작도 달라지지 않기 때문이다.

[HTTP의 안전한 메서드](../WEB/HTTP%20메서드와%20상태%20코드(HTTP%20Methods%20and%20Status%20Codes)/README.md#안전-safe)에서 서버가 접속 기록을 남겨도 GET의 안전함이 깨지지 않는다고 본 것과 비슷하다. 다만 기준이 조금 다르다. HTTP의 안전은 클라이언트가 요청하거나 기대한 변화인지를 보고, 명령과 질의 분리는 호출한 쪽에서 관찰할 수 있는 변화인지를 본다. 둘이 대부분 겹치지만 늘 같지는 않다.

<br/>

## HTTP의 GET과 이어지는 부분
HTTP의 GET은 질의, POST, PUT, DELETE는 명령에 가깝다. GET이 [안전](../WEB/HTTP%20메서드와%20상태%20코드(HTTP%20Methods%20and%20Status%20Codes)/README.md#안전과-멱등)해야 한다는 약속은 질의가 상태를 바꾸지 않아야 한다는 약속과 같은 모양이다.

이 약속이 있기 때문에 브라우저는 링크를 미리 불러오고, 검색 로봇은 링크를 마음껏 따라간다. GET 요청이 데이터를 지우도록 만들면 이 프로그램들이 질의인 줄 알고 부른 요청에서 데이터가 사라진다. 앞의 `getTicket` 에 디버깅 출력을 넣었다가 값이 바뀐 것과 같은 구조의 문제가 네트워크 너머에서 일어나는 것이다.

다만 HTTP의 명령 쪽 메서드는 응답 본문에 만든 자원을 담아 돌려주기도 한다. POST로 사용자를 만들고 201 응답에 그 사용자 정보를 받는 식이다. 그래서 HTTP 메서드가 명령과 질의 분리를 그대로 따른다기보다는, 질의 쪽의 약속이 GET의 안전과 겹친다고 보는 편이 정확하다.

<br/>

## 지키기 어려운 경우
명령과 질의를 나누는 것이 늘 자연스럽지는 않다. 바꾸기와 돌려주기를 한 번에 해야 오히려 쓰기 편하거나 안전한 경우가 있다. 번호표 기계와 비슷하다. 버튼을 누르면 내 번호를 알려 주면서 동시에 다음 번호로 넘어간다. 번호만 확인하는 버튼과 넘기는 버튼이 따로 있으면 오히려 불편하다. 앞의 `getTicket` 이 문제였던 것은 번호를 넘기면서도 조회처럼 보였기 때문이다. 번호표 기계처럼 받는 순간 번호가 넘어간다는 것이 모두에게 분명하면, 바꾸기와 돌려주기를 묶어도 헷갈리지 않는다.

### 스택의 pop
스택(Stack)에서 꺼내는 pop은 맨 위 값을 돌려주면서 그 값을 없앤다. 질의이면서 명령이다.

```js
const stack = [1, 2, 3];
console.log(stack.pop()); // 3
console.log(stack.pop()); // 2
console.log(stack);       // [ 1 ]
```

원칙대로라면 맨 위 값을 보는 질의와 맨 위 값을 없애는 명령으로 나눠야 한다.

```js
const s = [1, 2, 3];
const peek = (s) => s[s.length - 1];       // 질의
const remove = (s) => { s.length -= 1; };  // 명령

console.log(peek(s)); // 3
console.log(peek(s)); // 3
remove(s);
console.log(peek(s)); // 2
```

Fowler의 글에 따르면 Meyer는 pop 같은 메서드도 피할 수 있다고 보지만, Fowler 자신은 pop이 쓸모 있어서 이 경우에는 원칙을 어기겠다고 썼다.

### 반복자의 next
반복자(Iterator)의 사전적 의미는 되풀이하는 것이다. 공학적으로는 모음(리스트, 배열 등)에서 값을 하나씩 차례로 꺼내 주는 객체를 말한다. 자바스크립트 반복자의 `next()` 는 지금 값을 돌려주면서 다음 칸으로 넘어간다.

```js
const it = ['a', 'b'][Symbol.iterator]();
console.log(it.next()); // { value: 'a', done: false }
console.log(it.next()); // { value: 'b', done: false }
console.log(it.next()); // { value: undefined, done: true }
```

같은 `next()` 를 불렀는데 결과가 매번 다르다. Fowler는 Java 반복자의 `next` 를 이 원칙을 어기는 예로 들고, 다음 칸으로 넘기는 명령과 지금 값을 보는 질의를 따로 두는 쪽을 더 좋아한다고 썼다.

### 여럿이 함께 쓰는 값과 원자적 연산
여러 작업이 같은 값을 함께 쓰면, 나눠 놓은 질의와 명령 사이에 다른 작업이 끼어들 수 있다. 빵집에 마지막 빵이 하나 남았을 때, 두 손님이 동시에 진열대를 보고 "있네" 하고 손을 뻗으면 한 사람은 빈손이 된다. 보는 것과 집는 것 사이에 틈이 있기 때문이다.

아래는 이 상황을 자바스크립트 비동기 함수 두 개로 흉내 낸 것이다. 비동기 함수는 `await` 를 만나면 그 자리에서 잠시 멈추고, 그동안 다른 함수가 먼저 실행된다. 이 멈춤이 확인과 꺼내기 사이의 틈 역할을 한다.

```js
const stack = ['마지막 하나'];

async function worker(name) {
  if (stack.length > 0) {        // 질의: 비어 있지 않은지 확인
    await null;                  // 그 사이 다른 작업이 실행될 틈
    const item = stack.pop();    // 명령: 꺼내기
    console.log(name, item);
  }
}

worker('A');
worker('B');
// 출력 (두 호출이 모두 확인을 마친 뒤에 꺼낸다)
// A 마지막 하나
// B undefined
```

A와 B 모두 확인할 때는 값이 있었지만, B가 꺼낼 때는 이미 A가 가져간 뒤였다. 이런 경우에는 확인과 꺼내기를 한 번에, 중간에 아무도 끼어들 수 없게 해야 한다. 그래서 여럿이 함께 쓰는 자료구조는 꺼내면서 값을 돌려주는 연산을 일부러 하나로 묶어 둔다.

[원자적 연산](../동기화%20도구(Synchronization%20Primitives)/README.md#원자적-연산-atomic-operation)의 비교 후 교환(CAS, Compare-And-Swap)도 같은 이유로 바꾸기와 돌려주기를 함께 한다. 지금 값이 기대한 값과 같으면 새 값으로 바꾸고, 바꾸기 전 값(또는 성공 여부)을 돌려준다. 자바스크립트에서는 `Atomics.compareExchange` 가 이 일을 한다. 아래 코드의 `SharedArrayBuffer` 는 여러 스레드가 함께 볼 수 있는 메모리이고, `Int32Array` 는 그 메모리를 정수 칸으로 나눠 읽게 해 준다. 여기서는 칸 하나만 쓴다. 자세한 동작은 따로 정리한다.

```js
const shared = new Int32Array(new SharedArrayBuffer(4)); // 값 0으로 시작

// 지금 값이 0이면 5로 바꾸고, 바꾸기 전 값을 돌려준다
console.log(Atomics.compareExchange(shared, 0, 0, 5)); // 0 (바꿨다)
console.log(shared[0]);                                // 5
console.log(Atomics.compareExchange(shared, 0, 0, 7)); // 5 (0이 아니라서 바꾸지 않았다)
console.log(shared[0]);                                // 5
```

이것을 값을 읽는 질의와 값을 바꾸는 명령으로 나누면, 바로 앞의 빵집 문제가 다시 생긴다. 읽은 뒤 바꾸기 전에 다른 작업이 값을 바꿀 수 있기 때문이다. 이런 연산에서는 둘을 묶는 것 자체가 목적이다.

<br/>

## 원칙을 어떻게 받아들일까
명령과 질의 분리는 지키면 대부분 이득을 보는 기본값으로 받아들이는 것이 좋다. 새 함수를 만들 때는 먼저 둘로 나눌 수 있는지 생각하고, 나누는 쪽이 자연스러우면 나눈다.

묶어야 할 분명한 이유가 있으면 묶는다. 위에서 본 것처럼 함께 쓰는 값을 한 번에 확인하고 바꿔야 할 때, 또는 pop처럼 묶은 쪽이 훨씬 쓰기 편하고 널리 알려진 관례일 때다. 이때는 아래 두 가지를 챙긴다.

- 이름에서 상태가 바뀐다는 것이 드러나게 한다. `getTicket` 보다는 `takeTicket`, `issueTicket` 처럼 동작이 보이는 이름이 낫다
- 상태를 바꾸지 않는 질의도 함께 둔다. pop 옆에 peek을 두면, 값만 보고 싶은 쪽은 질의를 쓸 수 있다

원칙의 목적은 묻는 쪽이 안심하고 물을 수 있게 하는 것이다.

<br/>

## CQRS와의 차이
이름이 비슷한 CQRS(Command Query Responsibility Segregation, 명령과 질의 책임 분리)가 있다. Fowler의 2011년 글에 따르면 Fowler가 Greg Young에게서 처음 들은 패턴이고, 명령과 질의라는 말을 이 원칙에서 빌려 왔다.

명령과 질의 분리는 함수 하나를 어떻게 만들지에 대한 원칙이다. CQRS는 시스템 전체를 어떻게 나눌지에 대한 아키텍처 패턴이다. 데이터를 바꾸는 쪽과 읽는 쪽이 서로 다른 모델을 쓰게 하고, 경우에 따라 저장소까지 나눈다. Fowler는 CQRS가 생각의 큰 전환이 필요하고 자신이 본 사례 대부분이 좋지 않았다며, 시스템 전체가 아니라 필요한 일부에만 조심해서 쓰라고 경고한다. 자세한 내용은 따로 정리한다.
