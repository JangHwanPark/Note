## 동기화 도구란 ?
- 여러 스레드가 같은 데이터를 함께 쓸 때 순서가 엉켜 값이 깨지지 않도록 막는 장치
- 대표적으로 락(뮤텍스), 세마포어, 원자적 연산이 있다
- 동기화(Synchronization)의 사전적 의미는 시간을 맞추는 것이다. 여기서는 여러 스레드가 공유 데이터에 손대는 순서를 맞춘다는 뜻이다. 영어로는 Synchronization Primitives라고 하는데, Primitive는 더 큰 장치를 만드는 바탕이 되는 기본 요소라는 뜻이다
- 이 노트는 [서버의 동시 처리 방식](../서버의%20동시%20처리%20방식(Server%20Concurrency)/README.md) 노트에서 멀티 스레드 방식의 약점으로 짚은 경쟁 상태를 이어서 다룬다

<br/>

## 왜 필요할까
### 같은 냉장고를 쓰는 요리사들
서버의 동시 처리 방식 노트에서 스레드를 한 주방 안의 요리사에 비유했다. 같은 주방의 요리사들은 냉장고를 함께 쓴다. 덕분에 재료를 나누기는 쉽지만, 두 사람이 동시에 같은 재료에 손을 대면 일이 꼬인다.

예를 들어 냉장고 문에 붙은 계란 개수 메모를 두 요리사가 동시에 고친다고 해 보자. 둘 다 메모에서 10을 읽고, 각자 계란을 하나씩 넣은 뒤 11이라고 고쳐 적는다. 계란은 12개가 되었는데 메모는 11이다. 한 사람이 한 일이 사라졌다.

### 한 줄짜리 코드도 세 단계다
[변수](../변수(Variable)/README.md#읽기와-쓰기) 노트에서 `x = x + 1` 한 줄이 읽기, 더하기, 쓰기 세 단계로 실행된다고 했다. 스레드가 하나일 때는 중간에 잠깐 멈추더라도 그사이 이 값을 건드리는 다른 쪽이 없으니 문제가 없다. 스레드가 둘이면 한 스레드가 읽고 나서 쓰기 전에 다른 스레드가 끼어들 수 있다.

카운터 값이 50일 때 두 스레드가 각각 1을 더하면 아래처럼 될 수 있다.

```text
스레드 A: 읽기 (50)
스레드 B: 읽기 (50)
스레드 A: 더하기 (51)
스레드 B: 더하기 (51)
스레드 A: 쓰기 (51)
스레드 B: 쓰기 (51)     -> 두 번 더했는데 결과는 51
```

어느 순간에 끼어드는지는 운영체제가 스레드를 언제 바꿔 실행하느냐([컨텍스트 스위칭](../컨텍스트%20스위칭(Context%20Switching)/README.md), Context Switching)와, 여러 CPU 코어가 동시에 돌아가는 타이밍에 달려 있다. 그래서 같은 프로그램이라도 실행할 때마다 결과가 달라질 수 있다.

## 먼저 알아 둘 용어
### 경쟁 상태 (Race Condition)
경쟁(Race)의 사전적 의미는 경주, 누가 먼저 도착하는지 겨루는 것이다.
공학적으로는 여러 스레드가 같은 데이터를 거의 같은 때에 고치려 해서, 어느 쪽이 먼저 실행되느냐에 따라 결과가 달라지는 상황을 말한다. 스레드들이 같은 데이터를 두고 경주를 벌이고, 그 경주의 순서가 결과를 정한다는 뜻에서 이름이 왔다. 위의 계란 메모가 바로 경쟁 상태다.

### 임계 구역 (Critical Section)
임계(Critical)의 사전적 의미는 아슬아슬한 경계, 일이 크게 달라지는 고비다.
공학적으로는 공유 데이터에 접근하는 코드 중에서 한 번에 한 스레드만 실행해야 하는 부분을 말한다. 두 스레드가 함께 들어가면 결과가 깨지는 아슬아슬한 구간이라는 뜻이다. 위 예에서는 읽기, 더하기, 쓰기 세 단계 전체가 임계 구역이다.

### 상호 배제 (Mutual Exclusion)
상호(Mutual)는 서로, 배제(Exclusion)는 밀어내어 빼놓음이라는 뜻이다.
공학적으로는 한 스레드가 임계 구역 안에 있으면 다른 스레드는 들어오지 못하게 막는 성질을 말한다. 서로가 서로를 밀어낸다는 뜻 그대로다. 이 노트의 동기화 도구는 대부분 이 성질을 만들기 위한 것이다.

## 직접 재현해 보기
### 실행한 코드
스레드 네 개가 공유 카운터 하나에 각각 백만 번씩 1을 더한다. 경쟁 상태가 없다면 결과는 4,000,000이어야 한다. Node.js의 `worker_threads` 로 스레드를 만들고, `SharedArrayBuffer` 로 모든 스레드가 같은 메모리 칸을 보게 했다.

```js
const { Worker, isMainThread, workerData } = require('node:worker_threads');

const WORKERS = 4;
const TIMES = 1_000_000;

if (isMainThread) {
  const mode = process.argv[2]; // 'plain' 또는 'atomic'
  const shared = new Int32Array(new SharedArrayBuffer(4)); // 스레드가 함께 보는 칸 하나
  let done = 0;
  for (let i = 0; i < WORKERS; i++) {
    const w = new Worker(__filename, { workerData: { shared, mode } });
    w.on('exit', () => {
      if (++done === WORKERS) {
        console.log(`${mode}: 기대값 ${WORKERS * TIMES}, 실제값 ${shared[0]}`);
      }
    });
  }
} else {
  const { shared, mode } = workerData;
  for (let i = 0; i < TIMES; i++) {
    if (mode === 'plain') shared[0] = shared[0] + 1;   // 읽기, 더하기, 쓰기 세 단계
    else Atomics.add(shared, 0, 1);                     // 한 번에 끝나는 원자적 더하기
  }
}
```

파일을 race.js로 저장하고 `node race.js plain`, `node race.js atomic` 으로 실행했다.

### 결과
2026-10-27에 Windows 11, Node.js v24.22.1, 논리 코어 8개인 PC에서 실행했다. 일반 더하기(plain)는 다섯 번 돌렸는데 매번 값이 달랐고, 한 번도 4,000,000이 나오지 않았다.

```text
plain: 기대값 4000000, 실제값 3810359
plain: 기대값 4000000, 실제값 3012006
plain: 기대값 4000000, 실제값 3835289
plain: 기대값 4000000, 실제값 2180401
plain: 기대값 4000000, 실제값 3587024
```

원자적 더하기(atomic)는 세 번 모두 정확히 4,000,000이었다.

```text
atomic: 기대값 4000000, 실제값 4000000
atomic: 기대값 4000000, 실제값 4000000
atomic: 기대값 4000000, 실제값 4000000
```

일반 더하기에서 사라진 수십만 번의 더하기가 앞에서 본 끼어들기의 결과다. 코어 수나 운영체제가 다르면 잃는 양도 달라지므로, 위 숫자는 이 환경에서 나온 한 예로 보면 된다. 원자적 더하기가 무엇인지는 아래 "원자적 연산"에서 본다.

## 락 (Lock)
### 락이란 ?
락(Lock)의 사전적 의미는 자물쇠, 잠그다.
공학적으로는 임계 구역 앞에 거는 자물쇠 역할을 하는 변수를 말한다. 락은 비어 있음(풀림)과 잡힘(잠김) 두 상태 중 하나다. 임계 구역에 들어가려는 스레드는 먼저 락을 잡고, 다 쓰고 나오면 락을 푼다.

화장실 열쇠가 하나뿐인 가게와 같다. 화장실에 가려면 카운터에서 열쇠를 받아야 하고, 열쇠가 없으면 돌아올 때까지 기다린다. 열쇠가 하나라서 화장실 안에는 늘 한 사람만 있다.

### 어떻게 동작할까
카운터 예시에 락을 걸면 아래처럼 된다.

```text
lock(m)              // 락을 잡는다. 누가 잡고 있으면 풀릴 때까지 기다린다
counter = counter + 1
unlock(m)            // 락을 푼다. 기다리던 스레드 중 하나가 잡을 수 있다
```

락을 잡은 스레드가 읽기, 더하기, 쓰기를 마칠 때까지 다른 스레드는 `lock` 에서 기다린다. 그래서 세 단계가 중간에 끼어들기 없이 한 덩어리처럼 실행된다. 운영체제에 맡기고 잠들어 기다리는 락이라면, 기다리는 동안 스레드는 블로킹 상태가 된다([블로킹과 논블로킹](../블로킹과%20논블로킹(Blocking%20and%20Non-blocking)/README.md) 노트 참고). 잠들지 않고 기다리는 방법도 있는데 아래에서 본다.

위 재현 코드의 일반 더하기를 락으로 감싼 버전도 같은 환경에서 세 번 돌려 보았고, 세 번 모두 4,000,000이 나왔다. 이 버전은 `Atomics` 로 락을 직접 만들어야 해서 코드가 길어지므로 노트에는 싣지 않는다.

### 기다리는 방법은 두 가지
락이 잡혀 있을 때 기다리는 방법은 크게 두 가지다. 락이 풀렸는지 계속 확인하며 CPU를 쓰는 방법을 스핀 락(Spin Lock)이라고 한다. 스핀(Spin)은 제자리에서 돈다는 뜻이다. 다른 방법은 운영체제에 잠들어 있겠다고 맡기고, 락이 풀리면 깨워 달라고 하는 것이다. 어느 쪽이 나은지는 임계 구역이 얼마나 짧은지에 달려 있고, 자세한 비교는 TODO로 넘긴다.

## 뮤텍스 (Mutex)
### 뮤텍스란 ?
뮤텍스(Mutex)는 앞에서 본 상호 배제(Mutual Exclusion)를 줄인 말이다. 한 스레드가 임계 구역에 있으면 다른 스레드를 밀어낸다는 목적을 이름에 그대로 담았다.
공학적으로는 상호 배제를 위한 락을 말한다. 유닉스 계열의 표준 스레드 라이브러리(POSIX threads)도 락을 뮤텍스라고 부른다. 그래서 많은 글에서 락과 뮤텍스를 거의 같은 뜻으로 쓴다.

### 소유 개념
뮤텍스에는 주인(Owner)이 있다. 뮤텍스를 잡은 스레드가 그 뮤텍스의 주인이 되고, 원칙적으로 잡은 스레드만 풀 수 있다. POSIX 표준은 주인이 아닌 스레드가 뮤텍스를 풀려고 하면, 뮤텍스 종류에 따라 오류를 돌려주거나 동작을 정의하지 않는다고 적고 있다.

화장실 열쇠로 치면 열쇠를 받아 간 사람만 반납할 수 있는 것과 같다. 다른 사람이 대신 반납하면 안에 있는 사람이 있는데도 다음 사람이 들어올 수 있다.

<br/>

## 세마포어 (Semaphore)
### 세마포어란 ?
세마포어(Semaphore)의 사전적 의미는 깃발이나 등, 움직이는 팔로 신호를 보내는 신호 장치다. 철도의 완목 신호기처럼 지나가도 되는지를 알려 준다. 어원은 그리스어 sêma(표시, 신호)와 phoros(나르는 것)다.
공학적으로는 정수 값 하나를 가진 동기화 도구로, 그 값으로 지금 몇 개의 스레드가 더 들어올 수 있는지를 나타낸다. 지나가도 되는지 알려 주는 신호기의 역할을 스레드 사이에서 하는 셈이다. 다익스트라(Edsger Dijkstra)가 동료들과 함께 고안해 소개했다.

주차장 입구의 빈자리 표시판과 같다. 빈자리가 3이면 차가 들어갈 때마다 하나씩 줄고, 0이 되면 다음 차는 입구에서 기다린다. 차가 나가면 숫자가 하나 늘고 기다리던 차가 들어간다.

### 어떻게 동작할까
세마포어는 두 가지 동작으로만 다룬다.

- wait: 값을 1 줄인다. 줄인 값이 음수면 그 자리에서 기다린다
- post: 값을 1 늘린다. 기다리는 스레드가 있으면 하나를 깨운다

POSIX에서는 이 둘을 `sem_wait`, `sem_post` 라고 부른다. 다익스트라는 처음에 P와 V라고 불렀는데, 네덜란드어에서 따온 글자다. 위 정의대로라면 값이 음수일 때 그 절댓값은 기다리는 스레드 수와 같다. 실제 구현은 값을 0 아래로 내리지 않는 경우도 있다.

```text
sem_init(s, 3)       // 빈자리 3개로 시작
sem_wait(s)          // 자리 하나 차지. 남은 자리가 없으면 기다린다
... 공유 자원 사용 ...
sem_post(s)          // 자리 하나 반납
```

### 이진 세마포어와 계수 세마포어
값을 1로 시작하면 한 번에 한 스레드만 들어갈 수 있다. 결국 락과 같은 일을 하고, 들어갈 수 있는지만 따지면 된다와 안 된다 두 경우뿐이라서 이진 세마포어(Binary Semaphore)라고 부른다. 주차 자리가 하나뿐인 주차장이다.

값을 2 이상으로 시작하면 그 수만큼 동시에 들어갈 수 있다. 데이터베이스 연결을 다섯 개만 열어 두고 스레드들이 나눠 쓰게 하는 것처럼, 정해진 개수의 자원을 여럿이 나눠 쓸 때 쓴다. 남은 개수를 센다는 뜻에서 계수 세마포어(Counting Semaphore)라고 부른다.

<br/>

## 뮤텍스와 세마포어의 차이
이진 세마포어는 뮤텍스와 하는 일이 비슷해 보이지만 두 가지가 다르다.

첫째는 소유 개념이다. 뮤텍스는 잡은 스레드가 주인이고 그 스레드가 풀어야 한다. 세마포어에는 주인이 없어서 wait한 스레드와 post하는 스레드가 달라도 된다. 그래서 세마포어는 한 스레드가 일을 마쳤다고 다른 스레드에 알리는 순서 맞추기에도 쓸 수 있다. 예를 들어 값을 0으로 만든 세마포어에서 부모 스레드가 wait하고 기다리면, 자식 스레드가 일을 끝낸 뒤 post해서 부모를 깨운다.

둘째는 동시에 허용하는 수다. 뮤텍스는 늘 한 스레드만 들인다. 세마포어는 처음 값만큼 들일 수 있다.

비유로 정리하면 뮤텍스는 받아 간 사람이 직접 반납하는 화장실 열쇠 하나이고, 세마포어는 누가 들어가고 나가든 숫자만 세는 주차장 표시판이다.

<br/>

## 원자적 연산 (Atomic Operation)
### 원자적 연산이란 ?
원자(Atom)의 어원은 그리스어 atomos로, 더 쪼갤 수 없다는 뜻이다.
공학적으로 원자적 연산은 중간에 끊기지 않고 한 번에 끝나는 연산을 말한다. 다른 스레드가 보기에는 아직 시작하지 않았거나 이미 끝났거나 둘 중 하나이고, 반쯤 진행된 상태는 보이지 않는다. 더 쪼갤 수 없는 한 단위로 실행된다는 점이 원래 뜻과 이어진다.

계란 메모로 치면, 메모를 읽고 고쳐 적는 대신 버튼을 누를 때마다 숫자가 하나씩 올라가는 계수기를 쓰는 것과 같다. 두 사람이 거의 동시에 눌러도 계수기는 두 번 올라간다.

### 락 없이 푸는 경우
읽기, 더하기, 쓰기를 CPU가 다른 코어가 끼어들 수 없게 한 번에 처리해 주면 끼어들 틈이 없다. 이를 위한 명령은 CPU 종류마다 다르다. 그래서 카운터 증가처럼 값 하나를 바꾸는 단순한 일은 락 없이 원자적 연산으로 풀 수 있다. 앞의 재현에서 쓴 `Atomics.add` 가 이 경우다. MDN은 `Atomics` 가 공유 메모리에서 값을 예측 가능하게 읽고 쓰도록, 그리고 연산이 중간에 끊기지 않도록 보장한다고 설명한다.

원자적 연산은 락처럼 다른 스레드를 기다리게 하지 않으니 가볍다. 다만 값 하나를 바꾸는 일에만 쓸 수 있다. 계좌 두 개에서 한쪽은 빼고 한쪽은 더하는 것처럼 여러 값을 함께 바꿔야 하면, 그 전체를 묶어 줄 락이 필요하다. 원자적 연산은 락을 만드는 재료로도 쓰인다. 락이 비어 있으면 잡았다고 표시하는 일 자체를 원자적으로 해야 두 스레드가 동시에 락을 잡는 일이 없다.

## 교착 상태 (Deadlock)
### 교착 상태란 ?
데드락(Deadlock)의 사전적 의미는 양쪽이 버텨 꼼짝도 못 하는 막다른 상태다. 교착(膠着)도 단단히 달라붙어 움직이지 않는다는 뜻이다.
공학적으로는 두 개 이상의 스레드가 서로 상대가 가진 락을 기다리느라 아무도 앞으로 나아가지 못하는 상태를 말한다.

좁은 골목에서 마주 오던 두 차가 서로 상대가 먼저 비켜 주길 기다리며 멈춘 것과 같다. 둘 다 물러서지 않으면 영원히 그 자리에 있다.

### 어떻게 생길까
락 A와 락 B가 있고, 두 스레드가 서로 반대 순서로 잡는다고 해 보자.

```text
스레드 1                 스레드 2
lock(A)                  lock(B)
lock(B)   // B를 기다림   lock(A)   // A를 기다림
```

스레드 1이 A를 잡은 직후 스레드 2가 B를 잡으면, 스레드 1은 B를, 스레드 2는 A를 기다린다. 둘 다 자기 락을 놓지 않으니 영원히 멈춘다. 매번 생기지는 않고 실행 순서가 이렇게 맞물릴 때만 생기기 때문에, 시험할 때는 멀쩡하다가 운영 중에 가끔 터지는 경우가 많다.

### 네 가지 조건
1971년 코프먼(E. G. Coffman) 등이 정리한 바에 따르면, 교착 상태는 아래 네 조건이 모두 성립할 때만 생긴다.

- 상호 배제: 자원(락)을 한 번에 한 스레드만 쓸 수 있다
- 점유 대기(Hold and Wait): 이미 잡은 락을 쥔 채로 다른 락을 기다린다
- 비선점(No Preemption): 다른 스레드가 쥐고 있는 락을 강제로 빼앗을 수 없다
- 순환 대기(Circular Wait): 스레드들이 꼬리를 물고 다음 스레드의 락을 기다려 원을 이룬다

골목의 두 차로 보면, 길은 한 차씩만 지날 수 있고(상호 배제), 각자 들어온 길을 차지한 채 앞길을 기다리고(점유 대기), 상대 차를 들어서 치울 수 없고(비선점), 서로가 서로를 기다린다(순환 대기).

### 피하는 기본 방법: 락 순서 정하기
네 조건 중 하나만 깨도 교착 상태는 생기지 않는다. 가장 많이 쓰는 방법은 순환 대기를 깨는 것으로, 모든 스레드가 락을 같은 순서로 잡도록 정해 두는 것이다. 위 예에서 "항상 A를 먼저, B를 나중에" 잡기로 하면 스레드 2도 A부터 기다리므로 원이 생기지 않는다.

```text
스레드 1                 스레드 2
lock(A)                  lock(A)   // A가 풀릴 때까지 기다림
lock(B)
...
unlock(B)
unlock(A)                          // 이제 A를 얻음
                         lock(B)
```

락이 많은 큰 프로그램에서는 모든 락에 한 줄로 순서를 매기기 어려워서, 함께 잡힐 수 있는 락끼리만 순서를 정하기도 한다.

## 락을 너무 넓게 잡으면
### 넓은 락의 비용
락이 지키는 범위를 넓히면 실수할 여지는 줄어든다. 프로그램 전체에 락 하나만 두면 임계 구역을 빠뜨릴 일도, 락 순서를 고민할 일도 없다. 대신 그 락 안에서는 늘 한 스레드만 일할 수 있다. 스레드를 여러 개 띄워도 락 앞에 줄을 서 있는 시간이 길어지면, 결국 하나씩 차례로 처리하는 것과 비슷해진다.

화장실 열쇠 하나로 화장실뿐 아니라 창고와 탈의실까지 잠근 가게와 같다. 창고에 물건을 가지러 가는 직원도 화장실 쓰는 손님이 나오길 기다려야 한다.

### 좁게 나누기
그래서 서로 다른 데이터는 서로 다른 락으로 지키는 방법을 쓴다. 큰 락 하나로 모든 임계 구역을 묶는 것을 굵은 단위 락(Coarse-grained Lock), 데이터마다 락을 따로 두는 것을 세밀한 단위 락(Fine-grained Lock)이라고 한다. 락을 잘게 나누면 여러 스레드가 동시에 일할 수 있지만, 락이 많아질수록 잡는 순서가 복잡해지고 앞에서 본 교착 상태의 위험도 커진다.

락 안에서 하는 일도 짧게 둔다. 락을 쥔 채 파일을 읽거나 다른 서버의 응답을 기다리면 그동안 다른 스레드는 모두 줄을 서야 한다. 공유 데이터를 고치는 부분만 락 안에 두고, 기다리는 일은 락 밖으로 뺀다.
