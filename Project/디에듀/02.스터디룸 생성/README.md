# StudyRoom 생성(Create) 기능 개발 회고
스터디룸 생성 기능은 단순한 입력 폼이 아니라 `단계별 폼(Step Form)`   을 기반으로 한 복합 상태 관리 기능이었다.

단계적 폼 진행, 서버 연동, 라우팅 분기, 상태 일관성까지 모두 포함된 구조로 불완전한 요구사항 속에서 문제를 직접 정의하고 해결한 경험이었다.

## 1. 요구사항 및 분석
초기 기획은 `교사가 스터디룸을 생성할 수 있는 폼`이었다. 제공된 자료는 다음 두 가지뿐이었다.
- 디자인 시안(Figma)
- API 문서

그리고 명확히 정의된 스펙은 `제목(name)은 필수 입력`뿐이었다. 문제는 다음이었다. `사용자 추가`API가 studyRoomId를 요구하기 때문에 스터디룸이 먼저 생성되어야만 초대가 가능했다.

이로 인해 3단계 폼에서 생성 완료 시점과 초대 단계의 순서를 새로 정의해야 했다.

### 1.1. 요구사항 재정의
| 단계     | 목적                 | 주요 필드                                                | 조건       |
| ------ | ------------------ | ---------------------------------------------------- | -------- |
| Step 1 | 기본정보 입력            | `name`, `description`, `visibility`                  | 제목 필수    |
| Step 2 | 수업정보 입력            | `modality`, `classForm`, `subjectType`, `schoolInfo` | 생성 가능 단계 |
| Step 3 | (삭제됨 → 초대 페이지로 분리) | -                                                    | -        |

## 2. 설계 방향과 마주한 문제들
### 2.1. 생성이 늦어져 초대가 불가능한 문제
폼의 마지막 단계(Step 3)에서 초대 정보를 같이 처리하면 API 호출 순서상 studyRoomId가 존재하지 않아 초대 요청 불가능했다.

이 문제를 해결하기 위해 Step 2 단계에서 스터디룸 생성 요청이 가능하도록 구조 변경하고 스터디룸 생성 성공 시 id를 받아 모달(ConfirmDialog)을 띄워 사용자의 선택을 받도록 했다.
- 지금 초대하기: /studyrooms/:id/invite-member
- 나중에 할게요: /studyrooms/dashboard

### 2.2. 스텝 검증 로직 중복
초기 구현에서는 각 단계마다 유효성 검증 로직이 흩어져 있어 관리가 어려웠다. 같은 검증 규칙이 여러 곳에 중복되어 수정 시 모든 스텝 코드를 함께 변경해야 하는 비효율이 있었다.

이를 해결하기 위해 fieldsPerStep 객체를 도입했다. 각 스텝이 어떤 필드를 검증해야 하는지를 한 곳에서 정의해두고 현재 스텝의 필드만 trigger() 함수로 검증하도록 개선했다.

이 방식으로 검증 로직이 일관성을 갖게 되었고 새로운 스텝이 추가되더라도 fieldsPerStep에 필드 배열만 추가하면 쉽게 확장할 수 있게 되었다.

### 2.3. 라우팅과 상태 책임의 경계가 모호
처음 설계에서는 스터디룸 생성과 사용자 초대로직이 하나의 폼 안에 섞여 있었다. 이로 인해 상태 관리가 복잡해지고 폼이 지나치게 많은 역할을 수행하게 되었다.

이 문제를 해결하기 위해 초대 과정을 별도 페이지로 분리했다. 폼은 오직 스터디룸 생성을 담당하고 초대 페이지는 생성된 id를 주입받아 다음 과정을 이어가도록 했다.

이렇게 라우팅 경계와 상태의 책임을 명확히 나누자 전체 플로우가 훨씬 단순해졌고, 각 단계의 역할이 명확히 드러나 유지보수가 용이해졌다.

## 3. 스펙 변경 및 대응과정
초기 설계 단계에서 스터디룸 생성 플로우는 `기본정보 → 프로필 → 사용자 초대 및 생성`으로 구성된 3단계 폼 구조였다.

하지만 초대는 생성 이후에만 가능하다는 API 정책으로 인해 최종 단계에서 생성과 초대를 동시에 처리하려던 설계는 API 호출 순서상 논리적으로 불가능한 구조였다. 또한 최종 단계에서 검증 / 생성 로직이 중복되고 비동기 호출이 겹치며 복잡도가 상승했다.

이 문제를 해결하기 위해 Step 3을 완전히 제거하고 대신 Step 2 단계에서 스터디룸 생성 요청(useCreateStudyRoomMutation)을 수행하는 방식으로 설계를 변경했다. 사용자가 필수 정보를 모두 입력하면 Step 2에서 바로 스터디룸이 생성되고 성공 시점에 모달(ConfirmDialog)을 띄워 사용자의 다음 행동을 명시적으로 선택하게 했다.

- 지금 초대하기를 선택하면 /studyrooms/:id/invite-member 페이지로 이동
- 나중에 하기를 선택하면 /studyrooms/dashboard로 이동

이로써 생성과 초대의 책임이 분리되었고 플로우 역시 사용자가 행동을 결정하는 구조로 단순화되었다. 다만 일정상의 제약으로 초대 다이얼로그 로직을 일부 재사용하면서 중복 로직이 임시로 존재한다. 현재는 정상 동작을 우선했고 이후 리팩토링 단계에서 공통 컨트롤러로 통합해 재사용성과 유지보수성을 높일 예정이다.

## 4. 기술 구현 요약
| 구분       | 기술                                               | 목적                          |
| -------- | ------------------------------------------------ | --------------------------- |
| 상태 관리    | `useReducer` (`stepperReducer`, `dialogReducer`) | 단계 이동 및 모달 상태 관리            |
| 폼 검증     | React Hook Form + Zod                            | 단계별 검증 및 필드 유효성             |
| 비동기 처리   | React Query (`useCreateStudyRoomMutation`)       | 생성 후 캐시 무효화 및 UI 갱신         |
| UI 프레임워크 | Radix UI + TailwindCSS                           | 접근성과 시각적 일관성                |
| 라우팅 제어   | Next.js App Router                               | 분기 이동 제어 및 `studyRoomId` 주입 |

## 5. 배운점 및 회고
이번 스터디룸 생성 기능을 개발하면서 가장 크게 배운 점은 제한된 스펙 속에서도 핵심 흐름을 명시적으로 설계하는 힘이었다.

스펙이 충분히 정의되지 않은 상태였지만`생성 → 선택 → 이동`이라는 명확한 사용자 흐름을 중심으로 설계하니 복잡했던 구조가 오히려 단순해졌다. 결국 기술적 복잡도는 기능이 아니라 흐름이 불분명할 때 커진다는 걸 체감했다.

또 이번 작업을 통해 UI보다 중요한 것은 상태의 수명주기라는 점을 다시 확인했다. 폼의 입력 상태 스터디룸 생성 상태, 라우팅 상태를 명확히 분리하자
불필요한 리렌더링과 상태 충돌이 줄었고 디버깅도 훨씬 쉬워졌다.

문서화의 필요성도 분명해졌다. 이 시점에는 공식 명세 문서가 없어 개발자가 단계를 추론 및 정리해야 했다. 특히 `어떤 시점에 어떤 API가 호출되는지`가 문서화되어 있지 않아 작은 오해에도 플로우가 흔들릴 위험이 있었다. 문서화는 사후 정리가 아니라 혼란을 줄이는 도구임을 체감했다.

마지막으로, 이번 프로젝트를 통해 느낀 건 리팩토링은 완벽한 코드를 만드는 게 아니라 의도를 유지할 수 있는 구조를 만드는 과정이라는 점이다.

마지막으로, 리팩토링은 `완벽한 코드`가 아니라 의도를 유지할 수 있는 구조를 만드는 일이다. 생성 이후 초대 페이지에서 다이얼로그 일부를 재사용하며 중복이 생겼지만 일단 정상 동작을 확보한 뒤 공통 컨트롤러로 통합할 계획이다.

## 6. 개선 여지 및 다음 단계(Next Step)
다음 단계에서는 기술적 / 구조적 개선을 함께 진행할 예정이다.

Zod의 preprocess 기능을 활용해 기본값 처리와 타입 정합성을 더욱 강화하고 생성 완료 후에는 사용자에게 Toast 피드백을 추가해 UX 완성도를 높일 계획이다.

단계 간 데이터를 유지하기 위해 Auto Save 기능을 도입하고 현재 분리된 모달/초대 로직을 Dialog 기반으로 통합하여 공통 컨트롤러로 관리할 예정이다.

이번 프로젝트에서 경험한 `디자인 + 최소 스펙`환경은 현실적인 개발 환경에서도 자주 맞닥뜨리는 상황이다. 이를 교훈 삼아 Step Template 문서화를 도입해 앞으로 비슷한 구조의 폼을 쉽게 재활용할 수 있도록 정리할 계획이다.

마지막으로 이번 경험을 기반으로 FDD(Feature-Driven Development) 프로세스를 강화하려 한다. 기획, API, 테스트케이스를 한 문서 안에서 연결해
모든 기능이 하나의 문맥 안에서 관리되도록 개선할 예정이다.

이번 생성 기능을 통해 검증된 Controller / Query / UI 구조를 팀 공통 FE 아키텍처 표준으로 확립해 향후 모든 신규 기능에서 동일한 패턴을 적용할 수 있는 기반을 만들 계획이다.
