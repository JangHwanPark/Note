## 문제 인식 (합류 당시 상황)
내가 디에듀에 합류했을 때 처음 느낀 건 `서비스가 존재한다`는 사실보다 `서비스가 어떻게 여기까지 돌아왔나`라는 의문이었다.

코드를 열어보기 전에는 기능이 일단 있다고 느껴졌지만 막상 구조를 따라가 보니 겉은 멀쩡해 보여도 속은 이미 헐거워질 대로 헐거워진 상태였다.

### 코드 레퍼런스
- 프론트엔드 소스 저장소: [dedu-client](https://github.com/JangHwanPark/dedu-client) — 초기에 맞닥뜨린 의존성 얽힘과 타입 붕괴 사례를 추적한 코드 베이스.

이 프로젝트는 처음부터 명확한 기준 없이 속도전에 가까운 방식으로 진행됐다는 걸 기존에 계셨던 분들의 설명을 통해 더 분명히 알 수 있었다.

## 원인 분석 (명세 부재 도메인 부재 구조 붕괴 속도전)
먼저 `공통된 명세 문서가 없었다` 기능을 만들기 전에 해당 기능이 어떤 역할을 해야 하는지 어떤 데이터가 필요한지 무슨 제약이나 규칙이 있는지 그런 기본적인 합의조차 없는 상태였다

그래서 자연스럽게 `기능 정의 없이 바로 개발에 들어가는 흐름`이 반복됐다고 한다. 기능 단위가 아니라 화면 단위로 움직이는 방식 오늘 필요한 패스만 억지로 이어붙이며 만드는 식의 개발
문제가 생기면 그 순간만 봉합하는 방식....

그 와중에 `도메인 모델조차 존재하지 않았다` 같은 데이터를 누구는 이렇게 이해하고 다른 누구는 또 다르게 해석하고 그게 전체 기능 곳곳에 다른 형태로 흩어져 있었다.

물론 `FDD나 요구사항 명세 작업은 단 한 번도 정식으로 진행된 적이 없었다` 어떤 엔티티가 어떤 행위를 해야 하는지 기능 간 우선순위나 역할 분리가 어떻게 되어야 하는지를 문서로 잡아본 적 없는 프로젝트였던 것이다.

그 상태에서 `리팩토링 없이 누적되는 코드` 라는 결과는 너무나 자연스러웠다 코드를 개선하거나 정리하는 시간이 없었고 당장 필요한 기능을 빠르게 붙이고 다음 기능도 계속 추가하면서
구조는 점점 더 약해질 수밖에 없었다.

## 문제 현상 (순환참조 타입꼬임 구조 붕괴)
결국 그 개발 흐름은 `필요할 때마다 기능을 덧대어 붙이는 구조`를 만들었고 누군가는 전혀 다른 기능의 내부 타입을 들고와서 쓰고 다른 기능에서는 또 나름대로 타입을 새로 만들고 이렇게 서로 얽히면서 `공통 타입`이라는 개념조차 존재하지 않게 되었다.

이 지점부터는 문제가 단순히 불편함의 수준이 아니라 `프로젝트 전체가 서로를 갉아먹는 구조`로 변해갔다. 기능들은 서로의 타입을 참조하고 어떤 기능은 다른 기능의 API 응답을 그대로 재활용하고 서로가 서로를 끌어당기는 `의존성 거미줄`형태가 되었다.

```mermaid
graph LR
  subgraph Before: 기능↔기능 순환 의존
    FeatureA[Feature A UI·API·로직 뒤섞임] --공유 타입 없이 직접 참조--> FeatureB[Feature B 내부 타입]
    FeatureB --직접 의존--> FeatureC[Feature C API 응답 그대로 재사용]
    FeatureC --역참조·순환--> FeatureA
    SharedPseudo[shared 라고 불리지만 특정 기능 로직 포함] --암묵적 의존--> FeatureB
  end
```

위와 같은 흐름에서 한 기능의 타입이나 API 응답이 변하면 다른 기능이 연쇄적으로 깨지고 shared 안에서도 특정 기능 전용 로직을 건드리다 보니 순환참조와 타입 꼬임이 실제로 발생했다.

당연히 한쪽 타입이 수정되면 다른 쪽이 깨졌고 그 다른 쪽이 깨진 상태에서 수리를 하면 또다른 기능이 다시 터졌다. 이런 식으로 변화가 연쇄적으로 전파되는 `기능끼리 붙잡고 끌어당기는 위험한 구조`에 빠졌다. 여기서 특히 심각했던 건 `순환참조`가 실제로 발생하기 시작했다는 점이다.(실제로 눈에 띄게 경험한건 처음인것 같다.)

여기까지 파악한 문제들을 정리해보면 디에듀 초기 구조는 단순히 부채가 많은 수준이 아니라 `역할과 책임이 분리되지 않은 코드가 누적되며 생긴 복합적인 붕괴 상태`였다.

컴포넌트 안에는 `UI`, `도메인 로직`, `API`, `가공`, `검증`, `상태처리`이 모든게 뒤섞여 있었고 라이브러리 영역 역시 공용 함수와 특정 도메인의 로직이 뒤섞여 들어가 있었다.

공통 기능이라고 생각했던 파일 안에 사실 특정 화면 전용 코드가 들어있거나 화면 전용 유틸인 줄 알았던 코드가 또 다른 기능에서 쓰이고 이런 흐름이 계속되면서 `로직의 집` 위치라는 개념조차 사라졌다.

## 회고 (MVP 속도전 자체는 괜찮지만 회고 부재가 문제였다)
그 결과 각 기능은 자연스럽게 서로의 내부 코드를 참조하기 시작했고 순환참조가 발생하며 타입이 꼬이고 빌드 타임과 런타임 모두 예측할 수 없는 에러가 터지기 시작했다.

이쯤 되면 어떤 로직이 어디 있어야 하는지조차 판단이 어렵고
문제를 해결하려면 그 기능을 이해하는 것이 아니라 그 기능이 참조하고 있는 다른 기능들까지 전부 이해해야 하는 구조가 되어버린다. 즉 `기능 중심 속도전의 흔적이 코드 전체를 점령한 상태`였던 것이다.

사실 이 방식이 처음부터 완전히 잘못됐다고 생각하지는 않는다
초기 MVP 단계라면 빠르게 기능을 붙이고 화면을 만들고 유저 플로우를 검증하기 위해 속도전을 치는 건 충분히 있을 수 있는 일이다. 문제는 그 속도전의 한가운데서 잠깐 멈춰서 되짚어보는 시간이 없었다는 점이다.

기능을 만들었다면 그만큼 생긴 빚을 정리하는 회고가 필요했고
디버깅하면서 구조를 점검하는 시간이 필요했는데 그 과정 없이
그냥 계속 치고나가기만 했던 것 같다.

만들고, 붙이고, 다음 기능으로 넘어가고.. 그리고 또 붙이고
이 흐름이 반복되면서 부채를 정리할 기회가 완전히 사라져버렸고
그 축적된 흔적이 지금의 구조 문제로 이어졌다

속도전은 괜찮다고 생각한다. 하지만 속도로 인해 생긴 흔적을 돌아보는 과정이 빠지면 그 다음 단계로 넘어갈 수 있는 힘이 사라진다. 디에듀가 겪은 문제는 바로 그 회고의 부재라고 생각한다.

## 전환점과 재구조화의 필요성
[03. 지라 프로세스 개선](https://github.com/JangHwanPark/Note/tree/main/Project/%EB%94%94%EC%97%90%EB%93%80/03.%EC%A7%80%EB%9D%BC%20%ED%94%84%EB%A1%9C%EC%84%B8%EC%8A%A4%20%EA%B0%9C%EC%84%A0), [04. 문서 작성 프로세스 개선](https://github.com/JangHwanPark/Note/tree/main/Project/%EB%94%94%EC%97%90%EB%93%80/04.%EB%AC%B8%EC%84%9C%EC%9E%91%EC%84%B1%20%ED%94%84%EB%A1%9C%EC%84%B8%EC%8A%A4%20%EA%B0%9C%EC%84%A0)을 통해 팀의 문제점을 짚기 시작하면서 그동안 아무런 기준 없이 개발이 진행되어 왔다는 사실이 더 명확하게 드러났다.

문제는 단순히 기능마다 코드가 난잡했다는 정도가 아니라 팀 전체가 개발을 바라보는 방식 자체에 `체계와 기준`이 없었다는 점이었다.

그래서 기존의 스프린트 기반 개발 흐름을 유지하는 대신 명확한 목표 단위를 기준으로 움직일 수 있도록 `마일스톤 중심 개발`로 전환했다.

이 전환 이후 내가 맡게 된 MS2는 단순히 화면 몇 개를 만드는 수준이 아니라 기존 로직을 정상화하고 기능 간 의존을 정리하고
지금까지 누적된 부채를 안정화시키는 `구조 재정비의 핵심 시기`였다.

MS2를 진행하면서 버그를 고치기 위해 코드를 파고들면 들수록
결국 수정이 필요한 건 기능이 아니라 `아키텍처`라는 결론에 도달했다. 즉, 코드 조각을 고치는 것으로는 더 이상 프로젝트가 버텨줄 수 없는 상태였고 구조 자체를 다시 세워야만 다음 단계로 갈 수 있었다.
