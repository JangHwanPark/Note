## Next.js 14 업그레이드 이후 SVG 로더 문제 회고록
Next.js 14로 업그레이드한 직후, 예상치 못한 문제가 터졌다. 기존 `next.config.js`에서 쓰던 커스텀 SVG 로더 설정이 완전히 깨지면서, `.svg`파일을 import할 때마다 빌드와 런타임에서 `Module parse failed`오류가 쏟아졌다. SSR에서는 ImageOptimization과 충돌했고, CSR 번들에서는 `ReactComponent`타입 선언이 꼬여 타입 체커부터 막히는 지경이었다.

문제는 단순히 `로더 한 줄 잘못 넣은 것`이 아니었다. 리디자인 막바지라 SVG 아이콘을 대량 교체한 상황이었는데 배포 직전에 이런 장애가 터지니 당황스러울 수밖에 없었다. 로그를 하나씩 뜯어보다 보니 `CRA 시절 선언 파일과 Next.js 14의 모듈 해석 방식`, 그리고 `오래된 webpack 설정`이 서로 뒤엉켜 있었다. “이거만 고치면 되겠지”라는 단순한 기대가 완전히 깨진 순간이었다.

<br/>

## 원인 분석
디버깅 과정에서 드러난 문제는 예상보다 복잡했다.
- `.svg`파일에 `asset/inline`과 `@svgr/webpack`이 동시에 적용되어 두 번 변환(중복 변환)되고 있었다. 
- CRA 시절부터 쓰던 `.d.ts`가 Next.js의 모듈 해석과 충돌하며 타입 오류를 유발했다. 
- `Next 14에서 dev 서버가 Turbopack`이 되면서 dev 환경과 빌드 환경이 서로 다른 로더 체계를 사용하고 있었고 그 차이 때문에 dev에서는 되고 빌드에서는 터지거나 그 반대가 발생했다.

결론적으로 이 이슈는 로더 하나의 문제가 아니라 `로더 → 타입 선언 → 정적 자산 → dev/build 툴체인`이 모두 연결된 문제였다.

<br/>

## 해결 과정
### 1. 로더 단일화 및 Turbopack 대응
우선 webpack에서 `.svg`에 대해 `@svgr/webpack`만 남기고 다른 로더를 모두 제거했다.

그리고 Next.js 14에서는 개발 서버가 `Turbopack`으로 동작하므로, dev 환경에서도 동일하게 SVG를 ReactComponent로 인식하도록 `Turbopack 규칙(turbopack.rules)`을 추가했다.

이렇게 해서 dev(Turbopack)와 build(Webpack)가 동일한 로더 체계를 바라보도록 통일했다.

### 2. 타입 선언 정리
CRA 시절 남아 있던 `.d.ts`를 제거하고, `src/types/svg.d.ts`에 `ReactComponent`타입을 명확하게 선언해 CSR, SSR 타입 오류를 모두 해결했다.

### 3. 정적 자산 경로 보정
SVG 파일을 `public/...`로 이동시키고, 라우트 핸들러가 파일을 프록시하지 않도록 `rewrites`설정을 제거했다. 그 결과 export 환경에서도 아이콘이 정상적으로 포함되었다.

### 4. 빌드 및 배포 파이프라인 정비
Dockerfile과 GitHub Actions에서 `next build`후 `.next/static`을 캐시하도록 수정하고 기존 `next export`기반의 헬스체크를 `next start` 기준으로 전환했다. 빌드와 런타임 설정이 서로 엇갈리지 않도록 정리한 셈이다.

<br/>

## 진행하며 느낀 점
중복 로더가 SVG 하나를 변환할 때마다 두 번씩 처리를 시도해 빌드가 지연되고 있었는데 로더를 정리하자 빌드 타임이 몇 분에서 수십 초로 줄어들었다.
이 문제는 단순 기능 오류를 넘어서 생산성에도 큰 영향을 주고 있었다는 걸 뒤늦게 깨달았다.

또 한 가지는 CI 문제였다. 타입을 고치고 경로를 정리한 뒤에도 CI가 계속 실패했는데, 원인은 해결한 줄 알았던 `next export`스크립트가 여전히 남아 있었기 때문이었다. 빌드가 통과된다고 해서 런타임이 보장되는 건 아니라는 사실을 다시 한번 실감했다. 배포 스크립트와 헬스체크까지 포함해 전체 그림을 일관성 있게 맞춰야 했다.

마지막으로, 정적 폴더로 SVG를 옮기는 과정에서 import 경로를 일부 수정하지 않아 404가 발생하는 해프닝도 있었다. 단순한 경로 변경조차 lint로 강제해야 하는 이유를 체감했다.

<br/>

## 결과
- dev(Turbopack)와 build(Webpack)에서 `.svg`를 `React 컴포넌트`처럼 안정적으로 import할 수 있게 되었다. 
- 환경별 빌드 동작이 완전히 통일되어 `어떤 환경에서만 되는`문제들이 사라졌다.
- SVG 로더 문제로 시작했지만 그 과정에서 인프라 설정까지 함께 정비되며 릴리즈 실패 확률을 낮출 수 있었다.

<br/>

## 마무리하며
`SVG 하나쯤 금방 고치겠지`라는 생각으로 시작한 작업이 결국 프로젝트 설정의 역사를 되짚는 시간으로 이어졌다. 이번 이슈를 통해 `프론트엔드 개발도 빌드 - 배포 인프라와 강하게 연결되어 있다`는 걸 다시 확인했다.

앞으로는 이런 설정 변경도 코드 리뷰 범위로 포함시키고 dev/build 간 불일치를 초기에 잡아낼 수 있는 체계를 갖추는 데 더 신경 써야겠다는 생각이 들었다.

비록 장애 대응 과정은 고됐지만 그 과정에서 팀의 파이프라인이 더 단단해졌다는 점이 의미 있게 남는다.
