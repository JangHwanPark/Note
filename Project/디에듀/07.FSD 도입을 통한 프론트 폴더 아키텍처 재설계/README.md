## FSD 도입 결정 배경
FSD를 도입하기로 결정한 이유는 단순했다.

지금 프로젝트는 기능 단위로 움직이고 있었지만 정작 기능 간의 경계가 없었고 기능마다 서로 다른 책임과 규칙을 들고 있었다. 즉, 기능 중심으로 만들었지만 기능을 기준으로 쪼갤 수 없는 상태였다.

FSD를 도입하면 다음과 같은 정리가 가능하다. 기능이 독립적으로 존재할 수 있는 물리적 경계, 공통 로직과 도메인이 명확히 분리, 데이터 구조와 규칙을 한곳에서 정의, 각 기능이 엔티티에 의존하고 서로에게 의존하지 않음, 기능 사이 순환참조 제거, 도메인 기반으로 기능을 조립하는 구조로 이동 그리고 무엇보다 지금 디에듀가 가장 필요로 하는 것은 새 기능을 만드는 속도가 아니라 기능을 만들 수 있는 구조의 안정성이라 판단했다.

그래서 나는 기능 개발보다 먼저 폴더 아키텍처와 도메인 경계부터 다시 설계하는 작업에 들어갔다.

여기서 더 현실적인 문제도 있었다 사실 새로운 아키텍처를 설계할 충분한 시간조차 없었다. 마일스톤 일정은 이미 잡혀 있었고
기존 코드의 버그는 계속 터졌고 기능 요구사항도 동시에 들어오고 있었다.

그럼에도 이 구조를 지금 고치지 않으면 앞으로 어떤 기능도 정상적으로 만들 수 없다는 확신이 생겼다. 결국 시간이 없었지만 그렇기 때문에 반드시 지금 구조를 재정의해야 했다.

이 판단이 FSD 도입의 결정적 전환점이 되었다.

## 새로운 구조를 설계하기 시작하다
FSD를 도입하기로 마음먹었지만 그때부터가 사실 진짜 어려움의 시작이었다.
구조를 바꿔야 한다는 결론에 도달했다고 해서 바로 적용할 수 있는 것은 아니었다.
이미 기존 코드의 의존성은 완전히 뒤엉켜 있었고 서로를 참조하는 기능들은 어디서부터 잘라내야 할지 감조차 서지 않는 상태였다.

추가로 FSD라는 개념 자체를 완전히 이해하는 데에도 시간이 필요했다는 점이다. 폴더를 기능 기준으로 나눈다는 건 단순해 보였는데 실제로 적용해보려니 feature model API UI 도메인 규칙을 어디까지 분리해야 하는지, 어떤 기준으로 경계를 잡아야 하는지 이게 생각보다 훨씬 복잡했다.

그래서 첫 단계는 지금 존재하는 기능들을 그대로 옮기기 전에 무엇이 기능이고 무엇이 도메인인지 그 `경계`를 다시 그리는 작업부터 시작해야 했다.

처음에는 단순히 폴더만 나누면 해결될 줄 알았지만 곧 깨달았다. 문제는 폴더가 아니라
그 안에 들어가는 개념들 자체가 섞여 있다는 사실을....

`UI 로직`, `API 로직`, `도메인 로직`, `검증 로직`, `상태 로직`이 모든 것이 한 파일 안에서 뒤엉켜 있었기 때문에 폴더 구조만 바꾸는 것으로는 아무것도 해결되지 않았다.

구조를 제대로 재설계하려면 `도메인만의 집`과 `기능만의 집`을 완전히 분리하는 작업이 필요했다. FSD의 기본 원칙인 `feature`는 `기능을 담당`하고 `도메인은 별도 계층에서 관리`해야 한다는 구조였다.

FSD의 전체 구성을 이해하는 데 시간은 걸렸지만 이 계층을 도입하는 순간 무엇이 어디로 가야 하는지 처음으로 선이 그어지기 시작했다.

## 왜 Entities 계층이 필요했는가
구조 개편을 진행하면서 가장 먼저 드러난 문제는 데이터 해석의 혼란이었다.

같은 데이터를 기능마다 다르게 해석하고 있었고 어떤 기능은 API 응답을 그대로 쓰고
어떤 기능은 가공해서 쓰고 다른 기능은 전혀 새로운 타입을 만들어 쓰고 있었다.

그러니 기능 간 타입이 충돌하고 API 응답이 바뀌면 전체 기능이 줄줄이 무너지고
순환참조가 발생할 수밖에 없었다.

이 모든 문제의 공통 원인은 하나였다.
도메인을 관리하는 계층이 없다는 점이었다.

그래서 나는 FSD의 원칙에 따라 `feature`와 `shared`사이에 `entities`계층을 넣어
도메인 모델을 프로젝트 전체의 통합 기준으로 만드는 작업을 시작했다.

Entities는 단순한 타입 저장소가 아니라 디에듀의 데이터 흐름을 책임지는 새로운 중추 역할을 맡았다.
- API 응답을 domain 모델로 변환
- 공통 타입 정의 및 데이터 검증
- 도메인 규칙 적용
- raw response를 화면에 직접 전달하지 않도록 차단
- 기능별 중복 타입 제거
- 기능 간 데이터 해석 통일 

Entities가 도입되자 기능들은 더 이상 서로의 타입을 훔쳐 쓰지 않았고 순환참조도 하나씩 사라지기 시작했다.(이건 아직 작업이 진행중이다.) 무엇보다 중요한 변화는 데이터 흐름이 처음으로 안정성을 갖기 시작했다는 점이다.

기능 개발은 그 이후의 일이었다. 먼저 데이터의 집을 세우고 그 위에 기능이 올라가는 구조가 만들어졌다. 그리고 그때부터 디에듀는 비로소 확장 가능한 형태로 바뀌기 시작했다.

## 폴더 아키텍처 재편 과정

FSD의 원칙과 entities 계층의 필요성을 이해하고 나자
이제는 실제로 이 구조를 디에듀에 적용해야 했다.
그리고 이 과정은 내가 예상했던 것보다 훨씬 섬세한 판단을 요구했다.

단순히 폴더를 몇 개 나누는 것이 아니라
기능과 도메인 사이의 경계를 다시 정의하는 작업이었기 때문이다.

나는 먼저 기존 파일들을 전부 훑으면서
각 코드 조각이
UI인지,
도메인 로직인지,
API 요청인지,
공통 로직인지,
상태 관리인지,
하나씩 분류했다.

이 작업만 해도 시간이 꽤 걸렸다.
왜냐하면 디에듀의 파일들은 대부분 한 파일 안에 모든 것이 뒤섞여 있었기 때문이다.
이 문제를 하나씩 분해하면서
처음으로 “정말 이 프로젝트는 구조를 다시 만들어야 한다”는 확신이 생겼다.

그렇게 기능과 도메인을 분리한 뒤
나는 다음 기준에 따라 폴더 구조를 새로 설계했다.

UI는 features 내부에만 존재해야 한다

도메인 로직과 데이터 구조는 entities가 책임진다

공통 로직은 shared에서 관리한다

API 호출은 feature에서만 이루어지고

응답 모델링은 entity에서만 이루어진다

이 구조가 완성되자
처음으로 디에듀 코드는
**“각자의 자리에 머무르는 질서”**라는 것을 갖기 시작했다.

폴더 아키텍처의 1차 개편안은 이런 모양새였다.
```js
src  
  entities  
    member  
    study-room  
    study-note  
  features  
    study-room  
      list  
      detail  
      create  
    study-note  
      list  
  shared  
    http  
    utils  
    hooks  
    components
```

## 실제 리팩토링 중 겪은 문제들
폴더 구조를 정리하고 나서야 이제 본격적인 리팩토링이 시작됐다. 그리고 이 과정은 정말 말 그대로 전쟁이었다. 가장 먼저 터진 문제는 타입이었다. 기존 기능은 서로의 타입을 몰래 참조하고 있었고 API 응답 형태를 화면마다 다르게 해석하고 있었다. 이걸 entities로 통합하는 순간 기존 기능의 상당수가 에러를 뿜기 시작했다.

- “이 타입은 여기에 없는데?” 
- “이 API 응답을 왜 저 기능도 쓰고 있지?” 
- “이 기능은 왜 shared 안에 있는 함수를 건드리지?”

이런 질문들이 끊임없이 튀어나왔다.

순환참조가 사라지는 순간 그동안 숨어 있던 기능 간 의존이 드러났고 그걸 하나 하나 끊어내는 과정은 생각보다 훨씬 고통스러웠다.

또 한 가지 문제는 공통 로직을 shared로 이동했을 때 생겼다. 기존 기능들은 shared라는 개념 없이 그냥 눈에 보이는 파일에서 필요한 로직을 그대로 가져다 썼기 때문에 폴더 구조 변경만으로도 기능들이 무너졌다.

경로가 바뀌고 의존 방향이 바뀌고 도메인 모델이 생기면서 화면에서 직접 데이터를 처리할 수 없게 되자 UI 컴포넌트들이 대거 오류를 일으켰다. 리팩토링 내내 하나를 고치면 다른 하나가 깨지고 그걸 고치면 또 다른 기능이 터졌다. 하지만 그 혼란 속에서도 구조는 점점 더 정제되고 코드의 책임이 확실히 자리 잡기 시작했다.

## 개편 이후 체감된 변화
리팩토링이 어느 정도 안정되기 시작하면서 변화는 예상 이상으로 확실하게 느껴졌다.

첫 번째는 두려움이 사라졌다는 것이다.

예전에는 코드를 고칠 때마다 `이거 건드리면 어디가 터질까?`를 먼저 생각해야 했는데 이제는 기능 간 경계가 명확해지면서 변경이 다른 기능에 영향을 줄 가능성이 크게 줄어들었다.

두 번째는 데이터 흐름이 명확해졌다는 점이다.

API 응답은 entities에서 domain 모델로 변환되고 features는 그 모델을 UI에 전달한다. 이 단순한 원칙 하나만으로 머릿속 코드 지도가 훨씬 정돈되었다.

세 번째는 확장성이었다. 

기능을 하나 추가하려면 예전에는 기존 기능을 뜯어보고 타입을 확인하고 이 화면이 저 API를 쓰는지 이 기능이 저 기능을 참조하는지 이런 것부터 파악해야 했다.

지금은 그렇지 않다.

entities → features → shared

이 구조만 따르면 새로운 기능도 단단하게 올라갈 수 있다.

네 번째는 리뷰와 유지보수가 쉬워졌다는 점이다.

코드를 읽는 시간이 줄었고 어떤 파일이 어떤 책임을 가져야 하는지 이제는 자연스럽게 알게 되었다. 아무리 작은 변화라도 코드 전체의 안정성이 눈에 띄게 높아졌다.

## 최종 회고
돌아보면 이번 아키텍처 개편 작업은 단순히 폴더 구조를 바꾸는 일이 아니었다.

그동안 겹겹이 쌓여 있던 명세 부재, 속도전, 도메인 부재, 기능 간 의존, 순환참조, 타입 붕괴.. 이 모든 문제를 근본적으로 해결하기 위한 프로젝트의 재건축 작업이었다.

새로운 구조를 도입하는 과정은 고통스러웠지만 이제는 그 위에서 안전하게 기능을 만들 수 있다. 그리고 무엇보다 이 경험을 통해 나는 `구조가 만들어지는 순간 코드가 살아난다`는 사실을 몸으로 배웠다.

디에듀는 이제야 비로소 확장 가능한 시스템의 형태를 갖추기 시작했고 앞으로 더 큰 기능과 방향성을 담아낼 수 있는 튼튼한 기반을 가지게 되었다. 그리고 그 기반을 직접 세웠다는 것이 나에게 가장 큰 성취로 남았다.
