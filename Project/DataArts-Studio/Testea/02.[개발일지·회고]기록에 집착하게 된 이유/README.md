## 나는 기록에 집착한다.

커밋 메시지 하나에도 "왜 이 변경을 했는가"를 남기고, PR 설명에는 결정의 배경을 적고, 프로젝트가 끝나면 회고 문서를 쓴다. 때로는 기능 하나를 만드는 시간보다 그 과정을 정리하는 시간이 더 길 때도 있다.

과하다고 느낄 수도 있다. 하지만 이 집착에는 이유가 있다고 생각한다. 기록하지 않아서 무너진 프로젝트를 직접 겪었기 때문이다.

<br/>

## 디에듀 — 기록이 없던 프로젝트

테스티아 이전에 **디에듀(D'edu)** 라는 프로젝트에 참여했다. 12명 규모의 사이드 프로젝트 팀이었고, 교육 관련 웹 서비스를 만들고 있었다. Next.js App Router와 Spring 기반의 프론트-백 분리 구조, Jira와 Notion을 활용한 협업. 겉으로 보면 꽤 그럴듯한 팀이었다.

하지만 합류하고 나서 느낀 건 달랐다.

<br/>

### "왜 이렇게 만들었는가"에 대한 답이 없었다

가장 먼저 부딪힌 건 **기획 명세의 부재**였다. 기능 정의 없이 바로 개발에 들어가는 흐름이 반복되고 있었고, 구성원마다 같은 기능을 서로 다르게 해석하고 있었다. "스터디룸 생성"이라는 기능 하나에 대해서도 어떤 필드가 필수인지, 생성 후 어디로 이동하는지, 에러 시 어떻게 처리하는지.. 아무것도 정의되어 있지 않았다.

Jira 티켓을 열어봐도 상황은 마찬가지였다. 제목은 `회원가입 구현`, `API 연결` 같은 단편적인 문장뿐이었고, 설명란은 비어 있었다. 담당자도, 완료 기준도, 우선순위도 없었다. 스프린트를 운영한다고 했지만 실제로는 "주차별 일정표"에 불과했고, Jira는 **협업 도구가 아니라 개인 투두리스트**에 가까웠다.

<br/>

### 속도전이 남긴 것

팀은 빠르게 기능을 만들어내는 데 집중하고 있었다. MVP 속도전 자체는 문제가 아니었다고 생각한다. 진짜 문제는 **회고가 없었다는 것**이라고 생각한다.

속도전의 한가운데서 잠깐 멈춰서 "이 구조가 맞는가", "이 방향이 맞는가"를 되짚어보는 시간이 없었다. 그 결과는 예상보다 빠르게 나타났다.

- **순환참조**: 기능들이 서로의 타입을 참조하며 의존성 거미줄이 형성됐다
- **타입 꼬임**: 한쪽 타입을 수정하면 다른 쪽이 깨지고, 그걸 고치면 또 다른 기능이 터지는 연쇄 반응
- **책임 혼재**: 컴포넌트 하나에 UI, 도메인 로직, API 호출, 데이터 가공, 검증, 상태 처리가 전부 뒤섞여 있었다
- **import 루프**: `pages → types → utils → components → pages`로 순환하는 의존 구조

겉은 멀쩡해 보여도 속은 이미 헐거워진 상태였다. 수정이 필요한 것은 기능이 아니라 **아키텍처 그 자체**였다고 생각한다. 그리고 이 모든 혼란의 시작점은 결국 하나였다고 생각한다. **"기록되지 않은 결정"**.

<br/>

### 직접 나서다

한 달 가까이 기다렸지만, PM을 포함해 누구도 프로세스 개선에 움직이지 않았다. 결국 직접 나섰다.

**Jira 프로세스를 재설계**했다. 단일 워크플로우를 개발·QA·기획 3트랙으로 분리하고, 시간 중심 스프린트를 목표 중심 마일스톤으로 전환했다. 티켓에는 Feature와 Milestone 커스텀 필드를 필수화하고, "왜 멈췄는가"를 표면화하는 상태값(Pending, Need More Info)을 추가했다.

**문서작성 프로세스를 정비**했다. FDD(Feature-Driven Development) 기반의 간결한 명세 방식을 도입하고, 확정되지 않은 기획과 확정된 기획을 분리하는 워크플로우를 설계했다.

**로그인 아키텍처를 갈아엎었다.** 로컬스토리지에 토큰을 저장하던 방식을 HttpOnly 쿠키 기반 JWT 인증으로 전면 교체하고, BFF(Backend for Frontend) 구조를 도입했다.

**FSD(Feature-Sliced Design) 아키텍처를 도입**해 폴더 구조를 재설계했다. 혼재된 구조를 `entities/features/shared` 계층으로 분리하고, 도메인 모델을 entities 계층에서 통합 관리하도록 바꿨다.

이 모든 과정을 [GitHub Note 저장소](https://github.com/JangHwanPark/Note/tree/main/Project/%EB%94%94%EC%97%90%EB%93%80)에 10개 섹션으로 정리했다. 지라 프로세스 개선, 문서작성 프로세스 개선, 로그인 아키텍처 개선, 구조적 문제 분석, FSD 도입, BFF 전환, 그리고 마지막 회고까지.

<br/>

### 점 하나(.)

그렇게 컨벤션을 정비하고, 템플릿을 만들고, 워크플로우를 재설계한 뒤의 일이다.

버그 티켓이 하나 올라왔다. 열어보니 내용이 없었다. **마침표 하나(.)만 찍혀 있었다.**

그 순간 깨달았다. 이건 단순한 실수가 아니라 **우리 팀의 문화 그 자체**라는 것을. 구조는 혼자서 바꿀 수 있었다고 생각한다. Jira 워크플로우도, 폴더 아키텍처도, 인증 구조도. 하지만 **기록하는 문화**, **소통하는 문화**는 혼자서는 바꿀 수 없다고 생각한다.

> "기술적 경계는 개인이 바꿀 수 있다. 하지만 팀의 문화는 함께해야만 바뀐다."

디에듀의 마지막 회고에서 내린 결론이었다. 프로젝트는 결국 프로덕션 레벨까지 가지 못하고 멈췄다.

<br/>

## 기록이 바꾼 것

디에듀에서 가장 많이 아쉬웠던 건 기능 미완성이 아니었다. **"왜 이 문제가 발생했는가"를 공유할 수 없었던 것**이었다. 같은 실수가 반복됐고, 같은 논의가 반복됐고, 같은 혼란이 반복됐다. 기록이 없었기 때문이다.

이 경험이 나를 바꿨다고 생각한다.

기록은 단순한 문서화가 아니라고 생각한다. 기록은 **과거의 결정을 현재의 맥락에서 다시 읽을 수 있게 해주는 장치**라고 생각한다. "왜 이렇게 했는가"에 대한 답을 미래의 나에게, 미래의 팀원에게 남기는 행위라고 생각한다.

모든 혼란은 **정의되지 않은 것**에서 온다고 생각한다. 디에듀에서 명세가 없어서 구성원마다 다르게 해석했고, 프로세스가 정의되지 않아서 각자의 방식으로 움직였고, 회고가 없어서 같은 실수를 되풀이했다. 기록한다는 건 결국 **정의하는 것**이라고 생각한다. 모호한 것을 명확하게 만드는 것이라고 생각한다.

<br/>

## 테스티아 — 기록 위에 세운 프로젝트

테스티아(Testea)를 시작할 때 가장 먼저 정한 원칙이 있었다.

> **"회고와 기록은 반드시 남긴다."**

디에듀에서 얻은 가장 큰 교훈이 이 한 문장에 담겨 있다고 생각한다.

### 구조부터 달랐다

테스티아에서는 첫 커밋부터 FSD 아키텍처를 적용했다. 디에듀에서 기능 중심 속도전의 결과를 직접 겪었기 때문이다. "나중에 고치면 되지"라는 말이 얼마나 비싼 부채로 돌아오는지 알고 있었기 때문이라고 생각한다.

```
src/
├── shared/          # 공통 요소
├── entities/        # 도메인 모델
├── features/        # 기능 단위
├── widgets/         # 조합된 UI 블록
├── view/            # 페이지 수준 컴포넌트
└── app-shell/       # 전역 프로바이더
```

디에듀에서 entities 계층이 없어서 같은 데이터를 기능마다 다르게 해석했던 문제, 순환참조로 하나를 고치면 다른 하나가 깨지던 문제 — 이 모든 것이 구조 설계 단계에서 이미 반영됐다. 경험하지 않았다면 이 구조의 필요성을 느끼지 못했을 것이라고 생각한다.

### 결정의 이유를 남겼다

3개월간 451개의 커밋, 53개의 PR을 쌓으면서 **모든 기술적 결정에 "왜"를 남겼다**.

마일스톤과 테스트 런의 관계를 1:N에서 N:M으로 변경한 이유. `varchar`가 아닌 `text` 타입을 선택해야 했던 이유. `refetchOnWindowFocus`를 `false`로 설정한 이유. Server Actions를 선택하면서 감수한 트레이드오프. 이런 결정의 맥락들이 커밋 메시지와 PR, 그리고 회고 문서에 남아 있다.

덕분에 한 달 전에 내린 결정을 다시 마주했을 때 "왜 이렇게 했지?"라는 질문에 바로 답할 수 있었다. 디에듀에서는 불가능했던 일이다.

<br/>

## 기록은 투자다

디에듀의 경험을 돌아보면, 기록하지 않은 대가는 항상 나중에 더 큰 비용으로 돌아왔다고 생각한다.

- 명세를 기록하지 않아서 → 구성원마다 다른 해석으로 개발했고, 통합할 때 충돌이 발생했다
- 아키텍처 결정을 기록하지 않아서 → 같은 논의를 세 번이고 반복했다
- 회고를 기록하지 않아서 → 같은 실수를 다음 스프린트에서 되풀이했다
- 프로세스를 기록하지 않아서 → 새 구성원이 합류할 때마다 온보딩이 구두로 이루어졌다

반대로 테스티아에서는 기록이 개발 속도를 오히려 높여줬다.

- 초기 2주간의 아키텍처 기록이 이후 3개월의 개발 방향을 결정했다
- PR마다 남긴 맥락 덕분에 리팩토링할 때 이전 결정의 이유를 바로 파악할 수 있었다
- 회고를 쓰면서 다음에 개선할 점이 자연스럽게 도출됐다

코드는 **"무엇을"** 보여준다. 하지만 기록은 **"왜"**를 보여준다고 생각한다. 그리고 소프트웨어 개발에서 정말 중요한 건 "무엇을 만들었는가"가 아니라 "왜 이렇게 만들었는가"라고 생각한다.

<br/>

## 마무리

디에듀에서 10개의 회고 섹션을 남긴 건 프로젝트가 끝난 후였다. 이미 끝난 일을 되짚으며 "그때 이렇게 했어야 했는데"를 정리하는 작업이었다. 아쉬움이 많았다.

테스티아에서는 달랐다. 프로젝트를 진행하면서 동시에 기록했다. 결정을 내리는 순간에 그 이유를 남기고, 문제를 해결한 직후에 과정을 정리했다. 기록이 프로젝트의 일부가 됐다.

> "프로세스는 문서가 아니라 행동의 패턴이다."

디에듀의 지라 프로세스 개선 때 내린 결론이었다. 이 말은 기록에도 그대로 적용된다고 생각한다. 기록은 문서가 아니라 **습관**이라고 생각한다. 한 번의 거창한 회고가 아니라, 매일의 커밋 메시지에, 매주의 PR 설명에, 매 마일스톤의 회고에 스며들어야 한다고 생각한다.

기록에 집착하는 이유는 간단하다. **기록하지 않으면 잊히고, 잊히면 반복되기 때문이라고 생각한다.** 디에듀에서 겪은 혼란은 한 번으로 충분했다. 같은 실수를 두 번 하고 싶지 않았고, 그래서 기록하기 시작했다. 그리고 기록은 나를 더 나은 개발자로 만들어주고 있다고 생각한다.
