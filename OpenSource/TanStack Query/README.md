## TanStack Query 첫 기여 회고 (그냥 통과하는 테스트와 박제될 뻔한 버그)
사실 오픈소스에 기여해보고 싶다는 생각은 꽤 오래 전부터 있었다.

contributors 목록 한 켠에 내 이름이 박혀 있는 모습. 솔직히 말하면 개발자라면 한 번쯤 품어보는 자그마한 욕망 같은 거였다. 거창한 기능이 아니어도, 한 줄짜리 테스트라도 좋으니 *"내 흔적이 메인 브랜치에 박혀 있다"* 는 사실 그 자체가 갖고 싶었다.

그래서 평소 신세 지고 있는 라이브러리들의 이슈 탭을 차례로 열어봤다. React 본체, React 한글 공식문서, MSW, 리액트쿼리. 모두 매일같이 코드 어딘가에서 마주치는 이름들이었다. 어떤 곳은 활동이 너무 활발해 좋은 이슈가 30분 안에 잡혀갔고 어떤 곳은 반대로 너무 조용해서 PR이 묻혀버릴 것 같았다. 한참을 둘러본 끝에 시선이 가장 오래 머문 곳이 리액트쿼리였다.

그런데 막상 4.5만 스타짜리 모노레포 앞에 서면 어디서부터 손을 대야 할지 막막했다. 기능 추가는 메인테이너와 합의가 필요했고 버그 픽스는 이미 활발히 처리되고 있었다. 문서 오타 수정은 예전에 React 쪽에서 몇 번 해본 적이 있어서 이번에는 *조금 더 코드에 가까운 무언가*를 해보고 싶었다. *"의미 있는 한 줄"* 과 *"받아들여질 한 줄"* 사이의 좁은 교집합을 찾아야 했다.

여기서 솔직한 마음을 하나 인정하고 가야 한다. 처음에는 *"이왕 기여할 거 코어 쪽 한 번 멋있게 건드려볼까"* 하는 객기가 잠깐 들었다. 하지만 내 집 현관문에 생판 모르는 사람이 찾아와 *"제가 도어락을 더 좋은 걸로 갈아드릴게요"* 라고 한다면 나는 그 사람을 들이지 않을 것이다. 오픈소스 코어도 똑같다. 메인테이너 입장에서 `react-query`나 `query-core`의 핵심 로직은 4.5만 명이 매일 발 딛는 현관문이고, 처음 보는 닉네임에게 그곳을 열어주는 건 호의가 아니라 무책임이 된다.

그래서 첫 PR은 *"문 앞 화단을 정리해 드릴게요"* 같은 종류여야 했다. 안전하고, 결과가 명확하고, 잘못해도 집안 살림에는 영향이 없는 영역. 테스트 커버리지 보강이 정확히 그런 작업이었다. 그리고 처음 한 일은 코드를 짜는 게 아니라 *기여하기 좋은 슬롯이 어디에 비어 있는가*를 찾는 일이었다.

## 흐름이 보이는 자리, 흐름에서 빠진 자리
2026년 3월을 전후로 모노레포 안에서는 **테스트 추가 PR이 연쇄적으로 머지되는 흐름**이 있었다.

| 패키지 | 최근 머지된 테스트 PR |
|---|---|
| query-core | #10249, #10252, #10246, #10181 |
| vue-query | #10238, #10236, #10222, #10221 |
| angular-query | #10219, #10217 |
| react-query | #10213 |
| preact-query | #10197, #10195 |
| solid-query | #10148 |
| svelte-query | #10151 |
| **eslint-plugin-query** | **(없음)** |

메인테이너가 같은 결의 PR을 잇달아 머지하고 있다는 것은 *테스트 추가 PR을 환영하는 분위기*라는 강한 정황 증거였다. 그리고 그 흐름 안에서 `eslint-plugin-query`만 비어 있었다. 누군가의 손길을 기다리는 자리가 있다면 바로 여기였다.

대상 패키지가 잡혔으니 다음은 *그 안에서도 어디에 가장 큰 구멍이 있는가*였다.

```bash
npx nx run @tanstack/eslint-plugin-query:test:lib -- --coverage --coverage.reporter=text
```

룰별로 비교해 보니 `stable-query-client`의 브랜치 커버리지가 **78.57%** 로 눈에 띄게 낮았다.

그 다음으로 한 일은 *이 룰이 도대체 뭘 잡는 룰인지* 부터 파악하는 것이었다. 커버리지를 채우려면 룰의 의도를 알아야 valid/invalid 케이스를 어디에 그어야 할지 판단할 수 있기 때문이다. 한 줄로 요약하면 `stable-query-client`는 *"리액트 컴포넌트 본문 안에서 `new QueryClient()`를 직접 만들지 마세요"* 라고 잔소리하는 룰이다. 컴포넌트 본문에서 만들면 매 렌더마다 새 클라이언트가 생성되고, 그때마다 캐시가 통째로 날아간다. React Query의 핵심인 캐싱이 무용지물이 되는 대표적인 안티패턴이라, 룰은 이를 잡아내 *모듈 스코프로 빼거나 `useState`로 감싸라* 고 autofix까지 제안한다. 룰의 의도가 명확해지고 나서야 *어떤 분기가 왜 비어 있는지* 가 눈에 들어왔다.

미커버 분기 3개를 룰 소스에서 한 줄씩 추적해 보니 그중 두 개가 *실제 사용자가 흔히 마주치는 패턴* 이었다. 비동기 서버 컴포넌트 안에서의 `new QueryClient()`, 그리고 구조 분해 할당 형태의 `new QueryClient()`. 단순히 숫자를 채우는 게 아니라 실제로 누군가 디버깅에 시간을 쓸 만한 코드 경로였다.

## 첫 PR, 그리고 P2 리뷰의 한 줄
초기 커밋에서는 미커버 분기를 메우기 위해 **valid 케이스 2개 + invalid 케이스 1개**를 추가했다. 테스트는 모두 초록이었고 머지해도 될 것처럼 보였다. 그런데 valid 케이스 하나에 Codex 리뷰 봇이 P2 우선순위로 한 줄을 남겼다.

> 이 케이스가 통과하는 이유는 룰이 올바르게 동작해서가 아니라 `fnAncestor.id`가 `undefined`라 검사를 빠져나가는 false negative 때문이다.

문제의 케이스와 룰 코드를 나란히 놓고 보니 의미가 보였다.

```ts
// 내가 추가한 valid 케이스
const Component = () => {
  const queryClient = new QueryClient();
  return;
};

// 룰의 early return 조건 (stable-query-client.rule.ts:55)
if (
  !ASTUtils.isValidReactComponentOrHookName(fnAncestor?.id) ||
  isReactServerComponent
) {
  return
}
```

`fnAncestor`가 ArrowFunctionExpression일 때 `id`는 항상 `undefined`이므로 early return이 일어난다. 즉 룰은 PascalCase로 선언된 *function declaration 컴포넌트만* 검사하고 있었고 arrow function 컴포넌트는 검사 범위 밖이었다. 이 케이스가 valid로 통과되는 이유는 **버그**였고, 내가 한 일은 그 버그를 *"정상 동작"이라고 박제하는 테스트* 를 추가한 것이었다.

<br/>

## "그냥 통과한다"는 함정
이 지적이 무서웠던 이유는 머지가 되어도 표면적으로는 아무 문제가 없기 때문이었다. 테스트는 초록이고 커버리지는 올라가고 PR은 닫힌다. 하지만 미래의 어느 시점에 누군가가 *"arrow function 컴포넌트도 잡아야 한다"* 며 룰을 고치는 순간 그 수정이 내가 추가한 테스트 때문에 실패하게 된다. 즉 **버그가 사양으로 굳어버리는 것**이다. 결국 한 문장으로 정리되었다. *테스트가 통과하는 이유까지 검증해야 진짜 회귀 안전망이 된다.*

이 시각으로 다시 들여다보니 같은 결의 문제가 하나 더 있었다. 기존 async server component 케이스는 `@tanstack/solid-query` import를 쓰고 있어서 룰 상단의 import 체크에서 일찍 return되고 있었다. *목표 분기까지 도달하지도 못한 채로* 분기를 다루는 척하고 있던 것이다.

<br/>

## 어떻게 풀었나
arrow function 케이스를 어떻게 처리할지가 다음 결정이었다. 선택지는 세 개였다.

1. invalid로 옮긴다 → 룰이 실제로 잡지 못하므로 테스트가 즉시 실패한다.
2. 룰을 직접 고친다 → 이번 PR의 스코프(커버리지 보강)를 벗어난다.
3. 케이스를 제거하고 별도 이슈로 분리한다.

3번을 택했다. *"테스트 커버리지 보강"* 이라는 한 PR에 룰 동작 변경까지 끼워 넣는 순간 리뷰 부담이 두 배가 되고 머지 확률도 떨어진다. 작은 PR은 작은 PR답게 유지해야 했다. 커밋 메시지에 회고 내용을 명시했다.

> The current rule does not detect `new QueryClient()` inside arrow function components because `fnAncestor.id` is undefined for arrow functions.
> **This is a false negative (known limitation), not intended behavior.**

남은 두 케이스는 의미를 다시 정렬했다. async server component는 `@tanstack/react-query` import로 바꿔서 실제로 `isReactServerComponent` 분기에 도달하게 했고, destructuring pattern은 `output: null`을 명시해 *"에러는 리포트되지만 autofix는 적용되지 않아야 한다"* 는 분기를 검증하게 만들었다.

<br/>

## 결과
| 지표 | Before | After |
|---|---|---|
| Statements | 89.47% | **100%** |
| Branch | 78.57% | **92.85%** |
| Lines | 89.47% | **100%** |

남은 미커버 라인 1개는 ESLint < 8.37.0 하위 호환용 fallback이라 현재 테스트 환경에서는 애초에 도달할 수 없는 분기였다. 즉 의미 있는 모든 분기는 채워졌다.

변경된 코드는 한 파일, 24줄 추가. 그 24줄이 머지되기까지의 과정은 *"코드가 통과하면 OK"* 라는 직관이 얼마나 위험할 수 있는지를 알려준 것에 가까웠다.

<br/>

## 되돌아보면, 이슈는 따로 올렸어야 했다
지금 다시 그 시점으로 돌아간다면 한 가지 더 했어야 할 일이 있다. 그 케이스를 제거한 시점에 *별도 이슈를 따로 올리는 일* 이었다.

당시에는 커밋 메시지에 *"This is a false negative (known limitation), not intended behavior"* 라고 명시한 것으로 충분하다고 봤다. 메인테이너가 머지하면서 인지할 것이고, 첫 기여인 만큼 PR 하나를 깔끔하게 마무리하는 데 집중하고 싶었다. 하지만 커밋 메시지는 검색 가능한 트래커가 아니다. 누군가 *"arrow function 컴포넌트는 왜 안 잡히지?"* 라는 의문으로 GitHub Issues를 뒤져도 걸리지 않는다. PR 안에 묻혀 있는 한 줄은 사실상 사라진 정보다.

더 솔직해지자면, *이것이 정말 버그인지 의도된 동작인지에 대해서도 나는 아직 완전히 확신하지 못한다.* 룰 헬퍼(`getFunctionAncestor`)의 분기 구조를 보면 *"arrow function 컴포넌트를 잡으려다 도달 불가능한 코드를 남긴 것"* 으로 읽히긴 한다. 하지만 메인테이너의 의도가 *"룰의 스코프를 일부러 좁힌 것"* 일 가능성을 룰의 역사를 끝까지 들여다보지 않은 채로 단정할 수는 없다. 확신이 없으면 없는 대로 *이슈를 올려서 판단을 메인테이너에게 맡기는 것이 옳은 절차였다.* 내가 *"이건 버그입니다"* 라고 단정 짓는 게 아니라 *"이런 케이스가 잡히지 않는데 의도된 것인지 알 수 있을까요?"* 라고 묻는 것. 그것이 OSS 협업에서 신뢰를 쌓는 더 정직한 방식이었다고 본다.

<br/>

## 마무리하며
이 PR이 남긴 감각은 두 가지다.

**테스트가 통과한다는 것과 올바른 동작을 검증한다는 것은 같은 말이 아니다.** valid/invalid의 경계는 *"룰이 이 입력을 어떻게 처리하는가"* 가 아니라 *"룰의 의도상 어떻게 처리해야 하는가"* 를 기준으로 잡아야 한다. 그리고 **한 PR은 한 가지를 한다.** arrow function 미검출이라는 흥미로운 버그를 발견했어도 그것을 본 PR에 끼워 넣지 않은 것이 결과적으로 머지를 매끄럽게 만들었다.

작은 PR 하나, 24줄의 변경이었다. 하지만 *"비어 있는 자리를 어떻게 찾는가"*, *"통과하는 테스트의 이유까지 의심하는가"*, *"한 PR의 스코프를 어떻게 지키는가"* 라는 세 가지 감각을 동시에 단련시킨 작업이었다. 다음 OSS 기여에도 그대로 가져갈 수 있는 감각이라는 점에서 24줄 이상의 의미가 남았다.
