# 노트 글쓰기 가이드

CLAUDE.md의 규칙을 실제 문장으로 보여 주는 문서다. 항목마다 피할 예와 고친 예를 짝으로 둔다. 고친 예는 대부분 Python 노트에서 가져왔다.

## 1. 첫 섹션은 정의로 시작한다

피할 예는 제목만 있고 바로 세부 문법으로 들어간다. 읽는 사람이 이게 무엇인지 모른 채 읽기 시작한다.

```markdown
## 반복문
### for 문
for i in range(5):
```

고친 예는 "OO이란 ?"으로 열고 두세 줄로 무엇인지, 무엇으로 이루어지는지를 말한다.

```markdown
## 반복문이란 ?
- 같은 코드를 여러 번 실행하는 문법
- 파이썬은 값을 하나씩 꺼내 반복하는 `for` 와 조건이 참인 동안 반복하는 `while` 두 가지가 있다
- `break`, `continue` 로 반복 중간에 흐름을 바꿀 수 있다
```

"OO이란 ?"은 개념을 정의하는 노트에만 쓴다. 문제나 방법, 변경 사항을 정리한 노트에 붙이면 "FormEvent 사용 중단이란 ?"처럼 어색해진다. 이런 노트는 내용에 맞는 제목으로 연다.

```markdown
## 무엇이 바뀌었나
- React 타입 정의(`@types/react`)에서 `FormEvent` 가 사용 중단(deprecated)으로 표시됐다
```

## 2. 핵심 용어는 사전적 의미에서 공학적 의미로 잇는다

피할 예는 기술적 정의만 던진다. 왜 그런 이름인지 남지 않아 금방 잊는다.

```markdown
### 인스턴스
클래스로 생성된 객체.
```

고친 예는 단어의 원래 뜻을 먼저 쓰고, 그 뜻이 기술 용어로 어떻게 이어지는지 보여 준다.

```markdown
### 인스턴스 (Instance)
사전적 의미는 사례, 실례. 일반적인 개념이 실제로 나타난 하나의 예다.
공학적으로는 특정 클래스로 만들어진 객체를 말한다. 객체와 거의 같은 뜻인데, 어느 클래스에서 나왔는지를 강조할 때 쓴다.
```

## 3. 특징을 나열하고 끝내지 않는다

피할 예는 사실을 모아 두었을 뿐 왜 그런지가 없다.

```markdown
### with 문
- 파일을 자동으로 닫는다
- 예외가 나도 닫는다
- 권장 방식이다
```

고친 예는 왜 필요한지(문제), 어떻게 동작하는지(해결)를 순서대로 쓴다.

```markdown
### 왜 필요할까
`close()` 를 직접 부르면 빠뜨리기 쉽다. 게다가 읽고 쓰는 도중에 예외가 나면 그 아래의 `close()` 까지 가지 못한다.

### 동작
`with` 블록을 벗어나면 파이썬이 자동으로 파일을 닫는다. 블록 안에서 예외가 나도 닫는다.
```

## 4. 개념마다 일상 비유를 하나 둔다 (CS_Basic, 입문 노트)

비유는 개념의 핵심 동작 하나에 맞춘다. 여러 개를 늘어놓거나, 비유가 개념과 어긋나는 부분까지 끌고 가지 않는다.

피할 예는 비유가 동작을 설명하지 못한다.

```markdown
얕은 복사는 겉 상자만 새로 사고, 안의 물건은 원래 상자의 물건을 그대로 옮겨 담지 않고 같은 물건을 함께 가리키는 것과 같다.
```

고친 예는 짧고, 무엇이 둘이 되고 무엇이 하나로 남는지가 바로 보인다.

```markdown
물건 목록표를 한 장 더 베껴 쓴 것과 같다. 목록표는 두 장이 되었지만 거기 적힌 물건은 원래 물건 그대로다.
```

## 5. AI 문체를 쓰지 않는다

피할 예는 볼드 라벨과 콜론, 따옴표, 장식을 겹겹이 쓴다.

```markdown
**핵심 포인트:** 변수는 **"이름표"** 입니다!
**왜 중요한가:** 복사와 참조를 구분하기 위해서입니다.
---
```

고친 예는 같은 내용을 평범한 서술로 쓴다.

```markdown
변수는 값을 담는 상자가 아니라 객체에 붙은 이름표다. 이 차이를 알아야 복사와 참조를 구분할 수 있다.
```

볼드는 한 문서에 몇 군데만 쓴다. 따옴표는 실제로 인용할 때만 쓴다. 구분선 대신 `<br/>`로 대주제를 나눈다.

## 6. 콜론으로 끝내고 줄을 바꿔 목록을 시작하지 않는다

피할 예는 아래와 같다.

```markdown
자주 쓰는 메서드는 다음과 같다:

- strip()
```

고친 예는 문장을 마침표로 끝내거나, 콜론을 한 줄 안에서만 쓴다.

```markdown
자주 쓰는 메서드는 아래와 같다.

- strip()
```

## 7. 코드 스팬 뒤에 대시로 설명을 잇지 않는다

피할 예는 코드 뒤에 하이픈이나 긴 대시(U+2014)를 두고 설명을 붙인다.

```markdown
`open()` - 파일을 연다
```

고친 예는 문장으로 쓴다.

```markdown
`open()` 은 파일을 연다.
```

긴 대시는 이 경우가 아니어도 어디에도 쓰지 않는다. 이모지, "청크"라는 단어도 쓰지 않는다.

## 8. 표는 비교 항목이 세 개 이상일 때만

두 가지를 비교하면 문장 두 개로 충분하다. 세 가지 이상을 여러 기준으로 비교할 때 표를 쓴다. 9장의 리스트와 튜플 비교, 10장의 네 가지 묶음 자료형 비교처럼 쓴다.

## 9. 코드 예시는 실행해 본 결과를 쓴다

출력이나 결과를 주석으로 적을 때는 실제로 실행한 값을 쓴다. 실행하지 않은 예시가 있으면 작업 보고에 그렇다고 쓴다.

```python
0.1 + 0.2          # 0.30000000000000004
int(3.9)           # 3 (반올림이 아니라 소수점 아래를 버린다)
```

버전에 따라 달라지는 내용(예: 트레이스백의 `~^` 표시는 3.11부터)은 버전을 함께 적는다.

## 10. 모르는 것은 쓰지 않는다

확인하지 못한 사실은 빼거나 "확인 필요"라고 표시한다. 그럴듯한 숫자, 연도, 출처를 지어내지 않는다.

```markdown
파이썬 3.3부터는 `__init__.py` 가 없는 폴더도 가져올 수 있게 바뀌었다(네임스페이스 패키지).
```

위처럼 버전이나 연도를 쓸 때는 공식 문서나 실행 결과로 확인한 것만 쓴다.

## 11. 책처럼 이어지는 노트는 앞 장과 연결한다

이어지는 장에서 앞에서 배운 개념을 다시 쓸 때는 몇 장인지 짚어 준다. 용어는 앞 장에서 정한 쪽으로 통일한다.

```markdown
6장에서 볼 `input()` 은 입력을 항상 문자열로 돌려주므로 숫자로 쓰려면 이 변환이 필요하다.
```

장 끝에는 목차, 이전 장, 다음 장 링크를 둔다. 새 장을 추가하면 목차, 바로 앞 장의 다음 링크, TODO를 함께 고친다.

## 12. 범위를 지킨다

CS_Basic은 일반 CS 이론으로 쓴다. 프론트엔드, 특정 프레임워크, 실무 적용 이야기가 필요하면 별도 문서로 나누고 TODO에 적는다. 깊은 구현 이야기(예: 해시 테이블 내부 구조)도 입문 노트에서는 한두 문장으로 존재만 알리고 별도 문서로 미룬다.
