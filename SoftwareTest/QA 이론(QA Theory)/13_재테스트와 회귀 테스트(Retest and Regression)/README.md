## 재테스트와 회귀 테스트란 ?
- 재테스트(Retest)는 고친 결함이 정말 고쳐졌는지 그 결함만 다시 확인하는 테스트다. ISTQB 용어로는 확인 테스트(Confirmation Testing)다
- 회귀 테스트(Regression Testing)는 그 수정이 원래 잘 되던 다른 기능을 망가뜨리지 않았는지 확인하는 테스트다
- CTFL v4.0은 2.2.3절 확인 테스트와 회귀 테스트(Confirmation Testing and Regression Testing)에서 둘을 함께 다룬다. 둘을 변경 관련 테스트(Change-related Testing)로 묶어 부르는 것은 v3.1(2018) 표현이다. 외울 때는 재테스트는 점(결함 하나), 회귀는 면(주변 영향 범위)으로 기억한다

### 회귀 (Regression)
사전적 의미는 원래 상태로 되돌아감, 퇴행이다.
테스트에서는 잘 되던 기능이 변경 뒤에 다시 안 되는 상태로 되돌아가는 것을 말하고, 이렇게 생긴 결함을 회귀 결함(Regression Bug)이라고 한다. 회귀 테스트는 이런 퇴행이 없는지 보는 테스트다.

수도관 한 곳의 누수를 고친 뒤, 그 자리에서 물이 새지 않는지 보는 것이 재테스트다. 수리하면서 관을 건드려 다른 이음새가 헐거워지지 않았는지 집 전체를 둘러보는 것이 회귀 테스트다.

<br/>

## 핵심 비교

| 구분 | 재테스트 (확인 테스트) | 회귀 테스트 |
| --- | --- | --- |
| 목적 | 그 결함이 정말 고쳐졌나 | 수정 때문에 다른 기능이 망가지지 않았나 |
| 대상 | 고친 결함 하나 | 영향을 받을 수 있는 주변, 관련 기능 |
| TC 출처 | 원래 결함 리포트의 재현 절차, 필요하면 새로 만든 TC | 기존 회귀 스위트와 변경 영향 분석 결과 |
| 반복 여부 | 그 결함이 통과할 때까지 반복 | 변경이 있을 때마다 반복 |
| 실패의 뜻 | 결함이 아직 남아 있다 | 새 결함(회귀 결함)이 생겼다 |
| 순서 | 수정 직후 | 재테스트가 통과한 뒤 영향 범위를 정해 실행 |

<br/>

## 왜 둘 다 해야 할까
코드 한 곳을 고쳐도 그 코드를 공유하는 모듈, 전역 상태, 같은 데이터를 쓰는 다른 기능에 영향이 갈 수 있다. 재테스트만 하면 고친 결함은 사라졌지만 그 수정 때문에 다른 곳에 생긴 결함을 놓친다. 특정 브라우저, 다른 권한, 다른 데이터 상태에서만 나타나는 부작용은 특히 놓치기 쉽다. 그래서 결함을 고치면 재테스트로 그 결함을 확인하고, 이어서 회귀 테스트로 주변을 확인한다.

<br/>

## 회귀 범위 정하기
시간이 넉넉하지 않으면 영향이 클 만한 곳부터 고른다(선택적 회귀). 출시 직전이나 큰 변경 뒤에는 전체 회귀를 돌린다. 범위를 고를 때는 아래 순서로 넓혀 간다.

1. 고친 코드를 직접 부르는 함수와 컴포넌트
2. 고친 기능과 같은 데이터(같은 DB 테이블, 같은 전역 상태)를 쓰는 기능
3. 같은 사용자 흐름에 들어 있는 기능
4. 같은 빌드나 배포에 함께 들어간 다른 변경
5. 늘 확인해야 하는 핵심 흐름(스모크, 골든 패스)

<br/>

## 자동화
회귀 테스트는 같은 절차를 변경 때마다 반복하고 판정 기준이 분명해서 자동화하기 좋은 영역이다. 재테스트는 그 결함이 닫히면 끝나므로 수동으로 해도 되지만, 자동화해 두면 그대로 회귀 스위트에 들어가 다음 변경부터 회귀 테스트가 된다. CTFL v4.0도 회귀 테스트를 자동화하기 좋은 대상으로 꼽는다.

회귀 스위트를 오래 그대로 두면 같은 곳만 확인하게 되어 새 결함을 잘 찾지 못한다([살충제 역설](../01_살충제%20역설(Pesticide%20Paradox)/README.md)). 주기적으로 TC를 고치고 더한다.

<br/>

## 실무에서는
결함 관리 도구의 워크플로가 Resolved, Closed, Reopened 상태를 쓰는 팀이라면 이렇게 흘러간다(상태 이름은 팀마다 다르다).

1. 개발자가 수정하고 결함을 Resolved로 바꾼다
2. QA가 재테스트한다. 통과하면 Closed, 실패하면 Reopened
3. 영향 분석 메모를 남기고 회귀 범위를 정해 회귀 스위트를 돌린다
4. 자동화된 회귀 스위트가 있으면 CI가 변경마다 돌리고, 사람은 변경 근처만 수동으로 더 본다

<br/>

## 면접 답변 (30초)
> "재테스트는 고친 결함이 실제로 해결됐는지 그 결함의 재현 절차로만 확인하는 테스트이고, 회귀 테스트는 그 수정이 원래 잘 되던 다른 기능을 망가뜨리지 않았는지 영향 범위 전체를 확인하는 테스트입니다. 재테스트만 하면 수정 때문에 생긴 회귀 결함을 놓칠 수 있어서, 재테스트 통과 뒤 변경 영향 분석으로 범위를 정해 회귀 테스트를 이어서 합니다. 회귀 테스트는 반복되기 때문에 자동화의 핵심 영역이지만, 같은 TC만 돌리면 효과가 떨어지므로 주기적으로 갱신합니다."
