## 심각도와 우선순위란 ?
- 심각도(Severity)는 결함이 시스템에 미치는 영향의 크기, 우선순위(Priority)는 그 결함을 얼마나 빨리 고쳐야 하는지를 나타낸다
- 둘은 서로 독립이다. 심각도는 낮아도 우선순위가 높을 수 있고, 그 반대도 있다
- 한 줄로 외우면 "심각도는 기술적 영향, 우선순위는 비즈니스 긴급도"이다

### 심각도 (Severity)
사전적 의미는 상태나 정도가 매우 심한 정도다.
ISTQB 용어집은 결함이 컴포넌트나 시스템의 개발, 운영에 미치는 영향의 정도로 정의한다. 기능이 얼마나 망가졌는지를 보므로 주로 결함을 재현하고 분석한 QA가 판단한다.

### 우선순위 (Priority)
사전적 의미는 먼저 차지하는 차례다.
ISTQB 용어집은 결함 같은 항목에 매기는 (비즈니스) 중요도의 수준으로 정의한다. 일정, 대외 노출, 고객 영향 같은 사정을 함께 봐야 해서 보통 PM, PO 같은 제품 책임자가 정한다. 누가 정하는지는 조직마다 다르다.

<br/>

## 등급 예시
등급 이름과 기준은 표준으로 정해진 것이 아니라 조직이나 결함 관리 도구마다 다르다. 아래는 흔히 쓰는 예다.

| 심각도 | 의미 | 예시 |
|---|---|---|
| Critical | 시스템 중단, 데이터 손실이나 오염, 보안 사고, 핵심 업무 불가 | 결제 후 주문이 생성되지 않음, 모든 사용자 로그인 불가 |
| Major | 핵심 기능을 쓸 수 없고 우회 방법도 없음 | 검색 결과가 나오지 않음 |
| Minor | 부가 기능 오류, 우회 방법이 있음 | 정렬 옵션 일부만 동작 |
| Trivial | 화면 어긋남, 오타 같은 작은 결함 | 버튼이 1px 어긋남 |

| 우선순위 | 의미 | 처리 기한 예시 |
|---|---|---|
| P0 | 즉시 수정(출시 차단, 운영 장애) | 1시간 안 |
| P1 | 다음 릴리스 전에 반드시 수정 | 1~3일 |
| P2 | 일반 수정 일정에 포함 | 1~2주 |
| P3 | 여유가 있을 때 수정, 백로그에 보관 | 정하지 않음 |

<br/>

## 왜 따로 매길까
결함의 영향이 크다고 해서 꼭 먼저 고쳐야 하는 것은 아니고, 영향이 작아도 당장 고쳐야 하는 경우가 있다. 하나의 값으로만 매기면 이 차이가 사라져, 기술적으로 심각한 결함과 사업상 급한 결함을 구분할 수 없다. 면접에서도 이 독립성을 보여 주는 예시를 자주 묻는다.

| 사례 | 심각도 | 우선순위 | 이유 |
|---|---|---|---|
| 메인 페이지 회사 로고 오타 | Trivial | P0 | 기능 영향은 거의 없지만 모든 방문자에게 보여 즉시 고친다 |
| 새벽 배치 통계 값이 잘못 저장됨 | Critical | P3 | 데이터가 오염되는 큰 결함이지만 일부 내부 사용자만 보는 통계다 |
| 결제 완료 화면 색상이 살짝 틀림 | Trivial | P3 | 둘 다 낮다 |
| 결제 금액이 0원으로 처리됨 | Critical | P0 | 둘 다 가장 높다 |

두 번째 사례에서 P3를 매길 수 있는지는 그 통계를 무엇에 쓰는지에 따라 달라진다. 이런 판단을 하는 것이 우선순위를 정하는 쪽의 몫이다.

<br/>

## 면접 답변 (30초)
> "심각도는 결함이 시스템과 기능에 미치는 기술적 영향이고, 우선순위는 비즈니스 관점에서 얼마나 빨리 고쳐야 하는지입니다. 둘은 독립적입니다. 예를 들어 메인 페이지 로고 오타는 심각도는 낮지만 모든 방문자에게 보이기 때문에 우선순위는 가장 높을 수 있습니다. 보통 심각도는 QA가 분석해서 매기고, 우선순위는 PM이나 PO가 정합니다."

<br/>

## 실무에서는
버그 리포트에는 두 값을 따로 적는다. 우선순위 회의에서는 QA가 심각도와 영향 범위를 근거로 의견을 내고, 최종 우선순위는 제품 책임자가 정한다. 회귀 자동화를 어디부터 만들지 고를 때도 P0, P1이 나왔던 영역을 먼저 둔다.
