## 커버리지란 ?
- 테스트가 대상의 얼마만큼을 실행했는지를 비율(%)로 나타낸 값
- 코드 커버리지는 화이트박스 기법의 기준이 된다. 흔히 구문, 분기, 조건, MC/DC 순으로 소개하지만 한 줄로 엄격해지는 관계는 아니다. 분기 커버리지는 구문 커버리지를 포함하고 MC/DC는 분기와 조건 커버리지를 모두 포함하지만, 조건 커버리지는 분기 커버리지를 보장하지 않는다
- ISTQB CTFL v4.0이 다루는 것은 구문 커버리지와 분기 커버리지 두 가지이고, 조건 커버리지와 MC/DC는 Advanced(Technical Test Analyst) 레벨 내용이다

### 커버리지 (Coverage)
사전적 의미는 덮는 범위, 적용 범위다. 보험의 보장 범위를 커버리지라고 부르는 것과 같은 말이다.
테스트에서는 테스트로 덮은 부분이 전체에서 얼마인지를 말한다. 코드라면 실행된 구문이나 분기의 비율이다.

방 청소를 하며 바닥에 걸레가 닿은 칸을 세는 것과 같다. 모든 칸을 한 번씩 닦았다고 해서 얼룩이 다 지워졌다는 뜻은 아니지만, 한 번도 닦지 않은 칸이 어디인지는 분명히 알 수 있다.

<br/>

## 왜 필요할까
"테스트를 충분히 했다"는 말은 사람마다 기준이 다르다. 커버리지는 이를 숫자로 바꿔 테스트가 한 번도 지나가지 않은 코드를 찾게 해 준다. 실행조차 되지 않은 코드에 숨은 결함은 어떤 테스트로도 찾을 수 없으므로, 커버리지가 낮은 곳이 먼저 보강할 곳이다.

<br/>

## 네 가지 기준

| 단계 | 무엇을 한 번 이상 보나 | 범위 |
| --- | --- | --- |
| 구문 (Statement) | 실행 가능한 모든 구문 | CTFL v4.0 |
| 분기, 결정 (Branch, Decision) | 모든 결정의 참과 거짓 결과(각 분기) | CTFL v4.0 (분기 커버리지) |
| 조건 (Condition) | 조건식을 이루는 각 조건의 참과 거짓 | Advanced |
| MC/DC (Modified Condition/Decision Coverage) | 각 조건이 혼자서 결과를 바꿀 수 있다는 것 | Advanced |

분기 커버리지 100%를 채우면 구문 커버리지도 100%가 된다. 반대는 성립하지 않는다.

<br/>

## 예시 코드로 비교

```javascript
function check(a, b) {
  if (a > 0 && b > 0) {
    return "OK";
  }
  return "FAIL";
}
```

아래 결과는 Node.js v22.13.0에서 TC 묶음마다 실행된 구문, 결정 결과, 조건 결과를 직접 세어 확인했다.

### 구문 커버리지
`check(1, 1)` 하나로는 `return "FAIL"` 이 실행되지 않아 구문 3개 중 2개(67%)다. `check(0, 0)` 을 더하면 3개 모두 실행되어 100%가 된다.

### 분기(결정) 커버리지
조건식 `a > 0 && b > 0` 전체가 참인 경우와 거짓인 경우가 한 번씩 나오면 된다. `(1, 1)` 과 `(0, 0)` 이면 참과 거짓이 모두 나와 100%다.

### 조건 커버리지
조건 `a > 0` 과 `b > 0` 이 각각 참과 거짓을 한 번씩 가져야 한다.

조건 커버리지를 채워도 결정 커버리지가 채워지지 않을 수 있다. `(1, 0)` 과 `(0, 1)` 이면 `a > 0` 도 참과 거짓, `b > 0` 도 참과 거짓을 한 번씩 갖지만, 조건식 전체는 두 번 모두 거짓이라 `return "OK"` 가 실행되지 않는다.

또 자바스크립트의 `&&` 는 앞이 거짓이면 뒤를 계산하지 않는다(단락 평가). `(0, 0)` 에서는 `b > 0` 이 아예 계산되지 않아서, 실제로 계산된 결과만 세면 `(1, 1)`, `(0, 0)` 묶음에서 `b > 0` 은 참만 나온다. 단락 평가를 하는 언어에서는 이 점까지 생각해 TC를 고른다.

### MC/DC
각 조건이 다른 조건은 그대로 둔 채 혼자 바뀌어 결과를 바꾸는 쌍이 있어야 한다. 조건이 N개면 보통 N+1개 TC로 채울 수 있다.

- `(1, 1)` 은 결과가 참이다
- `(0, 1)` 은 `(1, 1)` 에서 `a` 만 바꿨는데 결과가 거짓이 된다. `a` 가 혼자 결과를 바꾼다
- `(1, 0)` 은 `(1, 1)` 에서 `b` 만 바꿨는데 결과가 거짓이 된다. `b` 가 혼자 결과를 바꾼다

이 세 TC는 구문, 결정, 조건 커버리지도 모두 채운다.

MC/DC는 항공 소프트웨어 인증 기준인 DO-178C에서 가장 높은 등급(Level A)에 요구된다. 자동차 기능 안전 표준 ISO 26262도 가장 높은 등급에서 권장한다. 의료, 금융 분야에서 요구하는지는 확인 필요다.

<br/>

## 커버리지의 함정
커버리지 100%는 결함이 없다는 뜻이 아니다. 모든 줄을 지나가도 기대 결과를 잘못 확인하면 결함을 놓치고, 명세에 있는데 코드에 아예 없는 기능은 커버리지로 드러나지 않는다. 테스팅 7원칙의 첫 번째, 테스트는 결함이 있음을 보여 줄 뿐 없음을 증명하지 못한다는 원칙과 같은 이야기다. 그래서 커버리지는 최소 기준으로 쓰고 충분하다는 근거로 쓰지 않는다.

<br/>

## 실무에서는
- Jest(Istanbul)는 구문, 분기, 함수, 줄 커버리지를 보여 준다. JaCoCo는 명령어(instruction), 줄, 분기 단위로 잰다. coverage.py는 기본이 구문 커버리지이고 `--branch` 옵션을 줘야 분기까지 잰다
- CI에서 "커버리지 80% 미만이면 실패" 같은 기준을 두기도 한다. 숫자 자체보다 새로 추가한 코드의 커버리지가 떨어지지 않는지를 보는 편이 실용적이다

<br/>

## 면접 답변 (30초)
> "커버리지는 테스트가 코드의 얼마만큼을 실행했는지를 나타내는 지표입니다. 구문, 분기, 조건, MC/DC가 있는데, 분기 커버리지는 조건식 전체의 참과 거짓을 보고 조건 커버리지는 각 조건을 따로 봅니다. 조건 커버리지를 채워도 분기 커버리지가 채워지지 않는 경우가 있습니다. MC/DC는 각 조건이 혼자 결과를 바꾸는 경우까지 확인해서 항공 같은 안전 필수 분야에서 요구됩니다. 다만 커버리지 100%가 결함이 없다는 뜻은 아니라서 최소 기준으로 씁니다."
