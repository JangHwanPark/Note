## 테스트 유형이란 ?
- 무엇을 확인하려고 테스트하느냐(목적)에 따른 분류
- [테스트 레벨](../07_테스트%20레벨(Test%20Levels)/README.md)이 "어떤 대상을"이라면 유형은 "무엇을"이다. 둘은 서로 독립이라 어느 레벨에서든 어느 유형이든 할 수 있다
- ISTQB CTFL v4.0은 기능, 비기능, 블랙박스, 화이트박스의 네 유형을 든다. 확인 테스트와 회귀 테스트는 유형이 아니라 변경 뒤에 하는 테스트로 따로 다룬다(예전 v3.1은 "변경 관련 테스트"를 네 번째 유형으로 두었다)

### 유형 (Type)
사전적 의미는 성질이나 특징이 비슷한 것끼리 묶은 갈래다.
테스트에서는 테스트가 확인하려는 품질의 성질로 묶은 갈래를 말한다. 같은 로그인 화면이라도 "로그인이 되는가"는 기능, "1초 안에 되는가"는 비기능 유형이다.

<br/>

## 네 가지 유형 (CTFL v4.0)
| 유형 | 무엇을 확인하나 | 예시 |
|---|---|---|
| 기능 (Functional) | 시스템이 무엇을 하는가 | 로그인, 결제, 검색 |
| 비기능 (Non-functional) | 시스템이 얼마나 잘 하는가 | 성능, 보안, 상호작용 능력(사용성) |
| 블랙박스 (Black-box) | 명세에 적힌 동작을 내부를 보지 않고 | 동등 분할, 경계값으로 만든 TC |
| 화이트박스 (White-box) | 코드 같은 내부 구조가 충분히 실행되는가 | 구문, 분기 커버리지 |

블랙박스와 화이트박스는 [4장](../04_블랙박스%20화이트박스%20그레이박스(Black,%20White%20and%20Grey%20Box)/README.md)에서 자세히 다뤘다.

<br/>

## 기능 테스트
요구사항과 명세를 근거로, 정해진 입력에 정해진 결과가 나오는지 본다. "X 화면에서 Y 버튼을 누르면 Z가 나오는가" 같은 형태다. 기능 QA가 가장 많이 하는 일이다.

<br/>

## 비기능 테스트
기능이 맞게 동작해도 느리거나 불안정하면 쓸 수 없다. 비기능 테스트는 이런 품질 특성을 확인한다. ISTQB 실라버스는 품질 특성을 국제 표준 ISO/IEC 25010의 제품 품질 모델로 설명한다. 아래 표는 2023년 11월에 나온 2판(ISO/IEC 25010:2023) 기준이다. 2판은 제품 품질 모델을 아홉 특성으로 나누는데, 그중 기능 적합성(Functional suitability)은 기능 테스트가 보고 나머지 여덟이 비기능 테스트의 대상이다.

| 품질 특성 | 무엇을 보나 | 대표 테스트 |
|---|---|---|
| 성능 효율성 (Performance efficiency) | 응답 시간, 처리량, 자원 사용, 최대 용량 | 성능 테스트, 부하(Load) 테스트, 스트레스(Stress) 테스트 |
| 호환성 (Compatibility) | 같은 환경에서 다른 제품과 함께 동작하는가(공존성), 다른 시스템과 정보를 주고받는가(상호 운용성) | 연동 테스트, 다른 프로그램과 함께 띄워 보는 테스트 |
| 상호작용 능력 (Interaction capability) | 배우고 쓰기 쉬운가, 사용자 실수를 막는가, 다양한 사람이 쓸 수 있는가(포용성) | 사용성 테스트, 접근성 테스트(a11y, WCAG) |
| 신뢰성 (Reliability) | 정상 운영에서 결함 없이 동작하는가(무결함성), 가용성, 장애 허용, 복구 | 장시간 실행 테스트, 장애 복구 테스트 |
| 보안 (Security) | 기밀성, 무결성, 부인 방지, 책임 추적, 인증, 공격에 버티는가(저항성) | 보안 테스트, 침투 테스트 |
| 유지보수성 (Maintainability) | 모듈성, 재사용성, 분석 용이성, 수정 용이성, 시험 용이성 | 정적 분석, 코드 리뷰 |
| 유연성 (Flexibility) | 다른 환경에 맞추기 쉬운가, 규모를 늘리고 줄일 수 있는가(확장성), 설치와 교체 | 설치 테스트, 환경 이전 테스트, 크로스 브라우저 테스트 |
| 안전성 (Safety) | 사람, 재산, 환경을 위험에 빠뜨리지 않는가. 운영 제약, 위험 식별, 안전한 실패, 위험 경고, 안전한 통합 | 위험 상황에서 안전한 상태로 멈추는지 보는 테스트 |

2011년판(1판)과 비교하면 2판 머리말이 밝힌 주요 변경은 아래와 같다.

- 사용성(Usability)은 상호작용 능력으로, 이식성(Portability)은 유연성으로 바뀌었다
- 안전성이 새 품질 특성으로 들어왔다
- 포용성(Inclusivity)과 자기 서술성(Self-descriptiveness)이 상호작용 능력에, 저항성(Resistance)이 보안에, 확장성(Scalability)이 유연성에 하위 특성으로 더해졌다
- 사용자 인터페이스 미학은 사용자 참여(User engagement)로, 성숙성(Maturity)은 무결함성(Faultlessness)으로 바뀌었다
- 접근성(Accessibility)은 포용성과 사용자 지원(User assistance)으로 나뉘었다
- 1판에 함께 있던 사용 품질(Quality in use) 모델은 ISO/IEC 25019로, 품질 모델의 개요와 쓰는 법은 ISO/IEC 25002로 옮겨 갔다

2판 3장의 상호작용 능력 정의에 붙은 주석은 사용성이 사용 품질 모델(ISO/IEC 25019)에서 따로 정의되고, 상호작용 능력은 사용성의 전제 조건이라고 설명한다. 그래서 실무에서 말하는 "사용성 테스트"라는 이름은 여전히 쓰인다. 크로스 브라우저 테스트를 호환성과 유연성 가운데 어디에 둘지는 표준의 정의로 갈리지 않아, 위 표에서는 다른 환경에 맞추는 쪽(유연성의 적응성)에 두었다. 이 분류는 내 판단이다.

부하 테스트는 예상한 정상 부하에서, 스트레스 테스트는 한계를 넘는 부하에서 어떻게 동작하는지 본다. 둘 다 성능 효율성을 확인하는 방법이다. 부하 테스트 도구는 [JMeter 노트](../../JMeter%20부하%20테스트(JMeter%20Load%20Testing)/README.md)에 정리했다.

<br/>

## 확인 테스트와 회귀 테스트
코드가 바뀐 뒤에는 두 가지를 짝으로 한다. 확인 테스트(Confirmation testing, 재테스트)는 고친 결함이 정말 고쳐졌는지 그 결함만 다시 확인한다. 회귀 테스트(Regression testing)는 그 변경 때문에 원래 잘 되던 기능이 깨지지 않았는지 확인한다. 자세한 차이와 회귀 자동화는 [재테스트와 회귀 테스트](../13_재테스트와%20회귀%20테스트(Retest%20and%20Regression)/README.md)에 정리했다.

<br/>

## 면접 답변 (30초)
> "테스트 유형은 무엇을 확인하느냐에 따른 분류로, ISTQB 최신 실라버스는 기능, 비기능, 블랙박스, 화이트박스 네 가지를 듭니다. 비기능에는 성능, 보안, 사용성, 호환성 같은 품질 특성이 들어갑니다. 코드가 바뀐 뒤에는 고친 결함만 다시 보는 확인 테스트와 기존 기능이 깨지지 않았는지 보는 회귀 테스트를 함께 하는데, 회귀는 자동화의 핵심 영역이지만 같은 TC만 반복하면 효과가 떨어지므로 주기적으로 갱신해야 합니다."

<br/>

## 실무에서는
기능 QA는 기능 테스트와 회귀 테스트가 중심이다. SDET는 회귀를 자동화하고 통합, 성능 테스트 일부를 맡는다. 보안과 성능을 깊게 보는 일은 보안 엔지니어나 SRE 같은 별도 담당이 맡는 경우가 많다.
