## 블랙박스, 화이트박스, 그레이박스란 ?
- 테스트 대상의 내부 구조를 얼마나 보고 테스트하느냐에 따른 분류
- 블랙박스는 내부를 보지 않고 입력과 출력만 본다. 화이트박스는 코드 같은 내부 구조를 보고 테스트한다. 그레이박스는 API 명세나 DB 구조처럼 내부 정보를 일부만 활용한다
- ISTQB CTFL v4.0은 블랙박스와 화이트박스를 테스트 기법의 분류이자 테스트 유형으로 다룬다. 그레이박스는 실라버스 용어가 아니라 업계에서 쓰는 말이다

### 박스 (Box)
사전적 의미는 상자다.
검은 상자는 속이 보이지 않아 넣은 것과 나온 것만 알 수 있고, 투명한(흰) 상자는 속이 다 보인다. 테스트 대상을 상자로 보고, 속을 들여다보느냐로 테스트 방식을 나눈 비유에서 온 이름이다. 회색 상자는 그 중간이다.

<br/>

## 비교
| 구분 | 내부 구조 | 무엇을 근거로 | 기법 예시 | 주로 하는 사람 |
|---|---|---|---|---|
| 블랙박스 | 보지 않음 | 요구사항, 명세, 사용자 시나리오 | 동등 분할, 경계값 분석, 결정 테이블, 상태 전이, 페어와이즈 | QA, 인수 테스트 참여자 |
| 화이트박스 | 봄(소스 코드 접근) | 코드의 구조와 흐름 | 구문, 분기 커버리지(CTFL v4.0), 조건, MC/DC 커버리지(Advanced 레벨) | 개발자, SDET |
| 그레이박스 | 일부만 봄 | 외부 동작과 일부 내부 정보(API 명세, DB 스키마 등) | API 테스트, DB 상태 검증 | QA, SDET |

"주로 하는 사람"은 경향일 뿐이다. 블랙박스 기법은 모든 테스트 레벨에서 쓸 수 있고, 화이트박스 기법도 단위 테스트에만 쓰는 것은 아니다.

<br/>

## 각각 언제 쓸까
블랙박스는 사용자 관점에서 요구대로 동작하는지 볼 때 쓴다. 코드를 몰라도 테스트할 수 있고 구현이 바뀌어도 TC가 덜 깨진다. 대신 코드의 어느 부분을 실행했는지는 알 수 없어서, 명세에 드러나지 않는 내부 로직의 결함을 놓치기 쉽다.

화이트박스는 코드가 실제로 얼마나 실행됐는지 확인할 때 쓴다. 커버리지로 실행되지 않은 분기를 찾아낼 수 있다. 대신 코드를 읽을 수 있어야 하고, 코드가 바뀌면 TC도 함께 바뀐다. 코드를 기준으로 하므로 명세에서 빠진 기능은 찾지 못한다.

그레이박스는 두 관점을 섞는다. 예를 들어 화면에서 주문을 넣고(블랙박스), API 응답과 DB에 저장된 값까지 확인한다. API 응답만 명세와 비교하는 테스트는 블랙박스이고, 응답 너머의 DB나 로그 같은 내부 상태까지 확인할 때 그레이박스가 된다.

<br/>

## 면접 답변 (30초)
> "블랙박스는 내부 구조를 보지 않고 입력과 출력만으로 검증하는 방식으로, 동등 분할이나 경계값 분석 같은 기법을 씁니다. 화이트박스는 코드 구조를 보고 구문이나 분기 커버리지를 채우도록 검증합니다. 그레이박스는 API 명세나 DB 구조처럼 내부 정보를 일부 활용하는 방식으로, API를 호출하고 DB 상태까지 확인하는 테스트가 대표적입니다. 블랙박스는 명세 기준이라 내부 로직 결함을, 화이트박스는 코드 기준이라 빠진 기능을 놓치기 쉬워서 함께 씁니다."

<br/>

## 실무에서는
기능 QA는 블랙박스 중심이고, 자동화와 API 검증을 맡는 SDET는 화이트박스와 그레이박스를 자주 쓴다. API 테스트 예시는 [Test-Automation의 api-suite](https://github.com/JangHwanPark/Test-Automation/tree/main/packages/api-suite)에 있다.
