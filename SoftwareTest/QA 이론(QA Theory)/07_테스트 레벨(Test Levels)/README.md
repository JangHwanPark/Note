## 테스트 레벨이란 ?
- 무엇을 단위로 테스트하느냐에 따라 테스트를 단계로 나눈 것. 작은 단위부터 단위(컴포넌트), 통합, 시스템, 인수 테스트로 올라간다
- 흔히 4단계로 외우지만, ISTQB CTFL v4.0은 통합을 컴포넌트 통합과 시스템 통합으로 나눠 5단계로 본다
- 외울 때는 "단통시인"(단위, 통합, 시스템, 인수)으로 묶고, 통합이 둘로 나뉜다는 것만 덧붙인다

### 레벨 (Level)
사전적 의미는 수준, 단계다.
테스트에서는 같은 활동을 묶어 둔 단계를 말한다. 레벨마다 테스트하는 대상, 목적, 근거 문서, 찾는 결함의 종류, 맡는 사람이 다르다.

<br/>

## 레벨별 비교
| 레벨 (CTFL v4.0) | 테스트 대상 | 주로 하는 사람 | 도구 예시 |
|---|---|---|---|
| 컴포넌트 테스트 (Component, 단위 테스트) | 함수, 메서드, 클래스 같은 단위 하나 | 개발자 | Jest, Vitest, JUnit, pytest |
| 컴포넌트 통합 테스트 (Component integration) | 컴포넌트 사이의 인터페이스와 상호작용 | 개발자, SDET | 테스트 프레임워크, API 테스트 도구 |
| 시스템 테스트 (System) | 시스템 전체의 동작(기능과 비기능) | QA, SDET | Playwright, Selenium, Cypress |
| 시스템 통합 테스트 (System integration) | 이 시스템과 외부 시스템, 서비스 사이의 인터페이스 | QA, SDET | Postman, Newman, 계약 테스트 도구 |
| 인수 테스트 (Acceptance) | 사용자와 비즈니스 요구를 채우는가, 배포해도 되는가 | 사용자, PO, QA | 사용자 인수 테스트(UAT) 시나리오 |

"주로 하는 사람"과 "도구 예시"는 흔한 경우이고, 레벨을 나누는 기준은 아니다.

<br/>

## 컴포넌트(단위) 테스트
DB나 외부 API 같은 의존 대상은 가짜 객체로 바꿔(모킹) 단위 하나만 떼어 테스트한다. 실행이 밀리초 단위로 빨라서 수천 개를 두고 코드를 고칠 때마다 돌릴 수 있다. 테스트 코드는 준비(Arrange), 실행(Act), 확인(Assert) 순서로 쓰는 AAA 패턴이 흔하고, 테스트를 먼저 쓰는 TDD의 기본 단위이기도 하다.

<br/>

## 통합 테스트
따로 테스트한 단위를 합쳤을 때 서로 맞물려 동작하는지 본다. 모듈 A가 B를 불렀을 때 B가 기대한 형식으로 응답하는지 같은 것이다.

합치는 방법에는 한 번에 다 합치는 빅뱅(Big Bang) 방식과, 위에서부터(Top-down) 또는 아래에서부터(Bottom-up) 하나씩 붙여 가는 점진(Incremental) 방식이 있다. 빅뱅은 결함이 났을 때 어느 연결이 원인인지 찾기 어려워서 보통 점진 방식을 권한다.

컴포넌트 통합은 한 시스템 안의 단위끼리, 시스템 통합은 결제 대행사나 외부 API처럼 다른 시스템과의 연결을 본다. API 테스트는 인터페이스의 입력과 출력만 보면 블랙박스이고, DB나 로그 같은 내부 상태까지 확인하면 [그레이박스](../04_블랙박스%20화이트박스%20그레이박스(Black,%20White%20and%20Grey%20Box)/README.md) 테스트가 된다.

<br/>

## 시스템 테스트
완성된 시스템을 사용자 시나리오대로 처음부터 끝까지(End-to-End) 돌려 본다. 기능뿐 아니라 성능, 보안, 호환성 같은 비기능도 이 레벨에서 많이 검증한다. Test-Automation 레포의 [playwright-suite](https://github.com/JangHwanPark/Test-Automation/tree/main/packages/playwright-suite)와 [demo-web](https://github.com/JangHwanPark/Test-Automation/tree/main/apps/demo-web)이 여기에 해당한다.

<br/>

## 인수 테스트
사용자나 비즈니스 관점에서 요구를 채우는지, 배포해도 되는지를 판단한다. ISTQB는 실제 사용자가 하는 사용자 인수 테스트(UAT), 운영 인수 테스트, 계약 및 규제 인수 테스트, 알파 테스트, 베타 테스트로 나눈다. 알파 테스트는 개발하는 조직의 사이트에서 잠재 고객이나 기존 고객, 운영자, 독립된 테스트 팀이 하고, 베타 테스트는 고객이 자기 환경에서 한다.

<br/>

## 테스트 피라미드
레벨별로 테스트를 몇 개씩 둘지 정할 때 쓰는 그림이다. 마이크 콘(Mike Cohn)이 알린 모델이다.

```
         /\
        /  \      인수, E2E (적게)
       /────\
      /      \    통합 (중간)
     /────────\
    /          \  단위 (많이)
   /────────────\
```

아래로 갈수록 빠르고 싸서 많이 두고, 위로 갈수록 느리고 깨지기 쉬워 적게 둔다. 위쪽 테스트가 실패하면 원인 범위가 넓어 디버깅 비용도 커진다.

<br/>

## 면접 답변 (30초)
> "테스트 레벨은 무엇을 단위로 테스트하느냐에 따라 단위, 통합, 시스템, 인수로 나뉘고, ISTQB 최신 실라버스는 통합을 컴포넌트 통합과 시스템 통합으로 나눠 다섯 단계로 봅니다. 단위는 함수와 클래스, 통합은 모듈이나 외부 시스템과의 인터페이스, 시스템은 전체 E2E 동작, 인수는 사용자 요구 충족 여부를 검증합니다. 테스트 피라미드에 따라 빠른 단위 테스트를 가장 많이 두고 E2E는 적게 두는 것이 효율적입니다."
