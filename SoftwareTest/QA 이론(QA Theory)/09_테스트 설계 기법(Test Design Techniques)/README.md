## 테스트 설계 기법이란 ?
- 테스트 케이스(TC)를 감이 아니라 정해진 규칙으로 뽑아내는 방법
- ISTQB CTFL v4.0(2023) 실라버스는 테스트 기법을 블랙박스, 화이트박스, 경험 기반 세 갈래로 나누고, 협업 기반 테스트 접근법(4.5절)을 따로 다룬다
- 이 노트의 분류와 기법 목록은 CTFL v4.0 4장 기준이다. v3.1(2018) Foundation에 있던 유스케이스 테스트는 v4.0에서 빠졌다. 페어와이즈는 v3.1에서도 Foundation이 아니라 Advanced(Test Analyst) 범위였다(확인 필요)

### 설계 (Design)
사전적 의미는 계획을 세워 도면으로 그려 내는 일이다.
테스트에서는 요구사항이나 코드에서 무엇을 확인할지(테스트 조건)를 고르고, 그 조건을 확인할 입력값과 기대 결과를 정하는 일을 말한다. 기법은 이 고르는 과정을 사람마다 다르지 않게 만드는 규칙이다.

시험 문제를 낼 때 교과서 단원마다 한 문제씩 내는 규칙을 정해 두는 것과 같다. 출제자가 바뀌어도 빠지는 단원이 생기지 않는다.

<br/>

## 왜 필요할까
입력값은 거의 무한하고 모든 경우를 테스트할 수는 없다(테스팅 7원칙의 완전한 테스트는 불가능). 그렇다고 떠오르는 값만 넣으면 사람마다 빠뜨리는 곳이 달라진다. 설계 기법은 적은 수의 TC로 결함이 잘 숨는 곳을 골고루 덮게 해 주고, 왜 이 TC를 골랐는지 설명할 근거가 된다.

<br/>

## 기법의 분류

| 분류 | 무엇을 근거로 하나 | CTFL v4.0 기법 |
| --- | --- | --- |
| 블랙박스 (명세 기반) | 요구사항, 명세 | 동등 분할, 경계값 분석, 결정 테이블, 상태 전이 |
| 화이트박스 (구조 기반) | 소스 코드의 구조 | 구문 테스트와 커버리지, 분기 테스트와 커버리지 |
| 경험 기반 | 테스터의 경험과 직관 | 오류 추측, 탐색적 테스트, 체크리스트 기반 테스트 |
| 협업 기반 접근법 (기법과 따로 다룸) | 개발자, 비즈니스 담당자와 함께 정한 내용 | 협업 사용자 스토리 작성, 인수 기준, 인수 테스트 주도 개발(ATDD) |

<br/>

## 블랙박스 기법

### 동등 분할 (Equivalence Partitioning)
입력 범위를 시스템이 똑같이 처리할 것으로 보이는 묶음(파티션)으로 나누고, 묶음마다 대표값 하나를 고른다. 같은 묶음 안의 값은 결과도 같을 것이라고 보기 때문에 하나만 확인하면 된다.

1~100을 받는 입력칸이라면 `1 미만`, `1~100`, `100 초과` 세 묶음이 생기고, 예를 들어 `-5`, `50`, `150` 세 TC로 덮는다.

### 경계값 분석 (Boundary Value Analysis)
동등 분할의 경계 부근을 확인한다. `<` 와 `<=` 를 헷갈리는 식의 실수(off-by-one)가 경계에서 많이 나기 때문이다. CTFL v4.0은 두 가지 방식을 소개한다.

- 2값 경계값 분석: 경계값과, 경계 바로 바깥 이웃 값. 1~100이면 `0, 1, 100, 101`
- 3값 경계값 분석: 경계값과 양쪽 이웃 값. 1~100이면 `0, 1, 2, 99, 100, 101`

### 결정 테이블 (Decision Table)
여러 조건의 조합과 그때의 결과를 표로 정리하고, 표의 열(규칙)마다 TC를 만든다. 회원 등급(VIP, 일반)과 결제 수단(카드, 현금)에 따라 할인율이 달라지는 규칙처럼 조건이 얽힌 비즈니스 로직에서 빠진 조합을 찾기 좋다.

### 상태 전이 (State Transition)
시스템이 가질 수 있는 상태와 상태 사이의 전이를 다이어그램이나 표로 그린 뒤 TC를 만든다. 주문이 `장바구니 → 결제 대기 → 결제 완료 → 배송 준비 → 배송 완료` 로 흐르는 식이다. 허용된 전이뿐 아니라 허용되지 않은 전이(배송 완료 상태에서 결제 취소 등)도 확인한다.

CTFL v4.0이 다루는 커버리지 기준은 모든 상태 커버리지, 유효 전이 커버리지(0-스위치 커버리지라고도 한다), 모든 전이 커버리지다. 전이 두 개 이상을 이어서 보는 1-스위치 이상은 Advanced 레벨 내용이다.

<br/>

## 화이트박스 기법
코드의 구문과 분기를 얼마나 실행했는지를 기준으로 TC를 만든다. 자세한 내용은 [10장 커버리지](../10_커버리지(Coverage)/README.md)에 정리했다.

<br/>

## 경험 기반 기법

### 오류 추측 (Error Guessing)
과거에 결함이 났던 곳, 개발자가 자주 하는 실수를 떠올려 TC를 만든다. null, 빈 문자열, 공백만 있는 문자열, 0, 음수, 아주 긴 문자열, 한글과 이모지 입력 같은 값이 대표적이다.

### 탐색적 테스트 (Exploratory Testing)
TC를 미리 쓰지 않고 시스템을 배우면서 동시에 설계하고 실행한다. [14장 탐색적 테스트](../14_탐색적%20테스트(Exploratory%20Testing)/README.md)에 정리했다.

### 체크리스트 기반 테스트 (Checklist-based Testing)
확인할 항목을 미리 목록으로 만들어 두고 하나씩 점검한다. 로그인, 결제처럼 자주 반복하는 흐름에 쓰기 좋다. 같은 목록만 계속 쓰면 효과가 떨어지므로 목록도 주기적으로 고친다.

<br/>

## 협업 기반 테스트 접근법
CTFL v4.0이 4.5절에서 기법과 따로 다루는 내용이다. 협업 사용자 스토리 작성(테스터, 개발자, 비즈니스 담당자가 함께 스토리를 쓴다), 인수 기준(Acceptance Criteria) 정하기, 인수 테스트 주도 개발(ATDD, 인수 기준에서 테스트를 먼저 만든 뒤 개발한다) 세 가지가 있다. 결함을 찾는 것보다 결함이 생기지 않게 막는 데 초점이 있다.

<br/>

## 면접 답변 (30초)
> "테스트 설계 기법은 ISTQB 기준으로 블랙박스, 화이트박스, 경험 기반 세 가지로 나뉘고, v4.0에서는 협업 기반 접근법을 따로 다룹니다. 블랙박스에는 동등 분할, 경계값 분석, 결정 테이블, 상태 전이가 있고, 화이트박스는 구문과 분기 커버리지를 기준으로 합니다. 경험 기반에는 오류 추측, 탐색적 테스트, 체크리스트가 있어 정형 TC가 놓치는 영역을 보완합니다. 실무에서는 경계값과 상태 전이를 가장 많이 쓰는데, 입력 검증과 주문처럼 상태가 바뀌는 흐름에서 결함이 잘 나기 때문입니다."

과제형 사전 테스트에서는 경계값 분석, 상태 전이, 결정 테이블이 자주 나온다. 입찰, 검수처럼 상태가 바뀌는 도메인이면 상태 전이를 먼저 떠올린다. 경계값을 명시해 TC를 쓴 예는 [Test-Automation 레포의 T-01](https://github.com/JangHwanPark/Test-Automation/blob/main/QA-Portfolio/assignment/testcases/tc01/README.md)에 있다.
