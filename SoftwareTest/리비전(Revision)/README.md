## 리비전이란 ?
- 리비전(Revision)은 버전 관리 시스템에 변경이 한 번 저장될 때마다 생기는 저장소의 한 시점이다. 그 시점을 가리키는 번호나 해시도 리비전이라고 부른다
- 테스트에서 리비전을 적는 것은 어느 소스 코드로 만든 빌드를 테스트했는지 밝히는 일이다
- 클라 리비전, 서버 리비전은 클라이언트(Client)와 서버(Server)를 각각 어느 리비전으로 만들었는지를 말한다. 클라는 클라이언트를 줄인 말이다. 둘은 따로 만들고 따로 배포하므로 숫자가 서로 다를 수 있다

리비전은 특정 회사나 도구의 말이 아니라 버전 관리 전반에서 쓰는 공용 용어다. 다만 클라 리비전, 서버 리비전처럼 붙여 부르는 방식은 팀의 관행이라 이름과 범위가 팀마다 조금씩 다르다.

### 리비전 (Revision)
사전적 의미는 다시 살펴보고 고치는 일, 또는 그렇게 고쳐 나온 새 판이다(Wiktionary revision). 명사 revision은 라틴어 revīsiō에서, 동사 revise는 라틴어 revīsō에서 왔고, revīsō는 re-(다시)와 vīsō(살펴보다)가 합쳐진 말이다(Wiktionary revise).

공학적으로는 버전 관리 시스템에 저장된 한 시점의 상태를 말한다. 고칠 때마다 새 판이 하나씩 생긴다는 사전적 의미가 그대로 이어진다. 책의 개정판에 1판, 2판처럼 번호를 붙이듯, 코드도 고쳐 저장할 때마다 새 리비전이 생기고 거기에 이름이 붙는다.

이 노트에서 쓰는 말 몇 가지를 먼저 정리한다. 버전 관리 시스템(Version Control System)은 코드가 바뀐 기록을 모두 남겨 두는 도구다. 기록이 모이는 곳을 저장소(Repository), 바뀐 내용을 저장소에 한 번 저장하는 일을 커밋(Commit)이라고 한다.

<br/>

## 리비전은 어떻게 생기나
도구마다 리비전에 이름을 붙이는 방식이 다르다. 테스트 현장에서 듣는 리비전 숫자가 어떤 모양인지는 팀이 어떤 도구를 쓰는지에 달려 있다.

### SVN: 저장소 전체에 붙는 번호
SVN(Subversion) 공식 안내서는 리비전을 이렇게 설명한다.

> Each time the repository accepts a commit, this creates a new state of the filesystem tree, called a revision.

저장소가 커밋을 받을 때마다 파일 트리의 새 상태가 생기고, 그것을 리비전이라고 부른다는 뜻이다. 번호 매기는 규칙도 정해져 있다.

- 새 저장소의 첫 리비전은 0번이고 빈 루트 폴더 하나만 있다
- 커밋할 때마다 바로 앞 리비전보다 1 큰 자연수가 붙는다
- 번호는 파일 하나가 아니라 저장소 전체에 붙는다("Subversion's revision numbers apply to the entire repository tree, not individual files.")

그래서 리비전 N은 N번째 커밋이 끝난 뒤의 저장소 상태를 가리킨다고 안내서는 정리한다. 리비전 숫자가 클수록 나중 상태라는 것을 번호만 보고 알 수 있다.

### Git: 커밋을 가리키는 해시
Git 공식 문서(gitrevisions)는 리비전 매개변수를 "typically, but not necessarily, names a commit object"라고 설명한다. 보통은 커밋 하나를 가리킨다는 뜻이다. 커밋을 가리키는 방법은 여러 가지다.

- 40자리 16진수 해시 전체, 또는 저장소 안에서 겹치지 않는 앞부분. 해시(Hash)는 커밋 내용으로 계산한 고정 길이 문자열이라 커밋마다 다르다. 40자리는 기본 해시 방식(SHA-1) 저장소 기준이다
- `main`, `HEAD` 같은 이름. `HEAD`는 지금 작업 중인 코드의 바탕이 된 커밋이다

빈 저장소에 커밋을 두 번 하고 확인하면 아래처럼 나온다. 해시는 커밋 내용과 시각에 따라 달라지므로 실행할 때마다 다른 값이 나온다.

```bash
git rev-parse HEAD         # 1616cfa538f36b968a91f4a87ce50f43d832f7d6
git rev-parse --short HEAD # 1616cfa
git rev-parse --short HEAD~1 # 9275955 (바로 앞, 첫 번째 커밋)
git rev-list --count HEAD  # 2 (HEAD까지 이어진 커밋 수)
```

Git 해시는 SVN 번호와 달리 크기 순서가 없다. 두 번째 커밋 1616cfa가 첫 커밋 9275955보다 나중이라는 것을 해시만 보고는 알 수 없다. 그래서 Git을 쓰는 팀은 테스트 대화에서 짧은 해시를 그대로 쓰거나, 커밋 수나 빌드 번호를 함께 적어 순서를 알 수 있게 하는 경우가 많다(관행이라 팀마다 다르다).

### 퍼포스: 체인지리스트 번호와 파일 리비전
퍼포스(Perforce, 서버 제품명은 Helix Core)는 게임 회사에서 많이 쓴다고 알려진 버전 관리 시스템이다(널리 알려진 이야기지만 이번에 출처로 확인하지는 않았다). 퍼포스에는 번호가 두 종류 있어서, 리비전이라는 말이 어느 쪽을 가리키는지 구분해야 한다.

- 체인지리스트 번호(Changelist Number, CL)는 제출(submit) 한 번에 붙는 번호다. 다른 도구의 커밋에 해당한다. 공식 문서는 체인지리스트가 "the next number in the changelist sequence"를 받는다고 적어, 번호가 하나의 순서를 따라 붙는다는 것을 보여 준다. 파일 이름 뒤에 `@n`을 붙이면 "The revision of file immediately after changelist n was submitted.", 곧 체인지리스트 n이 제출된 직후의 파일을 가리킨다
- 파일 리비전(File Revision)은 파일 하나가 몇 번째로 바뀌었는지를 세는 번호다. `파일#n`은 "The nth revision of file."이다. 파일마다 따로 세므로 `Player.cpp#3`과 `Enemy.cpp#3`의 3은 서로 상관이 없다

```text
//depot/Game/Source/Player.cpp#3      Player.cpp의 세 번째 리비전
//depot/Game/Source/Player.cpp#head   Player.cpp의 최신 리비전
//depot/Game/...@123456               체인지리스트 123456이 제출된 직후의 Game 아래 파일들
```

테스트 대화에서 "리비전 123456"처럼 큰 숫자 하나가 나오면 파일 리비전이 아니라 체인지리스트 번호일 가능성이 크다. 파일 리비전은 파일마다 세어 작은 숫자가 많고, 빌드 전체를 숫자 하나로 가리킬 수 없기 때문이다(문서가 아니라 번호 체계에서 이끌어 낸 추론이라 팀에 확인하는 것이 좋다). 위 예처럼 `#`이 붙으면 파일 리비전, `@`나 CL이 붙으면 체인지리스트 번호다.

체인지리스트는 제출 전에도 번호를 가질 수 있다. 제출 전 상태를 대기(pending), 제출된 상태를 제출됨(submitted)이라고 부르고, `@n`에는 대기 중인 번호를 쓸 수 없다고 공식 문서는 적는다("n cannot be a pending (non-shelved) change number."). 제출할 때 번호가 새로 바뀔 수 있다는 이야기도 있지만 이번에 문서로 확인하지 못했다(확인 필요). 그래서 개발자에게 수정이 들어간 번호를 물을 때는 제출된 체인지리스트 번호인지 확인하는 편이 안전하다.

### 세 도구 비교
| 도구 | 리비전을 가리키는 값 | 붙는 단위 | 숫자 크기로 순서를 알 수 있나 |
|------|-------------------|----------|----------------------------|
| SVN | 리비전 번호 (예: r1234) | 커밋, 저장소 전체 | 알 수 있다 |
| Git | 커밋 해시 (예: 1616cfa) | 커밋 | 알 수 없다 |
| 퍼포스 | 체인지리스트 번호 (예: @123456), 파일 리비전 (예: #3) | 체인지리스트는 제출, 파일 리비전은 파일 하나 | 체인지리스트 번호는 한 순서를 따라 붙는다. 파일 리비전은 그 파일 안에서만 순서가 있다 |

### 비슷하게 들리는 이름
위키백과 Version control 문서는 이 값을 "version number, version, revision number, revision, or revision level"이라고 여러 이름으로 부른다고 적는다. 체인지셋(changeset), 체인지 리스트(change list, CL)는 커밋 하나에 묶인 변경 자체를 가리키는 말이다. 리비전이 바뀐 뒤의 상태라면 체인지셋은 바뀐 내용이라 엄밀히는 다르지만, 같은 번호로 부르기 때문에 현장에서는 섞어 쓰기도 한다.

## 테스트에서 리비전이 왜 필요한가
### 어느 코드에서 난 버그인지 밝힌다
같은 기능이라도 리비전마다 코드가 다르다. 버그 리포트에 리비전이 없으면 개발자는 그 버그가 이미 고친 옛 코드에서 난 것인지, 최신 코드에서도 나는 것인지 알 수 없다. 리비전이 있으면 그 시점의 코드를 그대로 꺼내 재현해 볼 수 있다. [게임 QA 프로세스](../게임%20QA%20프로세스(Game%20QA%20Process)/README.md)에서 버그 리포트에 빌드 번호를 꼭 적는다고 한 것과 같은 이유다.

### 고쳤는지 판단하는 기준이 된다
개발자가 리비전 1234에서 버그를 고쳤다고 하면, 테스터는 1234 이상으로 만든 빌드에서 재테스트해야 한다. 그보다 앞선 리비전으로 만든 빌드에서 다시 버그가 보여도 수정이 실패한 것이 아니다. 아직 수정이 들어가지 않은 빌드를 본 것이다. 번호에 순서가 있는 SVN 리비전이나 퍼포스 체인지리스트 번호에서는, 같은 브랜치에서 만든 빌드라면 이 비교가 숫자 비교로 끝난다. 번호는 브랜치와 상관없이 하나의 순서로 계속 커지므로, 다른 브랜치에서 만든 빌드는 번호가 커도 수정이 들어가 있지 않을 수 있다. 퍼포스에서 이렇게 비교하는 것은 체인지리스트 번호이고, 파일 리비전(`#n`)으로는 빌드끼리 비교할 수 없다.

### 리비전과 빌드 번호는 다르다
리비전은 소스 코드의 한 시점이고, 빌드 번호는 그 소스를 실행 파일로 만든 작업에 붙는 번호다. 같은 리비전으로 빌드를 두 번 하면 빌드 번호는 둘이지만 리비전은 하나다. 빌드 시스템이 빌드마다 어느 리비전으로 만들었는지 함께 기록해 두는 경우가 많아, 빌드 번호를 알면 리비전을 찾을 수 있다(팀의 빌드 설정에 따라 다르다).

## 클라 리비전과 서버 리비전
### 무엇을 말하나
클라이언트와 서버로 나뉜 프로그램에서, 클라 리비전은 테스트하는 클라이언트 빌드를 만든 리비전이고 서버 리비전은 접속한 서버를 만든 리비전이다. 클라이언트와 서버의 역할은 [클라이언트-서버 구조](../../CS_Basic/클라이언트-서버%20구조(Client-Server%20Architecture)/README.md)에서 다룬다.

### 왜 따로 적나
클라이언트와 서버는 따로 만들고 따로 배포한다. 서버는 테스트 서버에 새로 올리고, 클라이언트는 테스터가 기기에 새로 설치해야 바뀐다. 그래서 한쪽만 바뀐 상태로 테스트하는 일이 흔하다. 한 저장소를 쓰더라도 서버는 리비전 1250으로 올라가 있고 클라이언트는 1234로 만든 빌드일 수 있다. 저장소가 따로면 번호 체계부터 다르다.

이 상태에서 버그가 나면 원인이 어느 쪽 코드에 있는지 둘 다 알아야 좁힐 수 있다. 서버 쪽 수정이 들어간 리비전인데 클라이언트가 옛 리비전이라 생기는 문제라면, 코드 결함이 아니라 버전이 맞지 않아 생긴 문제일 수도 있다.

식당과 비슷하다. 손님은 지난주 메뉴판(클라이언트)을 보고 주문하는데 주방(서버)은 어제 메뉴를 바꿨다면, 주문이 안 될 때 메뉴판이 몇 판인지와 주방 메뉴가 몇 판인지를 둘 다 봐야 원인을 안다.

### 버그 리포트에 적는 예
아래는 형식의 예다. 항목 이름과 필수 여부는 팀이 정한 양식을 따른다.

```text
[환경]
클라 리비전: 1234 (빌드 #567)
서버 리비전: 1250 (QA 서버 2)
기기: Galaxy S24 / Android 15
```

## 근거 정리
| 주장 | 근거 | 확인 정도 |
|------|------|-----------|
| revision의 사전적 의미와 어원 | Wiktionary revision, revise | 직접 확인 |
| SVN 리비전은 커밋마다 생기는 저장소 전체의 상태이고 0부터 1씩 늘어난다 | SVN Book 1.7, Revisions 절 | 직접 확인 |
| Git 리비전은 보통 커밋을 가리키고 해시나 이름으로 적는다 | Git 문서 gitrevisions | 직접 확인 |
| Git 명령의 출력 모양 | 빈 저장소에 커밋 두 번을 하고 직접 실행 | 실행해서 확인. 해시는 실행마다 다르다 |
| 퍼포스의 체인지리스트 번호(`@n`)와 파일 리비전(`#n`)의 뜻, 대기 중인 번호는 `@n`에 쓸 수 없다 | P4 Command Reference, File specifications와 p4 submit | 직접 확인 |
| 퍼포스를 게임 회사에서 많이 쓴다, 제출할 때 번호가 바뀔 수 있다 | 없음 | 확인 필요 |
| 테스트에서 듣는 큰 숫자 하나는 체인지리스트 번호일 가능성이 크다 | 번호 체계에서 이끈 추론 | 내 추론. 팀에 확인할 것 |
| 리비전을 부르는 여러 이름 | 위키백과 Version control | 직접 확인 |
| 버그 리포트에 빌드 식별자를 적는다 | 위키백과 Game testing ([게임 QA 프로세스](../게임%20QA%20프로세스(Game%20QA%20Process)/README.md) 노트에서 인용) | 그 노트의 출처 |
| 클라 리비전, 서버 리비전을 따로 적는 이유, 빌드 번호와 리비전의 관계, 리포트 예시 | 공개 문서를 찾지 못함 | 현장 관행을 정리한 내용이다. 팀마다 다르다 |
