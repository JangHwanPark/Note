# Black / White / Grey Box Testing

> **한 줄**: 내부 구조를 **얼마나 아는가**에 따른 분류. Black = 모름 / White = 다 앎 / Grey = 일부 앎.

## 비교표

| 구분 | 내부 구조 | 관점 | 기법 예시 | 누가 |
|---|---|---|---|---|
| **Black Box** | 모름 | 사용자 / 입출력 | 동등 분할, 경계값, 결정 테이블, 상태전이, 페어와이즈, 유스케이스 | QA, 인수 테스터 |
| **White Box** | 다 앎 (소스 접근) | 코드 내부 흐름 | 구문 / 결정 / 조건 / MC/DC 커버리지 | 개발자, SDET |
| **Grey Box** | 일부 (API 명세, DB 구조 등) | 외부 + 일부 내부 | API 테스트, DB 검증, 통합 테스트 | QA / SDET |

## Black Box
- **장점**: 사용자 관점, 코드 변경에 강함, 누구나 가능
- **단점**: 코드 커버리지 보장 불가, 내부 로직 결함 놓침
- **언제**: 시스템 / 인수 테스트, UI 테스트

## White Box
- **장점**: 코드 커버리지 보장, 내부 로직 결함 잘 잡음
- **단점**: 코드 지식 필요, 코드 변경에 취약, 사용자 관점 부족
- **언제**: 단위 / 통합 테스트, 보안 / 성능 분석

## Grey Box
- **장점**: 두 관점 결합, API / DB 검증 가능
- **단점**: 균형 잡기 어려움
- **언제**: 통합 테스트, API 테스트, SDET 영역

## 면접 답변 템플릿 (30초)
> "Black Box는 내부 구조를 모른 채 입출력만 보고 검증하는 방식으로 동등 분할 / 경계값 같은 기법을 사용합니다. White Box는 코드를 보고 구문·결정·조건 커버리지를 만족하도록 검증합니다. Grey Box는 API 명세나 DB 구조 같은 일부 내부 정보를 활용하는 절충 방식입니다. 실무에서는 Black은 시스템 / 인수, White는 단위 / 통합, Grey는 API 테스트에 주로 사용합니다."

## 실무 적용
- QA 기능 테스트 = Black box 중심
- SDET / 자동화 = White / Grey 자주 사용
- API 테스트 ([packages/api-suite/](../../../packages/api-suite/)) = Grey Box 대표 예시
