# 테스트 설계 기법 (Test Design Techniques)

> **한 줄**: **TC 를 체계적으로 도출**하는 기법들. Black box / White box / 경험 기반 3분류.

## 3대 분류

| 분류 | 근거 | 대표 기법 |
|---|---|---|
| **Black box (명세 기반)** | 요구사항 / 명세서 | 동등 분할, 경계값, 결정 테이블, 상태전이, 페어와이즈, 유스케이스 |
| **White box (구조 기반)** | 소스 코드 | 구문 / 결정 / 조건 / MC/DC 커버리지 |
| **경험 기반** | 테스터의 경험 / 직관 | 탐색적, 오류 추측, 체크리스트 |

## Black Box 기법 (★ 사전과제 단골)

### 1. 동등 분할 (Equivalence Partitioning)
- 입력 도메인을 **동등하게 처리되는 그룹**으로 나눠 각 그룹에서 대표값 선택
- 예) 1~100 입력 가능한 필드 → 그룹: `<1` (음수/0) / `1~100` (정상) / `>100` (초과). 각 그룹에서 1개씩 선택

### 2. 경계값 분석 (Boundary Value Analysis) ★
- 동등 분할의 **경계** 부근에서 결함이 자주 발생
- 예) `1~100` → 경계값 TC: `0, 1, 100, 101` (off-by-one 결함 검출)
- **크림 사전테스트 빈출**

### 3. 결정 테이블 (Decision Table)
- 여러 조건의 조합 → 결과 매핑
- 예) 회원 등급(VIP/일반) × 결제수단(카드/현금) × 금액대 → 할인율 매트릭스
- 복잡한 비즈니스 규칙 TC 도출에 강력

### 4. 상태전이 (State Transition)
- 시스템의 **상태와 전이**를 다이어그램으로 그려 TC 도출
- 예) 주문: `장바구니 → 결제대기 → 결제완료 → 발송준비 → 발송완료 → 수령`
- **유효한 전이**와 **무효한 전이** 모두 TC
- 커버리지: 0-switch (단일 전이), 1-switch (연속 전이)
- **크림 입찰/검수 도메인에 직접 적용 가능**

### 5. 페어와이즈 (Pairwise / All-pairs)
- 모든 조합이 아니라 **두 변수 간의 모든 조합**만 커버
- 예) 변수 3개 각 4값 → 전수 64개 → 페어와이즈 16개로 압축
- 모든 조합 불가능할 때

### 6. 유스케이스 (Use Case)
- 사용자 시나리오 / 액터 기반 TC
- 정상 흐름 + 대체 흐름 + 예외 흐름

## 경험 기반 기법

### 1. 탐색적 테스팅 (Exploratory)
- 학습 + 설계 + 실행을 **동시에**
- TC 미리 만들지 않음
- **살충제 패러독스 해결책**

### 2. 오류 추측 (Error Guessing)
- 결함이 자주 발생하는 곳을 직관으로 추측
- "null 입력 / 빈 문자열 / 한글 / 공백 / 0 / 음수 / 매우 긴 문자열"
- 경험 많은 QA의 무기

### 3. 체크리스트 (Checklist-based)
- 표준 체크리스트로 빠짐없이 검증
- 예: 로그인 체크리스트, 결제 체크리스트

## 면접 답변 템플릿 (30초)
> "테스트 설계 기법은 Black box, White box, 경험 기반 3가지로 나뉩니다. Black box에는 동등 분할, 경계값 분석, 결정 테이블, 상태전이, 페어와이즈, 유스케이스가 있고, White box에는 구문·결정·조건·MC/DC 커버리지가 있습니다. 경험 기반에는 탐색적 테스팅과 오류 추측이 있는데, 이는 정형 TC로 못 잡는 영역을 보완하며 살충제 패러독스 해결에도 사용됩니다."

## 실무 적용 우선순위
- 사전과제에서 가장 많이 묻는 건 **경계값 분석** + **상태전이** + **결정 테이블**
- 본 레포 [T-01](../../../../Test-Automation/assignment/testcases/tc01/README.md) 의 작성 조건에 "경계값 케이스 명시" 가 들어있는 이유
- 크림 입찰/검수 같은 상태 흐름 도메인은 **상태전이** 가 핵심
