# Retest vs Regression Test

> **한 줄**: Retest = **수정된 그 결함만** 다시 검증 / Regression = **그 수정이 다른 곳을 깨뜨리지 않았는지** 검증.

> **외우는 팁**: Retest는 **점**(한 결함) / Regression은 **면**(주변 영향 영역)

## 핵심 비교

| 구분 | Retest (확인 테스트) | Regression (회귀 테스트) |
|---|---|---|
| 목적 | 해당 결함이 정말 수정되었는가 | 수정으로 인해 기존 기능이 깨지지 않았는가 |
| 대상 | 수정된 결함 1건의 재현 TC | 영향 받을 수 있는 주변 / 관련 기능 TC |
| TC 출처 | 원래 결함 리포트의 재현 절차 | 기존 회귀 스위트 + 변경 영향 분석 결과 |
| 자동화 | 보통 수동 (1회성) | **자동화의 핵심 영역** (반복) |
| 결과 해석 | Pass = 결함 해결 / Fail = 미해결 | Pass = 부작용 없음 / Fail = 새 결함 (회귀 결함) |
| 우선순위 | 결함 수정 직후 즉시 | Retest 통과 후 영향 범위 산정 → 실행 |

## 둘은 짝꿍
결함 수정 → Retest로 그 결함 해결 확인 → Regression으로 주변 영향 검증.
Retest만 하고 끝내면 수정 자체로 인한 부작용을 놓친다.

## "Retest만 하고 끝내면 위험한 이유"
- 코드 수정은 **국소적인 변경도 전역적인 영향**을 만들 수 있다 (공유 모듈, 전역 상태, side effect)
- 수정한 결함은 해결됐지만 그 수정으로 **새 결함**이 생긴 사례가 많음 (회귀 결함, Regression Bug)
- 통합 환경 / 다른 브라우저 / 다른 권한 / 다른 데이터 상태에서만 발생하는 부작용을 놓침
- 살충제 패러독스와 별개로, **회귀 누락은 출시 직후 핫픽스의 주된 원인**

## 회귀 범위 산정 기준

| 우선순위 | 범위 | 근거 |
|---|---|---|
| 1 | 수정된 코드를 **직접 사용하는** 함수 / 컴포넌트 | 의존성 (Direct dependency) |
| 2 | 수정된 기능과 **데이터를 공유**하는 기능 | 같은 DB 테이블 / 같은 전역 상태 |
| 3 | 같은 사용자 흐름 / 시나리오에 포함되는 기능 | 유스케이스 인접성 |
| 4 | 동일 빌드 / 배포 단위에 포함된 변경 영역 전체 | 빌드 단위 |
| 5 | 핵심 비즈니스 흐름 (스모크 / 골든 패스) | 항상 실행 |

> 시간 / 리소스 제약 시 **선택적 회귀**, 출시 직전 / 메이저 변경 시 **전체 회귀**.

## 자동화 관점
- 회귀 = 반복 / 같은 절차 / 객관적 판정이라 **자동화 적합**
- Retest = 결함마다 1회성 / 수동도 무방 (자동화하면 회귀 스위트에 자연스럽게 합류)
- 살충제 패러독스 주의 — 회귀 스위트는 주기적으로 갱신해야 새 결함 검출력 유지

## 실무 적용
- Jira에서 결함 수정 후 "Resolved" 상태가 되면 Retest 수행 → Pass 시 "Closed", Fail 시 "Reopened"
- Closed 직전 영향 분석 메모와 함께 회귀 범위를 정해 회귀 스위트 실행
- 자동화된 회귀 스위트가 있으면 CI에서 매 변경마다 자동 회귀 → 사람은 변경 인접 영역만 수동 보조

## 면접 답변 템플릿 (30초)
> "Retest는 수정된 결함이 실제로 해결됐는지 그 결함 1건의 재현 절차로만 검증하는 활동이고, Regression은 그 수정이 기존 다른 기능을 깨뜨리지 않았는지 영향 범위 전체를 검증하는 활동입니다. Retest만 하고 끝내면 수정으로 인한 부작용, 즉 회귀 결함을 놓쳐 출시 후 핫픽스의 주원인이 됩니다. 따라서 결함 수정 후에는 Retest 통과를 확인하고, 변경 영향 분석으로 도출한 범위에 회귀 테스트를 수행하는 절차를 함께 가져갑니다. 회귀는 반복적이라 자동화의 핵심 영역이지만 살충제 패러독스에 취약해 주기적으로 갱신해야 합니다."
