## 게임 QA 프로세스란 ?
- 게임 개발에서 QA가 첫 플레이 가능한 빌드를 받는 때부터 출시 판정, 출시 뒤 패치 검증까지 일하는 흐름이다
- 게임 업계에서는 게임 테스트(Game Testing)를 QA 테스트라고도 부르고, 주된 일은 결함을 찾아 기록하는 것이다(위키백과 Game testing 첫 문단)
- 이 노트는 개발 마일스톤마다 QA가 하는 일, 빌드를 받아 검증하는 순서, 게임에만 있는 테스트, 버그 리포트와 분류, 출시 판정, 라이브 서비스 검증, 개발사와 퍼블리셔와 외주 QA의 차이를 다룬다. 일반 테스트 이론은 [QA 이론](../QA%20이론(QA%20Theory)/README.md)의 장으로 잇는다
- 근거는 위키백과 문서, Microsoft의 공개 Xbox 인증 문서, ESRB 공식 페이지, Unity Learn 페이지다. 조사 시점은 2026년 10월이다

### 프로세스 (Process)
사전적 의미는 일이 처리되는 경로나 공정이다.
게임 QA에서는 빌드가 어느 단계에 있느냐에 따라 테스트의 목적과 강도가 바뀌는 흐름을 말한다. 초반에는 새로 들어온 기능에 매일 짧게 의견을 주고, 출시가 가까워질수록 정해 둔 테스트 계획을 빠짐없이 돌리고 출시해도 되는지 판정하는 쪽으로 옮겨 간다.

연극 준비와 같다. 대본 읽기 단계에서는 장면이 말이 되는지만 보고, 총연습에서는 조명과 소품까지 실제 공연처럼 맞춰 보고, 개막 뒤에도 매회 공연을 보며 틀린 곳을 고친다. 같은 사람이 보더라도 단계마다 보는 것이 다르다.

<br/>

## 일반 테스트 프로세스와 무엇이 다른가
[테스트 프로세스](../QA%20이론(QA%20Theory)/16_테스트%20프로세스(Test%20Process)/README.md)에서 본 ISTQB의 CTFL v4.0의 일곱 활동(계획, 모니터링과 통제, 분석, 설계, 구현, 실행, 완료)은 게임 QA에도 쓸 수 있는 틀이다(직접 판단). 다만 위키백과 Video game development 문서의 Testing 절은 게임이 근본적으로 즐거움을 주려고 만든 소프트웨어라서, 게임 테스트는 코드가 정확한지보다 플레이어가 겪는 경험에 더 무게를 둔다고 설명한다. 같은 절은 게임 테스트를 어렵게 만드는 요인으로 무작위성이 들어간 시스템(선형적인 게임보다 밸런스와 버그 추적에 더 많은 테스트가 필요하다), 개발 예산 안에서 테스트에 쓸 비용과 시간, 변경을 거듭해도 게임이 계속 재미있는지 확인하는 일을 든다.

또 하나 다른 점은 표준이 없다는 것이다. 위키백과 Game testing 문서는 게임 업계에 표준 방법론이 없고 개발사와 퍼블리셔가 각자의 방법을 쓴다고 적는다. 그래서 아래의 마일스톤 이름, 버그 등급 이름, 역할 이름은 모두 회사마다 다르다. 이 노트에 나오는 이름은 대부분 위키백과와 Microsoft 문서에 실린 예시다.

## 마일스톤과 단계별 QA 활동

### 마일스톤 (Milestone)
사전적 의미는 이정표, 길가에 세워 지나온 거리를 알려 주는 돌이다.
게임 개발에서는 개발 진행을 재기 위해 정해 둔 주요 시점을 말한다. 위키백과 Video game development의 Milestones 절에 따르면 상업 게임 프로젝트는 퍼블리셔가 정한 마일스톤을 맞춰야 하는 경우가 많고, 개발사는 마일스톤을 달성할 때마다 돈을 받는 계약을 맺는 경우가 많다. 마일스톤 목록은 퍼블리셔와 개발사가 함께 정하며 3개에서 20개까지 다양하다.

등산로의 이정표와 같다. 일행은 이정표마다 예정한 시간에 왔는지 점검하고, 늦었으면 다음 구간 계획을 고친다. 퍼블리셔에게 마일스톤은 돈을 내 줄 지점이고, QA에게는 이번 빌드에서 무엇을 기준으로 볼지가 바뀌는 지점이다.

### 단계별 정의와 QA가 하는 일
같은 절은 마일스톤을 정의하는 업계 표준이 없고 퍼블리셔, 연도, 프로젝트마다 다르다고 밝힌다. 아래 표의 정의와 시기는 위키백과가 2년 개발 주기의 흔한 예로 든 것(Chandler 2009, Bethke 2003 인용)이다. 프로토타입 정의는 같은 문서의 Pre-production 절에서, 버티컬 슬라이스는 Unity Learn에서 가져왔다. QA가 하는 일 칸은 위키백과 Game testing의 Overview 절을 단계에 맞춰 옮긴 것이다.

| 단계 | 정의 | QA가 하는 일 |
| --- | --- | --- |
| 프로토타입 (Prototype) | 아이디어나 기능을 시험하는 개념 증명용 버전. 사전 제작 단계에서 종이로 만들기도 한다 | 단계별 QA 활동은 확인하지 못했다(확인 필요). Video game development의 Testing 절은 플레이 가능한 프로토타입이 생기면 테스터가 들어온다고 적는다 |
| 버티컬 슬라이스 (Vertical Slice) | 게임의 핵심을 모든 분야(프로그래밍, 아트, 사운드, 기획)에 걸쳐 작게 잘라 보여 주는 플레이 가능한 조각 | 출처에서 QA 활동은 확인하지 못했다(확인 필요) |
| 퍼스트 플레이어블 (First Playable) | 대표 게임플레이와 에셋이 들어간 첫 버전. 프리 알파라고도 한다. 코드 릴리스 12~18개월 전 | 작은 팀이 새 코드에 매일 의견을 준다 |
| 알파 (Alpha) | 주요 기능이 다 들어가 플레이할 수 있는 상태(기능 완료, Feature Complete). 에셋은 일부만 완성. 출처에 시기는 없다 | 인원이 늘고 테스트 계획을 쓴다 |
| 코드 프리즈 (Code Freeze) | 새 코드를 넣지 않고 버그만 고치는 단계. 코드 릴리스 3~4개월 전 | 출처에 따로 적힌 활동은 없다 |
| 베타 (Beta) | 기능과 에셋이 완성되어 버그만 고치는 버전. 출시를 막는 버그가 없어야 한다. 코드 릴리스 2~3개월 전 | 날마다 분명한 과제를 받는다. 리드 테스터가 프로듀서와 부서장에게 매일 보고하고, 외부 퍼블리셔가 있으면 퍼블리셔 QA와 조율을 시작한다. 콘솔 게임은 콘솔 회사 QA에 빌드를 보낸다 |
| 코드 릴리스 (Code Release) | 출시하거나 콘솔 제조사 심사에 낼 준비가 된 단계. 첫 출시 후보(Release Candidate)는 보통 코드 릴리스 3~4주 전에 나온다 | QA 테스트 계획 전체로 이 버전을 테스트한다 |
| 골드 마스터 (Gold Master) | 제품 생산의 원본으로 쓰는 최종 빌드 | 프로듀서가 골드를 승인한다. 리드 테스터가 승인해야 골드로 가는 회사도 있다 |

버티컬 슬라이스는 위키백과의 마일스톤 목록에는 없다. Unity Learn의 "Your First Milestone: Vertical Slice"는 이를 게임 개발의 첫 주요 마일스톤으로 소개한다. 퍼스트 플레이어블과 버티컬 슬라이스가 같은 것인지, 순서가 어떻게 되는지는 회사마다 달라 확인 필요다.

위키백과 Game testing의 History 절은 테스터가 알파나 베타 버전을 즐기며 가끔 버그를 보고한다는 생각을 흔한 오해로 꼽는다. 알파 이전에는 정해진, 때로는 지루한 방법으로 버그를 찾는 일에 집중한다고 적는다.

### 늦게 시작하면 생기는 일
Video game development의 Testing 절은 테스트가 출시 직전에만 몰리기 쉽다고 하면서, 공개된 여러 개발 회고(포스트모템)에서 가장 흔히 나온 문제가 테스트를 일찍 시작하지 않은 것이었다고 적는다. 개발 초반에는 게임플레이가 바뀌면 코드가 통째로 버려질 수 있어 테스트를 가볍게 하다가, 기능이 굳어지면 회귀 테스트처럼 엄격한 통제를 더한다. [테스트 7원칙](../QA%20이론(QA%20Theory)/02_테스트%207원칙(ISTQB%20Principles)/README.md)의 조기 테스트와 같은 이야기다.

마감 직전에 크런치(Crunch, 초과 근무로 마감을 맞추는 기간)에 들어가면 QA는 늦게 들어온 기능과 콘텐츠를 지체 없이 테스트해야 하고, 다른 부서 인원이 테스트를 돕기도 한다(Game testing, Overview 절).

## 빌드를 받아 검증하는 흐름

### 빌드 (Build)
사전적 의미는 짓다, 세우다이다.
소프트웨어에서는 소스 코드와 에셋을 실행할 수 있는 형태로 묶어 만든 결과물을 말한다. Game testing 문서는 테스터가 개발자로부터 정해진 일정에 따라, 서로 구분할 수 있는 식별자가 붙은 빌드를 받는다고 적는다. 버그 리포트에 빌드 번호를 꼭 적는 이유가 여기 있다. 어느 빌드에서 났는지 모르면 고쳤는지도 판단할 수 없다.

빌드 하나를 받으면 대체로 아래 순서로 본다. 이 순서는 아래 각 절의 출처를 이어 붙인 것이고, 실제 순서와 범위는 팀마다 다르다.

1. 스모크 테스트로 이 빌드를 테스트할 수 있는지 판정한다
2. 이번 빌드에서 고쳤다는 버그를 재테스트한다
3. 수정 주변과 핵심 흐름을 회귀 테스트한다
4. 새로 들어온 기능과 콘텐츠를 기능 테스트한다
5. 찾은 버그를 등록하고, 단계에 따라 호환성, 현지화 같은 특화 테스트를 더한다

### 스모크 테스트 (Smoke Test)
위키백과 Smoke testing (software) 문서는 스모크 테스트를 빌드 검증 테스트(BVT, Build Verification Test), 빌드 인수 테스트(Build Acceptance Test)라고도 부르고, 새 빌드가 테스트 팀에 넘어가기 전에 테스트할 수 있는 상태인지 확인하는 테스트 묶음이라고 설명한다. 프로그램이 켜지는지, 화면이 열리는지 같은 기본 질문으로, 더 테스트할 필요가 없을 만큼 망가졌는지를 가린다. 이름은 하드웨어 시험에서 왔다. 새 기판에 전원을 넣었는데 연기가 나면 더 시험할 것 없이 전원을 끈다는 데서 나왔다고 같은 문서는 설명한다.

가게 문을 열기 전에 불이 켜지는지, 계산대가 돌아가는지만 먼저 확인하는 것과 같다. 여기서 막히면 오늘 장사를 준비하는 다른 일은 의미가 없다.

게임에서는 설치, 실행, 로그인, 로비 진입, 주요 메뉴 열기처럼 이후 테스트가 모두 거쳐 가는 경로가 대상이 된다(직접 든 예시다). Xbox 인증도 같은 단계를 둔다. Microsoft의 "Certification step-by-step guide"는 인증 테스트의 두 번째 단계로 BVT를 두고, 제품이 완전히 테스트할 수 있는 상태인지 확인하는 축소된 테스트라고 설명한다. BVT를 통과해야 본 인증 테스트 일정이 잡힌다. PC용 BVT 가이드는 흔한 실패로 깨끗한 PC에 설치했을 때 필요한 구성 요소가 없어 실행되지 않는 경우, 실행이나 플레이 중 크래시와 멈춤, 업적이 조건을 채워도 열리지 않는 경우를 든다.

### 기능 테스트 (Functionality Testing)
Game testing 문서의 Methodology 절은 기능 테스트를 게임 테스트라고 하면 가장 먼저 떠올리는 일로, 어떤 형태로든 게임을 플레이하며 안정성 문제, 게임 메커닉 문제, 에셋 무결성 같은 일반적인 문제를 찾는 테스트라고 설명한다. 같은 문서의 Overview 절은 찾는 대상을 버그부터 아트 글리치(그래픽이 깨지는 현상), 논리 오류, 레벨 버그까지로 들고, 미묘한 버그를 찾으려면 창의적인 플레이가 필요하다고 적는다. 정해진 케이스만 따라가서는 찾기 어렵다는 뜻이라 [탐색적 테스트](../QA%20이론(QA%20Theory)/14_탐색적%20테스트(Exploratory%20Testing)/README.md)와 이어진다.

많은 게임 회사는 플랫폼 요구 사항 테스트를 기능 테스트와 따로 둔다. 필요한 기술이 다르기 때문이다(Game testing, Overview 절).

### 재테스트와 회귀 테스트
Game testing 문서는 프로그래머가 버그를 고치면 QA가 그 버그가 아직 있는지 보고, 이어 비슷한 테스트로 수정이 다른 것을 망가뜨리지 않았는지 본다고 적는다. 두 번째 단계를 헤일로 테스트(Halo Testing)라고 부르기도 하는데, 버그 주변을 두루 테스트하며 다른 버그를 찾는 것이다(이 이름에는 출처 요청 표시가 붙어 있다). Video game development의 Testing 절은 게임이 복잡한 시스템이라 한 곳을 바꾸면 겉보기에 상관없는 곳이 망가질 수 있다고 회귀 테스트의 이유를 설명하고, 같은 게임을 반복해서 플레이하는 단조로운 일이라 버그를 놓친 채 출시되는 일이 잦다고 덧붙인다.

재테스트와 회귀의 차이, 회귀 범위를 정하는 순서는 [재테스트와 회귀 테스트](../QA%20이론(QA%20Theory)/13_재테스트와%20회귀%20테스트(Retest%20and%20Regression)/README.md)에 정리했다.

## 게임에 특화된 테스트

### 밸런스 테스트 (Balance Testing)
밸런스(Balance)의 사전적 의미는 균형이다. 게임에서는 캐릭터, 무기, 전략 사이에 너무 강하거나 약한 것이 없어 여러 선택이 의미를 갖는 상태를 말한다. Video game development의 Testing 절은 무작위성이 들어간 게임플레이 시스템이 선형적인 게임보다 밸런스 확인에 더 많은 테스트를 요구한다고 적고, Maintenance 절은 온라인 게임이 공개 테스트 서버에서 버그와 함께 밸런스 데이터를 모은다고 적는다.

요리의 간 맞추기와 같다. 레시피 분량대로 넣었는지는 확인할 수 있지만, 짠지 싱거운지는 먹어 보고 의도와 비교해야 안다. 밸런스는 버그와 달리 명세와 비교해 맞다, 틀리다를 가르기 어렵다. 기획 의도가 기준이 되므로 QA는 수치가 기획 데이터와 맞는지, 의도하지 않은 조합으로 지나치게 강한 결과가 나오는지를 찾아 의견으로 올리는 일이 많다고 본다(직접 판단이고, 밸런스 테스트를 QA와 기획 중 누가 맡는지는 회사마다 달라 확인 필요).

### 콘텐츠 검수
게임은 코드뿐 아니라 레벨, 그래픽, 텍스트, 사운드 같은 콘텐츠의 양이 많다. Game testing 문서는 기능 테스트가 에셋 무결성을 보고, 테스터가 아트 글리치와 레벨 버그를 찾는다고 적는다. 목표 등급이 있는 게임이라면 그 등급에 맞지 않을 수 있는 표현을 찾아 보고하는 것도 테스터의 일이다(Methodology 절의 Compliance testing 항목). 콘텐츠 검수라는 이름의 공정이 따로 있는지, 어떤 항목을 보는지는 출처에서 확인하지 못했다(확인 필요).

### 호환성과 기기 테스트 (Compatibility Testing)
Game testing 문서는 호환성 테스트가 주로 PC 게임에서 필요하다고 적는다. 호환성은 최종 빌드에 크게 좌우되어 개발 막바지에 하고, 흔히 두 번 돌린다. 문제를 고칠 시간을 벌려고 베타 초반에 한 번, 베타 후반이나 출시 후보 때 한 번이다. 테스트할 하드웨어 목록은 보통 퍼블리셔가 상업적으로 중요한 것을 골라 준다. 결과는 광고하는 최소 사양을 정하는 데도 쓰이고, 오래된 하드웨어는 고치지 않고 지원을 끊기도 한다. 입력 장치 테스트는 게임패드, 조이스틱, 키보드, 마우스가 정확하고 일관되게 입력을 인식하는지 본다.

콘솔은 하드웨어가 같아 호환성 문제가 적은 대신 소비자용 기기가 아니라 테스트 킷(Test Kit)으로 테스트한다. 테스트 킷은 소비자용과 사양이 같지만 디스크나 USB에서 빌드를 실행하고, 지역을 바꾸고, 메모리 덤프를 남길 수 있다. 개발 킷(Dev Kit)은 메모리가 더 많은 프로그래머용 장비로, 테스터는 보통 쓰지 않는다(Game testing, Console hardware 절). Xbox 인증 문서에는 인증 팀이 콘솔 기종, 해상도, 오디오 출력, 컨트롤러 수, 언어, 전원 설정, 저장 장치, 설치 방식, 게임 옵션을 서로 다르게 맞춘 콘솔 다섯 대의 예시 구성이 실려 있다. 예를 들어 한 대는 게임 옵션을 기본값의 반대로, 한 대는 30분마다 바꿔 가며 테스트한다. 호환성 조합을 어떻게 나누는지 보여 주는 공개 예시다.

모바일 게임의 기기 파편화 대응은 이번에 읽은 자료에 없어 다루지 않았다.

### 네트워크와 멀티플레이 테스트 (Multiplayer Testing)
Game testing 문서는 멀티플레이 비중이 큰 게임은 별도 멀티플레이 QA 팀을 두기도 하고, 모든 연결 방식이 동작하는지 확인하며, 덕분에 싱글플레이와 멀티플레이 테스트를 나란히 진행할 수 있다고 적는다. 부하 테스트(Load Testing)는 MMO(Massively Multiplayer Online, 대규모 다중 접속 게임) 서버의 동시 접속자 수, 화면에 동시에 뜨는 스프라이트 수처럼 시스템의 한계를 시험하고, 많은 테스터나 부하를 흉내 내는 소프트웨어가 필요하다. 출시 전 공개 베타 테스트는 수천 명의 팬이 내부 테스터가 놓친 버그를 찾을 수 있어 효과적이라고 같은 문서는 적는다.

인증 요구 사항에도 네트워크 항목이 있다. XR-074(Loss of Connectivity to XBOX and Partner Services)는 Xbox와 파트너 서비스 연결 오류를 매끄럽게 처리하고, 네트워크가 느려지거나 끊겼다 이어져도 크래시나 멈춤이 없어야 하며, 사용자에게 알기 쉬운 오류 메시지를 보여야 한다고 요구한다. PC BVT 가이드는 멀티플레이를 지원하는 게임이라면 세션을 시작해 끝까지 마칠 수 있어야 하고, 인증 팀이 세션에 필요한 최소 인원을 모아 매치를 끝까지 진행해 본다고 적는다.

### 소크 테스트 (Soak Testing)
soak는 물에 푹 담가 두다라는 뜻이다. 게임에서는 대기, 일시 정지, 타이틀 화면처럼 여러 상태로 게임을 오래 켜 두어, 시간이 지나야 드러나는 메모리 누수나 반올림 오차를 찾는 테스트를 말한다. 처음 설정한 뒤에는 사람이 조작하지 않아도 되고, 반복 클릭 같은 동작은 자동화 도구로 흉내 내기도 한다(Game testing, Methodology 절). 같은 절은 소크 테스트가 인증 요구 사항의 하나라고 적지만 출처 요청 표시가 붙어 있어 확인 필요다.

새 물통에 물을 채워 하룻밤 두어야 바닥에서 조금씩 새는지 알 수 있는 것처럼, 한 판만 해서는 보이지 않는 문제를 시간으로 드러낸다.

### 현지화 테스트 (Localization Testing)
현지화(Localization)는 게임을 다른 언어와 문화권에 맞게 바꾸는 일이다. Video game development의 Localization 절은 자막 일부만 옮기는 기본 번역부터 음성을 새로 녹음하고 게임 자료까지 바꾸는 완전 현지화까지 수준이 다양하다고 적는다. Game testing 문서는 현지화 테스터가 게임 안 텍스트의 편집자 역할을 한다고 표현한다. 일반적인 텍스트 문제는 기능 테스트에서도 보지만, QA 부서가 현지화 전담 테스터를 두기도 하고, 해당 지역 원어민 테스터를 써서 번역의 정확성과 품질을 확인하기도 한다.

번역문에서 글자가 잘리거나 변수가 치환되지 않는 문제는 실제 화면에서만 보인다. Xbox 인증 테스트 벤치도 콘솔마다 시스템 언어를 다르게 둔다.

### 플랫폼 인증 (Platform Certification)
인증(Certification)의 사전적 의미는 어떤 것이 기준에 맞는다고 공식적으로 증명하는 일이다. 게임에서는 콘솔 같은 플랫폼을 가진 회사(플랫폼 홀더)가 정한 요구 사항을 게임이 지키는지 플랫폼 쪽에서 시험하고, 통과해야 출시를 허락하는 절차를 말한다.

건물 사용 승인과 같다. 건물을 다 지어도 소방 설비와 비상구가 기준에 맞는지 검사를 통과해야 입주할 수 있다. 검사관은 건물이 예쁜지가 아니라 정해진 항목을 지켰는지를 본다.

Game testing 문서는 예로 소니의 TRC(Technical Requirements Checklist), Microsoft의 XR(Xbox Requirements), 닌텐도의 로트체크(Lotcheck) 가이드라인을 든다. 같은 문서는 이 요구 사항들이 비밀 유지 계약 아래 개발사와 퍼블리셔에게만 배포되는 문서라 일반에 공개되지 않는다고 적는다. 그래서 TRC와 로트체크의 세부 항목은 이 노트에 쓰지 않는다. 같은 문서에 따르면 요구 사항 중 일부는 테스터의 범위를 넘는 기술 항목이고, 표준 오류 메시지 형식, 저장 데이터 처리, 상표와 저작권 자료 처리 같은 부분은 테스터가 맡는다. 한 건만 위반해도 반려될 수 있고, 재테스트와 재제출 비용에 출시 시기를 놓치는 손해까지 생길 수 있다.

Microsoft는 XR 문서를 learn.microsoft.com에 공개하고 있다. "XBOX Requirements for XBOX Games"(이번에 읽은 판은 Version 16.7, 2026년 10월 27일)는 XR을 모든 Xbox 게임의 개발사와 퍼블리셔가 따라야 하는 정책, 기술 요구 사항, 제품 구성 요소 요구 사항으로 정의하고, 제품이 안정적이고 신뢰할 수 있을 뿐 아니라 일관되고 안전하고 즐거운 사용자 경험을 주도록 하기 위한 것이라고 밝힌다. 이번에 확인한 항목 몇 개는 아래와 같다.

- XR-003(Title Quality for Submission)은 저장 데이터 호환성을 포함한다. 테스트 003-16은 콘텐츠 업데이트를 받은 게임이 업데이트 전 버전으로 만든 저장 데이터를 불러올 수 있어야 한다고 본다
- XR-037(Dependencies on Content Packages)은 추가 콘텐츠에 묶인 저장 데이터도 기본 게임에서 불러오거나, 불러올 수 없는 이유를 분명히 알려야 한다고 요구한다
- XR-074는 위 네트워크 절에서 본 연결 끊김 처리다
- XR-112는 처음 실행할 때와 일시 중단, 절전에서 돌아올 때 주 사용자와 컨트롤러를 정해 처리하라고 요구한다

"Certification step-by-step guide"에 따르면 제출물은 세 단계로 테스트된다. 제출 검사(제출 검증 도구와 악성 코드 검사), BVT, 그리고 테스트의 대부분을 차지하는 XR 테스트다. XR마다 테스트 단계, 기대 동작, 통과와 실패 예시가 담긴 테스트 케이스가 공개되어 있다. 출시 전 상태를 미리 보는 유료 선택 제출(Optional Submission)과 출시를 위한 최종 제출(Final Submission)이 나뉘고, 문서는 선택 제출이 개발 기간 내내 필요한 QA를 대신하지 않는다고 적는다. 제출 유형별 처리 기간(SLA, Service Level Agreement)도 공개되어 있다. 2026년 10월 확인 기준으로 디지털 본편 최종 제출은 영업일 4일, 디지털 콘텐츠 업데이트는 영업일 2일이다.

### 등급 심의 (Content Rating)
Game testing 문서는 목표 콘텐츠 등급이 있는 게임이면 테스터가 그 등급에 맞지 않을 수 있는 표현을 보고해야 하고, 원하는 등급을 받지 못하면 다시 편집, 테스트, 제출해야 한다고 적는다. 리드 테스터가 ESRB, PEGI 같은 등급 기관에 낼 게임 영상을 모으는 경우가 많다는 서술도 있지만 출처 요청 표시가 붙어 있다.

ESRB(미국과 캐나다의 등급 기관) 공식 페이지는 실물 게임의 경우 퍼블리셔가 관련 내용을 적은 질문지와 가장 극단적인 내용을 담은 플레이 영상을 내고, 훈련받은 심의원 최소 3명이 영상을 보고 등급을 권고한다고 설명한다. 출시 뒤에는 ESRB 쪽 테스터가 직접 플레이해 퍼블리셔가 내용을 빠짐없이 공개했는지 확인할 수 있다. 디지털 게임은 IARC 질문지로 등급을 받고 출시 뒤 ESRB가 확인해 등급을 바로잡을 수 있다. 추가 콘텐츠(DLC)가 본편 등급을 넘는 내용을 담으면 따로 제출해야 한다.

한국의 게임물관리위원회 등급분류 절차와 QA의 관계는 이번에 원문을 읽지 않아 다루지 않는다(확인 필요).

## 버그 리포트와 재현 단계
Game testing 문서의 Process 절은 버그 하나가 거치는 흐름을 넷으로 나눈다.

1. 식별(Identification): 잘못된 동작을 분석해 버그로 판단한다
2. 보고(Reporting): 결함 추적 시스템에 버그가 난 상황과 재현 단계(Steps to Reproduce)를 담아 등록한다. 개발자가 버그가 나는 장면의 영상 같은 자료를 더 요청할 수 있다
3. 분석(Analysis): 그 버그를 맡은 아티스트, 프로그래머, 기획자가 확인한다. 테스터의 일은 아니지만 리포트가 불분명하면 테스터에게 정보나 증거를 더 요구한다
4. 확인(Verification): 수정 뒤 테스터가 버그가 더 나지 않는지 확인한다

일반 소프트웨어와 다른 점은 버그를 맡는 사람이 프로그래머만이 아니라는 것이다. 레벨 버그는 레벨 디자이너에게, 텍스처 문제는 아티스트에게 간다. 이 네 단계는 [결함 생명주기](../QA%20이론(QA%20Theory)/15_결함%20생명주기(Defect%20Lifecycle)/README.md)에서 New부터 Retest, Closed로 가는 큰 흐름에 대응한다.

### 재현 단계 (Steps to Reproduce)
15장에서 재현 절차라고 부른 것과 같다. 재현(再現)의 사전적 의미는 다시 나타냄이다. 버그 리포트에서는 다른 사람이 같은 버그를 다시 일으킬 수 있도록 사전 조건과 조작을 순서대로 적은 것을 말한다. Game testing 문서는 어떤 버그는 기록하기 쉽지만 많은 버그는 개발자가 재현하거나 찾을 수 있도록 자세한 설명이 필요하다고 적는다.

처음 가는 사람에게 남기는 길 안내 메모와 같다. "역에서 나와 편의점을 끼고 왼쪽"처럼 출발점과 갈림길이 빠지면 같은 곳에 도착하지 못한다.

게임 버그는 상태가 복잡해 재현 단계에 적을 것이 많다. 아래는 이 노트에서 정리한 예시이고, 회사마다 양식이 다르다.

- 빌드 번호와 플랫폼, 기기 사양(호환성 문제인지 가르는 데 필요하다)
- 계정 상태와 진행도(레벨, 퀘스트 진행, 보유 아이템)
- 위치(맵, 좌표, 구역)와 시점(서버 시간, 이벤트 기간)
- 재현 빈도(10번 중 몇 번). Xbox 인증도 문제를 심각도와 함께 발생 확률, 반복성으로 분류한다(Certification step-by-step guide의 Certification issue types)
- 영상과 크래시 덤프 같은 증거

중복 등록을 막는 것도 테스터의 일이다. Game testing 문서는 테스터가 같은 버그를 여러 번 등록하지 않도록 조율하고, 리드 테스터가 중복되거나 잘못된 리포트를 걸러 내고 설명을 요청한다고 적는다.

<br/>

## 버그 분류와 우선순위
[심각도와 우선순위](../QA%20이론(QA%20Theory)/03_심각도와%20우선순위(Severity%20and%20Priority)/README.md)는 두 값을 따로 매기지만, 아래 A, B, C 등급은 심각도를 기준으로 출시 영향까지 한 축에 담는다. Game testing 문서는 대부분의 회사가 심각도를 추정해 버그 등급을 매긴다며 아래 세 등급을 든다. 등급 이름과 기준은 회사마다 다르고, 이것은 예시다.

| 등급 | 뜻 | 출시에 미치는 영향 |
| --- | --- | --- |
| A 버그 | 출시를 막는 치명적인 버그. 예를 들어 게임이 크래시된다 | 고쳐야 출시할 수 있다 |
| B 버그 | 주의가 필요한 중요한 문제지만 게임은 플레이할 수 있다 | B 버그가 여러 개면 A 버그 하나만큼 심각하게 본다 |
| C 버그 | 작고 드문 문제. 버그라기보다 제안인 경우가 많다 | 출처에 따로 적혀 있지 않다 |

크래시(Crash)는 게임이 비정상적으로 종료되는 것이고, 위 예시처럼 보통 가장 높은 등급에 들어간다. 블로커(Blocker)는 테스트나 진행을 막아 다른 확인을 할 수 없게 만드는 결함을 흔히 부르는 말이다. 이번에 읽은 게임 자료에는 블로커라는 등급 이름이 나오지 않아, 어느 회사가 어떤 기준으로 쓰는지는 확인 필요다. Xbox 인증 문서에는 비슷한 개념이 있다. 문제가 테스트를 막으면 제출물을 보류(Hold)하거나 실패 처리할 수 있다.

Xbox 인증은 찾은 문제를 심각도, 발생 확률, 반복성으로 나눠 다음처럼 부른다.

| 유형 | 뜻 | 출시에 미치는 영향 |
| --- | --- | --- |
| CFR (Condition for Resubmission) | XR의 취지를 어겨 출시를 막을 만큼 심각한 문제 | 고쳐야 다시 제출할 수 있다 |
| SRI (Standard Reporting Issue) | XR과 관련 있지만 실패시킬 만큼 심각하지 않은 문제 | 다음 제출에서 고치면 좋지만 필수는 아니다 |
| ION (Issue of Note) | XR과 상관없는 문제 | 고칠지는 개발사가 정한다 |

A, B, C 버그가 팀 안에서 쓰는 분류라면 CFR, SRI, ION은 플랫폼이 쓰는 분류라 기준이 다르다. 팀에서 C 버그로 본 것이 인증에서 CFR이 될 수도 있으므로, 인증 요구 사항과 관련된 버그는 따로 표시해 두는 편이 안전하다(직접 판단).

모든 버그가 고쳐지지는 않는다. Game testing 문서의 Process 절에 따르면 의도된 기능이라며 NAB(Not a Bug, 버그 아님)로 닫히기도 하고, 회사 정책에 따라 프로듀서, 기획자, 리드 테스터가 면제(Waive, 무시해도 된다는 허가)하기도 한다. NAB는 결함 생명주기의 Rejected와 비슷하다. 면제는 고치지 않기로 정한다는 점에서 다음 릴리스로 미루는 Deferred와 다르고, Bugzilla의 WONTFIX에 더 가깝다.

<br/>

## 출시 판정
출시 판정은 남은 버그를 안고도 출시해도 되는지 정하는 일이다. 이번에 읽은 자료에서 확인한 기준은 아래와 같다.

- 베타는 출시를 막는 버그가 없는 버전이어야 한다(Video game development, Beta 절)
- 코드 릴리스 버전은 QA 테스트 계획 전체로 테스트한다(Video game development, Code release 절)
- 베타 단계에서 테스터의 의견이 마지막에 어떤 기능을 넣고 뺄지 정하는 데 쓰이기도 한다(Game testing, Overview 절)
- 골드 승인은 보통 프로듀서가 하고, 리드 테스터가 승인해야 골드로 갈 수 있는 회사도 있다(Game testing, Roles 절)
- 콘솔 게임은 플랫폼 인증을 통과해야 한다. Xbox는 최종 제출이 통과하면 통과 보고서가 나오고 출시할 수 있으며(Released from Certification), 실패하면 CFR 목록이 담긴 실패 보고서가 나온다. CFR을 모두 고쳐 같은 방식으로 다시 제출해야 한다. 요구 사항을 지키기 어려운 사정이 있으면 제출 전에 예외를 요청할 수 있지만 승인은 보장되지 않는다(Certification step-by-step guide)

비행기 출발 전 점검과 같다. 기내 화면 하나가 고장 난 채로는 뜰 수 있지만 엔진 경고등이 켜져 있으면 뜰 수 없다. 무엇이 엔진 경고등인지는 미리 정해 두어야 출발 직전에 다투지 않는다. 출시를 막는 버그의 기준(A 버그, CFR)을 미리 합의해 두는 이유다.

출시를 미루는 비용도 판정에 들어간다. Video game development의 Release schedules 절은 대형 게임이 1년 이상 앞서 출시일을 발표하고 마케팅과 예약 판매를 진행하므로, 출시 연기가 재정적 손해로 이어지고 심하면 프로젝트 취소와 해고까지 갈 수 있다고 적는다. Game testing 문서도 인증 반려로 중요한 출시 시기를 놓치면 퍼블리셔가 더 큰 돈을 잃을 수 있다고 적는다. QA는 남은 버그의 심각도와 영향 범위를 근거로 의견을 내고, 최종 결정은 프로듀서 쪽이 한다는 구조는 [심각도와 우선순위](../QA%20이론(QA%20Theory)/03_심각도와%20우선순위(Severity%20and%20Priority)/README.md)의 우선순위 결정과 같다.

<br/>

## 라이브 서비스 단계
출시 뒤에는 유지보수 단계가 시작된다. Video game development의 Maintenance 절에 따르면 예전 콘솔 게임은 하드웨어가 같아 출시 뒤 고칠 일이 거의 없었지만, 온라인 서비스가 생기면서 다운로드 패치로 유지보수를 하게 됐다. PC 게임은 하드웨어와 소프트웨어 조합이 너무 많아 출시 뒤에야 드러나는 문제가 생긴다. MMO 게임은 출시가 곧 유지보수의 시작이고, 게임 세계가 계속 바뀌고 기능이 추가된다. 같은 문서의 Testing 절은 모바일 게임과 라이브 서비스 게임이 자주 업데이트되리라고 예상되고, 이를 출시 전 테스트와 실시간 피드백, 버그 리포트로 보완한다고 적는다.

### 패치와 핫픽스
패치(Patch)의 사전적 의미는 옷에 덧대는 헝겊 조각이다. 소프트웨어에서는 이미 배포한 프로그램의 일부를 고치는 업데이트를 말한다. 위키백과 Hotfix 문서는 핫픽스(Hotfix)를 정기 업데이트 주기 밖에서 내거나 운영 중인 시스템에 바로 적용하는 업데이트로, 대개 버그를 고치려고 낸다고 정의한다. 원래는 운영 중인(hot) 서버에 거는 수정을 뜻했고, 테스트할 시간 없이 적용하므로 위험하지만 그대로 두는 위험이 더 크면 적용한다고 설명한다.

정기 패치는 정해진 날 문을 닫고 하는 정기 보수 공사, 핫픽스는 수도관이 터져 영업 중에 급히 막는 응급 수리와 같다. 응급 수리는 빨리 해야 하는 만큼 확인할 시간이 짧다.

게임 회사에서 정기 점검, 패치, 핫픽스, 업데이트를 어떻게 나눠 부르는지, 핫픽스에 QA가 얼마나 시간을 쓰는지는 회사마다 달라 확인 필요다.

### 업데이트를 검증할 때 보는 것
업데이트도 새 빌드이므로 빌드 검증 흐름(스모크, 수정 확인, 회귀)을 다시 거친다. 여기에 출시 뒤에만 생기는 확인 항목이 더해진다. 아래는 이번에 읽은 자료에서 확인한 것이다.

- 기존 저장 데이터와의 호환. XR-003의 테스트 003-16은 업데이트된 게임이 업데이트 전에 만든 저장 데이터를 불러올 수 있는지 본다
- 추가 콘텐츠와 본편의 관계. XR-037은 추가 콘텐츠에 묶인 저장 데이터를 기본 게임에서 어떻게 처리하는지 본다
- 플랫폼 재인증. Xbox는 콘텐츠 업데이트도 인증 대상 제출 유형에 들어 있고, 처리 기간은 영업일 2일로 공개되어 있다(Certification step-by-step guide). 다른 플랫폼의 업데이트 심사는 확인하지 못했다
- 등급 재심의. ESRB는 본편 등급을 넘는 내용을 담은 추가 콘텐츠를 따로 제출하게 한다
- 공개 테스트 서버. 일부 개발사는 큰 변경을 출시 전에 시험하려고 공개 테스트 서버(PTR, Public Test Realm 또는 Player Test Realm)를 둔다. 플레이어가 새 기능을 미리 해 보는 동안 개발사는 버그와 밸런스 데이터를 모은다(Video game development, Maintenance 절)

Video game development의 Testing 절은 회귀 테스트를 소홀히 해 버그가 있는 채로 출시하면 고객 불만과 판매 목표 미달로 이어질 수 있고, 그때 개발사와 퍼블리셔가 대개 서둘러 패치를 낸다고 적는다. 반복되는 패치마다 같은 회귀 범위를 수동으로 돌리기 어려워지므로, 회귀 스위트를 자동화할 이유가 출시 뒤에 더 커진다고 본다(직접 판단).

<br/>

## 개발사 QA, 퍼블리셔 QA, 외주 QA
Video game development의 Publisher 절에 따르면 퍼블리셔는 게임을 직접 만들거나 외부 개발사에 개발비를 대고, 제조와 마케팅, 현지화 비용 등을 맡는다. 개발비를 대는 만큼 프로듀서를 두어 개발사의 진행을 지켜보고, 마일스톤마다 돈을 지급한다. 이 절에는 출처가 없다는 표시가 붙어 있다. 이 관계가 QA 조직의 구분으로 이어진다. 아래는 이번에 읽은 자료에서 확인한 범위다.

| 구분 | 출처에서 확인한 내용 | 확인하지 못한 것 |
| --- | --- | --- |
| 개발사 QA | 초기 게임은 개발자가 모든 테스트를 맡았다. 작은 개발사는 보통 QA 인원이 없다. 퍼블리셔의 큰 QA 조직이 있어도 많은 개발사가 바로바로 확인하는 작은 테스터 그룹을 둔다 | 개발사 QA가 맡는 범위와 퍼블리셔 QA와의 분담 기준 |
| 퍼블리셔 QA | 대부분의 퍼블리셔는 여러 개발사의 게임을 테스트하는 큰 QA 조직을 둔다. 주목받는 상업 게임은 퍼블리셔 QA 부서가 테스트한다. 외부 퍼블리셔가 있으면 베타 무렵 퍼블리셔 QA와 조율을 시작한다. 퍼블리셔 소속 테스터가 개발사 현장에 파견되기도 한다 | 퍼블리셔 QA가 마일스톤 승인에 어떻게 관여하는지 |
| 외주 QA | 리드 테스터가 알파와 베타 무렵 외부 테스트 팀과 조율한다. Methodology 절은 플랫폼 인증 요구 사항 테스트(Compliance testing)가 게임 테스트 랩이 존재하는 이유라고 적는다. 테스트 랩이 무엇인지는 원문에도 정의 요청 표시가 붙어 있어, 외부 대행 회사를 뜻하는지는 확인 필요다 | 외주 QA 회사가 맡는 업무 범위, 계약 방식, 현지화나 호환성 테스트를 외주로 주는 관행 |
| 플랫폼 인증 팀 | 콘솔 게임은 베타 무렵 콘솔 회사 QA 팀에 빌드를 보낸다. Xbox는 인증 팀이 정해진 절차와 테스트 케이스로 시험하고 통과 여부를 판정한다 | 소니와 닌텐도 인증 절차의 세부 |

출처는 Game testing의 History, Overview, Roles, Employment 절, Video game development의 Publisher 절, Microsoft의 Certification step-by-step guide다. Game testing 문서 상단에는 내용을 일반화해야 하고 출처가 더 필요하다는 표시가 붙어 있다. 한국 게임 회사에서 개발사 QA, 퍼블리셔 QA, 외주 QA가 실제로 어떻게 나뉘는지는 출처를 찾지 못해 확인 필요다.

역할 이름도 함께 정리해 둔다. Game testing의 Roles 절은 테스트 마감을 정하고 골드를 승인하는 프로듀서(Producer), QA 인원과 버그 목록을 관리하는 리드 테스터(Lead Tester), 게임이 동작하고 쓰기 쉽고 재미있는지 확인하는 테스터(Tester), 자동화 테스트와 프레임워크를 만들고 성능과 보안 같은 복잡한 문제를 맡는 SDET(Software Development Engineer in Test) 또는 기술 테스터(Technical Tester)를 든다. 같은 절은 기술 테스터 없이 개발되는 게임도 많다고 적고, Employment 절은 일부 스튜디오가 일반 소프트웨어 테스트에 가까운 기술적 접근을 시작했지만 기술 테스트 자리는 아직 드물다고 적는다.
