## 테스트 자동화란 ?
- 사람이 손으로 하던 테스트 절차를 스크립트로 작성해 도구가 대신 실행하게 하는 일
- 웹 UI는 Playwright, Selenium, 모바일은 Appium 같은 도구로 스크립트를 짠다. 실무에서는 QA 자동화라고도 부르는데, ISTQB 실라버스에는 test automation이라는 말만 나온다
- 핵심은 모든 케이스를 자동화하지 않는 것이다. 자주 반복하고 결과가 분명한 케이스만 골라 자동화하고, 나머지는 수동으로 남긴다
- 이 노트는 자동화가 맡을 수 있는 일과 사람이 해야 하는 일을 나누는 기준, 자동화의 이점과 리스크, 자동화할 대상을 고르는 법, 스크립트 설계 순서와 규칙을 정리한다

### 자동화 (Automation)
사전적 의미는 기계나 장치가 사람 손을 거치지 않고 스스로 작동하게 하는 것이다.
테스트에서는 사람이 매번 클릭하고 눈으로 확인하던 절차를 코드로 옮겨, 같은 절차를 같은 기준으로 몇 번이든 다시 돌릴 수 있게 만드는 일을 말한다. 사람이 하던 판단까지 맡기는 것은 아니다. 코드로 적을 수 있는 확인만 옮겨 간다.

## 테스팅과 체킹
무엇을 자동화할 수 있는지를 가를 때 쓸 수 있는 구분이 있다. 제임스 바크(James Bach)와 마이클 볼턴(Michael Bolton)이 2013년 글 "Testing and Checking Refined"에서 다듬은 정의다.

- 테스팅(Testing)은 제품을 직접 겪고, 탐색하고, 실험하면서 알아 가는 방식으로 제품을 평가하는 과정이다. 질문하기, 공부하기, 모델 만들기, 관찰, 추론이 어느 정도씩 들어간다.
- 체킹(Checking)은 제품에 대한 명제(참이나 거짓이 될 수 있는 진술)가 사실인지 기계적으로 따지는 과정이다. 체크(Check)는 체킹을 한 번 하도록 적어 둔 항목 하나를 말한다. 여기서 기계적이라는 말은 기계가 수행할 수 있을 만큼 명시적으로 적을 수 있다는 뜻이다.

check의 사전적 의미는 대조해 확인하다, 점검하다이다. 목록이나 기준을 옆에 두고 하나씩 맞는지 보는 일이라, 기준을 미리 적을 수 있으면 사람이 아니라 도구도 할 수 있다. 같은 글은 이 정의에서 몇 가지를 끌어낸다. 테스팅은 체킹을 포함하지만 체킹은 테스팅을 포함하지 못한다. 체킹은 원칙적으로 완전히 자동화할 수 있지만, 테스팅은 도구의 지원을 받을 수 있을 뿐 본질적으로 사람의 활동이다. 품질은 사실이 아니라 의견이라서 체킹으로 결론 낼 수 없고, 제품의 동작에 관한 많은 사실은 체킹으로 결론 낼 수 있다.

맞춤법 검사기와 편집자로 비유할 수 있다. 맞춤법 검사기는 띄어쓰기와 철자를 규칙대로 한 줄도 빠짐없이 점검하지만, 글이 읽을 만한지는 편집자가 읽어 보고 판단한다. 자동화된 체크는 맞춤법 검사기 쪽이다.

이 구분은 바크와 볼턴이 이끄는 RST(Rapid Software Testing) 쪽의 관점이고 ISTQB 용어는 아니다. 그래도 같은 방향의 문장이 실라버스에도 있다. CTFL v4.0.1 1.1절은 테스터가 도구를 쓰지만 테스트는 대부분 지적 활동이라 전문 지식, 분석, 비판적 사고와 시스템 사고가 필요하다고 쓴다.

## 무엇을 자동화할 수 있나
CTFL v4.0.1 6.1절은 테스트 도구가 여러 테스트 활동을 지원한다고 쓰고, 도구 종류를 아래처럼 나눈다. 표의 예시는 실라버스에 없는 것으로, 이 레포의 다른 노트와 흔히 쓰는 도구에서 내가 골랐다.

| 도구 종류 | 실라버스가 적은 역할 | 예시 |
|---|---|---|
| 테스트 관리 도구 | 개발 생명주기, 요구사항, 테스트, 결함, 형상 관리를 도와 프로세스 효율을 높인다 | Jira 같은 이슈 관리 도구, 테스트 케이스 관리 도구 |
| 정적 테스트 도구 | 리뷰와 정적 분석을 돕는다 | 린터, 타입 검사기 |
| 테스트 설계와 구현 도구 | 테스트 케이스, 테스트 데이터, 테스트 절차를 만드는 일을 돕는다 | 테스트 계정과 데이터를 만드는 스크립트 |
| 테스트 실행과 커버리지 도구 | 테스트를 자동으로 실행하고 커버리지를 측정한다 | [Playwright](../Playwright/README.md) |
| 비기능 테스트 도구 | 손으로 하기 어렵거나 불가능한 비기능 테스트를 하게 해 준다 | [JMeter](../JMeter%20부하%20테스트(JMeter%20Load%20Testing)/README.md) |
| DevOps 도구 | 배포 파이프라인, 작업 추적, 자동 빌드, 지속적 통합과 배포(CI/CD)를 지원한다 | GitHub Actions, Jenkins |
| 협업 도구 | 소통을 돕는다 | 메신저 알림 |
| 확장성과 배포 표준화 도구 | 가상 머신, 컨테이너 도구로 환경을 늘리고 같은 구성으로 맞춘다 | Docker |

실라버스는 이 목록이 전부가 아니라고 하면서, 테스트에 쓰면 스프레드시트도 테스트 도구라고 적는다.

### 테스트 실행 밖의 자동화
테스트 자동화라고 하면 보통 스크립트로 테스트를 실행하는 일을 떠올리지만, 표에서 보듯 실행 말고도 자동화할 일이 많다. 아래는 QA가 매일 되풀이하는 일 가운데 자동화하기 좋은 것을 내가 묶은 것이다.

- 빌드 점검. 새 빌드가 나올 때마다 설치, 실행, 로그인 같은 기본 경로를 돌려 테스트할 수 있는 빌드인지 먼저 가린다. 이 단계(스모크 테스트, 빌드 검증 테스트라고도 하는 BVT, Build Verification Test)는 [게임 QA 프로세스](../게임%20QA%20프로세스(Game%20QA%20Process)/README.md)의 빌드를 받아 테스트할 수 있는지 가리는 흐름에 정리했다.
- 테스트 데이터 준비. 계정, 아이템, 결제 상태처럼 테스트 전에 손으로 맞추던 상태를 스크립트로 만든다. 실라버스 6.2절도 같은 테스트 데이터를 다시 입력하는 반복 작업을 줄이는 것을 자동화의 이점으로 든다.
- 버그 리포트 보조. 빌드 번호, 기기, OS 버전, 로그, 스크린샷처럼 리포트마다 같은 방식으로 모으는 정보를 자동으로 붙인다. 실라버스 5.5절도 결함 관리 도구가 식별자, 날짜, 작성자, 처음 상태 같은 항목을 자동으로 채울 수 있다고 쓴다.
- 결과 집계와 보고. 테스트 진행률, 실패율, 실행 시간을 매번 손으로 세지 않고 리포터와 대시보드로 모은다.

## 자동화로 얻는 것과 생기는 리스크
CTFL v4.0.1 6.2절은 도구를 사들이는 것만으로는 성공이 보장되지 않고, 도입, 유지 보수, 교육에 노력이 들며 분석하고 줄여야 할 리스크도 있다고 먼저 말한다. 그다음 이점과 리스크를 나열한다.

### 이점
- 반복하던 수동 작업이 줄어 시간이 남는다. 회귀 테스트 실행, 같은 테스트 데이터 재입력, 기대 결과와 실제 결과 비교, 코딩 표준 점검이 예로 나온다.
- 일관성과 반복성이 높아져 단순한 사람 실수를 막는다. 테스트가 같은 순서, 같은 빈도로 실행된다.
- 커버리지처럼 객관적인 평가가 가능해지고, 사람이 세기 어려운 지표를 얻는다.
- 진행률, 실패율, 실행 시간 같은 정보를 모으기 쉬워 테스트 관리와 보고에 도움이 된다.
- 실행 시간이 줄어 결함을 더 일찍 찾고, 피드백과 출시가 빨라진다.
- 테스터가 새롭고 더 깊은 테스트를 설계할 시간이 생긴다.

### 리스크
- 도구의 기능과 사용 편의에 대한 비현실적인 기대
- 도구 도입, 스크립트 유지 보수, 기존 수동 프로세스 변경에 드는 시간과 비용을 잘못 어림하는 것
- 수동 테스트가 더 맞는 곳에 도구를 쓰는 것
- 도구에 지나치게 기대어 사람의 비판적 사고를 놓치는 것
- 도구 업체가 문을 닫거나 지원을 끊는 경우의 종속성
- 오픈 소스 도구가 버려지거나 내부 구성 요소를 자주 갱신해야 하는 경우
- 도구가 개발 플랫폼과 맞지 않는 경우
- 규제나 안전 기준을 지키지 않는 도구를 고르는 경우

테스터가 새 테스트를 설계할 시간이 생긴다는 이점과 도구에 지나치게 기댄다는 리스크가 앞의 테스팅과 체킹 구분과 이어진다. 자동화가 체킹을 맡아 주면 사람은 테스팅에 시간을 더 쓸 수 있다. 반대로 자동화된 체크가 다 통과했다는 사실을 품질이 좋다는 뜻으로 읽으면 도구에 지나치게 기대는 리스크가 된다.

### 왜 전부 자동화하지 않을까
자동화 스크립트도 코드라서 작성 비용과 유지 비용이 든다. 화면이 바뀌면 스크립트도 고쳐야 하고, 깨진 스크립트를 고치는 시간은 수동으로 한 번 확인하는 시간보다 길 때가 많다.

그래서 자동화 후보는 보통 회귀 테스트로 자주 돌려야 하거나, 수동으로 하기에 데이터 조합이 많거나, 화면이 자주 바뀌지 않아 유지 비용이 낮은 케이스에서 고른다. 반대로 탐색적 테스트, UX 평가, 자주 바뀌는 신규 화면은 수동으로 남겨 두는 편이 효율적이다.

## 자동화할 대상 고르기

### 테스트 설계의 일반적인 흐름
1. 요구사항(Requirements) 확인. 기능과 스펙을 정의한 문서를 읽는다.
2. 요구사항 분석. 모호하거나 빠진 부분, 엣지 케이스, 리스크를 찾는다.
3. 테스트 케이스 설계. 정상, 예외, 경계값 등 전체 케이스를 수동 케이스까지 포함해 작성한다.
4. 자동화 대상 선정. 반복성이 높고 회귀 리스크가 크며 결과가 안정적인 케이스만 골라 자동화한다.

### 자동화로 옮길지 판단하는 기준
수동 테스트를 자동화 스크립트로 옮길지 정할 때 아래 다섯 가지를 본다.

- 반복 빈도. 릴리즈마다, PR마다 다시 도는 회귀 시나리오가 대상이다. 한 번만 하는 탐색적 테스트나 임시 확인은 제외한다.
- 결과의 결정성. 입력이 같으면 항상 같은 결과가 나와야 한다. 시각적인 느낌이나 UX 판단이 필요한 확인은 제외한다.
- 비즈니스 리스크. 결제, 로그인, 데이터 손상처럼 깨지면 치명적인 흐름을 먼저 하고, 리스크가 낮은 화면은 뒤로 미룬다.
- 수동 비용과 자동화 비용. 수동으로 5분 걸리는 테스트를 릴리즈마다 반복하는 비용과, 자동화 작성 2시간에 유지 비용을 더한 값을 비교한다. 내 기준으로는 누적 수동 시간이 6개월 안에 자동화 작성과 유지 비용을 넘기면 옮긴다.
- 안정성과 Locator 신뢰도. UI가 자주 바뀌는 신규 기능은 스크립트가 깨지는 비용이 더 크다. 명세가 굳은 뒤에 옮긴다.

### 어디서부터 시작할까
아래 순서는 실라버스의 권고가 아니라 위 기준을 바탕으로 한 내 판단이다.

1. 매 빌드, 매 변경마다 반드시 되풀이하고 판정 기준이 분명한 일부터 한다. 빌드 점검과 핵심 경로의 회귀 테스트가 여기에 든다. 반복 횟수가 많을수록 자동화에 든 비용을 빨리 돌려받는다.
2. 테스트 전에 상태를 맞추는 준비 작업을 자동화한다. 테스트 자체는 사람이 하더라도 준비 시간이 줄면 그만큼 탐색에 쓸 수 있다.
3. 결과를 모으고 알리는 일을 자동화한다. 실패가 쌓여도 아무도 보지 않으면 자동화한 의미가 없다.

어느 층의 테스트를 얼마나 자동화할지는 [테스트 레벨](../QA%20이론(QA%20Theory)/07_테스트%20레벨(Test%20Levels)/README.md) 장에 정리한 테스트 피라미드(Test Pyramid)로 나눠 생각한다. CTFL v4.0.1 5.1.6절은 아래층일수록 작고 서로 독립적이고 빨라서 많이 두고, 위층의 엔드 투 엔드 테스트는 느리고 넓은 기능을 보므로 적게 둔다고 설명한다.

## 자동화 뒤에도 사람이 하는 일
CTFL v4.0.1 2.1.4절은 DevOps가 자동화된 테스트를 많이 쓰더라도 수동 테스트, 특히 사용자 관점의 수동 테스트는 여전히 필요하다고 쓴다. 자동화를 넣은 뒤에도 사람에게 남는 일은 아래와 같다.

- 무엇을 확인할지 정하는 일. 체크는 사람이 적어 둔 기대값만 본다. 어떤 기대값을 적을지는 요구사항을 읽고 리스크를 따지는 사람이 정한다. 제품을 보는 기준은 [QA 관점](../QA%20관점(QA%20Perspective)/README.md)에 정리했다.
- 실패를 해석하는 일. 자동화된 테스트가 실패했을 때 제품 결함인지, 테스트 코드나 환경 문제인지, 기대값이 낡은 것인지는 사람이 가린다.
- 적어 두지 않은 문제를 찾는 일. 화면이 어색하다, 흐름이 헷갈린다, 이 조합은 아무도 생각하지 않았다 같은 발견은 [탐색적 테스트](../QA%20이론(QA%20Theory)/14_탐색적%20테스트(Exploratory%20Testing)/README.md)의 몫이다.
- 자동화를 관리하는 일. 제품이 바뀌면 스크립트도 바뀌어야 한다. 낡은 체크를 지우고, 불안정한 테스트를 고치고, 새 위험에 맞는 체크를 더한다.

## 자동화 설계
대부분의 UI 자동화는 POM(Page Object Model) 구조를 기본으로 한다. 페이지 단위로 Locator와 동작을 클래스에 묶어 두고, 테스트는 그 메서드를 호출해 시나리오를 조립한다. 화면이 바뀌면 페이지 클래스 한 곳만 고치면 되므로 유지 비용이 줄어든다. POM 자체는 [POM](../Playwright/POM(Page%20Object%20Model)/README.md) 노트에 정리했다.

### 설계 순서
1. 자동화 대상 시나리오 확정. 테스트 케이스 표에서 자동화 후보로 고른 케이스를 정리한다.
2. 페이지와 컴포넌트 식별. 시나리오를 로그인, 장바구니, 결제 같은 화면 단위로 나눈다.
3. Locator 전략 결정. `getByRole` 을 먼저 쓰고, 안 되면 레이블이나 텍스트, 그다음 `data-testid`, 마지막으로 CSS를 쓴다.
4. 페이지 객체 작성. 페이지별로 비즈니스 동작 메서드와 상태를 읽는 메서드를 정의한다.
5. 테스트 데이터 분리. 계정, 상품, 쿠폰 같은 데이터는 fixture로 뺀다.
6. 테스트 케이스 작성. 페이지 객체를 호출해 시나리오를 조립하고, 단언(assertion)은 테스트에만 둔다. 단언은 실제 결과가 기대값과 같은지 판정하는 코드로, Playwright에서는 `expect` 가 맡는다([expect 객체 API](../Playwright/레퍼런스(Reference)/03_expect%20객체%20API(expect%20API)/README.md)). [QA 이론 12장](../QA%20이론(QA%20Theory)/12_검증과%20확인(Verification%20and%20Validation)/README.md)의 검증(Verification)과는 다른 말이다.
7. 공통 fixture와 훅. 로그인 상태, `beforeEach`, 네트워크 모킹을 공통으로 둔다.
8. 실행과 CI. 재시도, 트레이스, 병렬 실행, 리포터를 설정한다.

### 위에서 아래로, 아래에서 위로
위에서 아래로(Top-down) 짜면 스펙을 보고 페이지 객체를 먼저 설계한 뒤 테스트를 쓴다. 큰 그림은 잡기 쉽지만 실제로 쓰지 않는 메서드까지 만들기 쉽다.

아래에서 위로(Bottom-up) 짜면 테스트를 먼저 평범한 코드로 쓰고, 중복되는 부분을 페이지 객체로 뽑아낸다. 실제로 필요한 만큼만 추상화된다.

배우는 단계에서는 아래에서 위로 짜는 쪽을 권한다. 처음부터 완벽한 페이지 객체를 그리려 하면 추상화가 과해지기 쉽다.

### 페이지 객체 작성 규칙
- 페이지 객체 안에서는 `expect` 를 쓰지 않는다. 단언은 테스트에서만 한다. 그래야 같은 동작을 여러 테스트가 다른 기대값으로 재사용할 수 있다.
- 메서드 이름은 화면 조작이 아니라 업무 언어로 짓는다. `clickAddBtn()` 보다 `addToCart()` 가 낫다.
- 페이지 이동이 일어나는 메서드는 다음 페이지의 페이지 객체를 돌려준다.

위 규칙 중 상태를 읽는 메서드를 두는 것과 다음 페이지 객체를 돌려주는 것은 여러 스타일 가운데 하나다. [POM 리팩토링](../Playwright/POM%20리팩토링(POM%20Refactoring)/README.md) 노트의 `LoginPage` 는 `login()` 이 아무것도 돌려주지 않고 상태 메서드도 두지 않는 더 단순한 스타일이다. 페이지가 적고 흐름이 짧으면 단순한 쪽이 읽기 쉽고, 여러 페이지를 잇는 시나리오가 많으면 다음 페이지 객체를 돌려주는 쪽이 메서드를 이어 쓰기 좋다.
- Locator는 생성자에서 한 번만 정의하고 메서드에서 재사용한다.
- 페이지 객체 하나는 페이지나 영역 하나만 맡는다. 너무 커지면 컴포넌트 단위로 나눈다.

### Locator 우선순위
1. 역할 기반(`getByRole`). 접근성 트리를 기준으로 찾아서 의미가 분명하고 DOM 구조가 바뀌어도 잘 깨지지 않는다.
2. 레이블과 텍스트(`getByLabel`, `getByPlaceholder`, `getByText`). 사용자가 보는 문구로 찾는다. 텍스트는 문구가 잘 바뀌지 않을 때만 쓴다.
3. `data-testid`(`getByTestId`). 위 방법으로 잡기 어려운 컨테이너나 복잡한 UI에만 쓴다.
4. CSS와 XPath. 위 셋이 모두 안 될 때만 쓴다.

Playwright 공식 문서도 `getByRole` 처럼 사용자가 보는 속성과 `data-testid` 같은 명시적인 약속을 먼저 쓰라고 권한다. 순서와 이유는 [Locator 우선순위](../Playwright/레퍼런스(Reference)/05_Locator%20우선순위(Locator%20Priority)/README.md)에 정리했다.

### 피해야 할 것
- 고정 시간 대기. `page.waitForTimeout(1000)` 처럼 정해진 시간만큼 기다리면 느린 환경에서는 깨지고 빠른 환경에서는 시간을 버린다. Playwright는 클릭이나 입력 전에 요소가 준비될 때까지 스스로 기다리고(auto-waiting), `await expect(locator).toBeVisible()` 같은 단언도 조건이 맞을 때까지 다시 확인하므로 이 기능에 맡긴다. 공식 API 문서도 `page.waitForTimeout` 을 사용 자제(Discouraged)로 표시하고, 시간을 기다리는 테스트는 본래 불안정하다고 적어 두었다.
- 테스트 사이의 상태 공유. 테스트마다 따로 실행해도 통과해야 한다. 앞 테스트가 만든 데이터에 기대면 순서가 바뀌거나 병렬로 돌 때 깨진다.
- 한 테스트에서 여러 시나리오 확인. 한 테스트는 시나리오 하나만 확인해야 실패했을 때 원인을 바로 안다.
- 페이지 객체 안의 분기. 페이지 객체는 동작만 드러내고, 흐름을 나누는 판단은 테스트에서 한다.
